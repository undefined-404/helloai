# eng-verification 平台验证规范

> 来源：提炼自 DeepSeek Harness `dsh-pre-push-checks`，与 HelloAI VERIFICATION 围栏对齐（2026-08-20，§6.114）。
> 定位：约束执行侧交付物的验证证据——什么算「验证过」、证据怎么记录；审查侧 `prompts/subtask-review.md` 轨道 B 的 C3 验证强度与本规范同源。

## 执行速览（任务 required_skills 命中 eng-verification 时注入执行 Prompt）

1. **最小证据集**：按改动范围选择能证明「目标行为正确 + 无回归」的最小验证组合——编译 / 单测 / 验证脚本 / E2E 不必全上，但所选组合必须覆盖目标行为本身。
2. **证据真实可复现**：交付时写明验证命令、实测输出关键片段、通过 / 失败结论；不得用「已验证」「测试通过」的叙述代替证据。
3. **断言有效性**：验证断言必须因目标回归而失败（与 eng-code-review C3 同源）——写死预期、跳过断言等于无验证。
4. **环境可复现**：注明验证环境（JDK 版本 / 服务版本 / profile / 关键配置）；脚本类验证须遵循项目 UTF-8 编码规则，输出可读。

---

## 详细规范

### 最小证据集原则

- 先回答「这个改动最可能在哪里出错」，再选验证手段：改 SQL → 数据层用例；改状态机 → 状态迁移用例；改接口契约 → 契约用例 + 一次真实调用。
- 全量回归不是每轮必须：改动面外的测试保持绿色即可作为「无回归」证据，不必逐条重跑全量。
- 冒烟（happy path）与负路径（失败 / 边界）至少各一。

### 证据记录格式

```
验证命令: <实际执行的命令，含关键参数>
验证环境: <JDK 17 / profile=local / 服务版本>
关键输出: <断言命中的输出片段>
结论: PASS / FAIL + 一句解释
```

- FAIL 的证据同样有效：写明失败点与原因比宣称通过更有价值。
- 无法执行的验证（环境缺失 / 依赖不可达）如实声明，不冒充已验证。

### 断言有效性

- 删除 / 改写该断言后，对应回归会失败 → 有效断言；否则是装饰性断言。
- 禁止：注释掉断言、`assertTrue(true)`、只检查「没抛异常」而不校验结果值。
- 参数化用例禁止写死预期使所有分支通过。

### 环境可复现

- 验证脚本遵循项目 PowerShell / Shell UTF-8 编码规则（`.ps1` 头两行声明输出编码；CJK 只进注释）。
- 依赖外部服务（MQ / MinIO / 数据库）的验证须注明服务可用性前提。
