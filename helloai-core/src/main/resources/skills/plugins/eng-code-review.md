# eng-code-review 平台技能规范

> 来源：提炼自 DeepSeek Harness `dsh-code-review`，已按 HelloAI 语义适配（2026-08-20，§6.114）。
> 定位：本规范同时约束执行侧（按此纪律自查产出）与审查侧（`prompts/subtask-review.md` 轨道 B 按同一清单核验），双方共用同一词汇表，形成「执行侧产出 / 审查侧解析」闭环。

## 执行速览（任务 required_skills 命中 eng-code-review 时注入执行 Prompt）

1. **接口契约（C1）**：对外接口必须文档化——函数签名、返回值区分（错误 / 空 / 正常三种语义不混用）、异常约定（抛什么、谁处理）、边界条件（空输入 / 超限 / 并发 / 超时）。任何「调用方须知」不得靠口头约定，必须写进文档或注释。
2. **生命周期与并发（C2）**：资源创建与释放成对出现（文件 / 连接 / 锁 / 线程池），无可观测泄漏；涉及共享状态时说明锁粒度与竞态处理；异步任务必须定义取消路径与错误上报路径。
3. **验证强度（C3）**：每个关键行为至少一条真断言——删除或改写该断言会因目标回归而失败；禁止「永真」冒烟断言充当验证证据。
4. **范围与必要性（C4）**：不写投机泛化与过度抽象；新增依赖须说明必要性；能复用标准库 / 既有组件的不手写。
5. **自查产出格式**：自查发现的问题按四元组记录 `[defect] 缺陷描述 [location] 位置（文件名 / 行号 / 字段名） [impact] 影响 [evidence] 依据`，修复后随产出更新。

## 详细规范

### C1 接口契约

- 每个对外暴露的接口（函数 / REST 端点 / 配置项）须能回答四个问题：接受什么、返回什么、什么时候失败、失败后调用方怎么知道。
- 返回值语义区分：错误（异常 / 非 2xx）与空结果（空列表 / null）必须可区分，不得用空值吞掉错误。
- 异常约定文档化：声明抛出什么异常、由哪层捕获、是否重试安全。
- 边界条件显式处理：空输入、极大输入、并发调用、超时、下游不可用——逐项写清行为或声明不支持。

### C2 生命周期与并发

- 资源成对：每个 `open/acquire/connect/start` 须有对称的 `close/release/disconnect/stop`，且释放路径在异常分支同样可达（try-with-resources / finally / 生命周期钩子）。
- 共享状态：多线程访问的字段须说明锁粒度与竞态处理；无锁方案须写明依赖的内存模型保证。
- 取消与错误上报：异步任务被取消时不得静默悬空；错误必须可观测（日志 / 状态 / 回调）。

### C3 验证强度

- 验证证据必须能证明「目标行为正确」：断言失败意味着回归，而不是永远通过。
- 反例（禁止）：只断言「代码跑完了」「返回对象非 null」而不校验关键值；注释掉的断言；写死预期的假参数化。

### C4 范围与必要性

- 不为想象中的未来需求写泛化层；抽象层次超过 2 层时须有理由。
- 新增第三方依赖前核对：标准库是否已有等价能力、项目是否已有同类组件。
- 死代码（无调用方 / 永不触发分支）应删除或注明保留理由。

### 四元组产出格式

```
[defect] 问题一句话
[location] 文件:行号 或 字段/端点名
[impact] 对使用者或系统的实际后果
[evidence] 依据（规范条目 C1-C4 / 验收标准条目 / 复现方式）
```

- 验收类问题注明标准条目编号；纪律类问题注明 C1-C4 编号。
- blocker（验收未满足 / 纪律缺陷实际造成误用、泄漏、竞态、文档代码矛盾）与 nit（风格 / 命名 / 格式）分开记录，nit 不阻塞通过。
