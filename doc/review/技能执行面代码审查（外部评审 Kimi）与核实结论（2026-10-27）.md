## 一、结论先行

**六条技术断言中五条成立，架构方向正确，一处修法过头。**

1. **成立且最严重**：对话直出链路没跑 `check`，与 `skills/plugins/archify.md` 自定的验收契约不符。
2. **成立**：`scope = -conversationId` + 固定文件名，存在串产物窗口。
3. **成立**：`guessTypes` 截断到 2 份且顺序固定，会丢掉真正需要的 schema。
4. **成立**：降档 `standard` 对用户完全不可见（`Result` 无 quality 字段）。
5. **成立**：`skill-spec-preset` 是全局单值，技能包不能声明自己的运行时。
6. **成立**：产物 `iframe` 无 `sandbox` 属性（全仓 `sandbox=` 在 `.vue` 中 0 命中）。

**修法过头的一处**：建议搭 `PromptSkillExecutor / ExecutableSkillExecutor / CompositeSkillExecutor` 三层框架。

### 2.1 第 3 条的具体后果（用评审给的例子验算）

需求：「画一张支付审批的调用链时序图」

```
"支付"  → lifecycle   （:442 关键词含「支付」）
"审批"  → workflow    （:445）
"时序"  → sequence    （:451）
```

`hits = [lifecycle, workflow, sequence]` ⇒ `subList(0,2)` ⇒ **注入的是 lifecycle + workflow 的 schema，
sequence 被丢掉**。而 prompt 仍允许模型输出 `chartType: sequence`（`:335-339`）⇒ 模型拿到的是
「类型可以选 sequence，但看不到 sequence 的 schema」⇒ 只能凭印象编字段 ⇒ `validate` 失败 ⇒ 走重试。
**这是「重试率高」的一个确定性成因，不是概率问题。**

### 2.2 第 2 条的真实窗口（比评审描述更具体）

槽级 `ReentrantLock` 保证**单条命令**串行，但一次执行是两次独立调用：

```text
run(scope, "validate && deliver")      ← 命令结束，锁释放
                                       ← 此刻 B 可写入 spec.json 并重渲染
readArtifact(scope, "/workspace/out/artifact.html")   ← A 读到的可能是 B 的产物
```

所以**不需要真并发**：同一会话里前一次刚返回、后一次插入就够。另 `finally release(scopeId)`
（`:204-206`）在 A 结束时删除沙箱，排队的 B 会重建并重新注入（幂等，约 2.2s）——属性能损失，不是正确性问题。

## 三、`check` 的实测结论（决定 P0 怎么做）

### 3.1 回执结构（本地实跑，`payment-lifecycle.json` 作为输入）

```json
{
  "ok": true,
  "file": "/tmp/skx-check/a.html",
  "artifact": { "sha256": "c014b6e4…", "bytes": 840706 },
  "checks": [ { "name": "single_svg", "ok": true, "details": ["found 1 <svg> block(s)"] }, … 共 9 项 ],
  "composition": {
    "schemaVersion": 1, "profile": "showcase", "status": "pass",
    "summary": { "errors": 0, "warnings": 0 },
    "metrics": { "properCrossings": 0, "ambiguousCorridors": 0, "minProjectedNodeTextPx": 6.61, … }
  },
  "provenance": "current",
  "deliveryReceiptId": "…"
}
```

三条关键事实：

1. **没有 `issues` 字段**。`archify.md:28` 写的「issues 为空」实际是
   `composition.status = pass` / `composition.summary.errors = 0` 的口语化表述。判据须按真实字段写。
2. **`provenance` 默认是 `unknown`**（`archify.mjs:1994`：`if (!requireProvenance) return { ok: true, status: 'unknown' }`）
   ⇒ 要真检查必须带 `--require-provenance`，否则「provenance=current」这条验收是空的。
3. **`check` 不接受 `--quality`**（`COMMAND_USAGE.check` 只列 `--json` / `--require-provenance`）。
   且 `composition.profile` 记录的是**渲染时用的档**（本例 `showcase`）⇒
   降档 `standard` 重渲后，产物内嵌的 `profile` 就是 `standard`，`check` 读它也不会报那类诊断。
   **结论：补 `check` 不会让「降档兜底」失效**，两者不冲突。

### 3.2 因此 P0 的判定规则

| check 结果 | 处置 | 理由 |
|---|---|---|
| `ok=true` 且 `provenance=current` 且 `artifact.sha256` = 回读字节哈希 | 通过 | 三方对账，与 `SKX-9` 口径一致 |
| `composition.status != pass` 或 `summary.errors > 0` | 按布局门同类处理：重生成 spec → 降档 | 与现有 `isLayoutGateFailure` 策略一致 |
| `provenance != current` | **硬失败**（重试一次整链后仍失败即抛错） | 产物不是本条输入渲染的，属正确性问题，不能降档糊过去 |
| 回读哈希 ≠ `artifact.sha256` | **硬失败** | 读到的不是刚渲染的那份 |

## 四、对评审的两处订正

### 4.1 「每 runId 一个 scope」会让每次执行都付 2.2s 注入成本

评审建议 `scope = skillRunId` + `/workspace/runs/<skillRunId>/`。这能解决问题，但代价被忽略了：
沙箱复用的**唯一收益**就是「技能包只注入一次（首次 2.2s，之后 50ms）」。scope 一换，注入就重来。

**更划算的切法：隔离的最小单位是目录，不是沙箱。**

- 技能包 = **会话级资产**（注入一次，多轮复用）；
- 产物 = **执行级资产**（每次执行必须独立）。

故 `scope` 仍按会话（`-conversationId`），只把工作目录换成 `/workspace/runs/<runId>/`。
串产物窗口消失，注入成本不变。代价是要重新回答「沙箱何时回收」——本批**不改回收策略**
（仍 `finally release`），把这个决策留给 `SKX-13`（异步化必然要重做生命周期）。
> **订正（2026-10-30）**：`SKX-13` 已完成，但只做「提交即返回 + 后台执行 + 轮询」，**未动回收策略**
> ⇒ 「沙箱何时回收」这一问**仍然没有答案**，遗留不变。

### 4.2 三层 Executor 框架现在搭是过度设计

评审前后自相矛盾：先画 `PromptSkillExecutor / ExecutableSkillExecutor / CompositeSkillExecutor`
三层，后又说「只有一个可执行技能时没必要马上设计复杂插件框架」。

**本批只做一件事**：把 Archify 专属知识（图表类型、`archify` 命令、`composition/*` 诊断码、
降档策略）从 `ConversationSkillRunner` 收进一个专用类，通用层只留
「注入 → 执行 → 回读 → 落附件」。不抽接口、不建框架——第二个可执行技能进来时再按真实差异切。

## 五、为什么不会阻碍 DSH 架构调整

| 层 | 内容 | DSH 是否动它 |
|---|---|---|
| **机制层** | `skills/plugins/*.md` frontmatter（9 字段白名单）、目录扫描、`requiredTools` 语义、`internal_list_skills` | **会**（这是 DSH 的正题） |
| **执行层** | 沙箱注入、命令执行、产物回读、对象存储、附件登记、权限与审计 | **基本不会**（平台自持能力，DSH 无对应概念） |

特色技能全在执行层。执行层对机制层的依赖只有 **3 个点**：

1. frontmatter 的 9 个字段；
2. `requiredTools` 里三个 `internal_*` 工具名；
3. `SkillPackageExecutionService` 这一个接口。

⇒ DSH 改技能格式时，要改的是 **md + `SkillPackageScanner` + 两份故意写死的数量断言**
（`SkillPackageScannerTest` / `AgentSkillSpecServiceImplTest`）——全仓最便宜可改的部分。

**真正的两条负债（与技能数量无关）**：

1. **`ConversationSkillRunner` 这个名字**：叫「通用技能执行器」，装的是图表类型猜测、
   `archify` 命令、`composition/*` 诊断码。第二个技能进来时这些必须先搬走才能复用。
   现在不搬，届时就要动一个「看起来通用」的类。
2. **推断式契约**：`SkillCatalogController.chatOptions` 靠「`requiredTools` 是否含 `internal_run_skill`」
   ∧「`dependencies` 是否为空」反推「它能不能当独立对话技能」。这是**规则推断，不是声明**——
   评审建议的 `kind / chatEnabled / producesArtifact` 显式字段比 executor 抽象更值钱，
   因为显式字段是 DSH 能直接对接的东西。

### 6.1 P0 实施结果（2026-10-27）

**改动**：`ConversationSkillRunner` 拆出 `renderAttempt`（渲染 + 自检一次尝试）、
`checkArtifact`（自检回执解析与判定）、`newRunId` / `specPathOf` / `htmlPathOf`（执行级目录），

**判定落地**（对齐 §3.2）：

| 情形 | 代码行为 |
|---|---|
| `ok=true` ∧ `provenance=current` ∧ 构图 pass | 通过，并把 `artifact.sha256` 带回做三方对账 |
| `provenance != current` | 硬失败，**不重试**（`retryable=false`） |
| 构图 fail / errors>0 / `ok=false` | 可重试（`retryable=true`）⇒ 重生成 spec → 降档 standard |
| 回执不可解析（非 JSON / 空 / 半截） | 硬失败，不冒充布局门白重试 |
| 回读哈希 ≠ 回执 `artifact.sha256` | 抛错拒绝交付 |

**实测证据（本地 `node v22.22.2`，用 `doc/diagrams/payment-lifecycle.json`）**：

### 6.2 P1-c 实施结果（2026-10-28）

**补了一处评审没点到的同源入口**：除侧栏 `<iframe>` 外，「新标签页打开」也走
`window.open(blobUrl)` —— blob URL 继承创建者 origin，同样让产物脚本跑在同源上下文里。
两处一起修。

**判定依据（为什么是「真实高危」而不是理论风险）**：

- admin token 存在 `sessionStorage`（`stores/auth.ts` 的 `KEY_ADMIN_TOKEN`），JS 可读；
- 产物 HTML 由**模型生成**，用户在描述里塞 `<script>` 即可间接注入；
- 两处入口都让该 HTML 运行在「与主页面同源」的上下文 ⇒ 脚本可读 token。

**改法**：

| 入口 | 处理 |
|---|---|
| 侧栏预览 iframe | `:sandbox="isHtml ? 'allow-scripts' : undefined"`，**不加** `allow-same-origin`（内层成唯一源） |
| 新标签页打开 | HTML 套一层同样 sandbox 的包装页（只含 `style` + `iframe`，无业务脚本）；图片 / PDF 仍直接打开 |

**两个刻意的取舍**：

1. **PDF 不加 sandbox**：Chrome 内置 PDF viewer 在 sandbox iframe 里会白屏，而 PDF 的脚本面
   已被浏览器自身沙箱化，收益远低于代价。
2. **图片不加**：无脚本，加了只会平白多一层限制。

**验证**：`type-check` 0 error；`build` 通过（25.43s）；`dist` 内 `allow-scripts` 命中 2 处
（两处入口都进了产物）。**待实测**：archify 产物在沙箱内仍正常渲染——它是静态自包含 HTML，
不依赖同源能力，预期无影响。

### 6.3 P1-a / P1-b 实施结果（2026-10-29）

**P1-a 类型识别与 schema 注入**（对应 §2 第 3 条、§2.1 的「支付审批调用链时序图」算例）

原实现的问题不在「初判不准」，而在**截断的位置放错**：识别层 `subList(0,2)` 丢弃命中事实，
而注入层照单全收 ⇒ 模型「能看到 `sequence` 可选、看不到它的 schema」。三步改法：

1. **识别不截断**：`guessTypes` 返回全部命中（「支付审批调用链时序图」现在保留 lifecycle + workflow + sequence）；
2. **注入分层**：`pickInjection` 只挑 2 份注入全文（保留 prompt 预算），其余命中由
   `requiredFieldsSummary` 给「顶层 required + 字段名」（只列名，不展开 `$ref`）；
3. **类型一致性兜底**：`alignType` —— 模型若最终选了未注入全文的类型，用该类型 schema 补产一次
   （带「类型已定，按上面这份 schema 重写」的指令），而不是等 `validate` 失败再走 CLI 重试。

**为什么选「补产」而不是「先分类再生成」**：后者每次都要多一次 LLM 调用；补产只在初判漏掉时
才多一次，命中时零成本。而「原本会 validate 失败 → 重试一次生成 + 重跑 CLI」的成本更高，
所以这是净省。

**P1-b 降档留痕**（对应 §2 第 4 条）

`Result` 增 `qualityProfile` / `degradeReason`，`degraded()` 由 `degradeReason != null` 判定；
payload 增三字段；消息正文追加「严格布局门未通过，已用**兼容布局**产出（原因），建议人工核对重叠与连线」；
产物侧栏显示「· 兼容布局」（用 `--ha-info-text` 信息色，不用危险色——它是提示不是失败）。

**验证**

```
ConversationSkillRunnerTest  :: 12 → 16 例（识别不截断 / 注入只切 2 份 / 摘要含 participants,messages 且不展开 $ref / 降档 payload）
对话链路回归                  :: 121 例绿
前端 type-check               :: 0 error
```

**仍开放**：`SKX-14` 的「`$ref` 内联 + 落库前预校验」未做——类型兜底之后，剩余失败类型从
「看不到 schema」变成「看到了但写错」（枚举/数值越界、未知键），那才是预校验要解决的问题。
建议先看一轮真实一次成功率（日志已有 `补产后类型仍变化` / `类型补齐失败` 两个计数点）再决定投入。

## 七、评审中「肯定」部分的核实

评审列出的 9 项平台能力，逐项在代码里确有其物（不是恭维话）：

| 能力 | 落点 |
|---|---|
