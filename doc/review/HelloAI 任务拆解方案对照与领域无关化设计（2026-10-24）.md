# HelloAI 任务拆解方案对照与「领域无关化」设计建议

- 日期：2026-10-24
- 起因：用户明确指出「草案生成与拆解，**不仅仅是针对于代码开发的**」，并要求对照主流方案判断 Qoder 是否可满足
- 前序：`doc/review/HelloAI 草案生成与任务拆解 对照开源与 Qoder 的差距分析（2026-10-24）.md`（`LOG-20261024-033`）
- 本轮结论：**前序报告的对照基准选错了**——spec-kit / task-master / Qoder 全是编码工具，拿它们衡量一个通用 agent 编排平台存在结构性错位。真正需要补的不是「Qoder 那四段」，而是**拆解维度与验收判据的领域无关化**

## 一、主流任务拆解范式：按「计划形态」分，共六种

任务拆解没有单一主流方案。各家分歧点只有一个：**计划在执行中能不能变**。

| 范式 | 代表实现 | 计划形态 | 计划能否中途变 | 适合的任务 |
|---|---|---|---|---|
| 单 agent 循环 | ReAct | 隐式、逐轮生成 | 每轮都可变（等于没有计划） | 简单任务、工具调用 |
| **静态预规划**（orchestrator-worker） | LangGraph plan-and-execute、`claude-task-master`、`github/spec-kit`、**HelloAI 现状** | 显式 DAG / 任务清单，一次性生成 | **不能**（拆完即冻结） | 计划可预先画出的流程化交付 |
| 层级委派 | CrewAI hierarchical process、AutoGen `SelectorGroupChat` | 无显式计划，manager 看结果动态派活 | 随时可变，但**不可审阅** | 团队能力差异大、需动态协调 |
| 按需分解（ADaPT） | ADaPT | 懒分解：先给高层，执行者失败时才向下拆 | 分解时机动态 | 避免过度拆分 |
| **双账本自省** | **Magentic-One（微软）** | 显式 task ledger：facts / to-look-up / to-derive / educated-guesses + 计划 | **由 stall counter 触发重规划** | **计划本身未知的探索型任务** |
| 评估-优化 | evaluator-optimizer | 固定角色、固定环 | 输出可变，计划不变 | 有明确质量标准的内容产出 |

> 对照表来源：`agentpatterns.ai/patterns/multi-agent/magentic-orchestration` 的 Pattern 对比矩阵（**二手解读页**）+ 各项目官方文档。
>
> **勘察口径分级（2026-10-24 订正）**：`spec-kit` = 模板级实测（command 模板即行为本体，全文已读）；`claude-task-master` = **文档级**（未读实现源码）；`Magentic-One` = **论文级**（arXiv:2411.04468 正文，**未读 AutoGen 实际 orchestrator prompt**）；`LangGraph` / `CrewAI` / `ADaPT` = **文档与二手页**（本报告只取其范式定义，不取其实现）。→ 受影响：§四「ledger 模式」的五问措辞与 stall counter 实现细节，落 `TD-10` 前须补代码级核对。
>
> **上述缺口已于同日补齐（代码级核对完成，本地 `E:\workspace`）**：`claude-task-master` 与 `microsoft/autogen` 源码已读，本报告涉及的三处订正——① 复杂度分到推荐子任务数**无映射表**（两值均为模型输出），但发现更值得借的「门槛与数量分离」；② `max_stalls` **代码默认 3**（论文 ≤2 为实验配置）；③ stall counter 是**净值计数**（有进展 −1），非累加。详见 `LOG-20261024-036`。

### 1.1 关键判断

**HelloAI 现在只实现了表中「静态预规划」一档**，而静态预规划有一个硬前提：**计划可以事先画出**。

这个前提在两类任务上成立：
- 构建类（代码、配置、部署）——模块边界、类型系统、编译器天然给出偏序
- 流程类（报表、对账、上线清单）——行业已有成熟 SOP

在第三类任务上**不成立**：
- 研究类（竞品调研、技术选型、故障诊断）
- 方案设计类
- 决策类

对这类任务，静态 DAG 是**结构性错配**：拆出来的步骤在执行时必然作废，因为"下一步做什么"取决于"上一步发现了什么"。

> Magentic 模式的适用条件，`agentpatterns.ai` 总结的第一条就是 **"The plan is the unknown"** —— 计划本身就是未知量。这正是非代码任务里占比很大的一类。

**所以「不仅是代码开发」这个诉求，本质不是"把提示词写通用一点"，而是要覆盖不同的计划形态。**

## 二、Qoder 够不够：不够，但原因不是它做得不好

Qoder 整套 Spec 驱动的严谨性，建立在三个**代码专属**的前提上：

| 前提 | Qoder 怎么满足 | 非代码任务为何失效 |
|---|---|---|
| **交付物有文件路径** | 任务能定位到具体文件，"不重叠、合并后完整覆盖"是可判定的 | 文档 / 调研 / 运营的交付物没有路径，甚至一次交付多个产物，"覆盖"如何判定？ |
| **有客观裁判** | 编译、测试、lint、Repo Wiki 静态分析 | 没有编译器告诉你一份竞品分析"对不对"。验收只能写成"质量良好"（不可判定）或强行伪造成"输出到 xx.md"（假可判定） |
| **有现状地图** | Repo Wiki 自动生成代码库结构 | 无等价物。"做 Q3 竞品分析"时，Planner 无法自动知道公司已有哪些历史报告、竞品清单是否已确认、这份东西给谁看 |

它的 Spec 四段（需求描述 / 设计方案 / 任务拆分 / 验收标准）是**代码交付物的自然投影**。硬套到非代码场景会得到两种坏结果：**验收不可判定**，或**拆解维度错位**（按"改哪个文件"拆，而文档应该按"回答读者哪个问题"拆）。

### 2.1 但有三样与领域无关，值得抄

1. **Spec 作为可下载 / 可批注的文档**（前序报告 §6 已述，`P0-4`）
2. **`Recommend` 一键采纳默认答案**（`options[].recommended` 字段我方已有，缺动作）
3. **执行前强制"审核 Spec"关卡**（对应我方 fail-open → fail-close 的整改）

## 三、非代码任务拆解难的根因：三个锚点缺失

| 锚点 | 代码任务怎么得到 | 非代码任务的困境 |
|---|---|---|
| **终止锚**（拆到什么时候算完） | 覆盖所有待改动点，IDE/编译器能列出剩余项 | 文档拆几章？调研拆几个子问题？**没有天然边界** |
| **验收锚**（单条子任务怎么算完成） | 编译过 / 测试过 / lint 过 | 只有"够不够好"，**主观判断** |
| **依赖锚**（为什么 A 必须在 B 前） | 接口定义 → 实现 → 调用，类型系统给出偏序 | "先调研再写方案"是真的依赖，还是可以并行？**说不清** |

现有 `planner-decompose.md` 的「拆解原则」整段建立在代码语境上——`契约先行` 举例是「前后端联调 / 服务间对接 / 库表 + 接口 + 页面联合交付」，技能示例是 `eng-doc-standard`，验收模板是「运行 X 命令输出含 Y」。

> 这解释了为什么非代码任务拆出来"很假"：**提示词只懂软件交付的语法**。

## 四、设计建议

### 4.1 引入 `taskArchetype`：决定「按什么维度拆」

现在只有 `GRANULARITY`（FINE / STANDARD / COARSE）控制「拆多细」，**完全没有控制「按什么维度拆」**。这是核心缺口。

按「怎么判定完成」分类（不按行业分，因为**拆解边界由判据决定**）：

| archetype | 终止锚 | 验收锚 | 自然拆分维度 | 例子 |
|---|---|---|---|---|
| `BUILD` | 覆盖所有改动点 | 编译 / 测试 / lint | 模块分层 + 契约先行（**现状**） | 代码、配置、部署 |
| `DOCUMENT` | 覆盖读者的决策链 | 结构可检查 + 审查 agent | **读者问题序**（不是章节数） | 方案、报告、PRD、白皮书 |
| `RESEARCH` | 每个子问题都能独立佐证或推翻结论 | 证据充分性（有出处） | **问题分解树** | 竞品调研、技术选型、故障诊断 |
| `DATA` | 数据流每阶段校验通过 | 行数 / 分布 / 对账 | 采集→清洗→校验→加载→复验 | 报表、ETL、数据标注 |
| `OPERATE` | 时间轴节点全部触发且留痕 | 可观测结果（截图 / 日志 / 回执） | 前置→触发→监控→复盘 | 活动、发布、巡检 |
| `DECIDE` | 选项穷尽 + 评估维度覆盖 | 决策记录（ADR 式） | 选项生成 / 维度评估 / 推荐 | 技术选型、排期、供应商选择 |

**这张表不是给用户选的，是让 Planner 判的。** 判对 archetype，拆分维度、终止条件和验收写法就同时对了。

落库：`task.task_archetype VARCHAR(16)`，默认 `BUILD`（向后兼容）；拆解提示词按 archetype 注入不同的「拆分维度」小节。

### 4.2 引入 `acceptanceKind`：把「验收」从一段话升级成裁判声明

现在 `acceptance` 是自由文本。让模型写"判定动作 + 预期结果"，在代码场景有效（有命令可跑），在非代码场景只能编。

加一个枚举字段，显式声明**谁来判、怎么判**：

| acceptanceKind | 判定者 | 适用 | 写法要求 |
|---|---|---|---|
| `AUTOMATED` | 机器 | 代码、配置、数据文件 | 命令 + 断言 + 预期输出 |
| `STRUCTURAL` | 规则 + 机器 | 文档、报告、PPT | 可数的结构断言（章节数 / 必填要素 / 字数 / 条目数） |
| `REVIEWED` | 审查 agent | 方案、设计、分析 | 逐条打勾，输出 pass/fail + 理由 |
| `ATTESTED` | 人 | 决策、创意、对外沟通 | 明确「谁、什么时点、留什么痕」 |

**价值**：这一列直接回答"非代码任务的验收怎么写才不假"。更关键的是——**它能直接接到已有的 review 域**：`REVIEWED` 走现有审查 agent（`subtask-review.md` 轨道 A）、`ATTESTED` 走人工确认、`AUTOMATED` 走现有执行侧校验。**不需要新建链路，只是把已有能力显式声明出来。**

落库：`sub_task.acceptance_kind VARCHAR(16)`，默认 `AUTOMATED`。

### 4.3 拆解输入缺一个「现状快照」

拆解时实际读到的任务信息（`PlannerDecomposeAsyncServiceImpl:214-223`）：

| 占位符 | 来源 | 是否够用 |
|---|---|---|
| `{{TASK_TITLE}}` | `task.title`（255 字） | 太薄 |
| `{{TASK_DESCRIPTION}}` | `task.description` | 取决于用户写多细 |
| `{{TASK_REQUIRED_SKILLS}}` | `task.requiredSkills` | — |
| `{{TASK_DIFFICULTY}}` | `agentPolicy.difficulty`（LOW/MEDIUM/HIGH） | — |
| `{{GRANULARITY}}` | 运行时判定 | — |
| `{{REQUIREMENT_PACKAGE}}` | `task.context.requirementPackage` | 未走澄清链路时为空 |

**对非代码任务，这等于让 Planner 蒙着眼睛拆。**「做一份 Q3 竞品分析」时，Planner 不知道：历史报告在哪、竞品清单定了没有、交付给谁做决策。

而且有个**顺序问题**：`TaskBaseline` 是在 `PlannerAnalysisServiceImpl:203`（`finishConfirm` 里）初始化的——**确认草案之后才建**。顺序反了：baseline 应该是拆解的**输入**，不是确认的**副产物**。

建议：拆解前组装一份**轻量快照**（附件清单 + 知识库命中 topN + 历史同类任务标题 + 需求包），作为 `{{TASK_CONTEXT_SNAPSHOT}}` 注入。完整的 `TaskRunningSpec` 仍在确认后建，不冲突。

### 4.4 第二条路：为「计划未知」的任务引入 ledger 模式

这是回答「不仅代码开发」最本质的一条。

静态 DAG 不适用的任务，不该硬拆。Magentic-One 的做法是**不预先画死计划**，而是维护两个账本：

**Task Ledger（外层循环，任务的短期记忆）** —— 四类信息，与领域完全无关：
- `facts`：任务里已给出的、已验证的事实
- `facts to look up`：需要检索的（联网 / 附件 / 知识库）
- `facts to derive`：需要计算或推理得出的
- `educated guesses`：带标注的猜测，允许 agent 在卡住时兜底使用

**Progress Ledger（内层循环，每步自检）** —— 五个问题：
1. 请求是否已完全满足（任务是否完成）？
2. 团队是否在原地打转（looping）？
3. 是否在推进（forward progress）？
4. 下一个该谁说话？
5. 该给它什么指令？

**核心机制是 stall counter**：检测到循环或停滞则计数 +1；**计数器 ≤2 时继续**，**超过阈值则跳出内层循环、进入外层反思并重规划**；重规划后**强制清空所有 agent 上下文**，避免旧假设残留。

> 论文原文（arXiv:2411.04468）：「if the counter exceeds the threshold, the Orchestrator breaks from the inner loop, and proceeds with another iteration of the outer loop. This includes initiating a reflection and self-refinement step... It then updates the task ledger, revises the original plan.」

**对 HelloAI 的直接价值**：
- `uncertainties`（ASSUMPTION / UNCONFIRMED）已经是 facts/guesses 分离的**雏形**——不用另起炉灶
- 缺的是 `to-look-up` / `to-derive` 两类，以及**progress ledger 这一层自检**
- `sub_task` 已有 `rework_count` / `timeout_count`，但**没有 stall counter**（"没进展"和"失败了"是两件事）

建议：`archetype == RESEARCH | DECIDE` 或用户显式选「探索模式」时，产出物从 DAG 切换为 ledger 结构；stall 触发的重规划接到现有 `PAUSED` / `REWORK` 状态机上。

**这不是推翻现有拆解，是给静态 DAG 不适用的任务开第二条路。**

### 4.5 把 stall counter 也用到澄清侧

澄清现状：`progress` 是模型自评且零消费点（`ClarifyReplyParser:284,289,290`）。

可以照 Magentic 的思路做成**客观计数**：连续 N 轮用户的回答没有让 `openQuestions` 减少、没有让六维度从 `Missing` 变 `Clear` ⇒ 判定「无进展」，此时**停止追问、按现有信息出终稿并显式列出未决项**。

这比"模型自评 progress"可靠得多，因为它数的是**状态变化**，不是模型的说法。

## 七、一句话总结

> 主流方案没有「通用任务拆解」，因为**拆解维度与验收判据是由交付物的性质决定的**。HelloAI 现在只有一档（静态 DAG + 软件交付语法），所以非代码任务必然拆得假。补法不是把提示词写通用，而是让 `archetype` 决定「按什么维度拆」、让 `acceptanceKind` 决定「谁来判怎么判」——再加上一条给「计划未知」任务用的 ledger 通道。**Qoder 的 Spec 只覆盖第一档，抄它解决不了这个问题。**
