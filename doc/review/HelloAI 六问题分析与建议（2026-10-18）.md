## 1. 死信队列菜单：重复，建议隐藏

**现状**：侧边栏「死信池」入口是 `/sub-tasks?status=DEAD_LETTER` 的**带参跳转**，不注册独立路由：

```ts
// helloai-ui/src/router/dynamic.ts:7
// - path 含 '?' 的菜单（如死信池 /sub-tasks?status=...）仅侧边栏入口，不注册路由
// dynamic.ts:79  同上
```

即：**它本来就是子任务列表**，只是预设了筛选条件。

**问题定性**：不是「功能多余」，是**菜单层级多余**。用户看到两个入口指向同一页面，会以为死信池是另一个模块；而实际上子任务列表本身已有状态筛选。

**建议**（按推荐度排序）：
1. **隐藏独立菜单 + 子任务列表加「死信待处理」Tab 与数量角标**（推荐）。死信是「需要人工处置」的高优先队列，用角标比用菜单位置更能提示。
2. 若你想保留入口，改成子任务菜单的**二级项**（视觉从属关系明确）。
3. 不建议单独拆页面 —— 死信处置动作（人工验收/改派/重派）与普通子任务操作**完全重叠**，拆页会导致两套操作实现。

**工作量**：菜单配置改 1 处 + 列表 Tab 1 个 + 角标查询（`count(status=DEAD_LETTER)`，可复用现有统计接口）≈ 0.5 天。

## 2. Team 成员展示：数据全有，只缺 UI

**关键纠正**：不是「没有关联」，而是**关联数据三份都在，前端一行都没显示**。

| 数据 | 位置 | 含义 |
|---|---|---|
| `task.agent_policy.teamId` | `TaskAgentPolicy.KEY_TEAM_ID`（`task/policy/TaskAgentPolicy.java:44`） | 任务创建时选定的团队（来源元信息） |
| `team` + `team_member` | `agent/entity/Team.java` / `TeamMember.java` | 可复用组合：`slotRole`（PLANNER/EXECUTOR/REVIEWER）+ `weight`（**预留，不参与派发**） |
| `task_agent_member` | `V98__task_agent_member.sql:14` | 运行时成员快照：`join_source`（ASSIGNED/CLAIMED/REASSIGNED/MANUAL/REBUILT）+ `status`（ACTIVE/LEFT）+ `join_time` |

前端现状核实：`grep team --include="*.vue" helloai-ui/src/views/task/ helloai-ui/src/views/subtask/` **零命中**。

**建议：加数据项，不加按钮。**

按钮解决不了「看不到」——用户点一下才看到，等于默认把信息藏起来。团队与成员属于「任务的责任边界」，应当默认可见。

具体展示设计：

- **主任务详情顶部**：`执行团队：内容组（5 人）` + 成员 chips（头像 + 名字 + 槽位角色），点击 chip 跳 Agent 详情
- **主任务详情成员区**：区分「编制成员」（team_member）与「实际参与」（task_agent_member，带 join_source 与 join_time）
- **子任务详情**：`责任人：史航（EXECUTOR · 内容组）`，若为改派过的任务，显示 `由 A 改派至 B`
- **团队为空的任务**（没选 team）：显示 `未指定团队（系统按技能自动匹配）`，不隐藏该区块——避免「没数据」与「没功能」混淆

**一个必须注意的点**：`task_agent_member` 的 COMMENT 明确写着它的用途是「附件 visibility=TASK 范围的判据」，**不是展示用的花名册**。用它做展示前要确认：

- 成员是否只在实际「参与过」时才入表（`join_source=ASSIGNED/CLAIMED`）→ 那么「编制但未参与」的成员看不到，展示会误导；
- 因此展示应**同时**读 `team_member`（编制）与 `task_agent_member`（实际参与），分两栏，不要混成一个列表。

**工作量**：后端加 1 个查询（taskId → team + 编制成员 + 参与成员，可复用 `TeamService` 与 `task_agent_member` 查询）约 0.5 天；前端 2 个页面约 0.5~1 天。

## 3. 积分流水：链路存在，断在 UI

**现状取证**（这条链路比你想的要完整，只是没连起来）：

```java
// SubTaskStateMachineServiceImpl.java:355-374（子任务完成时）
ScoreResult scoreResult = implicitScoreCalculator.calculate(subTask, reviews, blockCount, timeoutCount);
subTask.setScoreFactors(factors);        // 五维：time/quality/coop/stability/efficiency
subTask.setCompositeScore(...);
subTask.setScoreGrade(...);
if (scoreResult.getRewardDelta() != 0) {
    rewardService.addReward(agentId, "隐式评分(S级)", rewardDelta, subTaskId);  // ← 写流水
}
```

```java
// RewardServiceImpl.java:57 —— 积分变化同时回写 Agent 余额
agent.setScore(newBalance);
```

所以真实关系是：**子任务完成 → 隐式五维评分 → 按等级给 Agent 加减积分 → 写积分流水 → Agent 总分变化 → 影响调度排序**。这条链是闭合的。

**你感觉「没关联」的三个真实原因**：

1. **评分列值为空**：评分**只在子任务完成时**写入（`compositeScore` 唯一写点就在上述代码）。进行中/已取消/未指派（`assignedAgentId == null` 直接跳过）的子任务**必然为空**——列名却像是「每条都有分」，视觉上像坏了。
2. **没有评分说明**：`scoreGrade`（S/A/B/C…）的**阈值与五维权重没有对外口径**，用户看到一个字母不知道意味着什么。
3. **两处不可互跳**：子任务详情能看到分，但看不到「这次评分给谁加了多少分」；积分流水能看到「+X 隐式评分(S级)」，但看不到是哪个子任务、评分明细是什么。

**建议**：
1. **隐藏独立「积分流水」菜单**（赞同你的判断），并入 **Agent 详情 → 「评分与积分」页签**：
   - 顶部：当前总分 + 近 30 天趋势
   - 中部：流水列表（时间/事由/变动/余额/关联子任务链接）
   - 底部：评分口径说明（五维定义 + 等级阈值）
2. **补评分口径**：把 `ImplicitScoreCalculator` 的权重与等级阈值做成可展示的常量/配置，在子任务详情与 Agent 详情同一处渲染（**单一事实源**，不要两边各写一份文案）。
3. **子任务列表评分列**：加 tooltip「仅在完成时评分」；有分时可点进详情，详情里显示「本次评分 → 给 X 加 N 分」并链接到对应流水。

**工作量**：菜单迁移 0.5 天 + Agent 详情页签 1 天 + 口径说明 0.5 天。

## 4. 调度算法：从「最高分独占」改为「加权最少连接」

**现状取证**：主路径排序键（`AgentSelector.pickFromCandidates`）：

```java
// AgentSelector.java:135-138 (javadoc)
// 按 score DESC 排序，选最高分；前置软优先级为
// dutyRank →（preferExternal 时）accessTypeRank → qualityRank×qualityWeight
//     → costRank×costWeight（B5.3 Fleet 成本选人）
// AgentSelector.java:193
.max(resolveComparator(qualityRanks, costRanks))
```

回退路径更极端（`SubTaskDispatchServiceImpl.java:520-523`）：

```java
.max(Comparator.comparing(AgentProfileSnapshot::score, nullsFirst(naturalOrder())))
```

**问题定性**：`max()` + `score DESC` 的本质是**赢者通吃**。只要最高分 Agent 还没打满并发额度，它就会一直中标；次优 Agent 只有在它满额/离线/熔断时才被选中。后果就是你观察到的：好模型持续高压、差模型长期闲置，且**高分模型的分数会被自己的高负载反噬**（超时/延迟拉低 timeScore），形成振荡。

**已有的缓解（不是没有）**：

- `concurrencyQuotaService.canAccept(agentId)`：并发额度满则跳过（`AgentSelector.java:189`）；
- `isRequireIdle()`：可配置「必须空闲才选」；
- `qualityRank` / `costRank` 已经参与排序（质量画像 + 成本分档）。

所以现状是「有硬上限、无软均衡」。

**建议：加权最少连接（Weighted Least Connections, WLC）**

不推荐纯轮询、不推荐一致性哈希：

| 方案 | 是否适用 | 原因 |
|---|---|---|
| 纯轮询（Round Robin） | ❌ | 会把任务等概率派给能力弱/贵的模型，牺牲质量与成本目标 |
| 一致性哈希 | ❌ | 适用于「同一键固定打同一实例」的缓存亲和场景；这里要的是分散负载，且无会话粘性需求 |
| **加权最少连接 WLC** | ✅ | 高分模型权重高 → 仍优先；但负载上升后按比例让位，天然均衡 |
| 加权轮询（WRR） | ⚠️ 次选 | 实现更简单，但不感知「当前在飞任务数」，慢任务会造成假空闲 |

**WLC 具体设计**：

```
score_effective = (inProgressCount(agent) + 1) / weight(agent)
选 score_effective 最小者

weight(agent) = f(agent.score, qualityRank, costRank)
  建议：weight = clamp(1.0, 5.0, 1 + (score - minScore) / (maxScore - minScore) * 4)
  —— 保证最低权重仍有 1/5 机会，避免差模型永久饿死
```

关键实现点：

1. **`inProgressCount` 已有**（`agentService.inProgressCount(agentId)`，`AgentSelector.java:188` 已在用），无需新查询；
2. **保留现有硬过滤**（在线/心跳/凭证/熔断/技能约束）——WLC 只替换排序段，不动过滤段；
3. **`forceAccessType` / `preferExternal` 语义保持不变**：仍在 WLC 之前分层（先按 accessType 分组，组内 WLC）；
4. **加开关**：`agent.dispatch.selection-strategy = score-desc | weighted-least-conn`，默认保持 `score-desc` **灰度可控**，观测到效果再切默认；
5. **可观测**：选中时在调度事件里记 `chosenBy=WLC, weight=X, inFlight=Y`，否则调完没人能证明它生效了。

**工作量**：`AgentSelector` 排序段改造 + 开关 + 单测 ≈ 1 天；回退路径 `pickApiKeyLlmAgent` 同步改造 ≈ 0.5 天；观测埋点 ≈ 0.5 天。

## 5. Team 组合与业务的结合点（参考开源）

### 5.1 开源对照结论

| 维度 | AgentTeams | Octop | 本项目现状 |
|---|---|---|---|
| 团队实体 | `Team` CRD（成员硬归属，1 个 leader） | `kind=team` + `manifest.members` | `team` + `team_member`（含 `slotRole` / `weight`） |
| 团队对任务的约束力 | **弱**：任务只有 `assigned_to` 字符串，`delegate_task` 只校验「房间成员」，不校验团队/技能 | **强**：Host 工具白名单（只留 `agent_list`/`ask_agent`）+ `team_peers=成员表` + 强制异步 | **中**：`agent_policy.teamId` 展开为选人白名单（`TeamPolicyExpander`） |
| 成员失败改派 | **无**（只能人工 re-delegate） | 无（成员失败由 Host 重新派工） | **有**：熔断降级 + 改派链（`AgentSelector.pickAlternative`） |
| 团队级熔断 | 无 | 无 | 无 |
| 技能匹配 | **无结构化**（Manager 侧 shell 过滤，建议非强制） | 成员 `metadata.description` 给 LLM 判断 | **有**：`required_skills` AND 硬过滤（`AgentSelectionConstraints`） |

**最重要的借鉴**：Octop 的团队落地靠**三把硬锁**，而不是靠模型自觉：

```python
# Octop-main/src/octop/infra/agents/teams/service.py:25-40
HOST_TOOLS_ALLOWED = {"agent_list", "ask_agent", "memory_search", "memory_get", "current_time"}
HOST_TOOLS_DISABLED = {所有不在白名单的工具}
# manager.py:3486-3492
updates["team_peers"] = tuple(members)   # 可调用对象 ⊆ 团队成员
updates["peer_invoke_mode"] = "async"
```

即：**协调人不给执行工具，执行人不给派工工具**。

### 5.2 本项目五项落地建议（按性价比排序）

**① `TeamMember.weight` 参与派发排序**（最小改动，最高性价比）

现状：`TeamMember.weight` 字段存在且注释写「预留，S1 不参与派发排序」。这意味着团队目前**只是个命名单 + 白名单**，对「谁更适合接这个活」零影响。

改法：`TeamPolicyExpander` 展开白名单时把 `weight` 一并带出，`AgentSelector` 在 WLC 的 weight 计算里叠加（team 内权重 × 全局 score 权重）。效果：团队内可以表达「主力/替补」。

**② 任务详情展示团队花名册**（见 §2）—— 让「团队」从后台概念变成业务可见事实。

**③ 团队内失败优先改派**（复用现有改派链）

现状：`pickAlternative` 排除失败者后**全局**重选，可能选到团队外。改法：改派时先在同 `teamId` 成员内选，无可用再全局。这能让「团队」在故障场景下真正发挥作用。

**④ 团队技能推导 + 匹配**

现状：团队无 `requiredSkills`，只有成员各自技能。建议在 `TeamService` 提供「团队技能 = 成员技能并集/交集」的派生查询，任务拆解时可用它做「哪些团队能接」的推荐。**注意**：AgentTeams 缺这块（它的文档明说「Team API 没有 domain/expertise/capabilities 字段」），这是本项目可以领先的点。

**⑤ 团队级熔断（登记不启动）**

连续 N 次失败 → 团队降级（不再接新任务，需人工介入）。当前无此能力（三个项目都没有）。**建议先不做**：单 Agent 熔断已存在，团队级熔断在没有足够样本前只会误伤。

**⑥ 参考 Octop 的「工具隔离」思路（可选）**

若 PLANNER 角色未来会承担协调职责，可考虑「PLANNER 只保留调度/编排类工具，执行类工具禁入」。当前本项目 PLANNER 是 `API_KEY_LLM` 单轮调用，暂无必要，**登记为方向**。

## 6. Browser 会话：把网页版 AI 当 planner

### 6.1 先说结论

**技术上做得出，但我不建议把它作为主路径。** 理由是三条硬约束，不是「难」，是「不可持续」。

### 6.2 三个开源项目的实测结论

| 项目 | 浏览器能力 | 是否把网页版 AI 当模型通道 |
|---|---|---|
| `octop-harness` | `browser_use` 单一工具（action 枚举：navigate / dom_tree / click / type / screenshot / eval_js / tab 管理），底层 `octop-browser` 走 CDP，**profile 持久化登录态**（`builtin/tools/browser_use.py:391-475`） | **不存在** |
| `Octop-main` | 完整：profile 管理（`~/.octop/browser-profiles`，按 user 隔离）+ WebSocket 实时画面 + 远程点击 + 录制回放生成 Skill（`api/routers/browser/`） | **不存在**（唯一 ChatGPT 相关是 `codex_oauth.py` 走 OAuth + HTTP API，不是网页 UI） |
| `AgentTeams-main` | 无浏览器模块 | 无 |

三个项目都验证了「浏览器可自动化第三方系统」，但**没有一个**尝试「用浏览器驱动网页版大模型当推理通道」。

### 6.3 三条硬约束（按严重度）

**① 服务条款与账号风险**

主流网页版（ChatGPT / Claude / Gemini / DeepSeek / 千问 / Kimi / MiniMax）的用户协议普遍禁止「自动化访问 / 非交互式使用 / 绕过界面限制」。检测到会封号，且企业账号被封会牵连主体。

**② 反自动化与 UI 脆弱性**

- Cloudflare / 指纹检测 / 行为风控会拦 headless 或被识别为脚本的会话；
- DOM 结构随版本更新即变，**每次前端改版都是一次线上故障**；
- 无 `stream` 协议契约，只能靠 DOM 变化猜流式边界 → 与你刚修好的 SSE 体验（reasoning 分离、过程步骤）**完全无法对齐**。

**③ 无计量、无并发、无 SLA**

- 拿不到 token 计量 → 成本不可控、无法做 §4 的加权调度（权重没有数据基础）；
- 单账号并发受限（多为 1~3 条会话），吞吐天花板极低；
- 无超时/限流契约，编排链路无法做可靠性设计。

### 6.4 替代方案（成本对比）

你要的能力是「用最强的模型帮我分析、拆解方案」。这件事有更稳的路径：

| 方案 | 稳定性 | 成本 | 工作量 |
|---|---|---|---|
| **官方 API（推荐）** | 高（SLA + 计量 + 流式契约） | 低（国产模型 ¥1~10/百万 token 级） | 小（本项目已有 provider 抽象，加一个 provider 即可） |
| 官方开放平台的「深度思考」模型 | 高 | 低 | 小 |
| 浏览器驱动网页版 | 低（封号/改版/风控） | 隐性极高（人力维护 + 封号损失） | 大（登录态、DOM 适配、流式伪造、异常恢复） |

**一句话**：用浏览器白嫖网页版 AI，省的是钱，赔的是稳定性、合规和你的时间。

### 6.5 如果仍要做：建议的收敛形态

把构想**重新定位**为两件独立的事，而不是一件：

**A. Browser 会话 = 「操作没有 API 的系统」的能力**（这才是浏览器的不可替代价值）

- 场景：SaaS 后台、内部旧系统、需要登录+多步操作的表单/报表导出；
- 形态：`browser_use` 类工具（参考 octop 的 action 枚举），profile 持久化登录态，**人工扫码/登录一次**；
- 与现有架构的契合：作为 `internal_*` 工具族的一员（`internal_browser_*`），受执行链上下文闸门约束，**沙箱化**（禁网白名单 + 零凭据 env）；
- 落地成本可控，且与你正在做的「沙箱执行链」同构（都是「受控外部执行」）。

**B. 「网页版 AI 当 planner」= 明确的实验性可选通道**

若你确实想验证这条路，建议严格限定：

- **人工登录、人工持有会话**（不做自动登录，不碰凭据）；
- 只在**非关键路径**用（如「给我一份初稿方案」），失败自动降级到本地模型；
- **强契约**：输入「结构化任务书」，输出「固定 JSON schema」，用 DOM 抓取 + schema 校验（不依赖 markdown 猜结构）；
- 明确的合规声明与开关（默认关）；
- **不做并发**（单会话串行），避免风控。

### 6.6 我建议的排序

1. **先做 A（浏览器操作无 API 系统）**——这是真实痛点，风险低，与沙箱执行链复用。
2. **B 先做 PoC 验证成本收益**：拿一个场景（如「用某网页版模型生成方案初稿」）实测「成功率 / 单次耗时 / 改版频率」，用数据决定是否继续。
3. **如果目标只是「最强模型帮我拆方案」**，直接接官方 API —— 这是当前最高性价比的选择。
