## 4. 关键发现

### 4.1 检出能力：内部组显著更全（23 vs 14），且内部独有项多为高价值缺陷

内部独有且外部漏检（均为数据正确性 / 状态一致性类）：`N14`（`error==null` 反推成功）、`N19/N20`（状态迁移无事务 + 归批返回值丢弃，可致重复投递）、`N22`（无分布式锁）、`N23`（重推换 messageId 破坏幂等）。外部独有仅 3 条（单实现抽象 / 逐批 INFO 日志量 / select 应用层过滤）。

> 归因提示：差异可能来自执行模型对「状态机 / 并发 / 事务」类判据的扫描深度，非约束链路本身（两侧均读到同一规范正文）。单组样本，不作为能力定论。

### 4.2 冲突判定：同一事实、相反结论（对比价值最高）

| 事实点 | 内部组 | 外部组 |
|---|---|---|
| unip-sync 反向依赖 unip-app（pom） | N04 **不合规**（结构缺陷固化） | P-13/P-14 **合规**（契约清晰） |
| 裸 Map 跨模块契约 | N06 **不合规** | P-03 **合规**（未跨域） |
| 分页 pageNo 溢出 | N21 **不合规** | P-09 **合规**（夹取） |

> 同类事实出现相反判定 ⇒ 「规范给出判据」不等于「判定一致」；规范条款的**可判定性**（能否机械裁决）与 **scope 精准性**（引用哪些章节）是两组差异的另一解释变量。

### 4.3 约束文档路径语义对沙箱执行器的误导（★观察点 1，机制缺陷）

- 现象：trae 首轮声称在 `E:\yhzx\1027\unip-platform`（宿主机原始路径，**沙箱内不存在**）执行 ls/wc 留痕 → kimi 沙箱实测戳穿 → score=2 驳回 → rework。
- 根因链：拆解 prompt 要求「优先读取约束文档记录的**本地绝对路径**」；manifest 的 `path` 恰为宿主绝对路径。内部执行器读正文后自行落到 `/workspace`（凭系统沙箱提示语义），外部执行器缺这层语义，把宿主路径当工作区根。
- 第二轮修复后，外部组后续 4 条全部一次通过（90 分）——外部 agent 纠错/学习信号强，但首轮代价真实存在。
- **定性**：`ConstraintDocCatalog` 只有「平台侧读取路径」，契约里缺「执行侧可达路径」维度（如 repo 相对路径 / 沙箱内路径）。这是本次测试发现**最确定的机制缺口**。

### 4.4 评审 coverage 声明对「验证型验收」的系统性缺失（★观察点 2，与执行端无关）

- 现象：4 次转人工全部命中同类静态校验——kimi verdict `pass=true` 但产物达标（人工复核均 APPROVED），触发 `acceptance_not_covered` BLOCK 的均为「UTF-8 无乱码 / 汇总表条目数=上游之和 / 覆盖章节集合」这类**字符集 / 数值聚合 / 集合型**验收条目。
- 定性：`ReviewCoverageCritic`（RV-3）对 `pass=true` 时 coverage 声明的核对是**对**的（防护有效），但评审 prompt 对「验证型验收」的 coverage 声明引导不足。内外部组受害者相同（审查端为常量 kimi），不影响内外对比干净性，但**影响整链自动化率**（人工介入频率）。

### 4.5 执行纪律：外部组证据链反而更规范（亮点）

外部组报告含 sha256 只读取证（5 文件逐字校验 + `/workspace` ro 挂载取证）、上游附件引用登记（6 条 storageUrl 逐字一致）、机器校验脚本 ALL PASS——证据形式比内部组更结构化。可能受外部 CLI 工具的产物规范模板影响，值得在评审 prompt 侧借鉴。

## 5. 演进设计输入（用户补充思路，只沉淀不立项）

> 本节为**设计输入沉淀**，非承诺排期、不含任务分解；正式立项由后续 `plan/` / `design/` 决定（治理规则 §3.5 / §3.6 口径）。与差距表 `G-033`（执行环境维度：仓库注入调查）**强关联**——用户思路实质是 `G-033` 「执行侧仓库注入」的候选定案方向。

用户对「后期代码开发类任务」的产品思路，要点如下（原文意译 + 平台语境化）：

1. **外部 agent 代码改造任务的领取前置准备**：任务下发时须显式携带环境与拉取信息——git 项目地址、拉取方式（https/ssh、分支/commit 锁定）、所需运行环境（JDK/Node/依赖）。缺项应阻塞领取（对齐 `G-033` 的 `ExecutionPrereqChecker` 方向）。
2. **约束写法**：任务要求中「参考 `xxx` 文档 `xxx` 章节规范执行本任务」——即现链路 `constraintRefs{kind:DOCUMENT, ref, scope[]}` + 执行侧按需读取，本次已验证该通道可通；对外部组补「执行侧路径」后即完备（观察点 1 的修复方向）。
3. **渐进式提交流程（分阶段提交）**：
   - 第 1 步：执行者提交**改动的代码文件本体**（java/js 等 + 说明改了哪里），而非只交报告；
   - 第 2 步：reviewer 在沙箱内**基于提交的代码 + 同一规范**做验证测试（编译 / 规范条款命中 / 测试）。
   - 即把「代码即交付物」前移，报告退居说明位。这需要产物通道支持「代码文件集」增量提交（现 `attachment` 方向已支持产物登记，需补「执行中代码文件」语义）。
4. **中期 git 组件集成（gittree 类）**：在沙箱内支持**拉取外部 agent 提交后的分支**，基于最新代码做集成测试/调试；代码审查可基于 commit diff 而非整包回传。
5. **对照参照系**：workbuddy / trae / claude code 对项目代码修改均有 git 组件集成能力（clone → 改 → commit → diff 审查），作为形态参照。**该参照系属外部调研，需另行 `research/` 勘察（带源码/文档 [实测] 口径）后再定边界，本报告不预设结论。**

**与本次实测的直接呼应**：用户的「git 拉取」思路恰好能消解观察点 1——若执行器先 clone 目标 repo，规范文档随仓库就位，`ref` 只需给出 repo 内相对路径，引用式约束即对内外执行器同等可靠（不占 prompt、不会与仓库版本分叉）。「植入正文 vs 引用文档」的选择建议：短红线用 `TEXT` 内联，长规范用 `DOCUMENT` 引用 + 执行侧可达路径。

## 6. 待决：如何证实「规范让代码改得更好」

本次未证实（任务形态为诊断非改造），建议对照实验（**尚未立项**）：

- 靶子：20~50 行小改动任务（如把 `GrantSyncServiceImpl` 推送挪出事务边界并补状态迁移）；
- 三组同模型同任务：A 无规范 / B `constraints` 植入 u13 正文 / C `constraintRefs` 引用 u13 + 执行侧自读；
- 度量：规范条款命中数、kimi score、返工次数、diff 行数、是否引入新违规；
- 样本：每组 ≥3 次取中位数（单次噪声大）。结论方可用于「约束提升产出质量」的宣示。
