**❌ 【本次新发现】Redis ACL 写法缺陷 —— 已提交的 P0 级部署安全缺陷**

| 项 | 内容 |
|---|---|
| **位置** | `deploy/middleware/docker-compose.yml:93`（**HEAD 版本，已入库**） |
| **原写法** | `- "default on >${REDIS_DEFAULT_PASSWORD} ~* &* +@all -FLUSHALL …"` —— 整条 ACL 规则串作为**单个 argv 元素**传入 |
| **后果** | Redis 将每个非 `--` 开头的 argv 元素**单独转义为一个配置 token**，故整串被当作 `user` 指令的**唯一参数（用户名）**，`on` / 密码 / `~*` / `+@all` / 各 `-` 禁用项**全部丢失**。**（2026-09-30 午后订正）实际后果比"规则失效"更严重**：ACL 加载失败 → **容器 ExitCode=1 崩溃循环，RestartCount=11359**（`5ad5e1d` commit 载明），即**服务不可用**；若仅修复崩溃而保留整串写法，才会退化为 `default` 用户 `nopass` 裸奔 |
| **风险叠加** | 同文件 `ports: "26379:6379"` **映射到宿主机**——若错误写法被"修成能启动但规则仍丢"的形态，宿主机公网可达即**无认证裸奔**（与 G-017 R7「MinIO 默认凭据 + 端口暴露」属同类部署侧风险） |
| **修复状态** | ✅ **已修复并提交**（2026-09-30，`5ad5e1d`）：每条 ACL token 拆为独立 argv 元素；同时新增 `deploy/middleware/scripts/diagnose-redis.sh`（只读取证）与 README 事故收据 |
| **建议** | ①`deploy/middleware/README.md` 已记录「**.env 公开泄露**，需人工换凭证」——**请尽快轮换**；②把「ACL 生效验证」纳入部署检查单（`redis-cli ACL LIST` 应可见 `on` + `>密码`） |

1. 子任务 2（DONE）产出文件《按两组不同关键词执行 web_search 并收集可溯源证据.md》**total = 22685 字符**，其中 7 条检索关键词字符串分散在文件中后段；
2. **执行侧注入截断**：`AgentRuntimeContextAssembler.java:84` `DEP_CONTENT_MAX_CHARS = 4000`——前置产出注入下游 Prompt 时**截断到 4000 字符**（`render.substring(0, 4000)` + 「已截断至 4000 字符」标注）；

**为什么重派链救不了它**：`DEP_CONTENT_MAX_CHARS=4000` 与截断后的 prompt 在**每次重派都相同** → 重派 4 次都在做一个**结构性不可能完成**的任务。兜底链（重派 / 评审返工上限 / 死信 / 人工介入）**逐一正确工作**，但它**无法区分「可重试失败」与「结构性不可能」**，于是空转 4 次、烧掉 4 次 tokens（这恰好是 tokenUsage 落地后**第一次可量化**的成本浪费）、最终仍需人工。

1. 短期：对「下游验收依赖上游具体字段」的场景，改注入**结构化字段**（而非整篇截断正文）——例如上游产出强制附「检索关键词清单」独立小节并**免截断前置**；
