## 2.6 W1~W11 清偿工程全貌：改了什么、付出什么、得到什么

> 差距表 C-17 只登记了**结论**，本节补工程细节与**可复用判据**；逐轮执行记录另见 `doc/log/2026-10.md` 与《优先级决策分析》§16.9。

### 2.6.1 起因：全仓最后一条、也是最大的一条反向依赖

`agent` 域直接持有 `task` 域的实体（`SubTask` / `Uncertainty` / `ExecutionRecord`）与 Service（`SubTaskService` / `TaskTimelineService` / `TaskRunningSpecService` …），共 **68 处 import / 20 个文件**。按 §6 依赖方向（`planner > review > task > agent > system > shared`），这是「下层 → 上层」的**反向依赖**，其性质是：

- **编译期可见、运行期无害** ⇒ 极易被容忍并持续累积（实测自 2026-09-14 起长期挂账）；
- 让 `task` 的任何改动**反向传播**到 `agent`，两域无法独立演进；
- `agent` 是执行热路径（派发 / 执行 / 回调 / MCP），耦合面最广。

**为什么不能「一次性大改」**：实测 20 个文件里 **12 个同时跨 2~4 种机制**（实体形参 / 只读 Service / 带判定写 / read-check-write 事务序列）。若按「import 类型」分批，同一文件会被反复改动、反复锁基线，且中间态可能编译不过。⇒ 计划由「按 import 类型分 5 批」**重排为「按文件收敛的 W1~W11」**：**一个文件必须一次性改完**，每轮独立提交、独立锁基线、独立回归。

### 2.6.3 沉淀的六条机制（后续改造可直接复用）

| # | 机制 | 一句话判据 | 首次 |
|---|---|---|---|
| 1 | **端口反转（含归位）** | 让依赖落在顺向那侧，**端口放顺向依赖的被依赖方**；消费方高于提供方时端口**必须落提供方域** | W2 / W8 |
| 2 | **快照值对象** | 跨域只读 → 传 `record` 投影、**不泄漏实体**；字段按需增长，规模大改 `@Builder` | W1 / W7 |
| 3 | **不透明命令端口** | 带判定的写 → 消费方只传意图，**判定+写整体落提供方**；契约不带 `@Version` | W3 / W10 |
| 4 | **ID 契约** | 接口形参是跨域实体而消费方短期迁不动 → **降为 `Long id`**，提供方自读快照 | W6 |
| 5 | **提供方派生字段** | **判定依据属于谁、判定就由谁做**；由提供方映射器算好布尔透传，消费方不复制常量 | W11 |
| 6 | **整类删除 / 能力下沉** | 反转后某类只剩「转发到端口」⇒ **整类删除**；判定按「读谁的字段」归域 | W3 / W8 |

**两条排期铁律**（本次踩出来的，规划轮次时先问）：

- **接口与其实现必须同轮**（改接口签名不改实现必然编译不过）；
- **迁移时点由「跨域类型的最终消费方」决定，不由持有者决定** —— `LocalExecutionCommandConsumer` 自己只用 `SubTask` 少数字段，却把实体**原样传给**装配器（要用 12 个字段，含返回 task 实体 `List<Uncertainty>` 的 `getUncertainties()`），故必须与装配器（W11）同轮。规划时对每个待迁文件问一句：**「这个跨域实体还被本域哪个类消费？」**

# 6. 结论与建议排序

## 6.1 直接回答两个问题

**① V2 架构改造进度如何？**

**结构性改造已达里程碑**：`agent->task` 从 68 清零，且这是全仓**最后一条**反向依赖 —— 六域依赖方向自此**结构性正确**。配合守卫 20 条规则与 CI 门禁，该成果**已被机制锁死**（只降不升 + 30 域对独立矩阵复核为 0）。

**但 V2 的「能力层」与「结构层」进度严重不对称**：B2/B3/B4/B5 自 2026-09-14 起**连续 3 个迭代零推进**。《目标架构》§0 列出的 `Partial`/`Planned` 五项中，**有 4 项卡在同一处**（Sandbox 隔离、Event Recovery/Fork、Quality Gate、Fleet 成本）。

**② 整改后是否还存在质量问题？**

**存在，但性质与上轮完全不同**：

- 上轮的问题是「**红线被破**」（反向依赖在库、守卫覆盖不足）→ 现已**清零**。
- 本轮的问题是「**红线之外的规范缺口**」：
  - **守卫有三类盲区**（F-1 模块级 / F-2 规则级 / F-3 方向级）——即「**现在没问题，但未来不会被拦住**」；
  - **类规模越过 §9 硬阈值**（3 个 >1000 行，且 2 个还在变大）；
  - **一处未登记的双轨残留**（F-5），与你的「不留退路」决策相悖；
  - **契约仍泄漏实体**（F-4）+ **前向实体泄漏 61 行**（F-3）。
