# 子任务执行对话流补「阻塞结论」消息 设计（2026-11-12）

- 状态：待实施（本设计文档存 `doc/review/`，实施前经人工确认）
- 范围：HelloAI 子任务执行对话流（conversation_message）
- 关联实证缺陷：子任务 `2120690863084126210` 执行轮 2 只有「执行请求」、无任何执行结论

---

## 1. 背景与问题

### 1.1 现象（用户报告 + 本机 DB 实证）

子任务 `2120690863084126210` 的 conversation_message：

| 时间 | tool_name | 归属 |
|---|---|---|
| 09:31:17 | sub_task_execute_user_prompt | 执行轮 1 |
| 09:33:25 | sub_task_execute | 执行轮 1 |
| 09:33:45 | subtask_review_prompt / _verdict / _result | 核验轮 |
| 09:33:46 | sub_task_execute_user_prompt（执行请求 #6） | **执行轮 2** |
| 10:00:04 | subtask_recheck_prompt / _verdict / _result | 抽检轮 |

执行轮 2 之后**始终没有** `sub_task_execute` / `sub_task_execute_failed` 结论行。子任务当前状态 **BLOCKED**、rework_count=1。

时间线尾部（task_timeline）佐证：

```
sub_task_execute_start → sub_task_report_blocked
  → sub_task_manual_intervention_required
  → sub_task_execute_result_discarded（reason=subtask_status_not_in_progress）
```

前端 [SubTaskDetail.vue](file:///E:/yhzx/1027/helloai/helloai-ui/src/views/subtask/SubTaskDetail.vue) 的 `roundMeta()`：执行轮内无 `sub_task_execute_failed` 时状态标签默认绿「已完成」。**因此执行轮 2 渲染成绿色的「已完成 / 无结论」，误导运维以为它成功结束。**

### 1.2 根因（源码确认）

三处都不写对话流结论消息：

1. `ExecutionResultHandler#handleReport`（[ExecutionResultHandler.java:297](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/command/ExecutionResultHandler.java#L297)）：
   当 `subTask.status() != IN_PROGRESS` 时硬拦，只记 timeline(`SUB_TASK_EXECUTE_RESULT_DISCARDED`) 即 return，**对话流写入块（356-380 行）完全没执行**。自报阻塞后子任务已变 BLOCKED，故第二轮 INTERNAL 回写在这里被丢弃，结论永远缺失。
2. 内部出口 `InternalLlmExecutorTools#internalReportBlocked`（[InternalLlmExecutorTools.java:268](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/tool/InternalLlmExecutorTools.java#L268)）：只调 `block` + `markManualIntervention`，不写对话流。
3. 外部出口 `McpAgentReportServiceImpl#reportBlocked`（[McpAgentReportServiceImpl.java:402](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/service/impl/McpAgentReportServiceImpl.java#L402)）：只调 `block`，不写对话流。

三者互补后：凡「自报阻塞」，执行对话流必悬空一轮。

## 2. 方案（已与用户确认方向，取「自报阻塞路径补」而非通用 discarded）

### 2.1 目标

在「自报阻塞」路径补写一条对话流结论消息，让执行轮不再悬空、前端不再渲染成绿「已完成」。

- **新 toolName**：`sub_task_execute_blocked`
- **内容**：「Agent 能力不足 / 产出未达要求 → 需人工介入：{reason}」风格（前端展示时再渲染得更精确，见 §4）。
- 该消息与时间线 `sub_task_report_blocked`（执行受阻）用语一致性对齐。

### 2.2 判定边界（不扩大语义）

- **只在「自报阻塞」路径补**；REWORK 返工自有核验结论语义，不混入本消息。
- round 判据：`轮内有 sub_task_execute_blocked → 状态标「已阻塞」`，与 `sub_task_execute_failed → 失败` **独立并存**。

### 2.3 改动半径

后端 2 出口各加一次 `conversationService.addMessage(...)` 调用；前端加 1 条 tag 映射 + roundMeta 判据。**不动状态机、不动 ExecutionResultHandler 的 discarded 分支、不动 review 语义。**

> 说明：`ExecutionResultHandler` 的 discarded 分支**不补**。它覆盖所有「状态非 IN_PROGRESS 却被回写」的竞态过期场景（含超时改派等），语义是「结果丢弃」而非「本轮明确结论」；与用户确认的方案聚焦「自报阻塞」这一有明确原因出口，避免把歧义竞态也写成阻塞结论。若日后需覆盖，另立小项。

## 4. 前端改动（SubTaskDetail.vue）

### 4.1 toolName → 标签/颜色的映射

`CONV_TAG_MAP` 新增：

```ts
sub_task_execute_blocked: { label: '阻塞结论', type: 'warning' }
```

### 4.2 消息块语义 / 头像

- `convTagType`：维持 `warning`（黄色），不随 verdict 切色（阻塞结论非通过/驳回二值）。
- `convItemClass`：`is-execute` 分支不在列表内（`sub_task_execute_blocked` 不属 `sub_task_execute`/`_failed`），保持其 `is-analysis=false / is-result=false / is-user=false` 的默认灰。可接受：黄色 tag「阻塞结论」已表达语义，无需额外修饰类。
- `convAvatarText`：`sub_task_execute_bloocked` 不在 `sub_task_execute`/`_failed` 分支 → 落到默认 `·`。可接受（结论条来自执行者，但无独立视觉；为最小改动保留默认）。若需更清晰，可在后续润色单独立项。
- `convRounds` 执行轮识别：`sub_task_execute_blocked` 应并入执行轮（与 `sub_task_execute` / `_failed` 同轮），故 **`isExecute` 判定需加该 toolName**：
  ```ts
  const isExecute = tool === 'sub_task_execute_user_prompt' || tool === 'sub_task_execute'
      || tool === 'sub_task_execute_failed' || tool === 'sub_task_execute_blocked'
  ```
  （否则它会落入「默认开 execute 轮」的兜底分支，仍算执行轮但轮头判定依赖首条——必须显式纳入，避免歧义。）

### 4.3 轮次状态标签（核心：不再误标「已完成」）

`roundMeta()` 改为四态，新增「已阻塞」独立于「失败」：

```ts
function roundMeta(round) {
  const failed = round.messages.some(m => m.toolName === 'sub_task_execute_failed')
  const blocked = round.messages.some(m => m.toolName === 'sub_task_execute_blocked')
  const statusLabel = blocked ? '已阻塞' : (failed ? '失败' : '已完成')
  ...
  return { statusLabel, failed, time }
}
```

- 渲染处维持 `failed` 布尔驱动失败红；`blocked` 经 `statusLabel` 用「已阻塞」文案（可配标签色 `warning`，改动集中在 `statusLabel` 计算，模板处是否加染色另视现状）。
- 注意当前 `roundMeta` 只返回 `{ statusLabel, failed, time }`；如需给「已阻塞」上色，需在其驱动模板处按 `statusLabel==='已阻塞'` 判色，或扩展返回值加 `blocked`。**实施时以「改文案即可达意」为最低要求，染色列为可选润色。**

## 5. 测试与验收

无既有单测覆盖这两个出口的对话流写入。实施后验证方式：

1. 后端编译 + 全量门禁（app 在跑时用 `ci-gate --no-clean`，勿用 `mvn clean` 以免破坏运行中的 target/classes）。
2. 行为级：构造一次「自报阻塞」（内部 `internal_report_blocked` 或外部 `reportBlocked`），跑后查 conversation_message 出现 `sub_task_execute_blocked` 行、时间线出现 `sub_task_report_blocked`，前端该执行轮显示「已阻塞」。
3. 回归：不阻塞的正常执行轮仍绿「已完成」；REWORK 返工轮不出现 `sub_task_execute_blocked`。

## 6. 影响面 / 风险

- **写入链路**：新增的 `addMessage` 与既有 execute/review 结论写入同为 `REQUIRES_NEW` + try/catch 降级，不侵入主事务；若对话流表不可写，仅告警不影响 `block` 本身。
- **前端**：只加映射/分支，不重构既有 round 分组逻辑；`sub_task_execute_blocked` 仅在阻塞路径出现，不污染正常轮次。
- **向后兼容**：历史库中已悬空的执行轮（如 `2120690863084126210`）不会回填（不写数据迁移），仅对之后的新事件生效。存量悬空轮不在本需求范围内修复，如需冷修另立项。

---

## 7. 不做 / 边界

- 不补 `ExecutionResultHandler` discarded 分支（理由见 §2.3 说明）。
- 不做存量数据回填（§6 兼容）。
- 不动状态机、不动 REWORK 语义、不动死信/熔断路径。
