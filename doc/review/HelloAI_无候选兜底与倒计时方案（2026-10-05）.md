> 依据：用户 2026-10-05 22:40 拍板「现在就派白客实施」+ 阈值 10 轮 + 重试间隔 120s + 前端倒计时。
> 前置修复：P1-1（`NoCandidateAgentException` 不烧预算）已落地，本方案在其上叠加。
>
> **★落地状态（2026-10-07 复核）**：本方案**已全部实现** —— 后端时钟 C 计数/节拍/转人工见 `SubTaskPendingOrphanTask`（`091f714`、`0751f16`），前端倒计时见 `usePendingCountdown.ts` + `SubTaskDetail.vue` / `SubTaskList.vue`（`0bcead9`）。下文按「实施时的设计口径」保留存档。

## 1. 需求与痛点

- **场景**：4 个主任务并发、只有 2 个外部 ai agent，且外部 agent 单会话只能接一个子任务（物理瓶颈）。
- **后果**：另外 2 个主任务的子任务持续「无可用候选」，原设计每 60s 空扫一次，用户只看到任务长期停 PENDING、不知所云。
- **目标**：① 长期无候选 → 自动转人工介入（可见、可处置）；② 前端显示「约 N 秒后重试」倒计时，让等待可视化；③ 每个子任务倒计时**天然各不相同**。

## 2. 核心设计：把「重试节拍」从全局 tick 里独立出来

| 时钟 | 现状 | 本方案是否改 |
|---|---|---|
| A · 孤儿扫描 tick | `pending-orphan-scan-interval-ms`=60000，`@Scheduled fixedDelay` + ShedLock | **不改**（仍是 60s 一跳的调度框架） |
| B · 重派退避 | `REASSIGN_BACKOFF_SECONDS={60,180,600,1800}`，读 `last_attempt_time` | **不改**（只对「已派出过」的重派生效） |
| **C · 无候选重试节拍（新）** | 无 | **新增**：每子任务自带 `nextDispatchAt`，默认 +120s，带抖动 |

**关键**：时钟 C 是**每子任务独立**的（因此倒计时各不相同），写在与 `manualIntervention` 同款的 `sub_task.context` JSONB 内，**无需 Flyway 迁移**。

## 3. context 结构

```json
"noCandidate": {
  "rounds": 3,                         // 连续无候选轮数（选中人则清除）
  "nextDispatchAt": "2026-10-05T22:47:30+08:00",  // 下次允许重试时刻 = 基准 + 120s
  "reason": "no_available_candidate",
  "updatedAt": "2026-10-05T22:45:30+08:00"
}
```
达阈值后额外写入（复用现有 `markManualIntervention`）：
```json
"manualIntervention": { "reason": "no_candidate_long_wait", "rounds": 10, "waitedMs": 1200000, "ts": "..." }
```

## 4. 配置项（`AgentDispatchProperties`，prefix `helloai.dispatch`）

| 键 | 默认 | 说明 |
|---|---|---|
| `no-candidate-max-rounds` | `10` | 连续无候选达此次数 → 转人工介入 |
| `no-candidate-retry-interval-seconds` | `120` | 无候选后下次重试间隔基准（用户选 120） |
| `no-candidate-retry-jitter-seconds` | `15` | 抖动上限，`nextDispatchAt = now + (120 ± rand[0,15])`，防同步惊群 |

## 5. 改动点

### 5.1 `SubTaskPendingOrphanTask.java`（helloai-job）
- 在 `catch (NoCandidateAgentException)` 分支内（现有落 `sub_task_no_candidate` 处）：
  1. 计数：`rounds = ctx.noCandidate.rounds + 1`；
  2. 判断 `rounds >= noCandidateMaxRounds`：
     - **是** → 调 `markManualIntervention(subTaskId, "no_candidate_long_wait", Map.of("rounds", rounds, "waitedMs", ...))`（该 API 内部已落 `sub_task_manual_intervention_required` 事件）；
     - **否** → 计算 `nextDispatchAt = now + interval + jitter`，写回 `context.noCandidate`；
  3. 两分支后续扫描都会被现有逻辑自然跳过（`isManualInterventionMarked` 跳过 / `nextDispatchAt` 未到跳过）。
- **在调用 `dispatchPendingSubTaskAuto` 之前**新增前置门控：读 `context.noCandidate.nextDispatchAt`，`now < nextDispatchAt` 则 `skipWaiting++` 并 `continue`（不计数、不重试）。
- 选中人成功分支：清除 `context.noCandidate`（计数归零）。
- 上下文读写统一走 `SubTaskService.updateContext(subTaskId, ctx)`（注意：该方法是**整体覆盖** context，需先 `getById` 取旧 map 再 put 后整体写回）。

### 5.2 `AgentDispatchProperties.java`（helloai-common）
新增上述 3 个配置字段（带 javadoc，说明与 `maxReassignAttempts` 语义不同）。

### 5.3 前端 `SubTaskDetail.vue` / `SubTaskList.vue`（helloai-ui）
- `context` 字段已在 `SubTaskResponse` 暴露，**无需改 DTO**。
- PENDING 且 `context.noCandidate.nextDispatchAt` 存在 → 显示「等待执行者 · 约 N 秒后重试」，每秒刷新（`setInterval`，组件卸载 `clearInterval`）；存在 `manualIntervention` 时改显示「等待人工介入」。
- 新增事件登记三处（若引入新 eventType，见 §6）。

## 7. 不做（范围冻结）
- 不改时钟 A tick、不改时钟 B 退避常量、不改 `dispatchPendingSubTaskAuto` 本体。
- 不新增 Flyway 迁移。
- 事件驱动路径（依赖解锁 `SubTaskCompletionListener`、草案确认 `PlannerAnalysisServiceImpl`）保持即时尝试，不套用 120s 节拍。

## 8. 验收
- 单测：连续无候选累加 rounds；达阈值调 `markManualIntervention`（reason 正确）；未达阈值写 `nextDispatchAt`；选中人清除 noCandidate；`now < nextDispatchAt` 时 `skipWaiting` 且不调 dispatch。
- 反证：达阈值后再扫 → 因 `manualIntervention` 跳过、不再累加。
- 前端：PENDING + nextDispatchAt → 倒计时显示；达阈值 → 人工介入面板可见。
