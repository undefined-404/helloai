## 1. 缺陷①：执行对话流按「类型」分段，未按 Agent 分段

### 1.1 现象

截图轮次头显示 `#1 · execute  inner-kimi-2.6-executor  失败`，但轮内第 3、4 条消息的发送者是 `inner-qwen3.7-plus-executor`，且第 4 条是**成功产出**。用户据此误判「之前有问题的 LLM 模型又好了」。

### 1.2 证据（DB 实测 `conversation_message`）

| seq | role | sender_name | tool_name |
|---|---|---|---|
| 1 | user | inner-kimi-2.6-executor | `sub_task_execute_user_prompt` |
| 2 | assistant | inner-kimi-2.6-executor | `sub_task_execute_failed` |
| 3 | user | inner-qwen3.7-plus-executor | `sub_task_execute_user_prompt` |
| 4 | assistant | inner-qwen3.7-plus-executor | `sub_task_execute` |
| 5 | user（platform，`sender_id` 为空） | — | `subtask_review_prompt` |
| 6–8 | assistant | inner-minimax-2.5-reviewer | `subtask_review_thinking` / `_verdict` / `_result` |

四条执行消息**全部落进同一轮**。

### 1.3 根因

`helloai-ui/src/views/subtask/SubTaskDetail.vue`：

- `convRounds`（`:1060`）开新轮的判据只有 `type`（`execute` / `review`），**不含 Agent 维度**；只要 `current.type === 'execute'`，换 Agent 也会继续往同一轮 push。
- `roundAgentName`（`:1213`）取轮内**第一条有 `senderId`** 的消息 ⇒ 轮头显示 kimi。
- `roundMeta`（`:1219`）`failed = 轮内存在任意 sub_task_execute_failed` ⇒ 整轮被标「失败」。

### 1.4 改法（`SubTaskDetail.vue`，仅 2 处）

**(a) `ConvRound` 增加发送者键（`:1053`）**

```ts
interface ConvRound {
  type: 'execute' | 'review'
  roundNo: number
  /** 本轮的发送者（Agent ID 字符串）；平台侧消息 senderId 为空，不参与 */
  senderKey: string | null
  messages: ConversationMessageItem[]
}
```

**(b) `convRounds` 增加「Agent 变更即开新轮」判据（`:1060`）**

```ts
const startRound = (type: 'execute' | 'review', senderKey: string | null) => {
  flush()
  current.value = { type, roundNo: type === 'execute' ? ++executeNo : ++reviewNo, senderKey, messages: [] }
}

for (const msg of conversation.value) {
  const tool = msg.toolName || ''
  const isExecute = tool === 'sub_task_execute_user_prompt' || tool === 'sub_task_execute' || tool === 'sub_task_execute_failed'
  const isReview = tool.startsWith('subtask_review') || tool.startsWith('subtask_dual_review') || tool.startsWith('subtask_recheck')
  const key = msg.senderId != null ? String(msg.senderId) : null
  const cur = current.value
  // 仅新增一个开轮条件：执行/核验 Agent 变更（平台侧 senderId 为空，不触发）
  const agentSwitched = cur !== null && key !== null && cur.senderKey !== null && cur.senderKey !== key
  if (isExecute && (!cur || cur.type !== 'execute' || agentSwitched)) {
    startRound('execute', key)
  } else if (isReview && (!cur || cur.type !== 'review' || agentSwitched)) {
    startRound('review', key)
  }
  if (!current.value) {
    startRound('execute', key)
  } else if (current.value.senderKey === null && key !== null) {
    current.value.senderKey = key   // 平台侧前置消息（review prompt）归属到随后的 Agent
  }
  current.value!.messages.push(msg)
}
```

**逐条推演（样本数据）**：m1→开 `#1 execute/kimi`；m2 同键→并入；m3 键变 qwen→开 `#2 execute/qwen`；m4 并入；m5 类型变 review 且键为空→开 `#1 review/未定`；m6 键 reviewer→**采纳**为 `#1 review/reviewer`；m7/m8 并入。
⇒ `#1 execute kimi 失败`[m1,m2] + `#2 execute qwen 已完成`[m3,m4] + `#1 review reviewer 已完成`[m5–m8]。

### 1.5 影响面与回归

- **不改后端、不改数据**，纯渲染分组。
- `roundAgentName` / `roundMeta` **无需改动**：分段后自然取到正确的 Agent 与状态（已推演验证）。
- 卡头「共 N 条 · M 轮」的 M 会由 2 变 3（预期行为，非回归）。
- 回归点：① 单 Agent 多轮执行不误拆；② 平台侧前置消息不会把 review 轮拆成两轮；③ 旧数据（只有一个 Agent）分组结果与改动前**逐字一致**。

## 2. 缺陷②：空 system 消息发往 LLM

### 2.1 现象

kimi 首派执行 0.26 秒即失败：

```
400 - {"error":{"message":"Invalid request: the message at position 0 with role 'system' must not be empty","type":"invalid_request_error"}}
```

时序（`task_timeline`）：`13:05:21.509 llm_call_start` → `13:05:21.769 sub_task_report_blocked` → `13:05:21.773 sub_task_execute_failed`，**无任何自动换模型降级**，子任务直接 `BLOCKED`。人工换到 qwen 后 `13:10:25` 正常产出。

### 2.2 根因链（3 处，条件必然成立）

| 位置 | 代码 | 作用 |
|---|---|---|
| `AgentRuntimeContextAssembler:221` | `.systemPrompt("")` | 子任务执行链**硬编码空串** |
| `RuntimeTurnExecutor:115` | `new AgentLoopInput(ctx.getChatModel(), ctx.getSystemPrompt(), …)` | 原样透传空串 |
| `ChatModelToolLoop:68` | `messages.add(new SystemMessage(input.systemPrompt() != null ? input.systemPrompt() : ""))` | **无条件插入空 SystemMessage**（`null` 走 `""`，空串同样是空） |

`API_KEY_LLM` 各 provider 容忍度不同：deepseek / minimax 忽略空 system 消息（样本中两者均执行成功），**kimi / moonshot 严格拒收** ⇒ 400。

### 2.3 改法（推荐「最小修 + 同仓先例一致」）

`ChatModelToolLoop:68`：

```java
// 空 system 消息不发送：部分 provider（moonshot/kimi）对空 system 消息返回 400
// （与 AgentChatClientServiceImpl#doGenerate 的 hasText 守卫同口径）
if (StringUtils.hasText(input.systemPrompt())) {
    messages.add(new SystemMessage(input.systemPrompt()));
}
```

**同仓先例**：`AgentChatClientServiceImpl#doGenerate:86` 已是 `if (StringUtils.hasText(systemPrompt)) { prompt = prompt.system(systemPrompt); }` —— 即「platfom 侧 generate 链」一直有守卫，「AgentLoop 链」漏了。本次是把两条链的口径拉齐，**不是新增约定**。

**行为兼容性**：对 deepseek / minimax 而言，空 system 消息是 no-op，删除后语义不变；对 kimi / moonshot 由「必然 400」变为「正常」。⇒ **只修不破**。

**根治（建议单独立项，不在本次）**：给子任务执行链装配**非空** system prompt（如 Agent 角色设定 / Task Running Spec 头部），让 system 角色真正承载语义。这会改变所有执行链的提示词，需独立评估与回归，不夹带在缺陷修复里。

### 2.4 影响面与回归

- `helloai-core/src/test/.../ChatModelToolLoopTest.java` 现有断言只检查**末位**消息（`lastMessages().get(size()-1)`），**不校验首位**，改动不会致红。
- 需**新增**回归用例：① `systemPrompt` 为空/null ⇒ 首位消息是 `UserMessage`（无 `SystemMessage`）；② 非空 ⇒ 首位仍是 `SystemMessage` 且内容一致。
- 验证命令（本机铁律：应用在运行禁 `mvn clean`）：
  `mvn -o -B -DskipTests=false -Dsurefire.failIfNoSpecifiedTests=false -pl helloai-core -am test -Dtest=ChatModelToolLoopTest`

## 3. 缺陷③：`ASSIGNED` 无人工改派入口

### 3.1 现象

首个被指派的 Agent 若不可用，子任务停在 `ASSIGNED`，**界面连「更多」按钮都不出现**，只能等自动回收。

### 3.2 证据

- 时间线：`12:54:51 sub_task_dispatch_prepare(auto_assign)` → **静默 10 分钟无任何执行事件** → `13:05:20 sub_task_unclaimed_timeout_reassign`。
- 超时阈值：`application.yml:166 helloai.dispatch.assigned-timeout-minutes: 10`（`AgentDispatchProperties:114` 默认同为 10）。

### 3.3 根因（前后端各一道门，双重拦截）

**前端** `SubTaskList.vue`：
```ts
const MORE_ACTION_STATUSES = ['PENDING','IN_PROGRESS','PAUSED','BLOCKED','DEAD_LETTER']   // ← 无 ASSIGNED
```
⇒ `hasMoreActions(row)` 对 `ASSIGNED` 返回 false，`<el-dropdown>` 整个不渲染，只剩「详情」。且下拉项的状态门控也**没有** `ASSIGNED` 分支。

**后端** 三个入口各自收口：

| 入口 | 服务方法 | 当前允许状态 |
|---|---|---|
| `/reassignById` | `dispatchBlockedSubTask` | 仅 `BLOCKED` |
| `/redispatchInProgressById` | `redispatchInProgress` | 仅 `IN_PROGRESS` / `PAUSED` |
| `/redispatchDeadLetterById` | `redispatchDeadLetter` | 仅 `DEAD_LETTER` |

⇒ `ASSIGNED` **无路径可走**。

### 3.4 改法

**(a) 后端放开 `ASSIGNED`（`SubTaskDispatchServiceImpl.redispatchInProgress`，约 `:476`）**

```java
// 现状
if (subTask.getStatus() != SubTaskStatus.IN_PROGRESS
        && subTask.getStatus() != SubTaskStatus.PAUSED) {
    throw new BizException("只有 IN_PROGRESS 或 PAUSED 状态的子任务才能改派，当前状态: " + subTask.getStatus());
}
// 改后：ASSIGNED 表示「已指派未开工」，同样属人工处置窗口
if (subTask.getStatus() != SubTaskStatus.ASSIGNED
        && subTask.getStatus() != SubTaskStatus.IN_PROGRESS
        && subTask.getStatus() != SubTaskStatus.PAUSED) {
    throw new BizException("只有 ASSIGNED / IN_PROGRESS / PAUSED 状态的子任务才能改派，当前状态: " + subTask.getStatus());
}
```

**为什么不需要改状态机**：`SubTaskServiceImpl.block()`（`:1008`）的允许集已经是 `IN_PROGRESS || ASSIGNED || REWORK`；`SubTaskStateMachine` 也允许 `ASSIGNED → BLOCKED`。因此 `ASSIGNED` 走 `block() → BLOCKED → dispatchBlockedSubTask`（后者 `resetToPendingForDispatch(..., Set.of(BLOCKED))`）**全链路已通**，仅差入口校验这一行。`resume()` 分支只对 `PAUSED` 生效，`ASSIGNED` 天然跳过。

**(b) 前端纳入 `ASSIGNED`（`SubTaskList.vue`，3 处）**

```ts
// :705 MORE_ACTION_STATUSES 增补 ASSIGNED
const MORE_ACTION_STATUSES: readonly SubTask['status'][] =
  ['PENDING', 'ASSIGNED', 'IN_PROGRESS', 'PAUSED', 'BLOCKED', 'DEAD_LETTER']
```

```html
<!-- :286 附近新增下拉项（沿用既有 command="reassign" 通道） -->
<el-dropdown-item
  v-if="row.status==='ASSIGNED' && auth.hasPermission('subtask:reassign')"
  command="reassign"
>
  <span class="dropdown-danger">换人</span>
</el-dropdown-item>
```

```ts
// :705 doReassign 分支：ASSIGNED 与 PAUSED 同走 redispatchInProgress
if (reassignDialog.row.status === 'PAUSED' || reassignDialog.row.status === 'ASSIGNED') {
  await subTaskApi.redispatchInProgress(reassignDialog.row.id, reassignDialog.agentId)
} else {
  await subTaskApi.reassign(reassignDialog.row.id, reassignDialog.agentId)
}
```

**(c) 待裁定：人工入口是否跳过退避窗口？**

`ASSIGNED` 刚指派时 `attempt_total ≥ 1`、`last_attempt_time = 指派时刻`，退避首档 **60s** ⇒ 指派后 60 秒内的手动换人会被闸门按 `backoff` 拦下（**现在会明确回传 `applied=false + nextAllowed`，不再静默**，见 ⑤）。

- **方案 A（推荐，改动最小）**：保持闸门统一，人工也受退避约束。理由：第一档仅 60s，且已有明确回执；闸门语义单一，不引入"人工特权"分支。
- **方案 B**：给 `evaluateReassignGate` 加 `manual` 参数，人工入口跳过 `backoff`、仍保留 `circuit_open`（预算保护）。理由：人工介入是显式决策，不应被退避延迟。

> 倾向 A：用户诉求是「能介入」而非「零延迟介入」，60s 不构成卡死；避免为省 60 秒引入第二套闸门语义。

### 3.5 影响面与回归

- **新增**可用状态，**不减少**任何既有路径 ⇒ 对既有状态行为零影响。
- 需补测：① `ASSIGNED` 改派全链路（`block` → `BLOCKED` → `PENDING` → `ASSIGNED(new)`）；② `ASSIGNED` 子任务的 `attempt_total` 递增与熔断阈值联动；③ 非上述三状态（如 `REVIEW`）仍按原样抛 `BizException`。

## 4. 缺陷⑤：前端未消费 `RedispatchResult`（闸门已不静默，前端仍静默）

### 4.1 现象

后端 `2026-10-05 修 804` 后，被闸门拦截时返回 `RedispatchResult(applied=false, reason=backoff|circuit_open, nextAllowed=…)`；但前端：

```ts
await subTaskApi.reassign(reassignDialog.row.id, reassignDialog.agentId)
ElMessage.success('已重新调度，子任务重新进入分发链')   // ← 无条件成功提示
```

返回体被丢弃，`applied=false` 时仍提示成功、仍关弹窗 ⇒ **用户感知依旧是「点了没反应」**。

### 4.2 改法（`SubTaskList.vue`，1 处）

```ts
const result = await subTaskApi.redispatchInProgress(...) /* 或 reassign */
if (result?.applied === false) {
  const tip = result.reason === 'backoff'
    ? `重派被退避窗口拦截，最早可于 ${fmtTime(result.nextAllowed)} 重试`
    : '重派被熔断闸门拦截（预算耗尽），子任务已转 DEAD_LETTER，请走死信「重新指派」'
  ElMessage.warning(tip)
  reassignDialog.visible = false
  load()
  return
}
ElMessage.success('已改派，子任务重新进入分发链')
```

同时需给 `subTask.ts` 的 `reassign` / `redispatchInProgress` 补返回类型（`RedispatchResult`）——`request.post` 已返回 `R.data`，仅缺类型标注。

### 4.3 回归

模拟 `attempt_total` 打满至 5 后点「重新调度」⇒ 应见「熔断」警示而非成功；在退避窗口内点 ⇒ 应见带 `nextAllowed` 的警示。

## 5. 缺陷④：退避时钟（已修，回归清单）

当前实现（**已落地，勿重复改**）：

| 项 | 位置 | 内容 |
|---|---|---|
| 独立列 | `V102__sub_task_last_attempt_time.sql` | `sub_task.last_attempt_time TIMESTAMPTZ`，存量 `attempt_total>0` 行按 `update_time` 回填 |
| 唯一写入点 | `SubTaskMapper.incrementAttemptTotal` | 与 `attempt_total` **同批**原子写；`updateById` 一律不写 |
| 统一判定 | `SubTaskDispatchServiceImpl.evaluateReassignGate:678` | 返回 `ReassignGateDecision(blocked, reason, nextAllowed, taskId)`；`reason ∈ {terminal, circuit_open, backoff}` |
| 时钟读取 | 同上 `:728` | `subTask.getLastAttemptTime().plusSeconds(REASSIGN_BACKOFF_SECONDS[...])` |
| 拦截留痕 | `recordRedispatchSkipped:742` | 落 `sub_task_redispatch_skipped` |
| 顺序修正 | `redispatchInProgress:484` | 闸门判定**前置**到 `block()/resume()` 之前 |
| 接口语义 | 三处控制器 | 返回 `R<RedispatchResult>` |

**回归清单**：

1. `SELECT column_name FROM information_schema.columns WHERE table_name='sub_task' AND column_name='last_attempt_time'` 有行；Flyway `V102` 状态 `Success`。
2. `attempt_total ≥ 1` 的子任务，在 `last_attempt_time + 60s` 内点「重新调度」⇒ `applied=false, reason=backoff`，且 `task_timeline` 出现 `sub_task_redispatch_skipped`。
3. 用 `UPDATE sub_task SET update_time = now()` 人为扰动 `update_time`，再次点重派 ⇒ **应正常放行**（证明时钟不被 `update_time` 污染，即本缺陷的原始症状不再复现）。
4. 打开「换人」（`redispatchInProgress`）⇒ 不应再出现「先 block 掉状态、但重派被自己刷新出的窗口拦下」的组合。

## 6. 附带未解异常：已离线 13 天的 CLI Agent 被 `auto_assign` 选中

> **不属本次三缺陷，但同源（首派 Agent 不可用是 ③ 的触发前提），建议单独立项。**

**事实**：`12:54:51` 子任务被 `auto_assign` 指派给 `workBuddy-executor(2102935207752503297)`：

```
access_type  = CLI_CLIENT
online_status = OFFLINE
last_seen_time = 2026-09-24 08:41:47
offline_time   = 2026-09-24 08:47:41     ⇒ 已离线 13 天
score = 55, convex_failure_count = 0
```

**矛盾**：`AgentSelector.pickFromCandidates` 两道过滤都应将其排除——

```java
.filter(a -> a.getOnlineStatus() != AgentOnlineStatus.OFFLINE
        || (a.getAccessType() != null && !a.getAccessType().requiresRuntimeLiveness()))   // CLI_CLIENT ⇒ true ⇒ 必须排除
.filter(this::isHeartbeatFresh)   // offline-minutes = 5，lastSeen 13 天前 ⇒ false ⇒ 必须排除
```

且 `AgentAccessType.requiresRuntimeLiveness()` 确为 `this == CLI_CLIENT`（`helloai-common/.../AgentAccessType.java`）；`AgentHealthProperties.offlineMinutes` 默认 5 且三份 yml 均无覆盖；候选池唯一调用点 `SubTaskDispatchServiceImpl:195`，无第二套选择器、无 `@Cacheable`。
