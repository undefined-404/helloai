## 0. 一句话结论

**两项的挡路石曾是同一个**：平台**还没有「内容引用」的统一形状**（大对象放哪、事件/载荷里放什么、谁能读、去重按什么）。

**`REF-5.2b` 已按最小形态结项（2026-10-10，用户确认）**：**不给模型侧造第二条通道**，而是
① 截断标注行补 `id=<attachmentId>`（可寻址 ref）+ ② **复用既有** REST 取回通道
（`attachments/downloadById`，实测团队成员 200）⇒ **不新增 MCP 工具**，工具面保持 13 个。
判据侧连带把「子任务视图读」三处统一到 task-team（§2.1）。

**`REF-7` 维持立项但先定引用契约**（`ref` 形状 / 去重口径 / 读取权限 / 闭合 schema 落地形态）；
契约成文前不开工 —— 而 `5.2b` 的落地正好是这份契约的第一个既成实例，可为它提供先例。

> **前提修正**：计划 v2 订正把当前状态记为「真丢数据点 = 超 64K 极端超长附件被兜底截断」。
> 实测口径应改为：**丢的是「模型 / 外部 Agent 的可见性」，不是数据**（F2+F3+F5）——
> 原文在 PG / MinIO 里是全的，人（管理端）也取得到，**只有消费侧拿不全、且没有回取通道**。
> 这个差别直接改变两项的定性：它们是**能力/可观测性**改进，不是**可靠性**缺口。

### 1.1 原设计初衷（上游出处）与「为什么可以改形」

`REF-5.2b` 的原始设计不是本项目发明，出处是 Octop 的 UI payload offload
（`infra/agents/middleware/octop_ui_offload.py:56-85` + `docs/octop-ui-payload-offload.md:19-28`，研究文档已引原文 `[实测]`）。
它的问题定义是**「一个载荷、多类需求对立的消费者」**：

```text
一个 tool result 字符串同时服务 4 类消费者——
  LLM 上下文（越小越好）/ 历史持久化（要全量）/ Dashboard 渲染（要全量）/ 插件 UI（要全量）
⇒「模型与 UI 的需求对立，截断不可行，必须在 tool 执行后、进 state 前把数据面与控制面分离」
```

即初衷是**「模型要小、UI 要全」这一对矛盾**，解法是把全量挪到对象存储、state/上下文里只留**摘要 + `ref`**；
其推论有两条：① **不要只调大截断阈值**（只是推后问题）；② 摘要**必须带可回取的 `ref`**。
配套的第二条（`middleware/workspace_image.py`）同思路：`base64 永不落 state / 永不进历史 payload`。

**关键在于：这一对矛盾在 helloai 已经解决了**（F3+F9+F10）：

| 消费者 | helloai 的载体 | 是否全量 |
|---|---|---|
| Dashboard / 审计（人看） | `conversation_message`（实测最长 **118491 字符**，2 行 > 64000）+ 附件下载/预览端点 | ✅ 全量 |
| 历史持久化 | 同上 + `attachment` + MinIO 对象 | ✅ 全量 |
| LLM / 外部 Agent 注入 | `UpstreamAttachmentRenderer` / `AttachmentContentPolicy`（64000 字符/件、200000 总量） | ❌ 有界（**这是设计选择，不是丢失**） |

也就是说：**helloai 早已把「数据面」与「控制面」分开了**（4 类消费者各走各的载体），
只是**没有 `ref`** —— 上下文里被截断时，消费侧拿不到"剩下的在哪"。
故 `REF-5.2b` 在本项目的**真实残留只剩一条**：**有界注入 + 无 ref ⇒ 无法按需回取**。
「改形」不是换需求，而是**补上原设计的最后一环（ref + 回取）**，并把它对准唯一真正取不到全量的那类消费者
（管理端有下载/预览端点、有对话流；**外部 Agent 的 13 个工具没有任何读正文的工具**，见 F5）。

## 2. REF-5.2b：建议**改形 + 降级为按需触发**

**结论：不按原方案做**（不引入 `ToolResult.modelView` / `uiPayload` 双视图），理由四条，前三条是实测：

1. **前提是"可见性"不是"丢失"**：不是数据丢失（F3），是注入可见性受限 —— **但这不是理论问题**：
   按总预算语义（F12）实测**现网已在触发**（F14：至少 2 条、最坏 12 条子任务越限，最大一条 64 文件 / ≈20 万字符）。
   ⇒ 原先「无触发样本」的说法**作废**（那是按单件算的）。
2. **落点不存在**（F6）：所谓「改 `ToolResult`」等于**新造一个跨层契约面**（执行结果 DTO → 端口 → 渲染端），
   回归面与 5.2a 那类"常量单源化"不是一个量级。
3. **可观测「有标注、无可操作性」**（F4+F13）：被截时有 `[TRUNCATED]` 标注，但**不带 `attachmentId`** ——
   消费侧**不知道拿什么去取**，这才是"回取"缺口的完整形状。
4. **"调大阈值"不是答案**（研究文档已指出）：预算共享下，调大只是把触发点推后（且放大每轮 token 成本）。

**改形后的形态：两处配套，缺一不可（一页即可说清）**

```text
① 标注行补可操作地址：[TRUNCATED] file=<名> id=<attachmentId> shown=<n> total=<n> reason=<...>
   —— 否则下游再全也无人能用（F13）
② 取回通道：**复用既有**，不新增 MCP 工具（见下方实测）——
   GET /api/attachments/downloadById/{attachmentId}（已受附件可见性判据保护）
   工具面保持 13 个不变（getSubTaskDetail 的描述本就指向该 REST 端点）
③ 权限判据：复用 `AttachmentVisibilityPolicy`（唯一入口），视图侧另有一处需统一（见 §2.1）
```

**② 的实测依据（决定性）**：用一个临时注册的 CLI Agent（真实 API Key 打 agent 通道）对
同一批端点做了「非成员 → 加入 team」两轮请求，结果：

| 端点 | 非成员 | 加入 team 后 | 判定 |
|---|---|---|---|
| `attachments/downloadById/{id}` | **403** | **200 + 正文** | ✅ 通道已通、判据已生效 ⇒ 无需新工具 |
| `sub-tasks/getById/{id}` | **200** | 200 | ❌ **无任何校验**（任何有效 API Key 可读任意子任务详情） |
| `sub-tasks/listTimelineBySubTaskId/{id}` | 403 | **仍 403** | ❌ 旧判据把**合法团队成员**也拒了 |
| `sub-tasks/listConversationBySubTaskId/{id}` | 403 | **仍 403** | ❌ 同上 |

（临时 Agent 与成员行已删除，未留测试数据。）

### 2.1 连带修正：三处子任务视图读判据统一（用户裁定 2026-10-10）

上表后两行 + `getById` 那行暴露的是同一件事：**「谁能读子任务视图」原来有两套判据、且都有问题**。
用户裁定**统一到 task-team**（与附件侧同一条），据此已改：
`listTimelineBySubTaskId` / `listConversationBySubTaskId` / `getById` 三处一律走
`SubTaskViewGuard.assertAgentCanView` → 判据委托 `AttachmentVisibilityPolicy.canReadTaskScoped`
（= 同一方法的 `uploaderAgentId=null` 形态，**逻辑零复制**）；平台账号 / 无主体通道照旧由管理侧鉴权覆盖。
**未动**：MCP `getSubTaskDetail`（它的"仅本人已分配 / 未分配且 PENDING 可查"是**工作面**约束，不是可见性面，
两者语义不同，本批不混）。

**收益**：外部 Agent 从「只能看被截断的部分、且不知道缺了什么」变成「知道缺什么、可按需取回」；
**成本**比双视图低一个数量级，且**不动**既有载荷契约。
**触发条件**：① 用户明确要求「外部 Agent 自行回取全文」（**已由用户 2026-10-10 提出**）；
② 引用契约（§4）的最小三问已定（`ref` 形状 / 标注字段集 / 读取权限边界）—— 本场景**一页即可**，无需为 `REF-7` 把契约做大。

## 3. REF-7：维持立项，**先定引用契约**，`C1~C3` 的建议倾向

`C1~C3` 是计划要求"动手前必须先定"的三条。本评估只给**倾向**（不代替拍板）：

| # | 约束 | 建议倾向 | 依据 |
|---|---|---|---|
| C1 | 与 `REF-6.2`「审计事件闭合 schema」的张力 | **双面**：快照原文落 MinIO、时间线只放**结构化索引 + `snapshotRef`**。**但**：`REF-6.2` 尚未实现（F7）⇒ "闭合"当前无强制，须在契约里把它变成**显式字段白名单**（而不是靠约定），否则第一个自由文本字段就会进来 | F7 |
| C2 | 审批方是谁 | **复用人工介入通道**（`sub_task_manual_intervention_required` + 复核端点，F8）—— 不新建第二套审批/状态机（治理红线） | F8 |
| C3 | 落时间线的粒度 | 先做**一条汇总事件 + `snapshotRef`**；逐阶段拆解后置（拆解需要先有阶段定义，属另一件事） | 计划建议 + 成本 |

**触发条件**（计划已定，本评估不改）：对子任务**内部执行深度**的审计需求成立（返工争议 / 质量复盘 / 责任界定）。

## 4. 合并点：**一份「内容引用契约」**

两项是同一个模式的两次出现（研究文档 A1 与 `REF-7` 的 C1 都指向它）：**大对象放对象存储，结构化面只放索引 + ref**。
若各写一套，就会出现两套 ref 形状、两套去重口径、两套读取权限。**建议先把契约定成一页**（落 `design/`），
它同时解锁 5.2b 的回取与 REF-7 的快照。契约需要回答四个问题：

```text
① ref 形状：复用既有 minio://{bucket}/{objectKey}（附件已在用）还是新语法？—— 倾向复用，避免第三种寻址方式
② 去重口径：内容哈希 vs 固定哨兵 —— 上游用的是固定哨兵 "data_ref": "artifact"（研究文档勘误已记），
   内容哈希是本项目**自研增量**，必须单独论证（什么场景会重复引用同一份大对象、省下的存储是否值得引入哈希计算）
③ 读取权限：谁能读被引用的原文（外部 Agent / 评审 / 管理端）—— 两项的答案应一致，否则契约不成立
④ 闭合 schema 的落地形态：事件/载荷里**允不允许**自由文本字段；不允许时，结构化索引的字段白名单怎么定（see C1）
```

**顺序建议**：`内容引用契约（design/）` → 5.2b 改形后的只读工具（契约为其第一消费者）→ REF-7 快照（复用同一 `ref`）。

## 5. 明确不做（写进结论，避免下次重新讨论）

```text
✗ 不引入 ToolResult 的 modelView / uiPayload 双视图（落点不存在 + 收益窄 + 契约改动面大）
✗ 不为「64K 上限」调参（当前无触发样本；调大只是推后，且会放大每次注入的 token 成本）
✗ 不为 REF-7 新建第二套审批流（复用人工介入通道）
✗ 不在引用契约成文前开工 5.2b 或 REF-7
```
