# HelloAI 文档体系分类与治理规则

> **状态：GOVERNANCE / 元文档**
>
> 本文件定义 `doc/` 的**分类模型、各目录准入规则与文档生命周期**，是「文档该怎么放、怎么流转、怎么命名」的**唯一事实源**。
>
> 与 `README.md` 的分工：`README.md` 是**索引 + 权威清单 + 读取顺序**；本文件是**分类规则 + 准入判据 + 流转纪律**。两者互补，冲突时以本文件为准。
>
> **本文件是规则，不是记录。** 只写「现在该怎么做」——历史过程（何时立规、归档批次、执行进度、裁定经过、编号清偿过程）一律在 `doc/log/`（按 `LOG-YYYYMMDD-NNN` 检索）。**规则可以扩充与细化，但不得写入与规则无关的内容**；发现规则文档里出现历史叙述，按「迁 `log/` + 正文只留判据」处理。
>
> 最后更新：2026-10-23

# 0. 权威优先级（与 `README.md` 一致）

```text
代码 / 可验证事实  >  项目基线  >  目标架构  >  实现差距  >  实施计划  >  历史归档
```

任何跨文档冲突，一律以**更高优先级**者为准。历史归档**永不作**为当前状态依据。

---

# 1. 分类原则

**不按主题分类，按「文档在主线上扮演的角色 × 事实等级」分类。**

一条主线贯穿全目录：

```text
当前事实  →  目标边界  →  演进差距  →  专项设计  →  实施计划/方案  →  代码落地  →  过程记录  →  历史归档
```

四问定类（对任何一份新文档，先回答它回答哪一个问题）：

| 问题 | 归入 |
|---|---|
| 现在**是什么**、已落地什么？ | 根目录 · 项目基线 |
| **要去哪**、稳定边界？ | 根目录 · 目标架构 |
| 当前与目标**差什么**？ | 根目录 · 实现差距表 |
| 工程上**怎么写**（代码 / AI 协作）？ | 根目录 · 规范 |
| **该怎么建**（专项设计，会影响后续实现）？ | `design/` |
| **按什么顺序建**、具体**怎么改**（方案/清单/预案）？ | `plan/` |
| **做过什么、为什么**？ | `log/` |
| **验过没、查出什么**（对既成事实的检查结论）？ | `review/` |
| **别人怎么做**、值得借鉴什么？ | `research/` |
| **怎么用**（对外交付）？ | `manual/` |
| 旧的是什么、已被谁取代？ | `archive/` |

# 2. 分类总表

| 目录 | 角色 | 回答的问题 | 时效 | 收录 | 禁收 |
|---|---|---|---|---|---|
| `doc/`（根） | 核心权威 | 是什么 / 去哪 / 差什么 / 怎么写 | 随代码同步 | 基线 / 目标架构 / 差距表 / 规范 / `README` / 本治理规则 | 设计、方案、报告、记录、归档 |
| `plan/` | 计划 · 方案 | 按什么顺序建、怎么改 | 进行中有效 | 实施计划 / 改造·修复·测试方案 / 执行清单与预案 | 已成文设计、检查报告、调研、历史归档 |
| `design/` | 专项设计 | 该怎么建 | 稳定 | 专项设计（带 `Status/Scope`） | 报告、已执行方案、进度数字 |
| `log/` | 过程记录 | 做过什么、为什么 | 只增不改 | 月度记录、架构变更记录、日志格式规范 | 当前状态、待办清单 |
| `review/` | 报告 | 验过没、查出什么 | 时间点快照 | 审计 / 复核 / 排查 / 验证 / 决策分析 | **任何待执行方案或计划** |
| `research/` | 外部调研 | 别人怎么做 | 只读 | 外部项目 / 技术调研与借鉴（`Status=Analysis`） | 本项目的排期与进度 |
| `manual/` | 对外手册 | 怎么用 | 随接口 | 外部执行者职责手册、对外集成指南 | 内部架构决策 |
| `diagrams/` `images/` `helloai_avatar/` | 资产 | 图长什么样 | 随内容 | 架构流程图（svg/html/png）/ UI 截图 / AI 形象资产 | 正文文档 |
| `archive/` | 历史归档 | 旧的是什么 | 冻结只读 | `implemented/` 已实施方案 · `legacy/` 旧体系 · `log/` 归档日志 · `reference/` 只读参考 | **一律不得作当前依据** |

# 3. 各分类定义与准入规则

## 3.1 `doc/`（根目录）· 核心权威文档

**定位**：当前开发**直接依据**的事实与规范，必须与代码保持同步。

| 文档 | 事实等级 | 职责 |
|---|---|---|
| `HelloAI 项目基线文档.md` | `CURRENT / FACT` | 当前真实代码与已落地能力 |
| `HelloAI 目标架构.md` | `TARGET ARCHITECTURE` | 未来稳定架构边界 + 实现状态 |
| `HelloAI 实现差距表.md` | `CURRENT GAP` | Current → Target 的真实差距（**逐条进度的唯一事实源**；**只记当前状态、随迭代就地更新，不累加批次过程**） |
| `HelloAI_CODE_STYLE.md` | 规范 | 代码与工程规范 |
| `HelloAI_AI开发协作规约.md` | 规范 | AI Agent 开发行为规约（生命周期 / 验证 / 红线） |
| `README.md` | 元文档 | 索引 + 权威清单 + 读取顺序 |
| `文档体系分类与治理规则.md` | 元文档 | 分类规则 + 准入判据 + 流转纪律（本文件） |

**准入**：只收上表所列。**新增根文档须本文件同批登记**。

## 3.2 `plan/` · 计划与方案层

**定位**：承载**进行中 / 待执行 / 待拍板**的实施计划、方案与执行清单。这是「设计（稳定）」与「代码（已落地）」之间的**行动层**。

**收录**：

1. **实施计划**：业务主线（如 `HelloAI 重构实施计划.md`）、专项（如 `HelloAI 借鉴落地实施计划.md`，`REF-x.y`；已执行完成的专项如 `HelloAI 基础架构调整实施计划.md`（`BASE-xxx`）已迁 `archive/implemented/`）。
2. **方案**：改造方案 / 缺陷修复方案 / 回归测试方案 / 兜底与倒计时方案 / 清偿计划。
3. **执行清单与预案**：上线前检查清单、回滚预案、复测执行清单。

**禁收**：

- 已成文的稳定设计（设计价值长期有效）→ `design/`；
- 对既成事实的检查 / 审计 / 复核结论 → `review/`；
- 外部项目调研 → `research/`；
- **已执行完成**的方案 / 清单 → `archive/implemented/`。

**文档头要求**：每份计划建议声明 `Status`（`Active | Done | Superseded`）+ 依据 + 日期，并在执行完成后**主动离线归档**（见 §4）。

**在册清单以 `doc/README.md` §2.3 为唯一事实源**，本文件不复制表格以免腐烂。

**记录性段落**：`plan/` 文档**可以**自带「决策 / 缺陷留痕」段落——它们是**行动计划的决策依据**，与该计划同源，拆到 `log/` 反而失去上下文。**处置：维持原地**（迁移成本 > 收益）。**纪律：冻结新增**——此后新产生的过程记录 / 缺陷清偿 / 决策留痕一律进 `doc/log/`。**判据**：「计划自带的、为解释该计划取舍所必需的」可留；「纯粹的历史过程叙述」应进 `log/`。文档头若含**版本变更史**，同样适用本条。

**任务条目的逐项状态**：`plan/` 内的任务条目必须让人与 AI agent **直接扫出「做完没有、还差什么」**，与《差距表》§1 矩阵同一套九态中文口径（`待开始 / 设计中 / 实现中 / 验证中 / 已完成 / 部分完成 / 阻塞 / 暂缓 / 明确不做`）。

- **表格式条目**（条目在一行表格里）：末两列为「状态」+「剩余动作」。
- **章节式条目**（`### ATT-1` 这类）：标题下紧跟一行 `> **状态**：已完成 ｜ **剩余动作**：—`。
- **判据**：状态值必须 ∈ 九态；状态 = `已完成` ⇒ 剩余动作必须是 `—`；状态 ≠ `已完成` ⇒ 剩余动作不得为空或 `—`。
- **与文档头 `Status` 的分工**：头写**整体**生命周期（`Active | Done | Superseded`），列/行写**逐项**完成度；两处不得都写完成度（同一事实双写必分叉）。
- **机械守卫**：`scripts/shell/verify-plan-status.sh`（**增量式**——白名单在脚本内维护，改造一份纳入一份，未改造的存量计划不报红）。
- **编排视图不承载状态**：`HelloAI 计划编排与排期总览.md` 只给「编号体系 → 落点」指针，状态仍以各计划文件为唯一事实源。

**文档结构骨架**：各计划**内容**（借什么、改哪里）本就不同，但**骨架必须一致**——否则读计划的人每次都要重新找「现状在哪、任务表在哪、还剩什么」。

**最小必需五节**（缺一即不合格）：

| 节 | 标题（固定写法） | 必须回答什么 |
|---|---|---|
| 0 | `定位与边界（★先读）` | 四段固定结构：**问题来源 / 本计划做什么 / 本计划不做什么 / 诚实边界**（细则见下） |
| 1 | `编号建号声明（防撞号）` | 号段、`x` 的取值域、登记位置（差距表 §0）、编号 ↔ 语义的映射表 |
| 2 | `现状（勘察结论，[实测]）` | 起点事实，**逐条带 `[实测]` 证据**（路径 / 行为 / 数据） |
| 3 | `任务表（xx-1 ~ xx-N）` | 逐项任务 + 状态 + 剩余动作（见上条「任务条目的逐项状态」） |
| 末 | `引用材料` | 上游调研、差距表锚点（`G-0xx`）、ADR、相关计划 |

**按需增补**（有则加、无则省略，不占编号）：`关键设计决策`（选型与取舍）、`依赖与实施次序`、`验收`（也可并入任务表）、`风险与边界`、`前置待决`。

**唯一例外：执行清单类**（如 `HelloAI 上线核对清单.md`）——它不是「实施计划」而是「逐条核对的清单」，豁免 §1 编号声明与 §2 现状两节，但**必须保留 §0 定位与边界**与**核对项的逐项状态**。

**§0 的四段结构**：§0 是这份计划唯一的「为什么做 + 做到哪为止」入口，必须回答下面四问，缺任一段视为不合格。

| 段 | 写什么 | 判据 |
|---|---|---|
| **① 问题来源** | 这份计划是被什么驱动的。**来源可多源**：用户反馈 / GitHub issue / `review/` 检查报告 / `design/` 设计文档 / 差距表 `G-0xx` / `log/` 观测数据 | 必须能指到具体对象（链接、编号、日期），不得写「根据需求」这类空来源 |
| **② 本计划做什么** | 一段话目标 + 3~5 条具体产出 | 产出要能被 §3 任务表逐项对应 |
| **③ 本计划不做什么**（边界，防越界） | **逐条**：不做什么 → 为什么 → 依据（裁定编号 / 差距表 / 协作规约条款） | 每条必须带依据；无依据的「不做」是懒，不是边界 |
| **④ 诚实边界** | 落地后**哪些仍不成立**、须在差距表登记什么事实 | 必须点名「做了什么 ≠ 能力已可用」的那一层（如「Provider 已实现但执行链未消费」） |

**为什么 ③④ 是必填**：项目里反复出现的两类事故正是这两段缺失导致的——**越界扩张**（把「接入契约」做成「宣称能力完成」）与**夸大完成度**（写了 Provider 就说沙箱可用了）。③ 用「不做什么 + 依据」把范围钉死，④ 用「落地后仍不成立什么」把话说全。

**三条硬约束**：

1. **禁止跳号**——节号必须连续。旧稿出现过 `§1 → §4 → §5` 的跳号，读者会以为中间丢了内容。
2. **`[实测]` 是承诺不是装饰**——§2 每条现状必须有证据来源；拿不到证据的写「待核」，不得当作事实陈述。
3. **拆分/迁移场景可沿用历史节号**，但必须在文档头写明理由——`log/` 与 ADR 里的历史引用按旧号书写，重编会让它们失准。**新建计划一律用标准骨架，不适用本例外。**


## 3.3 `design/` · 专项设计

**定位**：只保留仍具独立技术价值、且会影响后续实现的**设计**。

**准入（与《目标架构》§0 维护规则 3 同源）**：

1. **只收设计文档**。过程性产物一律出列：实测 / 排查 / 复核报告 → `review/`；**已执行的改造 / 修复 / 预研方案 → `archive/implemented/`**；**未执行的方案 / 计划 → `plan/`**。
2. 每份设计必须在 H1 之后声明 **`Status` / `Scope` 头**：`Status` 取 `Implemented | Partial | Planned | Non-goal`；`Scope` 写清边界与**不含项**，并给出差距表锚点（`G-0xx`）。
3. 进度百分比与逐条差距**只以 `HelloAI 实现差距表.md` 为唯一事实源**，`design/` 不复述数字。

`design/adr/` 存**架构决策记录（ADR）**，编号 `ADR-xxx`。

## 3.4 `log/` · 过程记录

**定位**：回答「做过什么、为什么」。

**收录**：月度记录 `YYYY-MM.md`、`HelloAI 架构变更记录.md`（架构决策 `ARCH-YYYYMMDD-NNN`）、`README.md`（**日志体系说明 / 记录格式规范**，非记录本身；原 `HelloAI 迭代执行记录.md`，2026-10-09 更名）。

> **差距表订正的唯一载体**：原独立文件 `log/HelloAI 差距表订正留痕.md`（承载 `C-1`~`C-42` 与 `§0.2`~`§0.7`）**已取消**——判据是「**一次订正 = 一条 Log**」：订正记录与产出它的迭代记录**同源**，分两份存储必然漂移。全部 `C-NN` 已并入对应月份的 `LOG-YYYYMMDD-NNN` 条目（`C-1`~`C-15` → `doc/archive/log/2026-09.md`；`C-16`~`C-42` → `doc/log/2026-10.md`）。**`C-NN` 编号自此退役**，一律改用 `LOG-YYYYMMDD-NNN` 寻址。

**规则**：月度记录**只增不改**；**一天一条**（2026-10-27 用户规范）——同一天的所有工作记在**一个** `## LOG-YYYYMMDD <当天汇总>` 之下，用 `### LOG-YYYYMMDD-NNN 标题` 逐项展开，**不再为同一天的每件小事新开一个 `## LOG-...`**。`NNN` 仍是全仓引用锚点，**只续编、不改名**（改名会断掉 `grep -rn "LOG-YYYYMMDD-NNN" doc/` 的全部引用）。`log/**` 内的历史引用**不作修正**（当时事实的现场记录）；**例外**——月度记录文件头「格式规范见 …」属**导航指针**而非历史事实，随规范文档更名同步更新（见 §7）。

**8 段式唯一格式（2026-10-26 定则，取代「编号小节式」「自由 bullet」等历史写法）**：

1. **8 段为唯一合法段结构**，顺序固定：`背景 / 问题 / 决策 / 实现 / 验证 / 结果 / 影响 / 关联`。每段以 `#### 段名` 四级标题开头（条目本身已是 `### LOG-...`，故段名下沉一级）。**不再允许**「### 一、背景 / 二、改动 / 五、验证」这类编号小节写法，也不允许无段标题的自由 bullet 正文。
2. **段名对照表**（历史条目段名 → 标准段名，用于改写时归一）：

| 历史段名 | 标准段 | 说明 |
|---|---|---|
| 一、背景 / 起因 / 现象 | 背景 | 为什么做 / 触发点 |
| 问题 | 问题 | 原有缺陷 |
| 二、改动 / 改法 / 修复 | 实现 | 改了哪些模块 |
| 三、修复 / 过程 | 实现 | 实施过程 |
| 四、验证 / 五、验证 / 验证（全部实测） | 验证 | 怎么验 |
| 结果 / 结果与影响 / 结论（三句话） | 结果 | 最终结果 |
| 影响 / 边界与后续 / 未完成 | 影响 | 影响范围 / 待办 |
| 关联 / 判据沉淀 / 判据 / 文档回填 | 关联 | 前序 / 依据 / Commit / 判据 |
| 五、判据沉淀 / 六、判据 / 七、判据 | 关联（判据子项） | 判据沉淀属「关联」的判据部分 |

3. **改写边界**：存量条目（含编号小节式）改写时**只重组段落归属、不增删事实**；内容确实缺失的段（如早期条目无「决策」）标注「（不可考）」而非编造。**「只增不改」指不改历史事实与编号，不禁止格式归一**——格式归一属于文档治理，不属于篡改历史。
4. **新条目硬约束**：新增 LOG 必须 8 段齐全；确无某段内容的（如纯记录型条目无「决策」）可省略该段，但**不得**用自定义段名或自由 bullet。

**承载口径**：

- 此后架构决策的**即时承载**转为**月度 Log（`### 决策` 段）+ 差距表**（长期锚点另有 `design/` ADR）；本文件**按开发周期迭代定期汇总回填**（`ARCH-YYYYMMDD-NNN`），**不要求逐决策即时更新**。
- **不得删除**：它是 `ARCH-` 编号的**唯一事实源**，被 `doc/archive/log/2026-09.md` 的 4 处 `### 关联 → - Design：` 引用（:5043 / :5086 / :5126 / :5356）；删除会让这些结构化锚点指向不存在的对象（不同于 archive 内「路径过期」的历史引用）。

## 3.5 `review/` · 报告

**定位**：对**既成事实**的检查结论，回答「验过没、查出什么」。**属于时间点快照，不承诺排期、不含待执行动作。**

**收录（准入白名单）**：审计报告、代码级复核、排查报告、独立验证报告、优先级 / 决策分析、检查清单的**结论归档**。

**禁收**：任何**待执行**的计划 / 方案 / 清单 → `plan/`；任何设计 → `design/`。

**归档判据**：`review/` 默认**长期留存**（时间点快照本身即历史事实，不因「旧」而归档）。**仅在同时满足**下列两条时迁 `archive/reference/` 并标 `Superseded`：

1. **其核心结论已被交付消化** —— 报告提出的判断 / 建议已全部落地、或被后续能力推翻，正文不再对任何决策有约束力；
2. **不再被任何活文档引用** —— 以文件名（去 `.md`）为 grep 键在 `doc/` 内实测，除自身外命中数为 0（被 `archive/**`、`log/**` 引用不计）。

> 判据 2 的作用是防误伤：仍被 `plan/` / `doc/` 根引用的报告即便结论已旧，也仍是「编号 → 依据」链的一环，**留原地**并按需在头部补订正指针。

## 3.6 `research/` · 外部调研

**定位**：收集对外部项目 / 方案 / 技术的调研与借鉴分析，回答「别人怎么做的、哪些值得借鉴、哪些明确不抄」。

**准入**：只收调研 / 借鉴 / 预研；`Status` 固定 **`Analysis`**；引用外部源码必须标明勘察口径（`[实测]` 附 `路径:行号` / `[推断]` 单列）；**不在 `research/` 里写排期与进度**。可执行结论若进入实施，另立 `plan/` 或 `design/` 文档。

## 3.7 `manual/` · 对外手册

**定位**：对外交付的使用手册。

- `manual/executor-duty/`：外部执行者（Agent）职责手册（`00-manual-contract` ~ `06-consistency-audit` + `manual-assembled.md` 拼装产物）。
- `manual/helloai-integration-guide/`：第三方接入指南 + 端到端演练记录。
- `manual/platform-backup-restore/`：平台备份与停机恢复流程运维手册（`runbook.md`；能力边界 / 备份判据 / 恢复三路径与三门 / 停机清单）。

> 代码侧 `helloai-core/src/main/resources/onboarding/{role}/guide.md` 是**外部 Agent 接入手册**（交付 ZIP 内名 `SKILL.md`），与能力包 `skills/plugins/*.md` 是两件事，**禁止混用 SKILL 一词**，且不属于本文档体系。

## 3.8 资产类 `diagrams/` `images/` `helloai_avatar/`

- `diagrams/`：架构 / 流程可视化。约定风格：**`*.svg` 为交付态**；早期同时保留 `*.html` 源 + `*.png` 导出三件套。
- `images/`：UI 截图与说明性配图。
- `helloai_avatar/`：AI 形象资产（生成产物 + 提示词）。

## 3.9 `archive/` · 历史归档

**定位**：只用于追溯背景、已完成设计与被替代方案。**冻结只读，禁止作为当前 Roadmap 或架构入口。**

| 子目录 | 存什么 |
|---|---|
| `archive/implemented/` | 已执行完成的改造 / 修复 / 预研方案、Phase 执行方案 |
| `archive/legacy/` | V2 文档体系重组前的旧事实源快照与旧体系文档（含 `V1_README.md`） |
| `archive/log/` | 已归档的月度 Log（如 `2026-09.md`） |
| `archive/reference/` | 只读参考资料（架构设计参考 / 长期思路 / 调度解耦分析 / 历史进度 / **已消费的审计与定位报告**） |

**四个子目录各自带目录级 `README.md`**，写明本目录存放类型、准入规则与只读纪律。

# 4. 文档生命周期与流转

```text
① 新想法 / 调研       → research/（Analysis）
② 形成稳定设计         → design/（Status: Planned → Partial → Implemented）
③ 成立实施计划 / 方案  → plan/（Status: Active）
④ 执行中              → plan/ 就地更新（或按里程碑重打分轮）
⑤ 执行完成            → archive/implemented/（Status: Done）
⑥ 被取代 / 废弃       → archive/（标 Superseded）
```

**关键纪律**：

- **方案一旦执行完成，必须离出 `plan/` 进 `archive/implemented/`**，防止 `plan/` 无限膨胀、并让「进行中」保持纯净。
- 现象（能力变化）→ **回归根目录事实源**（基线 / 差距表状态变更），`plan/` 与 `design/` 均不承载「当前事实」。
- 状态变更须同步「判定依据」（日期 + 代码 / DB 证据出处）。

# 5. 文档头规范

除 `log/**` 外，正式文档建议在 H1 之后声明头部：

```markdown
> **状态：<STATE>**
> 最后更新：YYYY-MM-DD
```

`<STATE>` 取值按目录：

| 目录 | 允许的 State |
|---|---|
| 根 · 基线 | `CURRENT / FACT` |
| 根 · 目标架构 | `TARGET ARCHITECTURE` |
| 根 · 差距表 | `CURRENT GAP` |
| `plan/` | `Active` / `Done` / `Superseded` |
| `design/` | `Implemented` / `Partial` / `Planned` / `Non-goal` |
| `research/` | `Analysis` |
| `archive/**` | `HISTORICAL` / `SUPERSEDED` |

# 6. 命名规范

1. 根目录与 `plan/` / `design/` 的主文档用 **`HelloAI …`** 前缀（如 `HelloAI 实现差距表.md`）；报告类带**括号日期或主题**（如 `…审计报告（2026-10-02）.md`）。
   - **例外**：`design/` 下**概念契约类**文档**维持无前缀**（现存 4 份：`Agent_Event_Stream.md` / `Agent_Runtime.md` / `Sandbox_Provider.md` / `Skill_Capability.md`）——其标题即代码契约名（`AgentEventStream` / `AgentRuntime` / `SandboxProvider` / `SkillPackage`），加 `HelloAI` 前缀会破坏「文档 ↔ 代码契约」的一一对应。**判据**：文件名/标题与**代码契约名**一致者归此类；其余 `design/` 设计文档仍用 `HelloAI …` 前缀（如 `HelloAI Task-Team 与附件可见性设计.md`、`HelloAI 专项设计：…`）。
2. 元文档（`README.md` / `文档体系分类与治理规则.md`）不加前缀。
3. 不要在文件名里堆叠版本号（`V1` / `V23` 等）；版本信息放文档头。
4. 目录统一用**无前缀小写**（`design`、`plan`、`review`），不再新增下划线前缀目录（历史遗留 `helloai_avatar` 维持）。
5. **分期标签（`Phase` / `阶段` / `Step`）是历史过程口径，已冻结**：活文档与生产代码**不得再新增**；分期口径只进 `doc/log/`（做过什么）与《HelloAI 实现差距表》§0「历史分期编号注册表」（曾有哪些）。**理由**：这些标签曾以裸名跨 6 套体系复用，造成同号不同义（详见注册表）。
   - **口径**：「阶段 + 序号」寻址已由 `PC-x` 号段取代（见《差距表》§0 编号口径表）；该寻址方式不再是合法形式，新增文档一律用号段。

# 7. 引用完整性规则

文档新增 / 移动后，**引用必须同批修正**。

1. **必改**：活文档（根目录、`plan/`、`design/`、`review/`、`research/`、`manual/`）中指向旧路径的引用。
2. **不改（有意保留）**：`archive/**` 与 `log/**` 内指向旧路径的引用——它们是**当时事实的现场记录**，改写等于篡改历史。
   - **例外①（导航指针）**：**当月**记录文件头的「格式规范指引」（如 `doc/log/2026-10.md` 首行）是**导航指针**，随规范文档更名同步更新；`archive/log/` 内**已归档月份**的同类指针保持原样。
   - **例外②（目标被删除** ≠ **路径变更）**：被引用对象**整体退役/删除**时，其引用不再是「路径过期」，而是**指向不存在的对象** ⇒ **活文档与当月 Log 内的引用必须改写**，`archive/**` 仍保留原样。**判据**：路径变更只让读者多点一次跳转；对象删除会让读者**找不到任何东西**。
     - **判据示例**：一个编号体系退役后，其旧引用从「路径过期」变成「指向不存在的对象」——活文档里的引用必须改写成新载体（如 `LOG-YYYYMMDD-NNN`），`archive/**` 内保留原样；改写前先 `grep -o` 全仓数清锚点，再逐条确认「内容是否另有归属」。
     - **操作纪律**：退役一个编号体系前，**先数清锚点**（`grep -o` 全仓计数），再逐条比对**内容是否另有归属**（本例：`C-1`~`C-38` 的实质工作已在 `2026-09.md` / `2026-10.md` 有 Log 条目；`C-39③`/`C-40`/`C-41`/`C-42` **无** —— 必须先补 Log 才能删）。**「内容能在别处找到」不能凭直觉，必须逐条实测**（特征词命中数）。
   - **例外③（目录级 `README.md`）**：子目录 `README.md` 是**导航 / 索引**（各子目录应带目录级 README，写明存放类型与准入规则——要求见本规则 §3.9 与 `README.md` §2 / §3 各目录成节），**非历史记录** ⇒ 其标题与自述目录名**随目录更名同步更新**，不受本条「`archive/**` 不改」约束。
3. **不改**：Flyway `V*.sql` 注释里的已归档方案路径——**迁移 checksum 校验**，改注释会导致 `flyway validate` 失败。
4. 裸文件名引用（同目录唯一、按名可解析）保留，以维持可读性。

**自检**：搜索旧路径字符串是否仍有活文档命中。

```text
README.md
→ 文档体系分类与治理规则.md（本文件）

→ 代码
```

冲突时以当前文档和代码为准。
