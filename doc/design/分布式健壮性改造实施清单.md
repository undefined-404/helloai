## 零、为什么这份清单是"分布式扩容"的地基

水平扩容（k3s 多副本）后，三类"单实例时不会暴露"的问题会立刻显形，本清单逐项对应：

| 扩容后显形的问题 | 本清单的对应改造 |
|---|---|
| 同一锁被多实例并发获取，手写 setIfAbsent + 无条件 delete 的误删窗口被放大成必然 | Step 1/2：RLock 持锁校验 + ShedLock 注解，误删在结构上不可能 |
| 多实例消费者并行拉取，prefetch=250 导致慢实例囤积、快实例饿死，削峰失效 | Step 3.1：prefetch 收紧，消息按消费能力均匀分发 |
| 多实例生产者同时放量，无界队列把 RabbitMQ 节点内存/磁盘打满，集群级故障 | Step 3.2：x-max-length + reject-publish，broker 主动快速失败护住节点 |
| 某副本 LLM 批量超时，消息涌入死信后无人知晓，任务静默死亡 | Step 4：DLX 告警消费者 + 死信台账，死信可见、可追溯、可重放 |

即：可靠性（消息不丢）你们 Phase 2F 起已建全，本清单补的是**容量治理（系统不被压垮）+ 死信可见性（失败可追溯）**——后者才是分布式部署的准入门槛。

### 1.2 MQ（可靠性已建全，容量治理是缺口）

| 维度 | 现状 | 判定 |
|------|------|------|
| 持久化 + DLX | 6 队列全 durable 挂死信交换机 | ✓ |
| 发布可靠性 | publisher-confirm-type=correlated + returns + mandatory | ✓ |
| 消费可靠性 | MANUAL ACK + 失败 basicNack(requeue=false) 走 DLX + 幂等（AbstractIdempotentConsumer 两级） | ✓ |
| 反序列化安全 | Jackson2JsonMessageConverter 封死 Java 毒消息（§6.119） | ✓ |
| **队列阈值** | 无 x-max-length / x-max-length-bytes / x-message-ttl，队列可无界堆积 | ✗ 缺口 |
| **快速失败** | 无 x-overflow=reject-publish，队列满 broker 不拒绝发布 | ✗ 缺口 |
| **削峰阀门** | 无 prefetch（默认 250），LLM 秒级消费下慢消费者囤积、快消费者饿死 | ✗ 缺口 |
| **死信出口** | 失败进 DLX 后无告警无台账，任务静默死亡、无法追溯重放 | ✗ 缺口 |

**v1.1 勘误**：① NACK 回调日志已存在（RabbitMQConfig L121-125 `log.error("RabbitMQ publish NACK: ...")`），Step 3.2 仅需在该行补"可能队列已满"提示文案，非新增；② prefetch 为 `spring.rabbitmq.listener.simple` 全局配置，收紧后对全部 3 个 @RabbitListener 消费者（MqReviewCommandConsumer / MqExecutionCommandConsumer / NotificationConsumer）统一生效，notification 量小无碍，后续如需分级再按队列拆分（见观察项）。

设计要点：**三个改造方向各管一段的理由**——
- 锁拆两类：11 处 job 锁是"定时任务只在一个实例跑"，ShedLock 注解一行消灭 `tryLock/unlock/token/Lua`，测试里也不用 mock 锁；review 锁是**业务级互斥**（动态 key、防 L1/L2/L3 三路并发双审、TTL 与双审 deadline 有配合关系），需要 RLock 精细控制。只引 Redisson 则 job 锁仍留 mock 仪式，只引 ShedLock 则覆盖不了动态 key，各引一个依赖、各管一段改动最小；
- MQ 只补容量治理不动可靠性：阈值/溢出/阀门/告警全是配置与声明层的增量，不触碰现有 publisher/consumer 业务逻辑，风险可控。

## 二、选型条款草案（CODE_STYLE V1.16 新增 §3.y + §3.z，迭代记录 §6.150）

```
### 3.y 分布式锁选型（V1.16 新增）

【必须】分布式锁只允许两种实现，禁止新增手写 setIfAbsent 锁：
1. 定时任务单例锁（@Scheduled 防多实例并发）→ ShedLock @SchedulerLock，
   name 用任务名，lockAtMostFor = 原 TTL 口径，lockAtLeastFor 不设；
2. 业务互斥锁（动态 key / 请求级并发互斥）→ Redisson RLock：
   - 一律 tryLock(0, leaseTime, unit)，显式传 leaseTime；
   - 【禁止】裸 lock() / tryLock() 不带 leaseTime——看门狗自动续期会
     改变"崩溃残留自动过期"的既有语义（review 锁 TTL=120s 与双审
     deadline 90s 的配合依赖该语义，§6.142）；
   - 释放仅 unlock()，持锁校验由 RLock 保证（结构上不可能误删他人锁）；
3. RedisTemplate 仅保留缓存/会话/队列用途，不再承担锁职责；
4. 豁免清单（多实例并行无害，无需 ShedLock，新增 @Scheduled 先对照）：
   scanReviewOrphans（review:lock 业务锁兜底）、ExecutionCommandPoller
   （DB 条件更新幂等）、DoorbellKeepaliveTask / SessionAuthCleaner /
   McpSessionAuthCleanupTask（本地内存，实例私有）。
   §12 分布式锁章节（旧 RedisLockUtil 口径，文档失真）并入本条，不再单独成型。

### 3.z MQ 容量治理（V1.16 新增）

【必须】消息队列实行容量治理，防止"消息不丢但系统被压垮"：
1. 每个业务队列声明必须带容量阈值与溢出策略：
   x-max-length（核心队列 50000 / 非核心 1000~10000 起步，按实测深度校准）、
   x-overflow=reject-publish（队列满时 broker 拒绝发布，显式失败而非静默堆积；
   前置：RabbitMQ ≥ 3.10，低于该版本只声明 x-max-length 并记录例外）；
2. 监听端必须配 prefetch，禁止默认值 250（慢消费者囤积、快消费者饿死）；
   LLM 等秒级消费 prefetch ≤ 10；
3. 死信队列必须有告警出口（DlxAlertConsumer），死信消息必须落台账
   （mq_dead_letter_archive）后再 ACK，禁止死信静默堆积或无法追溯；
4. 消息体必须瘦身（载荷 ≤ 10KB），超阈值先落 MinIO/DB 再传引用；
5. 生产端 ConfirmCallback 的 NACK 日志必须带"可能是队列满"提示，便于
   快速分辨 reject-publish 触发的快速失败。
```

## 四、Step 1：review 核验锁迁 Redisson（收益最大，先独立小闭环）

### 4.1 SubTaskReviewServiceImpl 改造点（§6.150）

```java
// 构造器：StringRedisTemplate redis  →  RedissonClient redissonClient
// （全文 redis 仅锁两处用途——L215 setIfAbsent / L224 delete——依赖可整体摘除，v1.1 行号勘误）

// reviewSubTask 内：
RLock lock = redissonClient.getLock(REVIEW_LOCK_PREFIX + subTaskId);
boolean locked;
try {
    locked = lock.tryLock(0, REVIEW_LOCK_TTL_SECONDS, TimeUnit.SECONDS);  // leaseTime=120 显式传入，禁看门狗
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    log.warn("核验锁获取被中断: subTaskId={}", subTaskId);
    return;
}
if (!locked) {
    log.debug("自动核验跳过：已有核验进行中（防双审）, subTaskId={}", subTaskId);
    return;
}
try {
    doReview(subTaskId, executorAgentId);
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

要点：
- `tryLock(0, ...)` 保持"抢不到立即跳过"的既有语义，不引入等待；
- TTL 120s、key 前缀均不变，与双审 deadline（90s，§6.142 P2 修正后）的包含关系原样保持；
- `isHeldByCurrentThread()` 防御：持锁期间超时丢锁时 unlock 抛 IllegalMonitorStateException，加判断后 finally 不炸——这正是无条件 delete 隐患的 Redisson 正解；
- 类 Javadoc §6.82 注释更新：锁实现自 setIfAbsent 迁 RLock，语义不变；
- **v1.1 额外前置：core/pom.xml 声明 redisson 依赖（编译期必需，见第三节）**。

```
  → AssignedSubTaskTimeout → SubTaskPendingOrphan → ReviewerRecheck
```

每提交一次：该任务单测过 + `mvn -pl helloai-job compile` 过，即闭环。不追求单日迁完。

## 六、Step 3：MQ 容量治理（阈值 + 快速失败 + 削峰阀门）

> 现状盘点（commit `87ef33e`）：可靠性已建全——6 队列全 durable 挂 DLX、publisher confirms/returns + mandatory、消费端 MANUAL ACK + 幂等（AbstractIdempotentConsumer 两级）+ 失败 `basicNack(requeue=false)` 走 DLX、`Jackson2JsonMessageConverter` 封死 Java 反序列化毒消息（§6.119）。**缺口集中在容量治理**：队列无 `x-max-length`/`x-message-ttl`、yml 无 `prefetch`（spring-amqp 默认 250）、生产端无队列深度探测、DLX 无告警出口。

### 3.1 prefetch 收紧（削峰阀门，一行配置，最高性价比）

`spring.rabbitmq.listener.simple.prefetch` 未配置 = 默认 250。你们 `MqReviewCommandConsumer`/`MqExecutionCommandConsumer` 是 MANUAL ACK 且消费体内调 LLM（秒级~分钟级），250 的 prefetch 会让单消费者一次性把 250 条拉成 unacked 囤着，慢消费者积压、快消费者闲置，"匀速削峰"打折。k3s 多副本后此问题按副本数放大。

```yaml
# helloai-start/src/main/resources/application.yml，spring.rabbitmq.listener.simple 下追加：
      prefetch: 10        # LLM 消费场景起步值；轻量消费队列后续可按实测单独上调
```

说明：prefetch 是"每个消费者最多同时持有多少条未 ACK 消息"，调小后消息在 broker 侧排队、按各副本实际消费速率被拉走——这正是削峰想要的"洪峰在队列里摊平、消费匀速"。**v1.1 提示：该配置全局生效（3 个消费者统一收紧），NotificationConsumer 量小无碍；若要按队列分级，见观察项。**

### 3.2 队列容量阈值 + reject-publish（broker 主动快速失败）

`RabbitMQConfig` 6 个 `QueueBuilder` 各补两个参数。核心思想：队列不再无界，满了 broker 回 basic.nack 拒绝发布——显式失败（有 NACK 日志、可追溯），远好于静默堆积拖垮节点。**v1.1 前置核查：`x-overflow=reject-publish` 是 RabbitMQ 3.10+ 才支持的参数，实施前必须探测 dev/prod broker 版本（`rabbitmq-diagnostics status`），不满足则只声明 `x-max-length` 并在 CODE_STYLE §3.z 记录例外。**

```java
// 以 executorQueue 为例，其余 5 个队列同法（DLX_QUEUE 见下注意点）：
@Bean
public Queue executorQueue() {
    return QueueBuilder.durable(EXECUTOR_QUEUE)
            .withArgument("x-dead-letter-exchange", DLX_EXCHANGE)
            .withArgument("x-dead-letter-routing-key", DLX_QUEUE)
            .withArgument("x-max-length", 50000)          // 容量阈值（起步值，按实测深度校准）
            .withArgument("x-overflow", "reject-publish") // 满了拒绝发布 → broker 主动快速失败
            .build();
}
```

分队列起步阈值（待压测/实测校准，勿拍脑袋定死）：

| 队列 | x-max-length 起步 | x-overflow | 理由 |
|------|------------------|------------|------|
| execution-command / executor / reviewer / planner（核心调度链） | 50000 | reject-publish | 核心链路，宁可宽，避免误杀正常业务洪峰 |
| notification（通知，非核心） | 1000 | reject-publish + 可加 x-message-ttl | 通知可降级，收紧阈值 + 消息过期防无效堆积 |
| dlx（死信） | 不设 max-length | —— | 死信是最后兜底，**不要**再加 overflow 拒绝，否则死信无处可去；靠 Step 4 台账与告警控制量 |

两个必须心里有数的行为：
1. **reject-publish 触发后的表现**：broker 对 durable 消息回 basic.nack → 走你们已有的 `setConfirmCallback` NACK 分支打 error 日志（RabbitMQConfig L121-125 已存在，v1.1 仅补提示文案）：
   ```java
   log.error("RabbitMQ publish NACK（可能队列已满触发 reject-publish 快速失败）: correlationData={}, cause={}",
             correlationData, cause);
   ```
2. **x-max-length 是队列级、对存量消息生效**：上线后先用 RabbitMQ Management UI 看各队列 ready/unacked 曲线，再校准阈值——核心队列放宽、非核心收紧。

### 3.3 生产端限流（缓议，本轮不动）

Outbox 中继（OutboxRelayTask）本身就是天然削峰——消息先落 DB、relay 按 `fixedRateString=1000ms` 匀速泵出。直连 `DomainEventPublisher.publish()` 的场景若将来出现洪峰，再考虑在该方法内加 Guava RateLimiter 或发布前探测队列深度。**本轮不做**，避免过度设计；列入观察项。

## 七、Step 4：DLX 死信告警 + 死信台账（防任务静默死亡，v1.1 升级版）

现状：消费失败 `basicNack(requeue=false)` 进 DLX 后**没有任何出口**——死信静静躺在 `helloai.dlx.queue`，任务实际已失败但无任何感知。多副本场景下这是任务丢失的主要盲区。

**v1.1 关键设计：死信消息在自动 ACK 后即从队列消失，"按原 routingKey 重放"必须另有数据源——新增死信台账表，告警消费者先落台账再 ACK。重放工具（观察项）以台账为源。另注意 dlxQueue 未挂 DLX，消费异常 basicNack(requeue=false) 即丢弃，因此不能依赖"打回队列"保留消息。**

### 7.1 死信台账表（Flyway V60）

```sql
-- V60__mq_dead_letter_archive.sql
CREATE TABLE mq_dead_letter_archive (
    id                    BIGSERIAL PRIMARY KEY,
    original_exchange     VARCHAR(255),
    original_routing_key  VARCHAR(255),
    first_death_exchange  VARCHAR(255),
    first_death_queue     VARCHAR(255),
    first_death_reason    VARCHAR(255),
    headers               JSONB,
    body                  TEXT,
    created_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    replayed_at           TIMESTAMPTZ          -- 重放预留：重放工具回填，本轮不实现
);
CREATE INDEX idx_mq_dead_letter_archive_created_at ON mq_dead_letter_archive (created_at);
```

（列名与 RabbitMQ 死信 header `x-first-death-exchange/queue/reason` 一一对应；body 快照截断至 64KB 防台账膨胀——死信告警场景以 payload ≤10KB 为规范前提，超长截断即可。）

### 7.2 告警消费者（新建 DlxAlertConsumer，helloai-core，独立小类，不进现有消费链路）

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class DlxAlertConsumer {

    private final JdbcTemplate jdbcTemplate;

    /** 死信告警：先落台账再 ACK（消息可从 dlx.queue 消失，台账为唯一可追溯数据源），并保留原始路由信息便于重放。 */
    @RabbitListener(queues = RabbitMQConfig.DLX_QUEUE, ackMode = "MANUAL")
    public void onDeadLetter(Message message, Channel channel,
                             @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        try {
            MessageProperties props = message.getMessageProperties();
            String body = new String(message.getBody(), StandardCharsets.UTF_8);
            // 1) 先落台账（失败仅记 error，不阻断告警；极小窗口容忍丢台账）
            try {
                jdbcTemplate.update("""
                        INSERT INTO mq_dead_letter_archive
                        (original_exchange, original_routing_key, first_death_exchange,
                         first_death_queue, first_death_reason, headers, body)
                        VALUES (?, ?, ?, ?, ?, ?::jsonb, ?)""",
                        props.getReceivedExchange(), props.getReceivedRoutingKey(),
                        props.getHeader("x-first-death-exchange"),
                        props.getHeader("x-first-death-queue"),
                        props.getHeader("x-first-death-reason"),
                        serializeHeaders(props), truncate(body, 64 * 1024));
            } catch (Exception e) {
                log.error("死信台账写入失败（仅记录，不阻断告警）", e);
            }
            // 2) 告警
            log.error("【死信告警】消息进入 DLX，需人工介入或重放: originalExchange={}, originalRoutingKey={}, body={}",
                    props.getReceivedExchange(), props.getReceivedRoutingKey(),
                    body.length() > 500 ? body.substring(0, 500) + "...(截断)" : body);
            // 3) 后 ACK（防告警消费者自身异常把死信反复打回造成循环）
            channel.basicAck(tag, false);
        } catch (Exception e) {
            log.error("死信告警消费异常", e);
            channel.basicNack(tag, false, false);  // dlxQueue 未挂 DLX：此路径消息被丢弃，台账已在写库阶段兜底
        }
    }
}
```

要点：
- 消费顺序固定为 **台账 → 告警日志 → ACK**（对齐 §11.4"禁止先 ACK 再持久化"）；
- 台账写入失败降级：记 error 不中断（丢台账窗口极小，且告警日志本身仍落盘可捞）；
- 死信告警**只告警 + 落台账、自动 ACK**（防告警消费者自身把死信又打回 DLX 造成循环）；真正重放是人工或后续工具的事，数据源即台账表；
- 恢复重放是后续增强项（按 original_routing_key 读台账重发），列入观察项，本轮不做（replayed_at 列已预留）。

## 九、风险与回退

| 风险 | 应对 |
|------|------|
| Redisson 与 Boot 3.4.10 版本不兼容 | 引入前先 dependency:tree 验证 netty/lettuce 无版本冲突；不兼容则降级 redisson-spring-boot-starter 至官方兼容线（3.46.x），仍不行则 Step 1 回退为"review 锁改 token+Lua"（复用 AssignedSubTaskTimeoutTask 模板，十行） |
| ShedLock 注解对 `fixedRateString`/`fixedDelayString` 动态配置的任务失效 | ShedLock 代理的是 Bean 方法，与 @Scheduled 的属性来源无关，正常生效；但需启动后观察一轮确认（见门禁 2） |
| 迁移期双写（部分任务新锁 key、部分任务旧锁 key） | 无冲突：ShedLock key 带 `helloai:schedlock:` 前缀，与旧 key 物理隔离；单任务迁移是原子的（同提交内注解替换手写锁），不存在同一任务两套锁并存 |
| Redisson 独立客户端的连接数/资源占用 | 默认连接池对当前单实例部署绰绰有余；application.yml 无需配置，如后续容器化多实例再评估 `redisson.config` |
| **队列参数 immutable 导致启动 `PRECONDITION_FAILED`** | 这是加 x-max-length/x-overflow 最常见的坑：已存在的同名队列参数不匹配会拒绝重建。开发/测试环境直接 Management UI 删旧队列让其以新参数重建；生产环境先评估存量消息再择低峰删队列，或临时改队列名滚动 |
| **RabbitMQ broker 版本 < 3.10 不支持 reject-publish（v1.1 新增）** | 实施前探测 dev/prod 版本；不满足则仅声明 x-max-length（跳过 x-overflow），并在 CODE_STYLE §3.z 记录环境例外；升级 broker 后再补 |
| x-max-length 阈值定太小误杀正常洪峰 | 起步值宁宽勿紧（核心 50000），上线后按 Management UI 实测深度分布再收紧；reject-publish 触发有 NACK 日志可追溯，是显式失败非静默丢 |
| **死信台账写入失败（v1.1 新增）** | 消费顺序"先台账后 ACK"保证失败只丢台账不丢告警；写库失败记 error 供事后补捞；重放以台账为准，极小窗口无法重放可接受（告警日志仍在） |
| DLX 告警消费者异常把死信打回 DLX 循环 | 告警消费体内 basicNack(requeue=false) 兜底（dlxQueue 未挂 DLX，消息终态丢弃，台账已兜底）；告警逻辑只读不改状态，无重投副作用 |
