## 1. 背景与问题

`SKX-12`（对话内选技能当场出图）上线后，线上实测一次技能请求 **377s**。

**问题不在「慢」，在「慢且不可观测」**：

1. 整条链（LLM 生成 → 技能包注入 → 三段门禁 → 回读 → 落附件）跑在**单个
   `http-nio-*-exec-N` 线程**上 ⇒ 请求生命周期 = 执行生命周期。
2. 客户端超时断开后，**服务端工作不会中止**，只会持续刷 `Broken pipe` ERROR，
   并让线程池被长任务占住。
3. 前端已被迫把对话类超时从 120s 抬到 300s —— **抬超时是止痛，不是解**：
   最坏分支（重生成 spec + 降档重渲）本身就可能到 170s。

`SKX-13` 要求把 377s 从 HTTP 线程摘出去，并让「还在跑」这件事**可见**。

## 2. 候选方案与取舍

### 2.1 执行载体

| 方案 | 取舍 |
|---|---|
| **独立线程池**（选定） | 与既有 `chatAttachmentParseExecutor` 同构；无跨机分发需求；拒绝策略 `CallerRuns` 保证任务不丢 |
| MQ（RabbitMQ） | 引入「投递失败 = 任务丢失」的额外失败面；技能执行是会话内一次性任务，无跨机需求 |
| 复用 `chatStreamExecutor` | 那是 SSE 长连接池（每条连接占用到流结束），一条长技能就能把流式连接全占掉 |

### 2.2 状态载体

| 方案 | 取舍 |
|---|---|
| **DB 新表 `chat_skill_run`**（选定） | 进度可查要跨请求；幂等闸门要条件更新；重启后能查到「上次跑到哪」而不是静默丢 |
| Redis | 只适合临时态，重启即失忆 —— 与「客户端断开不丢工作」的诉求相悖 |
| 进程内 Map | 多实例下前端轮询可能打到另一台；重启即丢 |

### 2.3 前端交互

| 方案 | 取舍 |
|---|---|
| **轮询**（选定） | 与「提交即返回 + 后台跑」天然匹配；仓库已有 `useAutoRefresh` 范式；实现面小 |
| SSE | SSE 通道当前明确拒绝技能命令（`ClarifyStreamServiceImpl` 「命令与技能暂不支持流式」），接 SSE 要改流式分派语义；且技能是「提交后独立运行」，与「一条流跑完一轮」的模型不同构 |

### 2.4 取消语义

选定**协作式取消**：状态先置 `CANCELLED`，worker 在**阶段边界**自查到就停。
不选强制中断：执行链的每一步要么是一次 LLM 调用、要么是一条沙箱命令，
强制中断意味着在 SDK 层做线程中断 —— 而沙箱命令的中断语义由 SDK 决定、
LLM 流的取消语义另有一套，强行打通会引入不可控路径。
代价是「取消后最多多跑一个阶段」，换来的是行为可预测。

## 3. 决策

1. **执行载体**：独立线程池 `skillExecutionExecutor`（`helloai.skill-execution.pool-size`，默认 2），
   拒绝策略 `CallerRuns`。
2. **状态载体**：新表 `chat_skill_run`（V128），状态机
   `PENDING → RUNNING → SUCCEEDED | FAILED | CANCELLED`。
   - `PENDING → RUNNING` 是**条件更新**，是执行幂等的唯一闸门；
   - 阶段列 `phase`（`SPEC/RENDER/CHECK/EXPORT/DONE`）承载进度可见性；
   - 部分唯一索引 `uk_skill_run_active` 在**数据库层**兜住「同会话同时只有一个 RUNNING」。
3. **前端交互**：轮询。`ClarifyConversationDetail` 增三个字段（`skillRunId` / `skillRunStatus` /
   `skillRunPhase`），前端据此启动轮询；新增 `GET /skillRun/{runId}` 与
   `POST /skillRun/{runId}/cancel` 两个端点。
4. **同会话并发**：**拒绝，不排队**。沙箱槽按会话复用（槽键 = `-conversationId`），
   并发两次会互相踩工作目录与产物路径；而「同一会话连着发两条技能」本身是用户误操作，
   排队等 377s 不如直接提示。
5. **客户端断开**：**不中止执行** —— 这正是要修的 `Broken pipe` 根因。
6. **超时**：服务端硬上限（`helloai.skill-execution.timeout-seconds`，默认 600s），
   到点判失败并落原因，用户不会永远转圈。

## 4. 代价与缓解（必须随代码一起记住的副作用）

| 代价 | 缓解 |
|---|---|
| 技能轮的响应**不再包含产物**（那是后面的事了） | 响应带 `skillRunId`，前端轮询终态后再拉一次会话详情 |
| 多一张表 + 一套状态机要维护 | 状态机只有 4 个终态路径，全部用**条件更新**表达（`markRunning` / `markSucceeded` / `markFailed` / `markCancelled`），并发下不会互相覆盖 |
| 取消是协作式，最多多跑一个阶段 | 阶段只有 5 个、每个约 1~2s，最坏多花几秒 |
| 同会话并发被拒 | 提示语直说「本会话已有技能在执行，请等它结束再试」 |
| 需求正文不从运行记录读，改从会话消息读 | 避免「正文存两处必然漂移」；编辑重发会重新提交一次执行记录 |

## 5. 后果

- 技能执行**不再占用 HTTP 线程** ⇒ 长任务不再拖垮整个应用的线程池，
  前端也不再需要为技能请求把超时抬到 300s。
- 「还在跑」变成**可观测的阶段**（生成输入 / 渲染 / 自检 / 回读导出），
  而不是一根没有信息的转圈。
- 失败与取消在对话里的表现被区分开：**取消不落「生成失败」**（用户自己叫停的，
  再报一次失败是噪音）；**超时落失败**（用户需要知道为什么没有产物）。

## 6. 补充（2026-10-30，代码复核后的收口）

实施记录见 `LOG-20261030-003`。三处补齐，不改变上文的状态机与载体选型：

1. **启动清扫（`SkillRunStartupRecovery`）**：活跃态（`PENDING`/`RUNNING`）的写者只有本进程，
   因此**进程启动时看到的所有活跃行必然是上一个进程的遗留**，统一置 `FAILED` 并落原因。
   不做「定时清扫 + 超时阈值」：基准执行耗时实测 377s，任何阈值都可能误杀正常任务。
   **前提是单实例部署**（当前 `docker-compose.server.yml` 只有单个 `app` 服务）。
   一旦上多副本，必须改为「运行记录加 owner/心跳列，只清本机或心跳超时的行」——
   否则每台实例启动都会杀掉其他实例正在跑的执行。
2. **客户端状态断点闭合**：`skillRunId` 只存在于提交响应，刷新即丢。
   新增 `GET /skillRun/active/{conversationId}`（返回该会话最近一条活跃记录），
   前端打开会话时据此接回轮询。写侧入口不变，状态机不变。
3. **取消的「立即性」在前端实现**：后端保持协作式（阶段边界停），前端在取消接口成功后
   立即停轮询并撤占位气泡，再拉一次详情对齐。服务端的克制不应外溢成用户的等待。
4. **三个超时量纲的澄清（`B1` 结案）**：`timeout-seconds` 这个名字在配置里出现三次，
   各管一段，**不可横向比较**：
   - `spec-presets.node.timeout-seconds: 900` ⇒ 沙箱**生命周期 TTL**
     （`OpenSandboxExecutionService#resolveSandboxTimeoutSeconds` → `Sandbox.Builder.timeout`）；
   - 单条沙箱命令的等待 ⇒ `resolveTimeoutSeconds`（缺省 30s、**硬钳 300s**），
     技能执行路径实际传 `ConversationSkillRunner.COMMAND_TIMEOUT_SECONDS = 180`；
   - 整次执行的服务端上限 ⇒ `helloai.skill-execution.timeout-seconds`（600s），
     由 `SkillRunControl` 在**阶段边界**检查。
   因此 §3 第 6 条的「到点判失败」应读作「**到下一个阶段边界**判失败」，
   最坏晚一个阶段（≤180s 命令 + 一段 LLM 调用）。这不构成参数冲突，preset 保持 900s。
