# 0. 定位与边界

## 0.1 问题来源（试点验证结论）

`G-037` 试点（2026-11-24 真机内外组对比）验证结论：

- **机制层已证实**：约束文档目录白名单（manifest）、章节按标题匹配（行号漂移免疫）、`internal_list_constraint_docs` / `internal_load_constraint_doc`（目录/正文分离 + fail-open）全部真实闭环；内部 LLM（平台侧工具读取）与外部 AI agent（MCP 载荷 + 沙箱读取）两条通道都能拿到规范正文；且两组 agent 读规范后输出收敛为「判据矩阵 + 章节号 + 原文引用」结构——「契约锚定异质 agent」机制在 HelloAI 链路内得到真实复现。
- **验收判据的「声明环」未触发**：planner 对诊断类任务输出 `constraintRefs=[]`（示例偏改造类 + 「不熟悉时允许留 []」宽松出口），链路实际退化为「constraints 文本提及 + 执行器自助取数」备份路径。
- **三个待修问题**（本设计各层逐一对应）：
  1. **声明引导偏差**（声明层，§2）——planner 将诊断类任务判为「不适用结构化约束」；而诊断类恰恰最依赖规范（读完才能判定合规）；
  2. **manifest 缺执行侧路径**（数据层，§3）——外部 agent 拿到 `{ref}` 无处定位，按 prompt 里「本地绝对路径」去猜宿主路径 → 伪造留痕（测试唯一确认的缺陷）；
  3. **评审 coverage 声明系统性缺失**（审查层，§5）——对「UTF-8 / 数值聚合 / 集合类」验收条目不写 coverage 声明，RV-3 静态校验 BLOCK，4 次转人工全此因（审查端为常量 kimi，与内外执行无关）。

前序依据：`research/需求规约化与两级拆解调研（2026-11-23）.md` §4（落点：执行侧主注入 / 拆解侧摘要引用 / 契约沿任务树继承）；试点设计 `design/HelloAI 任务约束类型化设计（试点）.md`；验证报告 `review/HelloAI G-037 任务约束真机验证报告（内外组对比，2026-11-24）.md`。

# 1. 设计原则（试点教训凝练）

- **P1 契约默认注入，不靠 LLM 自觉声明**。试点 `[]` 的直接根因是把「声明约束」交给 planner 自觉（宽松出口 + 示例偏差）。正式形态：平台按任务类型**默认注入**项目级契约集，LLM 只负责裁剪 scope，不得「不声明」；「不适用」须在 `constraints` 中说明理由。
- **P2 取数通道固化进契约，不留给执行器自由发挥**。内部 LLM 缺工具我们给了工具（成功）；外部 agent 缺的是「不靠猜的取数通道」——要么载荷内联正文（100% 可靠），要么卷内相对路径（省 token 变体），二者都杜绝「执行器自行推断文档位置」。外部组伪造留痕的直接根因就是取数方式未固化。
- **P3 一主一辅落点不动摇**（调研 §4.3）：执行侧主注入契约全文 / 拆解侧只声明引用不复制全文（唯一事实源判据：双写必分叉）。
- **P4 约束从「参考文档」升级为「验收检查表」**。试点两组都不约而同产出判据矩阵——把这种自发生长固化为标准产物形态，约束就不再是参考建议而是逐条核验的验收清单。

# 2. 声明层：默认契约注入 + scope 裁剪

## 2.1 机制

拆解输入中，在「约束文档目录摘要」之外增加「**项目默认契约集**」注入：manifest 登记的文档按任务类型自动匹配（涉及代码 / 产物质量 → `code-style`；涉及文档交付 → 文档体系治理引用），作为拆解时 `constraintRefs` 的**兜底骨架**。planner 的职责从「决定要不要声明」变为「**裁剪 scope**」：

- 默认：任务涉及代码 → 注入 `{kind: DOCUMENT, ref: code-style, scope: [按任务内容预选章节]}`；
- LLM 按子任务内容增删章节（scope 裁剪）、可追加其它已登记文档，但**不得输出空数组**；
- 确不适用（纯问答、无产物质量判定）→ 必须在 `constraints` 写明「不适用理由」，平台校验该理由存在才放行（防静默漏声）。

## 2.2 拆解 prompt 修改点（`planner-decompose.md`）

1. 删除「不熟悉时允许留 `[]`」宽松出口，改为「不声明必须说明理由」；
2. 补充**诊断类 / 审查类任务示例**（读规范 → 产出合规判定 → 按章节引用组织结论），消除「示例全偏改造类」的引导偏差；
3. 新增「默认契约集」说明：`{{CONSTRAINT_DEFAULT_SET}}` 占位渲染预选 scope，LLM 做减法而非从零声明。

## 2.3 与 `G-027` 的关系

粗→细 scope 继承策略（粗带摘要、细取全文，调研 §4.3）由 `G-027` 交付编排实施时定义；本设计只保证模型层（`constraint_refs` 结构 + scope 语义）可被该策略叠加，不提前实现。

# 3. 数据层：manifest 执行侧路径

## 3.1 字段扩展

每条文档登记项由 `{ref, path, title, summary, sections[]}` 扩展为：

```json
{
  "ref": "code-style",
  "path": "doc/HelloAI_CODE_STYLE.md",        // 平台侧读取路径（唯一；仅供内部工具与正文内联裁剪）
  "sandboxPath": "doc/HelloAI_CODE_STYLE.md", // 执行侧卷内相对路径（挂载点 /workspace 之下）
  "repoPath": "doc/HelloAI_CODE_STYLE.md",    // git 仓库相对路径（G-033 落地后第一通道，规范随仓库版本一致）
  "title": "...", "summary": "...", "sections": [...]
}
```

- **`path` 语义收窄**：仅平台侧工具 / 正文内联裁剪读取，**禁止注入任何执行上下文**（宿主绝对路径对沙箱执行器不可见，本次外部组伪造留痕的根因）；
- `sandboxPath` / `repoPath` 唯一语义：告知执行器「规范的仓库内位置」，取值与 `path` 解耦（允许平台侧文件在 docRoot 之外、仓库内另有副本）。

## 3.2 扩登记（按调研 §6.4 优先级）

一级（保质量）：`code-style`（现有）+ 协作规约（AI 改代码生命周期 + 红线）+ 差距表指针。扩登记须同批维护 manifest（引用完整性规则）；白名单机制与章节匹配不改。

# 4. 执行读取契约：内外双通道

| 通道 | 取数方式 | 适用 | 护栏 |
|---|---|---|---|
| **内部 LLM**（默认） | `internal_load_constraint_doc(ref, scope)`——平台侧读 manifest `path`，正文进模型上下文 | 所有内部执行 | scope 外章节白名单拒绝；文件缺失返回 `unavailable` 不得编造（试点已验证） |
| **外部 agent · 主形态** | **载荷内联正文**：`buildSubTaskDetail` 下行载荷增 `constraintDocs: [{ref, scope, content[]}]`（平台按声明 scope 裁剪正文、只读字段） | 默认所有外部执行 | 正文只读 + scope 裁剪控 token；载荷**不出现宿主绝对路径**；存在「找不到文档」的借口归零 |
| **外部 agent · 辅形态** | 卷内读取：载荷带 `sandboxPath`，agent 在 `/workspace` 下 `cat`（或 grep 章节） | 有沙箱卷挂载时 | prompt 明示「工作区根 = /workspace，宿主路径不可见」；要求带 sha256 只读取证（试点外部组已自发形成，固化为验收要求） |
| **git 前置后**（`G-033` 承载体，未立项） | 任务声明 `repo`（地址 + 版本），执行器 clone 后按 `repoPath` 读取 | 代码改造类任务 | 规范随仓库版本一致、零额外传输；diff 回传 + reviewer 沙箱按规范验证 |

**关键语义**：内部 LLM 永远走工具（平台代读）；外部 agent **主给正文、辅给路径**——两条路都不依赖执行器推断，杜绝「猜路径 → 伪造留痕」复现。

# 5. 审查层：coverage 引导 + 标准产物

## 5.1 reviewer coverage 声明引导（修观察点③）

reviewer prompt 的 coverage 声明段补充强制引导：对**字符集 / 数值聚合 / 集合类**验收条目（如「UTF-8 无乱码」「覆盖章节数 ≥10」「汇总表条目数=上游之和」），必须写证据位置（沙箱实跑命令 / 产物行号范围），否则视为未覆盖。**修引导而非改 RV-3 静态校验**——RV-3 的 fail-open 语义保留，减少误放行风险依赖真机误报率数据（同 MA-9 口径）。

## 5.2 判据矩阵标准产物形态（P4）

产出物模板固化为（试点两组自发收敛的形态，正式化后作为拆解验收判据的默认要求）：

```
| 编号 | 规范条款（原文引用 + 章节号） | 目标文件:行号 | 现状 | 判定方法 | 合规性 |
```

任务要求固定写「产出物必须对照声明 scope 章节**逐条自检**并产出该矩阵」——约束从「参考文档」变成「验收检查表」，reviewer 与执行者按同一矩阵逐行核验。

# 7. 正式引入验收判据（一行）

> 默认契约注入 → 拆解产出**非空** `constraintRefs`（scope = LLM 裁剪子集，含诊断类任务）→ 落 `plan_draft` / `sub_task` → D6 段引用摘要 → 双通道取正文（内部工具 / 外部载荷内联或卷内 `sandboxPath`）→ 审查同引用且 coverage 声明对验证型验收全绿 → **改造类任务**产物 diff 对照 scope 条款自检矩阵抽样合规。声明环 + 双通道 + 审查环全通、且改造类补充验证通过，即正式引入验收通过。（「规范使代码改得更好」的行为验证需 A/B/C 对照实验，另立观察项，不并入引入验收。）
