## LOG-20261001-001 RabbitMQ 连接故障诊断与修复（ACCESS_REFUSED / guest loopback 限制）

### 背景

dev profile 启动时连接云端 broker `39.106.204.43:25672` 失败，报：

```text
AmqpAuthenticationException: ACCESS_REFUSED - Login was refused using authentication mechanism PLAIN
```

### 问题

1. **服务器侧**：生产 broker 是 `docker-compose.server.yml` 部署的 `helloai-rabbitmq` 容器（`guest/guest`、无 vhost 隔离、未挂 `rabbitmq.conf`）。RabbitMQ 默认 `loopback_users = [guest]`，guest **仅允许 localhost 连接**——本机应用远程连接必被拒，与密码无关；
2. **应用侧**：`application-dev.yml` 只覆盖了 rabbitmq `host/port`，username 沿用主配置写死的 `guest`、virtual-host 走默认 `/`，与云端 broker 口径（业务账号 `helloai` + vhost `/helloai`）不匹配。

**诊断教训（登记，避免重蹈）**：初始曾以 `deploy/middleware/.env` 的隔离方案凭据（`admin`/`helloai`）对 `25673` Management API 做只读探测得 401，一度误判为「密码错误」；实际服务器跑的是 server.yml 老部署（无 admin/helloai 用户），401 是必然结果。**结论：探测凭据须以服务器实际运行的 compose 为准，本地中间件部署目录的 .env 不一定是云端现状。**

### 决策

服务器侧补建业务账号与隔离 vhost（热生效、不重启容器）；应用侧补齐参数化占位，与 `aes-key-base64` 同口径（`application-dev.yml` 为 `skip-worktree` 不入库，默认值为本地私有凭据，生产 / CI 仍可经环境变量覆盖）。

### 实现

1. **服务器侧（人工执行）**：`helloai-rabbitmq` 容器内执行：

   ```text
   rabbitmqctl add_vhost /helloai
   rabbitmqctl add_user helloai <HELLOAI_RABBIT_PASSWORD>
   rabbitmqctl set_user_tags helloai management
   rabbitmqctl set_permissions -p /helloai helloai ".*" ".*" ".*"
   ```

2. **应用侧**：`application-dev.yml` rabbitmq 节点补齐参数化占位：

   ```yaml
   username: "${RABBITMQ_USERNAME:helloai}"
   password: "${RABBITMQ_PASSWORD:RabbitHelloai_2026}"
   virtual-host: "${RABBITMQ_VHOST:/helloai}"
   ```

### 验证

Management API 只读探测通过：`helloai` 账号远程认证 **200**、`/helloai` vhost 可见、rabbitmq **3.12.14**。

### 结果

本机 dev 启动不再报 `ACCESS_REFUSED`。

### 影响

- 服务器 app（`helloai-app` 容器）生效需**重打包 jar 替换 `/home/admin/helloai/helloai-start-1.0.0-SNAPSHOT.jar` 后 `docker compose restart app`**（jar 内置 dev.yml 默认值即 helloai 口径，compose 无需复制任何 yml 文件）；
- 服务器 compose 是否需补 `SPRING_RABBITMQ_USERNAME/PASSWORD/VIRTUAL_HOST` 取决于服务器现状，取证命令：

  ```text
  docker exec helloai-app env | grep -i rabbit
  grep -n "RABBITMQ" /home/admin/helloai/docker-compose.yml
  docker exec helloai-rabbitmq rabbitmqctl list_connections user vhost
  ```

- 切换 vhost 后 `/` 下旧队列成孤儿（`helloai.executor.queue` 等在 `/helloai` 自动重建），可稍后清理；
- 关联遗留：服务器 broker 仍为 guest/guest 无隔离部署，`deploy/middleware` 隔离方案（vhost + 业务用户）未迁移——与 2026-09-30 审计「R7 凭据轮换 / 端口白名单」同属部署侧待办。

## LOG-20261001-003 架构红线收口（第二批）：`system → task` 端口反转清零

### 背景

承上条，清偿基线内反向依赖第 2 条。`system → task` 全仓仅 1 处命中（2 条 import），真实用量极小：仅调 `AttachmentService.listAllIncludingDeleted()`，且只读 `storageUrl` / `fileSize` 两字段（该方法 javadoc 本就写明「**仅供对账巡检使用**」）。

### 问题

```java
// system/storage/impl/ArtifactStorageReconcileServiceImpl.java:7-8
import com.helloai.core.task.entity.Attachment;         // 实体泄漏
import com.helloai.core.task.service.AttachmentService; // 服务反向依赖
```

### 决策

**端口反转**，沿用项目既有约定「消费方域定义接口、提供方域实现」（先例 `ReviewPort` §6.146 / `TaskDispatchPort` §6.138 / `TaskPlannerPickerPort` §6.134 三处一致）：

| | 端口（消费方） | 实现（提供方） | 实现侧依赖方向 |

3. `ArtifactStorageReconcileServiceImpl` 删 2 条 `task.*` import 与 `AttachmentService` 字段，改注入 `ArtifactReferencePort`；
4. 测试适配：`ArtifactStorageReconcileServiceImplTest` mock 换端口（13 用例）；新增 `ArtifactReferencePortAdapterTest`（3 用例）；
5. 门禁同步：`check-arch-freeze.sh` 删该规则「存量标债」注记、`arch-baseline.txt` 刷新为 `system->task=0`、`verify-dependency-direction.ps1` 的 `system->task` 断言由 `-KnownDebt 1` 收紧为**严格 0**；

## LOG-20261001-004 元修复：CI 门禁「用例数」口径漏计 JUnit5 `@Nested`（已修）

### 背景

`helloai-job` 多个测试类在 surefire 报告中报 **0 用例**（`AgentHealthCheckTaskTest` / `AssignedSubTaskTimeoutTaskTest` / `ExternalAgentFallbackTaskTest` / `PlanningTimeoutTaskTest` / `SubTaskPendingOrphanTaskTest` / `ReviewerRecheckTaskTest` …），但控制台同时打印 `Running resolveModel → Tests run: 7 … in resolveModel`。

### 问题

Surefire 3.5.4 把 `@Nested` 用例写进**外层类**的 XML 文件，而该文件的 `<testsuite tests="N">`（及 failures/errors/skipped）**属性只统计外层容器自身**——外层类通常不直接声明 `@Test`，故恒为 0。逐条实证：

```text
grep -o 'tests="[0-9]*"' TEST-…AgentProviderResolverTest.xml | head -1   # → tests="0"
grep -c '<testcase'        TEST-…AgentProviderResolverTest.xml           # → 12
```

全仓核对：含 `@Nested` 的测试类 core **39** / job **8**；属性口径合计 **1144**，`<testcase>` 口径合计 **1783**。

后果：`scripts/ci/ci-gate.sh` **门禁 2**（「用例数 > 0」）用属性口径 → **指标低报 639（35.8%）**；门禁本身未失效（1144 > 0 仍拦得住「零用例假绿」），但**单模块「用例骤减」会被掩盖**（job 旧口径 17 / 真实 85）。历史结论中所有「1141 用例」均为属性口径（§13.3/§13.5、审计报告 §9 局限 #4 的 1764 为另一路 `@Test` 近似计数），**真实执行数为 1783**。

### 决策

门禁计数口径由「`tests` 属性」改为「数 `<testcase>` 元素」，并在脚本内写明口径理由与实测数据（防改回）。

### 实现

`scripts/ci/ci-gate.sh` 门禁 2 计数改为数 `<testcase>` 元素（含 skipped，skipped 同样产出 `<testcase>`）；`scripts/README.md` §6 表格同步。

### 验证

同一份 clean 全量产物（`mvn -o -DskipTests=false clean test`，Reactor 7/7 SUCCESS）按新口径独立复算：

```text
报告文件 177 个 / 用例 1783 / failure 0 / error 0 / skipped 0
分模块：core 1628 · job 85 · api 70
```

### 结果

门禁用例数口径修正为 `<testcase>` 元素计数。

### 影响

**教训（登记）**：**「0 用例」在 surefire 里可能是假象**——先看控制台是否打印了 `Running <嵌套类 DisplayName>` + `Tests run: N`，再看 XML 里的 `<testcase>` 元素，不要只读 `tests` 属性。

## LOG-20261001-013 `agent → task` 清偿 W5：加锁读走只读端口，事务边界仍归消费方（33 → 31）

### 背景

W4 收尾时预判 W5 需要**不透明命令端口**（「悲观锁 → 二次判重 → 三表同事务写，整条序列整体不透明化」）。

### 问题

实测**不成立**：`ExecutionCommandServiceImpl.createAssignedCommand` 里，加锁读只用于**校验/判重**（`assignedAgentId` 是否匹配、是否已有进行中执行记录），**唯一的写动作 `agentExecutionRecordService.createPending(...)` 落在 agent 域自己**，提供方 task 既不做判定、也不参与事务。⇒ 属于「**加锁读 + 校验**」而非「**有判定的状态推进**」，**只读端口即可**，无需把状态机搬回 task。

### 决策

**新增可复用判据**：**「加锁读」≠「命令端口」**。区分标准是**写动作发生在哪一侧**——

- 消费方只借锁做**校验/判重**、写动作仍由消费方自己的 ORM 完成 ⇒ **只读端口**（并在适配器上**显式标注不加 `@Transactional`**）；
- **判定 + 写整体要落提供方** ⇒ 才升级为**不透明命令端口**（W3 `SubTaskCommandPort`、W4 `SubTaskReviewContextPort`）。

误判的代价：把提供方无判定职责的读取也做成命令端口，会凭空造出一个「假状态机」，反而把事务边界撕成两半。

### 实现

1. `agent.port.SubTaskQueryPort` **扩一个加锁读方法** `findByIdForUpdate(Long) → SubTaskSnapshot`（不存在返回 `null`，与 `SubTaskService#getByIdForUpdate` 语义逐字一致）。**不新建端口、不新建适配器**——加锁读与普通读同属「读」语义、同属同一消费方。
2. task 侧 `SubTaskQueryPortAdapter` 增实现，**刻意不加 `@Transactional`**（javadoc 显式写明）：只转发 `SELECT ... FOR UPDATE`，**行锁必须随「调用方事务」存续**；若在提供方另开事务或提前提交，锁会立刻释放、互斥失效。事务边界仍由消费方 `createAssignedCommand` 的 `@Transactional(rollbackFor=Exception.class)` **独占**。
3. 消费方 `subTask.getAssignedAgentId()` / `getTaskId()` → 快照访问器 `subTask.assignedAgentId()` / `subTask.taskId()`（5 处）。**业务分支、异常文案、timeline 埋点、`TASK_ASSIGNED` 事件一字未改**。

### 验证

- 定向 **14 例 / 0 失败**（`ExecutionCommandServiceTest` 5 / `ExecutionCommandServiceDispatchTest` 4 / `SubTaskQueryPortAdapterTest` 5）。
- 冻结守卫：`agent->task` **33 → 31**（−2，与计划一致）；代价 `task->agent` **50 → 50（持平）**——端口方法扩在既有适配器上，**未新增 task 侧文件**，前向计数零增长。
- 基线锁定 **31 / 50**，复跑 `EXIT=0`。

- **端口「扩方法」比「新建端口」更省钱**：同一语义族（读 / 写）应落在同一端口；新增端口要多一个适配器文件 → `task->agent` 前向计数额外上涨。本轮零上涨即因此。

   - `block(report.getSubTaskId(), null, null)` —— **直接复用 W7 已有的三参 `block`**：`block(id, null, null)` 与 `block(id)` 逐字等价（提供方仅记 `blockedAt` + 落 `sub_task_report_blocked` 时间线，`reason` 记空串）。**不为「少传两个 null」新增重载**。
3. **「读改写回写」→ 新增 `SubTaskCommandPort.updateContext(Long, Map)`**（本轮硬核，见下）。
4. **执行记录回填 → `TaskRunningSpecPort.parseAndAppendExecutionRecord(...)`**（W10 新增方法）：把原先内联在 `handleReport` 里的「`ExecutionRecordParser.parse` → 解析失败取**前 200 字符 + `...`** fallback → `appendExecutionRecord`」**整块**搬进提供方适配器。**理由**：`ExecutionRecord` 与 `ExecutionRecordParser` 都是 **task 域协议类型**，暴露给消费方只会把反向依赖从 `service` 换成 `spec`（W1 已证计数不降）。契约只收「原始输出 + 归因标识」，返回 `void`。**异常不在端口吞掉**——「降级不阻断主链路」是**调用方的编排决策**，try-catch 留消费方。

**硬核：`updateContext` 为什么不能「快照 + version 写回」**

原代码是标准的**读改写回写**：

```java
SubTask subTask = subTaskService.getById(id);      // 读
Map<String,Object> ctx = new HashMap<>(subTask.getContext());  // 改
subTask.setContext(ctx);
subTaskService.updateById(subTask);                // 写回
```

消费方要提交的是「一整份新的 `context`」，而 `context` 的构造（`lastExecution` / 对话流摘要 / `hasUnresolvedLastRound` 预检）**确实属于消费方协议逻辑**，不能整体搬走。于是只剩两条歧路：

- **歧路一**：把 `SubTask` 实体交给消费方改 —— 就是当前状态，即反向依赖本身；
- **歧路二**：消费方拿快照改完，用 `updateContext(id, ctx, version)` 写回 —— 契约**被迫暴露 `@Version` 乐观锁字段**，消费方要复现 MyBatis-Plus 的 CAS 语义；这是**提供方存储实现细节**，换 ORM / 换锁策略都要改消费方。

**正解**：`updateContext(Long subTaskId, Map<String,Object> context)` —— 消费方只交**目标值**，提供方适配器自行 `getById(最新行) → setContext → updateById`。**取最新行而非消费方快照**是关键：既保留同行互斥（提供方事务内 CAS 仍生效），又避免消费方携带的陈旧 `version` 触发 `updateById` 返回 `false`（**MyBatis-Plus 版本不符时不抛错，只返回 false**）导致 `context` 写入**静默丢失**。子任务不存在时静默返回，与原 `updateById` 更新 0 行同样不抛错。

### 验证

## LOG-20261004-001 B3 Fork：快照复制落地（Claude Code/Codex 同款最朴素形态）

## LOG-20261004-008 B5 成本选人「0 档」语义缺陷订正 + 真实库实证（用户复核触发）

### 背景

B5.2/B5.3 成本选人落地（见 `LOG-20261003-003`）后，用户复核「无成本数据记 0 档」这一口径时提出反例，触发缺陷定位。

### 问题

`AgentSelector.resolveCostRanks` 返回的 Map **只含「有样本」Agent**（1~5 档），无样本者走 `getOrDefault(id, 0)` → **0 档**；而比较是 `max(...thenComparingDouble(rank × weight))`（**数值大者优**）⇒ **0 档 = 比最贵档（1）还差**，并非文档所称的「不参与比较」。后果恰在**部分覆盖**时暴露：候选内仅 1 个有样本 → 该 Agent 因 `min == max` 退化得**中立 3 档**（+0.3），其余得 0 ⇒ **「有历史样本」本身成为胜出理由**，与「缺失值须与最差值区分」判据相悖。既有单测 `AgentSelectorTest:1154 shouldDegradeNoCostDataToZeroRank` **把该行为固化为期望**（断言「有成本数据者胜出」）。

### 决策

用户批准**方案 C**：无样本者改记**中立档**（「不可比」的落点是**不偏袒**，不是「判最差」），并加**可比性门槛**。

### 实现

## LOG-20261007-001 §11.3「Controller 不得暴露 core Entity」口径固化 + Jackson `Long→String` 口径收窄

### 背景

两项**同型存量债务**：口径**存在但不强制**。① CODE_STYLE §11.3 只有「API 层不要直接暴露数据库 Entity」一句，**无计数口径、从未脚本化/门禁化**；② `JacksonConfig` 的全局 `Long→String` 规则**按 Java 类型一刀切**，非 ID 数值被一并污染为字符串。

### 问题

**① §11.3 从未被清偿的真实原因**：无计数口径 ⇒ 历史并存 ≥3 种数字（`13/5`、`17/7`、审计宽口径 `27 控制器/108 行`），审计方与研发方**互相不认账**；无脚本/门禁 ⇒ **无强制力**。附带发现：`scripts/ci/arch-baseline.txt` 记 `task->agent=53` 而实测 **57**，漂移 **+4** 长期未刷新；`verify-code-style-p0-layer.ps1` 引用已随 `tmp\` 清理而消失的 `tmp\kill-backend.ps1` ⇒ 收尾 `[5/5]` **恒失败**。

**② Jackson 契约谎报**：`Long`/`long`/`BigInteger` 一律 `ToStringSerializer` ⇒ 分页 `total/pages/current`、仪表盘计数、`leaseCount`/`latencyMs`/`fileSize`/`idleMinutes` 等**非 ID 数值**同样下发为字符串，与前端 TypeScript 声明（`number`）不符；**曾致 Element Plus `<el-pagination :total>` 校验失败、组件 DOM 不挂载**。该缺陷**自始未书面登记**，只在 `helloai-ui` 侧以兜底补丁（`api/request.ts#normalizePageResult` + 两视图 `Number()` 强转）被绕过。

### 决策

**① §11.3 口径固化 + 可执行校验**：定义唯一计数口径并冻结基线；校验**复用既有脚本**新增静态断言开关，**不新建脚本文件**（遵《协作规约》§23）。

**② Jackson 用户拍板「档 A：收窄全局规则」**：**默认层保持保守**（一律写字符串，护雪花 ID 精度），**例外层按属性名判定**转写 JSON 数字。

### 实现

**① §11.3 口径固化**

- **口径定义（CODE_STYLE 新增 §11.3.1）**：命中 = `helloai-api/**/controller/*Controller.java` 中**带 `@*Mapping` 的 public 方法**（HTTP 端点）签名（**返回类型或入参**）出现 `com.helloai.core.<domain>.entity.*` 类型；**计数单位 = 方法**（与签名换行无关）；`private` 映射器 / `*Response`·`*VO`·`*Request`·port record / 局部变量 **均不计**。
- **冻结基线 = 19 处 / 8 控制器**（响应侧 **17/7** + 请求侧 **2/1**）。
- **可执行校验**：既有 `scripts/powershell/verify-code-style-p0-layer.ps1` 新增 **[1b/5] 静态断言** + **`-StaticOnly`** 开关（只跑静态断言，不打包 / 不启动 / 不需口令）。
- **基线刷新**：`check-arch-freeze.sh --update-baseline`。
- **顺手修** `[5/5]` 坏引用 → 复用既有 `kill-old.ps1`。

**② Jackson 两层口径**

- **默认层**：`Long`/`long`/`BigInteger` 一律写字符串——护雪花 ID 精度，**且覆盖 `BeanSerializerModifier` 看不见的位置**（`R<List<Long>>` ID 列表 / `Map<String,Object>` 中的 Long 值 / 运行时泛型擦除处）；这些位置无法按属性名判定语义，偏安全侧是**唯一不引入精度回归**的选择。
- **例外层**：新增模块 `helloai-non-id-long-as-number`，`BeanSerializerModifier#changeProperties` 对「属性类型为 `Long`/`long` **且** 属性名非 ID 语义 **且** 未显式声明 `@JsonSerialize`」者 `assignSerializer(RawLongSerializer.INSTANCE)` ⇒ 写 JSON 数字。
- **ID 语义判定 `isIdName`**：恰为 `id`（忽略大小写）或以 `Id`/`ID` 结尾——**刻意大小写敏感后缀**（大小写不敏感的 `.*id` 会把 `valid` 误判为 ID；`idleMinutes` 因后缀不匹配天然不受影响）。
