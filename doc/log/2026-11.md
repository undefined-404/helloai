#### 决策

**G-026 设计口径（Q-1~Q-9）**

- **单表快照**：只建 `llm_balance_snapshot`（不建 account / usage_daily，避免与 vault、事件源双写漂移）；`quota` 归 `system` 域，
  不新建 Maven module。
- **SPI + 双层密钥抽象**：`BalanceProvider(key/supports/fetch)`，`fetch` 不抛异常、失败返回 `failed(reason)`；密钥按 provider 路由——
  deepseek/moonshot/minimax 走 vault，博查走 sys_config。跨域复用走**端口反转**：`system.port.PlatformApiKeyPort` / `WebSearchApiKeyPort`
  由 `system`（消费方、低层）定义，`agent` / `planner` 各自提供 adapter 实现，保持 `system` 不反向依赖上游（§6 / §7.2）。
- **缓存与熔断**：Redis RBucket 成功 60s / 失败 30s + Resilience4j `quotaFetch`；前端 30s 可见轮询、定时采集 15min；不采用 SSE。
- **收口装配**：新增 `QuotaConfig` 显式装配 4 provider + 有序注册表；`BalanceQueryService` 线程池补 `@PreDestroy`。
- **开关**：`sys_config["quota.widget.enabled"]` 平台开关 + `quota:view` 权限双闸门；另设 `GET /api/admin/quota/widget-enabled`
  （`quota:view` 保护），避免依赖未绑 ADMIN 的 `config:view`。

**G-026 UX-1 口径（Q-10）**

- **一个配置键统管自动刷新**：`sys_config["quota.refresh.interval-seconds"]`，`0`=仅手动、`60~3600`=自动间隔、空/非法回退 `60`。
  前端轮询、手动模式、定时采集共用这一口径，禁止第二套节奏定义。
- **手动模式也不假装新鲜**：新增 `GET /overview?fresh=false` 只读最近落库快照，打开面板不触网；用户显式点「刷新」才请求外部接口。
- **定时采集服从间隔**：手动模式不抓；自动模式逐家判断「最近快照是否已晚于间隔」，避免手动刷新单家导致其余家被饿死。
- **不改 yml**：`helloai.quota.collect-interval-ms` 仍是任务基础节拍（15min），sys_config 是用户可见的**最小抓取间隔**；两者取更保守的一侧。

### 个人助理工作台 PA-11 / PA-12 落地 + 独立代码复核与处置（原 `LOG-20261103`）

> 本条为 11-03 全天记录（原 `-001`~`-010` 子条目已按「一天一条」口径整合，内容无删减，改按问题域分组）。

#### 背景

用户复核个人工作台后指出两处方向问题：① 工作台中间框不应复用「需求澄清/建任务」对话，而应是能跨历史会话检索的「个人助理对话」；② 助理对话与新建对话都应有「上下文窗口」，支持手动/自动压缩，当前项目没有。要求参考开源项目逻辑设计后实施。当日完成 PA-11（助理对话）、PA-12（上下文窗口与压缩）落地，并追加一轮第三方视角代码复核与问题处置。

#### 问题

- 工作台入口仅切换右栏（`isWorkbenchEntry`），中间对话仍走 `clarifyApi.create/send` → 需求澄清 pipeline，不检索历史、产出任务草案。
- 长会话只有固定 40 条滑窗 + 首条用户锚点（`ClarifyPromptRenderServiceImpl.HISTORY_WINDOW=40`），无 token 计量、无摘要压缩、无手动/自动压缩、无占用面板。
- 「从对话创建任务」无显式动作与血缘。
- 上一批代码（PA-1~PA-7）复查发现：用户态为空时 `listConversations` / 长期记忆检索**返回全部**（外部 Agent 通道无用户态，跨用户外泄风险）；`TaskServiceImpl` 以 `eq(ownerId, null)` 拼条件退化为 `owner_id = NULL`（恒空）；控制器 `assistantProfile()` 直接用 `StpUtil` 重复解析用户，未复用 `CurrentUser`。

#### 决策（关键口径裁定）

- **存储同构、行为分流**：`requirement_conversation` 加 `kind`（REQUIREMENT / ASSISTANT），消息仍统一落 `requirement_message`（真相源），按 `kind` 分流 pipeline；**不新建第二套会话表**。
- **助理对话**：调用 LLM 前检索「最近工作 + 相关历史 + 精选长期记忆」预注入 system prompt（对齐 QwenPaw auto-recall），复用 `PlatformAgentExecutionService.executeSync`，**不新造执行链、不依赖 LLM 工具调用**（工具需 `@Tool` + `agent_mcp_server` 绑定授权，成本高，留二期）。
- **建任务显式化**：`createTaskFromContext` 新建 `kind=REQUIREMENT` 会话 + 写 `parent_conversation_id`/`forked_from_message_id` 血缘，**不静默转模式**。
- **上下文窗口**：token 分项占用（系统提示词/系统工具/Skill/消息/其他）+ 百分比；自动压缩按 `trigger_ratio`（默认 0.80）触发，手动 `/compact` 强制；**压缩只改「喂给模型的上下文」，原文全量保留可回查**。借鉴 QwenPaw（9 段渐进压缩 + recall）与 Yuxi（256K 阈值 + 保留最近 10 条）。
- **安全口径**：用户态为空时**返回空**而非全量；`pageTasks` 无用户态时不加 owner 条件（避免 `= NULL`）；控制器统一走 `CurrentUser`。
- **锁 TTL 口径**（N-1 处置）：配置值是**下限**，有效 TTL = `max(配置值, 各 provider 读超时最大值 + 1s)`；配置非正 fail-fast。方向唯一（只能调大），避免按 profile 维护多套值。
- **`profiles.active`**：曾回退 `dev`，后按「**先用 local 环境测试，最后上生产环境**」的裁定保留 `local` → 转为**上生产前检查项**。

### 活跃 Agent 名册化 + 助理状态卡精简与常驻 + 页脚精简（原 `LOG-20261103-002`）

#### 背景

用户 2026-11-03 连续提出三处 UI 反馈（均附截图）：① 设计稿右侧的「活跃 Agent」段在**工作台默认空态与对话进行中都不见了**，要求补上；② 助理状态卡里的「供应商可用率」与下方进度条要去掉，但「AI 助手 / deepseek-v3 / 已就绪 / 可用余额」要保留，并补上「进行中」状态；③ 状态卡在**进行中的助理对话里消失了**，且输入框下方的「余额」「账户中心」不要了。

#### 问题

1. **活跃 Agent 整段消失**：`WorkbenchQueryServiceImpl.activeAgents` 原逻辑只列出「存在 IN_PROGRESS 子任务」的 Agent，无人跑任务时返回空列表；前端又用 `v-if="activeAgents.length"` 把整段藏掉——空闲期该段从右栏消失，与设计稿「常驻的可用 Agent 列表」不符。
2. **状态卡只在空闲态出现**：模板上状态卡被 `v-if="isIdle"` 包住，而 `isIdle = messages.length === 0`，一旦对话有消息，卡片连同「已就绪」徽标一起消失，用户在对话中看不到助理状态。
3. **状态卡与页脚信息冗余**：「供应商可用率」进度条与「可用余额」并列且口径不一；页脚又有第二个余额胶囊，与右栏重复；「账户中心」按钮与顶部导航「系统设置」重复。

#### 决策（关键口径裁定）

- **活跃 Agent 改为「名册 + 每人实时状态」**：名册取 `agent.status = ACTIVE` 且角色 ∈ {EXECUTOR, REVIEWER}（PLANNER 不进右栏），逐人派生状态 `RUNNING`（该 Agent 名下 IN_PROGRESS 子任务 > 0）→ `REVIEWING`（REVIEW 子任务 > 0）→ `STANDBY`；排序 运行中 → 审核中 → 待命中，同状态按负载倒序、再按名称，截断 6 条。**不在无人跑任务时整段消失**，空名册才显示「暂无可用 Agent」。
- **审核中状态按「产出待审」计在执行者名下**：`sub_task.assigned_agent_id` 恒为执行者，审查者只在 `review_record.reviewer_agent_id` 事后留痕，故 `status = 'REVIEW'` 的子任务计入其执行者的「审核中」负载——这才是「该 Agent 手上还有活」的口径。
- **负载查询单条 SQL 聚合**：`selectActiveAgentLoads` 增 `review_count` 聚合列，owner 口径（`t.owner_id = 当前用户 OR t.owner_id IS NULL`）不变，上限 50 覆盖名册条数避免漏计，无 N+1。
- **状态卡常驻、徽标随轮次切换**：去掉 `v-if="isIdle"` 门控，空闲态与对话态同时显示；徽标文案绑定 `sending`（`进行中` / `已就绪`）。
- **删「供应商可用率」与进度条，保留「可用余额」**：额度型供应商剩余百分比与金额型余额并列易生歧义，设计稿无此元素。
- **删页脚「余额」「账户中心」**：余额在右栏状态卡已有唯一展示点；「账户中心」功能入口保留在顶部导航「系统设置」菜单，不丢入口。G-026 的右下角额度浮球是独立组件，不在本次范围。

#### 背景

### 助理对话补齐 SSE 流式 / 思考过程 / 停止生成（与需求对话同协议）（原 `LOG-20261103-004`）

#### 背景

用户 2026-11-03 实测工作台：「我问了 AI 小助理一个问题……确实走了联网查询，只不过没有思考过程，发出去的问题，也不像 RequirementChat.vue 中，发送按钮可以选择手动暂停，也没有 sse 流式输出」。确认后端助理链路只有同步端点（`assistant/create`、`assistant/send/{id}`），要等「联网搜索 + 完整 LLM 输出」一次性返回。用户裁定：「先按建议全量对齐，把 AssistantChatService 改成流式返回」，并要求遵循 `doc/HelloAI_CODE_STYLE.md` 与 `doc/HelloAI_AI开发协作规约.md`。

#### 问题

1. **无 SSE**：同步链路联网检索实测可达 20s+，整段生成期间前端只有「正在思考…」占位，没有任何增量反馈。
2. **无思考过程**：`executeSync` 只返回最终文本，模型 reasoning 在同步提取时被丢弃；平台侧检索动作也从未作为 `progress` 帧下发。
3. **无法停止**：同步 HTTP 请求一旦发出只能等结束，没有「停止生成」。
4. **过程不可回看**：assistant 消息 `payload` 为 null，刷新后即使检索过也看不到任何轨迹（工作台也没有渲染 `webSearch` / `process` 的组件）。

#### 决策（关键口径裁定）

- **不新建第二套服务**：在既有 `AssistantChatService` 上增加流式方法，与同步方法共享 `newConversation` / `prepareRound` / `loadPromptContext` / `buildSystemPrompt` / `buildAgentTask` 等内部件；同步端点保留作兜底，前端默认走流式。
- **一套事件协议**：复用需求对话的 `ChatStreamEvent`（`session` / `progress` / `reasoning` / `token` / `done` / `error`）与 Controller `streamSse` 骨架（断开 dispose = 停止生成；`Flux.defer` 兜底同步异常），避免两条链路各写一套取消与聚合逻辑。
- **锁只护前置段**：与澄清流式轮同口径，会话锁只包「幂等落 user 消息 + 自动压缩」，LLM 流不持锁；轮数用 `round_count = COALESCE(round_count, 0) + 1` 原子自增，避免锁外快照覆盖并发轮次。

### 助理联网搜索上下文改写 A+B 落地 + 真实链路四场景验收（原 `LOG-20261104`）

#### 背景

### GitHub CI 双红排查与修复（差距表状态词 / 长期记忆单测 / IT 上下文 / JSONB 反序列化）（原 `LOG-20261104-002`）

### 核验双域批次 2 落地（RV-2 三态 / SR-1 受限沙箱工具 / SR-2 自审证据围栏）（原 `LOG-20261104-005`）

#### 问题

1. **`RV-2` 人工审查入口会「自动接受」新枚举值**：`ReviewController` 用 `ReviewResult.valueOf(request.getResult().toUpperCase())` 直转枚举，扩值后人工接口会自动接受 `inconclusive` 并落 `ReviewServiceImpl.createReview` 的 `else` 支路（当驳回处理 + 触发返工），与本项「不返工、转人工」语义冲突。
2. **`RV-2` 会污染既有统计**：`ReviewRecordMapper` 三处 SQL 与 `selectIssuesForStats` 的分母均为 `COUNT(*)`，`QualityProfileUpdater` / `ReviewPortAdapter` 亦为二分判断；不排除 `INCONCLUSIVE` 会稀释放水率、均分与执行者画像。
3. **`RV-2` 单测的 mock 默认值与生产相反**：`SubTaskReviewServiceTest` 的 `reviewProperties` 是 mock，`isVerdictValidatorEnabled()` 默认 `false`，而生产默认 `true`；不显式 stub 会让新用例「看似通过、实际未触发 BLOCK」。
4. **`SR-1` 的上限不能用整轮累计计**：`sandboxToolCallCount(messages)` 是跨全部历史 turn 的累计值，直接比 `N=3` 会「一进收尾轮即超限」；且收尾轮是 `chatModel.call(...)` 直呼，不走主循环，没有「每次工具调用」的钩子时机。
5. **`SR-1` 有观测缺口**：收尾轮绕开 `ChatModelToolLoop` ⇒ 该轮不产生 `TOOL_CALL_*` 事件；排查时必须按「台账有记录、时间线无工具节点」的口径解释，不能假定时间线上有工具节点。
6. **`SR-2` 的解析器在观测旁路上**：证据块解析 / 对账写在收尾轮出口之后，任何异常都不能影响主链；且模型可能把 JSON 包进代码块、或用「部分合法」的证据块试探。

#### 背景

批次 2（`LOG-20261104-005`）落地后，按计划 §5 进入批次 3：`RV-3`（`coverage[]` 契约 + 拆分器 + 静态覆盖批评器 + JSONB 列 + 前端渲染）、`SR-3`（`SelfReviewGate` + `K=1` 有界重跑 + `self_review_failed` 事件）、`SR-4`（`degraded_no_sandbox` 显式降级）。用户指令「批次 3 开始吧」，并要求代码修改符合 `doc/HelloAI_CODE_STYLE.md` 与 `doc/HelloAI_AI开发协作规约.md`。本批同时清掉一处守卫假绿（`check-shell-portability.sh` 在 Windows 上长期恒真）。

#### 问题

1. **覆盖判据不能按「条数相等」**：真机 `sub_task.acceptance` 半角 `;` 全库 0 命中、全角 `；` 命中 9 条、圈号仅 5 条，且存在条目内嵌套 `；` 的样本 ⇒ 按分号拆分必然过拆或整段当 1 条，计数判据几乎恒假 ⇒ 全量转人工。
2. **两份归属判定易漂移**：`coverage.criterionRef` 与既有 `missingEvidence.acceptanceRef` 是同一件事（验收标准原文子串），各写一份匹配逻辑，日后必分叉。
3. **批评器会把「如实申报」误判成「多余条目」**：首版按「coverage 条目未被任何拆分项命中 ⇒ `extraneous`」实现，把 reviewer 诚实填的 `failed` / `not_verifiable` 条目也报了出来，3 条单测当场失败（期望 `acceptance_not_covered` 却多出 `coverage_extraneous`）。
4. **BLOCK 与 WARN 的先后不可依赖装配顺序**：调用方与单测按 `findings.get(0)` 断言最严重项，而 `contractFindings` 与 `gapFindings` 的拼装顺序并非严重度顺序。
5. **`RV-3` 的「整段不填」计划未定义**：计划只写「命中即 `INCONCLUSIVE`」，没定 `coverage` 缺失算什么。判 `Warn` 等于本项无拦截面（模型不填就能过），判 `Block` 又会把通过大量转人工——缺一个能单独关掉的回滚面。
6. **`SR-3` 的重跑会顶替正文**：收尾轮历史上出过「重跑那一轮重写正文、把已采纳交付物顶掉」的回归（2026-10-16 系列），闸门重跑若沿用同一指令等于复活该缺陷。
7. **`SR-3` 重跑轮失败会丢交付物**：重跑那一轮调用失败 / 空产出时，若按首轮逻辑退回草稿，就丢了上一轮已判定合格的产出。
8. **`SR-4` 降级标签与不合格标签混用即口径污染**：沙箱关时若仍写 `missing`，统计上就把「平台没给一手证据机会」算进「模型自审不合格」，反过来也会把沙箱关着的自述算进「已自审」。
9. **单测 mock 的开关默认值与生产相反**：`SubTaskReviewServiceTest` 的 `reviewProperties` 是 mock，未打桩的 `isCoverageCriticEnabled()` 返回 `false`，生产默认 `true` ⇒ 新用例「看似绿、实际没触发批评器」。
10. **守卫自身在 Windows 上假绿（两处）**：① `command -v python3` 命中 Microsoft Store 存根（有路径、零输出、退出码 49），原判定「解释器存在」即放行；② 反证注入物用 MSYS 绝对路径（`/e/...`），Windows 原生 python 的 `isfile` 打不开 ⇒ 注入物不存在 ⇒ 三条 `--inject-*` 断言恒真（全部 `exit 0`，本该非 0）。

#### 决策

- **覆盖判据用「子串双向归属」**：拆分项与 `criterionRef` 任一方包含另一方即算命中，对分隔符风格不敏感；与 `acceptanceRef` **共用** `ReviewVerdictValidator#isGroundedIn`，一份逻辑两处用。计数（`extraneous`、重复 ref）只作 `Warn`，不作 `INCONCLUSIVE` 判据。
- **拆分优先级钉死**：圈号 `①~⑳`（U+2460~U+2473）优先且**条目内 `；` 不再拆**；全角 `；` 仅作 fallback；半角 `;` 永不参与；上限 20 项、单项 500 字符。
- **「合格覆盖」与「文本归属」分离**：`extraneous` 只看文本归属，不看 `status`/`method` ⇒ reviewer 如实申报的 `failed` 条目不被冤枉成多余条目；同一条坏引用只报一次更精确的码（`coverage_ref_not_grounded` 优先于 `coverage_extraneous`，不重复报）。
- **结果按 BLOCK 优先稳定排序**：由 `findings.sort(Comparator.comparing(severity != BLOCK))` 保证，而非依赖装配顺序。
- **批评器只在 `pass == true` 侧产 BLOCK**：把一条确定的驳回升级为 `INCONCLUSIVE` 会丢掉确定结论，是最坏的取舍。
- **`coverage` 整段缺失按 BLOCK（`coverage_absent`），回滚面是独立开关 `helloai.review.coverageCriticEnabled`**：不放宽判据——判据一放宽本项就没有拦截面。关闭后 `coverage` 仍解析、仍落库（纯观测），只是不参与判定。
- **`SR-3` 重跑指令只要求补证据、显式要求保持正文与围栏结构不变**：重跑目的是让一手证据到位，不是再要一篇新正文。
- **`SR-3` 重跑轮不采信时沿用上一轮已采纳产出**（不退回草稿）：上一轮内容已合格可交付，补不上证据不能把已有的弄丢。
- **`SR-3` 判据取严**：「可执行交付物」关键词只列名词，不列「运行 / 执行」动词（实测「执行摘要」高频出现，会把文档类系统性判成档 1 并触发无谓重跑）；档 2（文档类）只校验形态，缺失/空数组不拦。
- **`SR-4` 用独立标签 `degraded_no_sandbox` 且该档位闸门不判**：没有一手证据可对账时强行判，会把「沙箱没开」伪装成「模型自审造假」。
- **JSONB 三件套按本仓真机口径**：`@TableName(autoResultMap = true)` + `@TableField(typeHandler = PgJsonbTypeHandler.class)`，不照抄计划写的 `JacksonTypeHandler`（本仓无该调用点）。
- **守卫自证优先于守卫结论**：把「解释器存在」升级为「解释器真能跑出一句已知输出」，把「清单有条目」升级为「清单每一项都真被读到」（`len(entries) != n_files` 即报红），杜绝「断言恒真伪装成全绿」。

### 全量测试第一轮（内部 LLM + 外部 CLI Agent）：两处缺陷修复 + 一处日志订正（原 `LOG-20261105-001`）

#### 背景

用户要求对核验双域改造做全量测试，覆盖内部 LLM 与外部 AI Agent。本机库基线：`APPROVED 79 / REJECTED 31 / INCONCLUSIVE 3`，其中带快照的仅 2 条（V141 之后产生）。今日按矩阵执行：T1 正常通过、T2 驳回路径、T3 沙箱回执、T4 外部 CLI 主链、T5 外部失败回执；外部 agent 侧 `trae-excutor`、`workbuddy-executor` 已打卡在线。

#### 问题

1. **`T3` 拆解被验收判据分类器误杀**：验收原文「判定动作 1：正文…字符数 ≤80…；判定动作 2：…出现次数 ≥1…」被判 `STRUCTURAL 不匹配`（`task_plan_failed`）。根因：`AcceptanceKindValidator.COUNTABLE` 只认「数字 + 单位」，
　比较符 + 数字（`≤80` / `≥1`）不含单位 ⇒ 判「无可数量词」。属**假阴性**（误拒正当验收）。
2. **外部失败回执的 timeline 仍无线索**：`LOG-20261104-015` 只修了对话流与 `context.lastExecution.error`；实测 `subTaskCommandPort.block(subTaskId, null, null)` 仍写空原因 ⇒ `sub_task_report_blocked.reason=""`、`sub_task_execute_failed.error=null`，时间线上依旧看不到为什么失败。
3. **`T2` 的第一条子任务落 `INCONCLUSIVE`**：批评器命中 `unconfirmed_silently_dropped`（执行侧申报的 UNCONFIRMED 在 reviewer 判定中无声消失）——属规则设计内的拦截，但会把整条任务停在 REVIEW 等人工裁决。
4. **日志订正（`LOG-20261104-012` 问题②）**：原文记录「两个子任务的 `depends_on` 指向一个不存在的子任务 ID」。复核证明**不成立**：MCP 查询层对 64 位整数按 double 显示（`…3457` → `…3500`），库里实际是正确的真实 ID（`depends_on::text` 逐字核对）。后续核验 64 位 ID 一律用 `::text`。

#### 决策

- **验收判据分类器补「比较符 + 数字」**：`≤ / ≥ / < / > / ＜ / ＞` 后跟数字也算可数量词；不放宽其它分支（无单位复述仍按原规则）。
- **失败原因单源**：失败链统一用 `failureReason(report)`（原始 error → finishReason 兜底）写入 `block` 原因与 `sub_task_execute_failed.error`，与对话流、context 同一文本，避免四处各写一份。
- **`INCONCLUSIVE` 不自动放行**：保持「转人工」语义；`T2` 的后续子任务停在 PENDING 是预期后果，由人工裁决推进。

#### 实现

- `AcceptanceKindValidator`：`COUNTABLE` 增 `[≤≥<>＜＞]\s*\d+|(不超过|不低于|不多于)\s*\d+`；`AcceptanceKindValidatorTest` 17 → 18（真机原文用例）。
- `ExecutionResultHandler`：`block(...)` 由 `(null, null)` 改为 `(failureReason, agentId)`；`sub_task_execute_failed` payload 的 `error` 由原始值改为 `failureReason`；`ExecutionResultHandlerTest` 更新 3 处断言 + 扩展外部失败用例断言两个时间线载荷。
- 无数据库迁移；无前端改动。

#### 验证

- `T2`（驳回路径）：planner 识别「验收条件①与②互斥」并改写为「出具不可满足判定」的 4 条子任务，未产生 `REJECTED`；第一条执行后落 `INCONCLUSIVE`（`unconfirmed_silently_dropped`），后续 PENDING → 规则按设计生效，`REJECTED` 样本仍缺。

### 个人工作台「选模型 / 活跃 Agent」口径修订（设计稿落地，前后端贯通）（原 `LOG-20261105-002`）

#### 背景

用户就「个人工作台」截图指出两处语义错误：①「可选的模型」应当只是**已注册的 LLM 模型**，且**工作台与新建页面不同**——新建页选的是**带角色的 Planner**，工作台选的是**无角色**的纯模型，注册且有效即可选；②「活跃 Agent」指**带角色的 Agent**（内部 LLM 或外部 AI Agent），但**外部 Agent 必须有心跳在线**，内部 LLM **常驻在线**、空闲状态显示「待命中」，干活时按实际状态显示（审核中 / 执行中）。

按此出设计稿（Ardot 画布 `744054948241116`：`2:1` 修订稿 + `2:292` 规则对照），再按 `HelloAI_AI开发协作规约.md` / `HelloAI_CODE_STYLE.md` 落地前后端。

#### 问题

1. **工作台 Composer 的「规划者」下拉是语义错位**：它调 `/listPlannerOptions`，候选来自 Agent 名册（仅 `PLANNER` + `API_KEY_LLM` + 在班校验）——用户在「选模型」的位置上实际在选一个**角色**，而名册里根本没有「无角色的已注册模型」这一维。
2. **活跃 Agent 把离线外部 Agent 也算作「活跃」**：名册取 `listActiveProfiles()` 后按角色过滤，不看心跳 ⇒ 离线外部 Agent 照样列在「活跃」里，用户点了也派不进去（等于给一个按不动的按钮）。
3. **「选了模型」到不了执行**：执行链以 `Agent` 为模型与凭证的载体（`PlatformAgentExecutionService` 全入口），会话上没有「本轮用哪个模型」的位置，选完也无处落地。

#### 决策

- **两套候选集分离，不共用下拉**：工作台「选模型」= `llm_provider_model` 注册表（新端点 `GET /requirement-conversations/listLlmModelOptions`）；需求对话页「选 Planner」= Agent 名册（既有 `/listPlannerOptions`）。同一份「有效」判定**只在 agent 域 `LlmProviderCatalogService` 一处**（`isModelAvailable × isProviderAvailable`），planner 域只转发不重算（判据「判断依据属于谁，判定就由谁做」／「同一事实双写必分叉」）。
- **「选模型」不改 `AgentTask`，改执行入参 Agent**：新增 `AgentModelPin.pin(agent, modelType)`——返回原 Agent 的**游离副本**并覆盖 `modelType`，凭证按 `modelType` 前缀解析供应商（`AgentLlmCredentialResolver`），故「用 A 家密钥调 B 家模型」不会发生。反方案（给 `AgentTask` 加 `modelType`、四类执行器各自判覆盖）影响面横跨四类执行器与 Runtime 上下文装配，属「为一条会话链改造整条执行链」，与最小变更原则冲突。
- **会话钉住落在会话行**：`requirement_conversation.model_type`（`V142`），**NULL = 沿用 Planner Agent 绑定模型**（老数据零变化）。切换用 `lambdaUpdate` 定点 `set`，**不整行 `updateById`**——后者会覆盖并发自增的 `round_count`。
- **可见性按接入类型分两类，不按心跳一刀切**：内部 LLM 常驻在线恒可见（它没有外部进程需要报活）；外部 Agent 须 `ONLINE`/`IDLE`。隐藏者**不静默**——`hiddenOfflineAgents` 单独回传条数（**不能让前端做「总数 − 可见数」**：名册里混着内部 LLM，减法会把常驻在线的内部 LLM 算成「被隐藏的外部 Agent」）。
- **失效模型不下发**（2026-11-05 修订，见 `LOG-20261105-003`）：无 API Key、供应商已下架、模型已停用的一律不进候选集，由服务端过滤并记 debug 日志；「为什么少了某个模型」由下拉底部的维护指引统一回答。
- **工作台不再选 Planner**：`streamAssistantCreate` 的 `plannerAgentId` 一律传 `null`（= 系统自动挑助理），角色的选择权收归需求对话页。

### 工作台模型下拉：默认值订正、候选集过滤、面板对齐设计稿（原 `LOG-20261105-003`）

### 工作台对话体验 PA-13~PA-17 落地与真机验收（原 `LOG-20261105-004`）

### 工作台主内容列宽令牌化 + 大屏三档扩展（原 `LOG-20261105-005`）

#### 背景
