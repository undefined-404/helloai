## 0. 定位与边界（★先读）

**本方案做什么**：把 OpenSandbox 沙箱从「契约已备、未被消费」变成「执行链已接、真正执行验证」——给内部 LLM（自检）与 Reviewer（验证脚本）注入一个 `internal_run_in_sandbox` 工具，走 `SandboxProvider.execute` 在 OpenSandbox 容器内执行命令 / 脚本，读取 `ExecuteResponse` 判定 pass/fail。这是用户指令「让沙箱真正参与『自检 / Reviewer 验证脚本』」的落地。

**本方案不做什么**（边界，防越界）：

1. **不触发 `G-005` 重新排期（整体）**——`G-005` 三个触发条件（① 碰宿主工具 / ② 技能包被执行 / ③ 平台自持浏览器）**仍均未命中**：本方案新增的是「在 OpenSandbox 容器内执行」，**不碰宿主**（容器文件系统 / 网络 / 资源隔离由 OpenSandbox server 强制，`ExecutionPolicy.openSandbox()` 诚实标注），不是「平台增加碰宿主工具」。但**需在差距表 G-005 行补注事实**：「沙箱执行链已接线，作为受控验证通道」——见 §7 差距表更新。
2. **不把 `docker.sock` 挂进 app 容器**（既有裁定 `D-2026-10-09-4③` 不变）——执行走 OpenSandbox server HTTP API + `api_key`，app 仍不加入 `opensandbox-net`。
3. **不引入「技能包被执行」语义**——`internal_run_in_sandbox` 只执行「LLM/Reviewer 现场写的验证命令或脚本正文」，**不执行**技能包正文（`REF-1.6` 只做安装/解析/校验，`internal_load_skill` 只读正文，两者都不把技能脚本送进沙箱执行）。技能脚本执行是 `G-005` 条件②的独立议题，本方案不越界。
4. **不开放给外部持牌 Agent**——`internal_` 前缀 + `requireInternalChain()` 闸门（`InternalLlmExecutorTools`）保证**仅内部执行链可调**，外部 MCP `tools/list` 不可见（`InternalToolCallbacks` 非 provider 承载）。
5. **不改变既有 3A 判定语义**（方案 C 边界）——S-9 只对「报告声明可执行文件交付物」的场景追加确定性判定；无脚本交付物时 `FinalReportFidelityGate` 行为逐字不变（`FinalReportFidelityChecker` 纯静态不动，注入经 Gate 扩展点，RM12 裁定同款）。

**诚实边界**：本方案让沙箱**参与**自检 / Reviewer 验证，但**不改变判定权威**——沙箱执行结果是给 LLM / Reviewer 看的**证据**，最终 pass/fail 仍由 LLM / Reviewer 判定（对齐 octop-harness：执行返回统一 `ExecuteResponse`，判定在消费方）。沙箱是「证据提供者」，不是「判定者」。

**默认关闭**：`helloai.sandbox.opensandbox.enabled` 默认 `false`（对齐 `REF-6.13` 新能力默认关闭）；开启后才给内部执行链注入 `internal_run_in_sandbox` 工具。

## 1. 调研对照（为什么这么做是对的）

### 1.1 开源沙箱功能调研结论（`[实测]`，来源 research 文档 + 本方案 §1.2 知名产品）

| 能力 | octop-harness（容器沙箱） | DSH（进程监禁） | OpenSandbox（我们的引擎） |
|---|---|---|---|
| 执行通道 | `BackendProtocol.execute` | 每次调用携带策略执行 | SDK `commands.run` |
| 统一返回 | `ExecuteResponse(output, exit_code, truncated)` | 结构化输出 | 命令输出 + 退出码 |
| 超时约定 | `command_timeout=120s` → exit 124 | 同 | 可配 `timeoutSeconds` |
| 网络隔离 | `network_mode="none"`（默认断网） | `network_access=false` 默认 | `networkPolicy.defaultAction=deny` |
| 环境继承 | 不继承宿主 + 白名单 key | 同 | 零平台凭据 env（`credential=ISOLATED`） |
| 探针 | write→read→delete 回环 | 同 | 已落地（S-4） |
| 生命周期 | `close` 解绑 vs `destroy` 销毁 | 每次调用即建即毁 | `close()` vs `kill()`（SDK） |

**结论**：HelloAI 的引擎（OpenSandbox）与 octop-harness 是**同一档**（容器级隔离，`filesystem/resource/credential=ISOLATED`）。差别只在**集成深度**——octop-harness 把沙箱当「执行通道」直接跑 agent 代码；我们目前是「契约已备、执行链未接」（`observeSandbox` 只打日志）。本方案就是补上这一档：**把沙箱接成内部 LLM / Reviewer 的受控验证执行通道**。

### 1.2 知名产品沙箱能力调研（`[外部]`，WebSearch 实测 2026-10-17）

#### Claude Code（Anthropic）

- **sandboxed Bash 工具**（`[外部]` Anthropic 官方工程博客 + docs）：基于 **bwrap（Linux）/ Seatbelt（macOS）**；文件系统隔离（默认写 CWD、读全盘、禁改外部）+ **网络隔离**（unix socket 代理，白名单域名）。
- 关键数字：沙箱化后**减少 84% 权限提示**；`/sandbox` 命令启用；`sandbox.failIfUnavailable` 硬门禁（沙箱不可用即失败，不静默降级）。
- **给我们的启示**：沙箱参与「命令执行」是产品级基线；文件系统 + 网络双隔离是标配；fail-closed 是安全底线。

#### Codex CLI（OpenAI）

- **三种 sandbox mode**（`[外部]` GitHub README + 深度拆解）：
  - `workspace-read`（只读）/ `workspace-write`（读写工作区）/ `network`（白名单联网）；默认 `workspace-write` + **网络全禁**。
- **approval policy 四档**：`untrusted` / `on-failure` / `on-request` / `never`——与沙箱模式**可独立配置**（如 `--sandbox read-only --ask-for-approval never` 用于 CI）。
- 平台机制：macOS Seatbelt / Linux Landlock+seccomp；容器化环境推荐 `danger-full-access`（容器即沙箱）。
- **给我们的启示**：沙箱模式 = 权限范围（不是能力）；approval policy 与 sandbox 正交；CI/自动化场景用「只读沙箱 + 不询问」。

#### WorkBuddy（腾讯）

- **Bash 命令沙箱**（`[外部]` 官方文档）：AI 操作与真实系统**严格隔离**；文件系统隔离（只能访问预先授权的工作空间目录）；**防沙箱逃逸**（阻止对配置文件的写入）；默认只读，编辑/运行需显式批准。
- 三层权限规则 `allow / ask / deny`；「完全访问」是全局开关用完即关。
- **给我们的启示**：沙箱默认只读 + 越界需确认是产品基线；「防沙箱逃逸」是明确的产品安全项。

### 1.3 与 deepseek harness 沙箱功能对照

DSH 的核心 = **进程监禁**（bwrap/Landlock/Seatbelt/ACL）——同主机进程级隔离，每次调用携带 `read-only / workspace-write / danger-full-access` 三档策略，禁止无监禁放行（fail-closed）。

**HelloAI 对照**：我们用 **OpenSandbox 容器**（更强的隔离轴——独立文件系统 + 资源限制 + 零凭据），对齐 DSH 的三个设计要点：

| DSH 要点 | HelloAI 对应 |
|---|---|
| 每次调用携带策略（三档） | `internal_run_in_sandbox` 入参携带 `command` + `timeoutSeconds`，沙箱规格由 `OpenSandboxProperties.spec` 声明（网络默认 deny） |
| 禁止无监禁放行（fail-closed） | 沙箱不可用 / 未启用 ⇒ 工具从模型可见列表**摘除**（`toolAvailability()=false`，对齐 Codex `failIfUnavailable` 硬门禁） |
| 进程效果监禁 | 容器级隔离（`ExecutionPolicy.openSandbox()` 诚实标注：filesystem/resource/credential=ISOLATED） |

## 3. 方案设计

### 3.1 总览：给内部 LLM / Reviewer 注入 `internal_run_in_sandbox`

```text
【自检链 / Reviewer 链 复用同一执行通道】

内部 LLM（子任务执行）                    Reviewer（子任务核验）
      │                                        │
      ▼                                        ▼
RuntimeTurnExecutor                    BusinessSurfaceLoopRunner
      │  bind(agentId,subTaskId)              │  bind(...)
      ▼                                        ▼
┌──────────────────────────────────────────────────────┐
│   AgentLoop（工具循环）                                │
│    模型可见工具 = ToolRegistry.resolve 结果            │
│      ├─ internal_get_sub_task_detail ...（既有 9 个）  │
│      └─ ★ internal_run_in_sandbox（本方案新增）        │
└──────────────────────────┬───────────────────────────┘
                           │ 调用 internal_run_in_sandbox
                           ▼
               InternalLlmExecutorTools.runInSandbox(...)
                           │  requireInternalChain() 闸门
                           ▼
                  SandboxExecutionService（本方案新增）
                           │  SandboxProvider.execute(context, command)
                           ▼
                  OpenSandboxSandboxProvider.execute(...)
                           │  SDK：create/resume → commands.run → kill
                           ▼
                 ExecuteResponse(output, exitCode, truncated)
                           │  （超时 → exitCode=124）
                           ▼
                  返回模型 / Reviewer 判定 pass/fail
```

### 3.2 新增工具定义

```java
/**
 * 内部执行链 / Reviewer 在沙箱内执行验证命令或脚本（S-7）。
 */
@Tool(name = "internal_run_in_sandbox", description = """
        【何时使用】需要执行一段命令或脚本以验证产出（自检：验证脚本跑通；Reviewer：
        验证脚本确实能通过目标缺陷）时调用。
        【Gotchas】
        - 命令在 OpenSandbox 容器内执行：默认禁网（egress 白名单外不可达）、零平台凭据 env、
          文件系统/资源/进程受容器隔离——执行不可信脚本的安全边界
        - 返回 {output, exitCode, truncated}；exitCode=124 表示命令超时（默认 30s）
        - 不能访问宿主文件系统 / 平台凭据 / 外部网络（白名单外）
        - 不执行技能包正文：只执行本调用传入的命令/脚本正文
        - 沙箱未启用时本工具不会出现（fail-closed，不静默降级）
        【相关工具】internal_get_sub_task_detail
        """)
public Object internalRunInSandbox(
        @ToolParam(description = "内部执行链鉴定的执行者 Agent ID（平台自动注入）", required = false) Long agentId,
        @ToolParam(description = "目标子任务 ID（平台自动注入）", required = false) Long subTaskId,
        @ToolParam(description = "要在沙箱内执行的命令（bash -lc 语义）或脚本正文", required = true) String command,
        @ToolParam(description = "命令超时秒数（默认 30，上限 300）", required = false) Integer timeoutSeconds) {
    ToolInvocationContext.Ids ids = requireInternalChain();
    return sandboxExecutionService.execute(ids.subTaskId(), command, timeoutSeconds);
}
```

### 3.3 新增服务 `SandboxExecutionService`

**职责**：单一执行通道——「把命令交给沙箱执行并返回统一结果」。屏蔽 SDK 细节，供 `InternalLlmExecutorTools` 调用。

```java
public interface SandboxExecutionService {
    /** 执行一次沙箱命令；返回统一执行结果（超时/失败也结构化返回，不抛异常）。 */
    ExecuteResponse execute(Long subTaskId, String command, Integer timeoutSeconds);
}

/** 统一执行结果（对齐 octop-harness ExecuteResponse 三字段）。 */
public record ExecuteResponse(String output, int exitCode, boolean truncated) {
    public boolean succeeded() { return exitCode == 0 && !truncated; }
}
```

**实现要点**：

1. **入口守卫**：`enabled` 配置（`helloai.sandbox.opensandbox.enabled`）为 false ⇒ 抛 `BizException`（工具已摘除，正常情况下不会被调用；此处是纵深防御）。
2. **超时兜底**：命令默认 `timeoutSeconds=30`（上限 300），OpenSandbox server 命令超时返回 `exitCode=124`（对齐 octop-harness）。工具自身用 `CompletableFuture` + 超时兜底，避免 SDK 调用悬挂。
3. **输出截断**：返回前截断到配置上限（默认 100KB，对齐 octop-harness `max_output_bytes=100_000`），`truncated=true` 标注。
4. **失败也结构化返回**：SDK 调用异常 ⇒ `ExecuteResponse("<err>", -1, false)`，不抛异常（与 `SandboxProvider.resolve` 的 null 语义一致的容错哲学）。
5. **生命周期**：复用 `OpenSandboxSandboxProvider` 的 scope=agent 语义——同一 Agent 复用同一沙箱（对齐 REF-3.5），执行结束后**不自动销毁**（显式回收，对齐既有裁定）。但**沙箱存活用短 TTL + 独立 scope**（见 §3.4 安全纵深）。

### 3.4 安全纵深（对齐 Claude Code / Codex / WorkBuddy 产品级基线）

| 维度 | 措施 | 对齐 |
|---|---|---|
| **fail-closed 工具摘除** | 沙箱未启用 / 不可达 ⇒ `internal_run_in_sandbox` 从模型可见列表**摘除**（`ToolCallbackContributor.toolAvailability()` 返回 false），模型看不到就不会编造调用 | Claude Code `failIfUnavailable`、Codex `danger-full-access` 兜底 |
| **执行链绑定闸门** | `requireInternalChain()`：仅内部执行链可调；外部 MCP 不可见、不可执行 | WorkBuddy `allow/ask/deny` |
| **凭据隔离** | 沙箱容器零平台凭据 env（`ExecutionPolicy.openSandbox()` credential=ISOLATED）；`HELLOAI_CREDENTIAL_AES_KEY_BASE64` 绝不进沙箱 | WorkBuddy 敏感保护 |
| **网络隔离** | `networkPolicy.defaultAction=deny`（默认禁出）；egress 白名单按需放行 | Codex 默认断网、Claude Code 代理白名单 |
| **资源限制** | `resourceLimits(cpu=500m, memory=512Mi)`（OpenSandbox server 强制） | octop-harness 512m/1CPU |
| **超时上限** | 命令默认 30s、上限 300s（`exitCode=124` 语义） | octop-harness 120s |
| **输出截断** | 100KB 上限 + `truncated=true` | octop-harness 100KB |
| **短 TTL + 独立 scope** | 执行用沙箱短 TTL（如 15min）+ 每次执行独立 command scope，不跨子任务共享（防「上一个子任务的残留文件影响下一个」） | octop-harness `sandbox_scope` |
| **命令级守卫（后置增强）** | 危险命令 YAML 规则引擎（block/warn/require_approval 三态）——**本方案不落地**，登记为 **S-10 后置项**（待执行通道被真实业务高频使用后评估误用面再启动，对齐 REF-8.9 独立预算闸同款处置） | octop-harness 危险命令规则引擎 |

### 3.5 判定语义（沙箱是证据提供者，不是判定者）

- **内部 LLM 自检**：`internal_run_in_sandbox` 返回 `ExecuteResponse` → 模型自己把「命令输出 / exitCode」写进 VERIFICATION 围栏（既有 `REF-8.2.2` 验证证据围栏）→ 平台按既有出口分类判定。
- **Reviewer 验证**：`subtask-review.md` 核验 Prompt 新增一条指引——「当交付物含脚本 / 可执行文件，且你怀疑脚本是否真能通过验收标准时，可调 `internal_run_in_sandbox` 执行验证命令，把输出与退出码作为核验证据」。Reviewer 据此把沙箱执行结果写进 `analysis` / `issues`，判定仍走 `VerdictParser`。
- **不改判定权威**：沙箱执行失败 ≠ 自动驳回（可能命令写错）；沙箱执行成功 ≠ 自动通过（可能测的是无关属性）。`ExecuteResponse` 只是给判定者的**一手证据**。

## 5. 可选路径与复杂度（用户已裁定方案 C）

### 方案 A：沙箱执行通道 + 工具接线（S-7 + S-8）

- **形态**：`internal_run_in_sandbox` 工具，内部 LLM / Reviewer 在循环里直接调。
- **复杂度**：中（~1 服务 + 1 工具 + 授权集 + Prompt 指引，纯 Java，无新基建）。
- **收益**：自检 / Reviewer 真正拿到「执行一手证据」——对齐开源 / 知名产品基线。
- **风险**：沙箱执行可能被 LLM 滥用（无脑调、写恶意命令）——用 `requireInternalChain()` 闸门 + 默认关闭 + 危险命令守卫后置缓解。

### 方案 B（最小）：只接 Reviewer 验证（S-8 的 Reviewer 半）

- **形态**：只给 `subtask_review` 场景注入 `internal_run_in_sandbox`，执行链（自检）不接。
- **复杂度**：低。
- **收益**：Reviewer 能实测验证脚本（用户指令最直接的「Reviewer 验证脚本」诉求）。
- **局限**：内部 LLM 自检仍无执行通道；后续补自检还要再动一次。

### 方案 C（裁定采纳）：全链路 + 判定接入

- **形态**：方案 A + 把沙箱执行结果接入 `FinalReportFidelityChecker`（机械判定「脚本类交付物是否可执行」）+ 探针自动纳入验证集。
- **复杂度**：高。
- **收益**：机械层也能用沙箱，判定更硬。
- **风险**：判定接入牵动评审主链，回归面大——**已用「纯静态 checker 不动、Gate 扩展点注入」缓解**（RM12 裁定同款），无脚本交付物时行为零变化。
