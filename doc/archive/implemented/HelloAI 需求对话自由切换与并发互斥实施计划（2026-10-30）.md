# 0. 定位与边界（★先读）

## ① 问题来源

- **用户反馈**：需求对话页（`RequirementChat.vue`）被顶层的全局 `sending` 闸门锁死——任一会话对话轮在跑时，其他会话一律不可切换、不可新建、不可发送（`sending` 为组件级 `ref`，`selectConversation` / `startNew` / `handleSend` 三处在 `sending===true` 时直接 `return`）。用户以 DeepSeek / Kimi 网页版可自由切换为参照，要求具备同等「多会话自由切换」体验。
- **并发竞写风险**：后端 `roundCount` 的「读 → +1 → 写回」在同步前置段**非原子**（`readRoundCount → addMessage(seq=max+1) → setRoundCount(+1) → updateById`）。自由切换放开前端闸门后，同一会话被并发请求命中该前置段即产生竞态（seq 错序 / roundCount 丢更新）。这是「自由切换」拆掉前端闸门后**必须后端兜底**的原因。
- **ADR-007 §6（2026-10-30 收口）** 在技能执行面已预告：启动清扫的「单实例前提」一旦上多副本必须改 owner/心跳；本专项的 `B`（每会话互斥）正是该多副本前提的配套骨架，两者同部署面。

## ② 本计划做什么

一段话目标：在**保持既有对话语义不变**的前提下，把需求对话页的「全局发送/切换闸门」拆成**每会话独立状态**（A），并在**后端为每个会话加一把跨实例互斥锁**（B），实现「多会话可自由切换、同会话不被并发竞写」，且**先落后端 B、再落前端 A**。

具体产出（3 条）：

1. **B（后端互斥）**：所有对话轮通道（流式 `streamRound` / `streamCreate`、同步 `sendMessage` / `doRound`，含技能轮 / 任务直达 / 转澄清等内部 round 出口）的**同步前置段**统一持一把每会话 Redisson RLock，抢占失败即拒，杜绝同会话并发竞写。
2. **A（前端自由切换）**：顶层流式态（`streamText` / `thinkingText` / `processSteps` / `streamBuffer` / `streamAbort`）重构为 `Map<conversationId, PerConversationStream>`；`sending` 从全局降级为「仅当前会话」，切换 / 新建 / 发送不再被其他会话的进行中轮拦死。
3. **验证与登记**：后端单测 + 前端真机验收，验收通过后按治理规则登记差距表 / 文档引用。

## ③ 本计划不做什么（边界，防越界）

| # | 不做什么 | 为什么 | 依据 |
|---|---|---|---|
| 1 | 不改命令 / 技能「暂不支持流式」的既有限制 | 命令（`/planner` `/task`）与显式技能（`[skill:name]`）流式通道要回读返回值做联动，本专项不改该协议契约 | `ClarifyStreamServiceImpl.runStreamRound:97-103` 既有守卫；属另一需求域 |
| 2 | 不引入 MQ / 消息总线做会话串行化 | 互斥点只在一把 Redis 锁即可覆盖，不引入新的基础设施面 | 治理规则——最小改动 |

## ④ 诚实边界

- 落地 **B ≠ 证明多副本已可用**：RLock 依赖 Redis 高可用；锁只是「并发不竞写」的机制保证，**多副本的完整拓扑 / owner 心跳 / 故障转移仍未实测**——本计划只验「同会话并发请求被正确互斥（单实例 / 直连 Redis 环境）」，多副本实测登记为未达成项，不提前宣称。
- 落地 **A ≠ 所有切换竞态消失**：前端 `sending` 降级为「仅当前会话」后，**同会话内**的并发仍由后端 B 兜底；跨会话各自独立互不干扰。前端侧的瞬间竞态（如连点发送）仍依赖既有 `skillRunId` / 确认卡等守卫。
- **C1 档对外表述纪律**：本专项验收记录只写「自动化检查通过；未经视觉复核」——`SKILL.md` 承诺的 browser-check 门本专项未过，不宣称「已视觉复核」。

# 4. 关键设计决策

## 4.1 B 的临界区只覆盖同步前置段，不跨异步 LLM 流

**结论**：锁只在「读 `roundCount` → `addMessage` → `setRoundCount` → `updateById`」的**同步前置段**持有，unlock 后再入 `runChatStream` / `runClarifyStream` 的 LLM 流段。

**理由**：竞态全部发生在前置段的「读→写」窗口（毫秒~亚秒级），LLM 流段（实测 377s）是单线程消费既有落库消息、不再写 `roundCount`。若把锁扩到流段：① 长流持锁放大故障面（一个慢 LLM 卡死整个会话）；② 引入 **SSE abort / `onTimeout` 跨线程 unlock** 的边界问题——本专项刻意避开该复杂度。

**后果**：锁 TTL 只需盖住毫秒~亚秒级前置段（取 30s 兜底崩溃残留），**不需要**技能执行那种 600s 长租期（对比 `FinalReportReviewLock.TTL_SECONDS=600`）。

**对齐**：`onErrorResume` / 流前段抛错路径不在持锁窗口（先解锁或未抢到锁即抛，保证 `unlock` 必成对、无泄漏）。

## 4.2 为什么用 RLock 而非仅 CAS

**结论**：B = Redisson RLock（用户裁定）。

**理由**：① 部署形态已拓宽为 **k3s 多副本**——CAS（`updateById ... where round_count=old`）在 DB 行层面行为人原子，但「加新消息 + 自增轮数」是**跨表多写**，用 DB 行级原子无法一次覆盖「消息 seq 分配 + 会话轮数」的组合；一把会话级 Redis 锁把「前置段」整体串行化，直观且语义单一。② 项目已有 Redisson 锁先例（防双审 `FinalReportReviewServiceImpl`），依赖已存在（B-8）、范式可复制（B-5/B-6）。③「抢占失败即拒」与「同会话并发即拒绝」的语义天然匹配。

**代价**：多副本下锁依赖 Redis 可用性；Redis 故障时 `tryLock` 抛异常，`ConversationRoundLocker` **拒绝请求**（抛可读 `BizException`「会话处理锁不可用」并记 ERROR），即 **fail-closed**——不做无锁放行，因为无锁下并发仍会竞写「消息 seq + 轮数」——留 `RC-6` 诚实登记，不提前宣称多副本已实测。

## 4.3 四通道共锁；内部 round 出口一并覆盖

**结论**：流式轮 / 流式新建 / 同步对话轮 /（技能轮 / 任务直达 / 转澄清 / 确认卡）等所有会 `setRoundCount(+1)` 的入口，**共用同一把锁**（`chat:conversation:{id}:round`）。

**理由**：竞写点不只在 `ClarifyStreamServiceImpl`，`ClarifyRoundOrchestratorServiceImplImpl` 的内部 round 出口（B-4）同样自增 `roundCount`。漏任一出口 = 该路径仍可并发覆盖轮数。

## 4.4 `FS-`/`FL-` 等候选号段弃用

**结论**：用 `RC-`，弃 `FS-`/`FL-`。

**理由**：专项 = A（自由切换）+ B（互斥）作为**配对整体**，`FS-`（Free Switch）只覆盖 A 半边、语义过窄；`FL-`（Flow）过泛。`RC-`（Requirement Chat）覆盖「需求对话页」这个整体主题，与先例（`SKX-`=技能执行面、`ATT-`=附件、`TD-`=拆解）同构。

## 4.5 锁内必须读最新行；流式态的值必须响应式（2026-10-30 审计修订）

**结论一**：持锁只保证「同一时刻只有一个执行者」，**不保证**「执行者手里是最新行」。
`requireActive` 在锁外取实体、锁内直接 `+1` 回写，等于把「锁外的读」和「锁内的写」拼成一个非原子序列——
两路请求先后进临界区，后到者仍可能拿旧 `roundCount` 覆盖前者。故所有自增统一走锁内 `getById` 重读
（`latestRoundCount`），锁只负责串行、最新行负责正确。**别处已按此写的（`enterClarify`）是正例，本次向其看齐。**
锁外/锁后只改局部状态的写（确认卡前置、确认卡落待确认标记）**一律定点 `lambdaUpdate`**，
整行 `updateById` 只允许出现在「手上有锁内最新行」的位置——否则它会顺带把 `round_count` 写回旧值。

**结论二**：`Map` 化只解决「状态放哪儿」，不解决「值变了视图知不知道」。`streamStates` 里的普通对象不被 Vue 追踪，
打字机/思考区/展开全部静默失效——**容器隔离与值响应式是两件事，要分别验证**（探针：写值后看 DOM 是否变化）。

# 5. 依赖与实施次序

```text
RC-1（后端锁·实现）──→ RC-2（错误语义）──→ RC-3（后端单测）
                                                      │
RC-4（前端 Map 化）──→ RC-5（前端闸门降级）──→  RC-6（端到端验收 + 登记）
        ↑                                            │
        └─────────────── 依赖 RC-3 打通 B ────────────┘
```

- **先 B 后 A**：`RC-1`~`RC-3`（B）先落地并打通，`RC-4`~`RC-5`（A）在前端闸门拆开前，B 已就位兜住并发——**保证「自由切换」的这个瞬间，后端不会竞写**。
- `RC-3` 单测是「B 已打通」的可执行判据；`RC-6` 验收同时复验 A、B、以及 A-4（技能轮询 per-conversation 守卫）不回归。
- **首个可判断「生效」的节点**：`RC-5`（前端闸门拆开 + 自由切换真实可用）——`RC-4`（Map 化）只是形态重构，闸门没拆用户仍被全局锁着。

# 6. 风险与边界

- **Redis 不可用**：B **不退化**——拿不到锁即拒绝（fail-closed，可读提示「会话处理锁不可用，请稍候再试」+ ERROR 日志），
  因为无锁放行会让「消息 seq + 轮数」继续竞写。已按实测口径订正（2026-10-30 审计，原稿「退化为无锁」与实现不符）。
- **单测跑法**：`mvn -DskipTests=false ...` 显式开启（默认 `skipTests=true`）。
- **不改命令 / 技能流式限制**：见 §0③ 边界 1，属另一需求域。
