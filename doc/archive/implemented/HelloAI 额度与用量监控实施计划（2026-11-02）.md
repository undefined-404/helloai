## 0. 定位与边界（★先读）

**① 问题来源**

- **用户裁定（2026-11-02）**：前置 `V1`~`V5` 复核通过后，裁定「可以进行着手开发了」。
- **差距表锚点**：`G-026`（LLM 额度与用量监控，设计 `Status=Implemented`）。
- **起点事实**：平台同时接入 4 家外部供应商，余额分散在各自控制台；当前「余额」无任何平台入口（`B1`），只有「调用失败」事后感知额度耗尽；密钥零散（`B2`）、无快照缓存（`B3`）、无定时采集（`B4`）、token 数据不可做趋势（`B5`）。详见 §2.2。

**② 本计划做什么**

把「分散在各供应商控制台的余额」变成平台内一个只读悬浮控件里可看、可信、可定位失败的监控面。四项产出：

1. **查得到**：4 家供应商余额查询（`Q-4`，deepseek / moonshot / minimax / 博查，通义不显示）。
2. **查得起**：Redis 快照缓存 + 定时采集，多实例不重复计费流量（`Q-5` / `Q-6`）。
3. **看得清**：只读浮球控件，区分金额型与额度型（MiniMax 百分比），带抓取时间与失败标记（`Q-8`）。
4. **关得掉**：开关可整体停用组件（`sys_config["quota.widget.enabled"]`，`Q-8`）。

**③ 本计划不做什么**（边界，防越界）

1. **不做 AGENT 级凭据余额**（原 `M2`）——需要「谁的 Agent 在花钱」时才逐家查。依据：设计 §6 明确暂缓。
2. **不做调度联动（额度低停止派单）**（原 `M2`）——有真实额度耗尽事故后才可虑。依据：设计 §6；本计划只读不改派单。
3. **不做 MCP 工具 `queryBalance`**（原 `M2`）——需外部 Agent 主动查询需求，且须走 `ToolCallbackContributor` + `ToolRegistry`，默认关。依据：设计 §6。
4. **不做 token 五分量拆分与趋势图**（原 `M2`）——`agent_completed.usage` 现 0 条落库，无数据底座。依据：设计 §6 + `B5`。
5. **不做峰谷价精算**（原 `M2`）——确认 `deepseek-v4-flash` 是否仍适用峰谷价之后。依据：`V4` 裁定 M1 不做。
6. **不做阈值告警（飞书 / 钉钉）**（原 `M2`）——已有 `helloai.alert.*` 通道，可后接。依据：设计 §6。
7. **不显示通义千问余额**（原 `M3`）——无公开接口；提供 AK/SK 签名后才考虑。依据：设计 §6 + 用户裁定。
8. **不新建 Maven module、不建第二张余额表**——`quota` 归 `system` 域其下，只建 `llm_balance_snapshot` 一张。依据：§8 边界。
9. **不做 SSE 增量推、不做 5 分钟轮询**——低频数据建高频通道成本高于收益。依据：设计 §6 + `六、非目标`。

**④ 诚实边界**

- **4 家余额可见 ≠ 额度耗尽联动**：本计划只做「看」，不做「停在派单」。判据「避免额度耗尽事故」不在本计划能力范围内——这是 `M2` 调度联动的范围。
- **通义不出现 ≠ 通义没余额**：只是无公开接口无法查询，列表里不出现不等于金额为 0。
- **百分比 ≠ 金额**：MiniMax 返回的是剩余比例（额度型），**不做换算金额的伪装**（设计 §5 硬约束）；与 deepseek/moonshot/博查的金额型严格分开。
- **成功缓存 60s / 失败缓存 30s 是承诺**：控件展示的是带「抓取时间」的快照，不是实时数字；抓取失败显示上次值 + 失败标记，**绝不显示 0**。

### 2.2 MiniMax 实测结论（`V3`）

**2026-11-02 真机联调**：用真实 API Key 依次请求三个候选 host 的 `GET /v1/token_plan/remains`（`Authorization: Bearer <key>`），结果如下：

| host | HTTP | 结果 | 判定 |
|---|---|---|---|
| `api.minimaxi.com` | 200 | `model_remains[]` + `base_resp{status_code:0,status_msg:success}` | `[实测]` ✅ 主域名（设计原文，鉴权通过） |
| `www.minimaxi.com` | 200 | 结构与上一致 | `[实测]` ✅ 官方别名 |
| `www.minimax.io` | 200 | `base_resp{status_code:2049,status_msg:invalid api key}` | `[实测]` ❌ quotapanel 依赖的失效第三方域，排除 |

**实测返回结构**（与 quotapanel `provider_minimax.go` 完全对齐，`[实测]` `[外部]`）：

- 顶层 `base_resp{status_code,status_msg}` 判错 + `model_remains[]` 按 `model_name` 分组。
- 取 `model_name="general"`（MiniMax-M3 关联项）读取两个**百分比**字段：`current_interval_remaining_percent`（5 小时滚动窗口剩余 %）与 `current_weekly_remaining_percent`（每周剩余 %）。
- 状态字段 `current_interval_status` / `current_weekly_status`，**`==3` 表示不限量**（实测 video 项 `status=3`）。
- 顶层**无** `data.remain` 字段（回退路径在本实测中不命中，结构稳定）。

**实测样例**（本次 key 的 `general` 项）：滚动窗口剩余 **100%**、每周剩余 **100%**，`status=1`；`total_count`/`usage_count` 均 0（套餐未消耗）。

**裁决（据实测定稿）**：

- **base-url 用 `api.minimaxi.com`**（设计原文 = 实测通过），`www.minimax.io` 返回 `invalid api key` 确认排除。
- **结构以实测为准**：`impl/MiniMaxBalanceProvider` 解析 `model_remains` 中 `model_name="general"` 的项，取两个百分比；`status==3` 不限量 → 记为 100%。保留对返回结构的容错（取不到 `model_remains` 或 `general` 项时返回 `failed(reason)`），防止官方结构升级时整家打空不放宽。百分比的**语义不换算金额**（设计 §5 硬约束）。
- 百分比为「额度型」，前端按进度条渲染；百分比本身虽是 0~100 数，UI 语义是「剩余比例」**非金额**，与 deepseek/moonshot/博查的金额型严格分开。

### 2.4 密钥位置（决定 resolver 分两层）

| 供应商 | 密钥位置 | 读取器 |
|---|---|---|
| deepseek / moonshot / minimax | `credential_vault`（`owner_type=PLATFORM`、`credential_type=API_KEY`、`status=ACTIVE`） | `PlatformApiKeyResolver` → `system.port.PlatformApiKeyPort` → agent 侧 `PlatformApiKeyPortAdapter` **复用** `PlatformProviderConfigServiceImpl.getApiKey(provider)` |
| 博查 | `sys_config["web-search.bocha.api-key"]`（加密）+ yml 兜底 | `WebSearchApiKeyResolver` → `system.port.WebSearchApiKeyPort` → planner 侧 `WebSearchApiKeyPortAdapter` **复用** `WebSearchCredentialKeyStore.resolveBochaApiKey()` |

> **为什么经端口**：余额查询在 system 域，直接 import agent / planner 会构成 §6 反向依赖；按 CODE_STYLE §7.2 情形①，端口定义在消费方 system、提供方实现适配器，取数逻辑仍只有一处定义（`agent → system` / `planner → system` 为顺向）。

**`V5` 已从代码读清（2026-11-02，`[实测]`）**：

- `CredentialVaultServiceImpl.getActiveApiKey` 按 `owner_type/owner_id/provider/credential_type=API_KEY/status=ACTIVE` 查，`orderByDesc(create_time) LIMIT 1`。
- 部分唯一索引 `uk_credential_vault_active_owner_provider_type`（`V15__credential_vault_active_unique.sql`）只覆盖 `deleted=0 AND status='ACTIVE'` 的行 ⇒ **每个 provider 恰一条 ACTIVE**，`orderByDesc(create_time)` 与「多 ACTIVE 并存」的疑问**不再成立**。
- ⇒ **`PlatformApiKeyResolver` 不复选逻辑，经 `PlatformApiKeyPort` 调用 `PlatformProviderConfigServiceImpl.getApiKey(provider)`**（vault ACTIVE 明文 → yml 兜底，全部现成），不新写查询。

### 8.7 UX-1 刷新间隔可配与拖拽修复（2026-11-02）

**用户反馈**：① 刷新频率是否 1 分钟一次、是否浪费 token；② 刷新频率能否放进系统设置—平台设置（1 分钟~1 小时自定义，或不自动刷新只手动点）；③ 浮球只能左右移动、无法上下移动。

**事实与根因**：

- 改造前：前端 30s 可见轮询 + 后端成功缓存 60s + 定时采集 15min ⇒ 页面打开时外部余额请求最多约 1 次/分钟。
- 余额接口是供应商账户查询端点（`/user/balance` 等），不走模型推理，**不消耗 LLM Token**；成本是网络请求与供应商请求配额。
- 纵向拖拽失效：`positionStyle` 用 `bottom` 定位，但 `onPointerMove` 写成 `dragStart.py + dy`，方向反转；从默认右下角向上拖时 `bottom` 立即收敛到最小值，看起来「动不了」。

**实现**：

| 层 | 改动 |
|---|---|
| 配置 | `sys_config["quota.refresh.interval-seconds"]`：`0`=仅手动、`60~3600`=自动间隔、空/非法回退 `60`；`V131` 种子默认 `60` |
| 后端 | `QuotaWidgetSettings` 归一化纯函数；`GET /quota/widget-config`（开关 + 间隔）；`GET /quota/overview?fresh=false` 只读落库快照；`BalanceCollectTask` 手动模式不抓、按间隔逐家判断跳过（清理照跑） |
| 前端 | 系统设置「额度监控」区（浮球开关 / 自动刷新开关 / 1~60 分钟）；浮球动态轮询；手动模式只读快照；纵向拖拽改 `py - dy`；「最后更新」取快照时刻 + 30s 时钟 |
| 单测 | `QuotaWidgetSettingsTest` 5 例；`BalanceQueryServiceTest` +4 例（cachedOverview 不触网 / 无历史 / 失败态 / 逐家判断） |
