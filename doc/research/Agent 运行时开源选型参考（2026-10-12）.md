## §0 三句话结论

1. **两个 runtime 都是开源的、许可宽松（均 MIT），源码可直接学**——DSH 在 `deepseek-ai/deepseek-harness`（TypeScript）；Octop 的 runtime 在 `TencentCloud/octop-harness`（Python，底层是 LangChain 团队的 `deepagents` + LangGraph）。
2. **Java 侧有「开箱即用」的等价物**：最对位的是 **LangGraph4j**（MIT / Java 17+ / 与 Spring AI、LangChain4j 原生集成 / 支持循环图 + checkpoint + HITL）。
3. **但对 HelloAI 而言，「借鉴 > 替换」**：外部框架能补的是**图层（显式图 / 断点恢复 / HITL）与拦截链**，**补不了** D1/D2/D3（工具面 / 手脚 / 技能装配形态）——那三块是**你自己要写的**。**换框架不会让内部 LLM 长出工具面。**

## §3 按 HelloAI 缺口映射：外部框架能补哪块、补不了哪块

| HelloAI 缺口（源自比对报告 §3/§7） | 外部框架能否直接补 | 可用落点 |
|---|---|---|
| **D1 工具面空**（内部 LLM 无工具） | ❌ **补不了** | 无框架替你决定「给谁发什么工具」。Spring AI `@Tool` + `ToolCallbackProvider` 已具备，**缺的是授权集与工具实现本身** |
| **D2 无手脚**（原附件读 / shell / 文件写） | 🟡 **部分** | 需自建工具，但可**照抄抽象**：DSH 的 `ctx.fs`/`ctx.shell` provider、Octop 的 `BackendWorkspace`、LangChain4j/Spring AI 的文件工具 |
| **D3 技能装配形态**（全量目录 + 惰性加载） | ❌ **补不了** | Java 侧无「DSH 式 skill 惰性加载」现成件；只能**照 DSH `tool-skill` 自建**（保留 HelloAI 的 `requiredTools` 语义位） |
| **D4 无通用拦截链** | ✅ **能直接补** | **Spring AI `Advisors API`**（HelloAI 已在用 Spring AI，接入成本最低）；可对照 Octop 7 中间件 / DSH waterfall 设计 |
| **D5 `maxIterations=5`** | 🟡 参考 | LangGraph4j `recursion_limit` / DSH 循环预算的取值口径可借鉴 |
| **D6 技能目录 digest** | ❌ 自建 | DSH 有 sha256 digest 变更感知；Java 侧无现成 |
| **第 7 层 Graph（显式图 / HITL / 断点恢复）** | ✅ **能直接补** | **LangGraph4j**：`StateGraph` + `CheckpointSaver` + breakpoints（pause/resume）|
| **第 4 层 Multi-Agent（已强）** | 🟡 可选 | LangGraph4j sub-graph / supervisor 可作为长期收编参考；当前不必动 |

## §4 借鉴 vs 替换：给 HelloAI 的判断

**核心结论：换框架不会自动让内部 LLM 长出工具面。**

理由：AgentTeams / Octop 的 runtime 之所以「成熟」，不是因为框架神奇，而是因为**它们把「循环 + 全量工具 + 工作区」整套配齐了**。HelloAI 的缺口（D1/D2/D3）**全部在「配齐」这一侧**，不在「框架」这一侧——换成 LangGraph4j，D1/D2/D3 照样空。

**因此建议分两步，不要一步跳到替换执行内核：**

```text
第一步（低风险，先做）：在现有 Spring AI 栈内补齐——
    · 用 Spring AI Advisors 建拦截链          → 补 D4（第 7 层扩展点）
    · 补内部 LLM 的工具面（非 MCP 会话通道）  → 补 D1
    · 补读原附件 / 文件写 / 交付动作           → 补 D2
    · 技能改「全量目录 + 惰性加载」            → 补 D3
    落点复用既有 ToolRegistry 语义位 + ToolCallbackContributor（REF-1.3 已具备），不新造平行通道。

第二步（按需，条件触发）：仅当确实需要「显式图 / 断点续跑 / HITL 关卡」时，
    引入 LangGraph4j 作为编排层——这正好对上第 7 层缺口与 B3 Recovery/Fork 的长期诉求。
    ⚠️ 代价：与既有 ADR-001 Run/Turn/Step 模型、ChatModelToolLoop 存在**重叠**，
       须先做「收编 vs 共存」的取舍，不可直接叠两层循环。
```

> **与既有投资的关系**：HelloAI 已自建 `ChatModelToolLoop` + ADR-001 Run/Turn/Step + 单轨 `RuntimeTurnExecutor`。**这些是资产不是负债**——循环本体没问题（比对报告 §7 已证），问题在循环的两端。**先补两端，再评估是否换图。**

## §5 许可与风险提示

- **许可**：DSH / Octop / octop-harness / LangGraph4j / Semantic Kernel 均 **MIT**；Spring AI / LangChain4j / Embabel / Koog / Spring AI Alibaba / ADK-Java 均 **Apache 2.0**。**全部可商用**，无 copyleft 传染（引用时仍需保留版权声明）。
- **稳定性**：DSH 是 **developer preview**（官方明示破坏性变更）；Embabel / Koog / LangChain4j-agentic / ADK-Java 均 **Beta 或 Pre-GA**；**生产引入须锁版本 + 读该版本文档**。
- **供应链**：引入外部 runtime = 引入其**全部依赖树**（DSH 的 Cordis 插件生态、octop-harness 的 LangGraph/deepagents）。对已上生产的 Java 服务，须评估依赖冲突与升级跟随成本。
- **不要把「框架 GA」等同于「你的 agent 会跑」**——工具面、权限、沙箱边界仍须逐个验证（DSH 官方也强调 sandbox ≠ 隔离保证）。
