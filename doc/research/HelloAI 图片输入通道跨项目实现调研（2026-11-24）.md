## 0. 一句话结论

**图片输入不是一个「能力问题」，是一条四层管道问题**：存储层只存引用、准入层判能力、装配层读**实际使用模型**的能力对象、发送层做规格化与三档降级。四个开源/商业实现全部按这四层切分，**没有任何一个把图片当文本塞进 prompt**，也没有任何一个把 base64 存进会话历史。

本项目当前缺的恰恰是第 2、3 层（准入与装配），而第 4 层（发送）Spring AI 已提供现成通道。

## 2. Aider：能力位门禁 + 图片独立成消息 `[源码]`

### 2.1 类型判定单点定义

`aider/utils.py`：

```python
IMAGE_EXTENSIONS = {".png", ".jpg", ".jpeg", ".gif", ".bmp", ".tiff", ".webp", ".pdf"}

def is_image_file(file_name):
    file_name = str(file_name)
    return any(file_name.endswith(ext) for ext in IMAGE_EXTENSIONS)
```

注意 `.pdf` 与图片**同一集合**、「按扩展名」而非按 MIME 嗅探——这是它的简化，也是它的弱点（改扩展名即可绕过）。

### 2.2 能力位在**准入时**拦截，且报错具体到模型名

`aider/commands.py`，两处（`cmd_add` 与 `_add_read_only_file`）：

```python
if is_image_file(matched_file) and not self.coder.main_model.info.get(
    "supports_vision"
):
    self.io.tool_error(
        f"Cannot add image file {matched_file} as the"
        f" {self.coder.main_model.name} does not support images."
    )
    continue
```

**要点**：`info.get("supports_vision")` —— 取模型元数据字典，**缺失即视为不支持**（fail-close）。错误文案带模型名，用户立刻知道该换模型而不是以为文件坏了。

### 2.3 图片转消息：base64 → `data:` URI → 独立 user 消息

`aider/coders/base_coder.py::get_images_message()`：

```python
def get_images_message(self, fnames):
    supports_images = self.main_model.info.get("supports_vision")
    supports_pdfs = self.main_model.info.get("supports_pdf_input") or self.main_model.info.get(
        "max_pdf_size_mb"
    )
    if not (supports_images or supports_pdfs):
        return None
    image_messages = []
    for fname in fnames:
        if not is_image_file(fname):
            continue
        mime_type, _ = mimetypes.guess_type(fname)
        if not mime_type:
            continue
        with open(fname, "rb") as image_file:
            encoded_string = base64.b64encode(image_file.read()).decode("utf-8")
        image_url = f"data:{mime_type};base64,{encoded_string}"
        rel_fname = self.get_rel_fname(fname)
        if mime_type.startswith("image/") and supports_images:
            image_messages += [
                {"type": "text", "text": f"Image file: {rel_fname}"},
                {"type": "image_url", "image_url": {"url": image_url, "detail": "high"}},
            ]
    if not image_messages:
        return None
    return {"role": "user", "content": image_messages}
```

调用侧显式补一条 assistant 应答，使其成为**合法的独立轮次**：

```python
images_message = self.get_images_message(self.abs_fnames)
if images_message is not None:
    chat_files_messages += [
        images_message,
        dict(role="assistant", content="Ok."),
    ]
```

**要点**：图片**不与正文混排**，而是独立 user 消息 + 紧随一条 `assistant: "Ok."`。这与本项目 `VU-1`/`VU-9` 采取的「图文本同条消息」是**两种都成立的策略**——Aider 用「独立轮次 + 确认应答」保证消息序列合法，本项目用「同条消息多 part」保证语义绑定更紧。**本项目维持同条消息更优**（用户意图与图不可分），此处只作为替代方案记录。

### 2.4 图片永不进文本通道（与本项目 `§2 #20` 同一判据）

`aider/coders/base_coder.py::get_files_content()`：

```python
for fname, content in self.get_abs_fnames_content():
    if not is_image_file(fname):
        relative_fname = self.get_rel_fname(fname)
        prompt += "\n"
        prompt += relative_fname
        # ... 拼进 fenced code block
```

**图片被 `if not is_image_file(fname)` 显式排除在文本拼接之外**。这是与本项目「图片不得进 `extractedText` / 不得 `new String(bytes, UTF_8)`」完全同一条判据的独立实现。**交叉验证了该判据不是本项目自创，而是行业共识。**

### 2.5 token 计数走独立分支

`aider/commands.py::cmd_tokens`：

```python
if is_image_file(relative_fname):
    tokens = self.coder.main_model.token_count_for_image(fname)
else:
    tokens = self.coder.main_model.token_count(content)
```

**图片 token 无法按文本估算**，必须用模型自带的图片计价。⇒ 本项目若做成本控制（`VU-7`），不能沿用文本 token 估算。

### 2.6 Aider 的两处已知不足（不采纳）

- **完全不做 resize / 压缩**：`get_images_message` 对原始字节直接 base64，仅靠 `supports_vision` 门禁。大图会直接顶到 provider 限额。
- **按扩展名判型**：不看文件头，改扩展名即可绕过；且 SVG 若被加入白名单会以文本形式误入。

## 3. GitHub Copilot SDK：能力是结构体，不是布尔 `[文档]`

官方文档 `copilot-sdk/features/image-input` 给出的接口定义：

```typescript
vision?: {
    supported_media_types: string[];   // e.g. ["image/png","image/jpeg"]
    max_prompt_images: number;         // 每 prompt 最大张数
    max_prompt_image_size: number;     // 字节
};
```

四个能力字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `capabilities.supports.vision` | `boolean` | 能否处理图片输入 |
| `capabilities.limits.vision.supported_media_types` | `string[]` | 接受的 MIME |
| `capabilities.limits.vision.max_prompt_images` | `number` | 每 prompt 最大张数 |
| `capabilities.limits.vision.max_prompt_image_size` | `number` | 单图最大字节 |

### 3.1 两种附件形态

- `type: "file"` + 绝对 `path` ⇒ **运行时读盘并转 base64**
- `type: "blob"` + base64 `data` + `mimeType` ⇒ 内存数据直接发，免落盘

```typescript
attachments: [{ type: "file", path: "/absolute/path/to/screenshot.png" }]
attachments: [{ type: "blob", data: base64ImageData, mimeType: "image/png", displayName: "screenshot.png" }]
```

### 3.2 自动规格化 + 无法收敛时**跳过**

> Images that exceed the model's dimension or size limits are automatically resized (preserving aspect ratio) or quality-reduced.
> **If an image cannot be brought within limits after processing, it is skipped and not sent to the LLM.**

**「跳过而非报错」是明确的取舍**：不让单张超大图阻断整轮对话。⇒ 但本项目须保证「跳过」是**显式可见**的（用户至少得到一句「这张图太大已忽略」），否则就是静默丢图。

### 3.3 最具指导性的一句

> **Check vision support first** — Sending images to a non-vision model wastes tokens without visual understanding.

⇒ **能力位不是装饰性字段，是省钱与正确性的前置条件**。这直接对上本项目 `CAP_SUPPORTS_IMAGE_UNDERSTANDING` 只写不读的问题（`§2 #18`）。

### 3.4 其他约束

- SVG 不支持（文本类，排除在图像处理外）
- 接收侧：工具返回图片时是 `{"type":"image","data":<base64>,"mimeType":...}` 内容块，出现在 `tool.execution_complete` 事件里 ⇒ **图片既能进 user 消息、也能进 tool result**，两条路都要支持

## 4. OpenCode：官方 issue 记录了与本项目**完全相同**的缺陷 `[源码]`+`[文档]`

### 4.1 两条喂图通道

**(A) 用户直接贴图**：`session/prompt.ts::materializeAttachment` → `normalizeImageAttachment`（`RESIZABLE_IMAGE_MIMES` 仅放行 png/jpeg/gif/webp/bmp）→ base64 → `session/runner/to-llm-message.ts`：

```typescript
const media = (file: FileAttachment): MediaPart => ({
  type: "media",
  media: Media.base64(file.data, file.mime),
  filename: file.name,
})
```

**(B) 模型主动 `read` 工具**：`tool/plugin/read.ts` 返回

```typescript
[
  { type: "text", text: "Image read successfully" },
  { type: "file", uri: `data:${output.mime};base64,${output.content}`, mime: output.mime, name: path },
]
```

该 `file` 块在下一次请求降级为 Anthropic `image` block，随 `tool_result` 回传。

⇒ **通道 B 与本项目 `internal_read_attachment` 是同一设计位**。本项目该工具当前会把图片当 UTF-8 文本解码（`§2 #21`，归 `VU-6`）——OpenCode 的做法证明这里**应当返回 `file`/`image` 块而非文本**。

### 4.2 规格化配置与「渐进重编码」

`opencode.json`：

```jsonc
{ "media": { "image": {
    "auto_resize": true, "max_width": 2000, "max_height": 2000, "max_base64_bytes": 5242880
} } }
```

处理逻辑（官方文档 + 源码交叉）：

> With `auto_resize: true`, OpenCode preserves the aspect ratio and scales down to the dimension limits. It then **tries progressively smaller PNG and JPEG encodings until the Base64 limit is met**, so the output media type can change.
> Input: 4000×2000 WebP → Limits 2000×2000 → Output 2000×1000 PNG or JPEG

**「逐级降质重试直到塞进去」**比本项目「超限就丢」更实用，且**输出 MIME 可能变化**（WebP→PNG/JPEG）——这点容易被忽略：只校验输入 MIME 而不校验输出 MIME 会漏。

### 4.3 两处边界声明（值得照抄为注释）

> If the image resizer is unavailable, OpenCode passes the original image through unchanged.
> **Image settings are therefore processing limits, not an upload or security boundary.**

⇒ **限额是「处理参数」，不是「安全边界」**。本项目若把「图片 ≤ N MB」写成安全校验（例如当作上传鉴权的一部分），就是概念混用。安全边界应是 MIME 嗅探 + 白名单 + 病毒扫描，与尺寸限额分开。

> Media type is detected from the bytes, so changing a filename or `data:` URL media type does not make an unsupported binary visible.

⇒ **按字节嗅探判型，不信扩展名与声明 MIME**。这正好是 Aider（按扩展名）的短板，OpenCode 补上了。

### 4.4 ★关键证据：issue #60736 —— 与本项目症状完全一致

标题：`attachments: chat image attachments dropped as "model does not support image input" while the read tool works`

现象与本事项目前状态逐条对应：

| OpenCode issue #60736 | 本项目现状 |
|---|---|
| 模型目录报告 `capabilities.input: ["text","image"]` | DB 实测四个模型均声明 `input:["text","image"]`（`§2 #19`） |
| 图片**已存进会话**但**没进模型请求** | 图片存进 `chat_attachment` 但执行器只读 `attachment`（`§2 #22`） |
| 同一个文件走 `read` 工具**模型能看见** | 走 `internal_read_attachment` 会得到乱码文本（`§2 #21`） |
| 请求里被替换成「此模型不支持图片输入」的说明文字 | 清单里显示「需识别（无正文）」（`§2 #23` 断点②） |
| 加了显式能力覆盖 + 重启，**仍然不生效** | ——（本项目尚未做能力位读取，等价于「怎么改都没用」） |

**维护者的根因判定（原文）**：

> **The note is added each time a request is built, based on the model the request actually uses.** … So in your setup the request was probably going to a model without image support, **even though `deepseek-flash` looked selected on the client**.

⇒ **这是本条调研最重要的结论**：能力位必须在**请求装配时按「实际将要调用的模型」解析**，不能取「前端选中的模型」或「会话声明的模型」。

- 后端存在模型回落 / 路由 / 变体（`default` / `high`）时，前端选中的 ≠ 实际调用的
- 本项目 `VU-9` 要动 `AgentChatClientService`，正好是「请求装配」这一层 ⇒ **必须在这一层读实际模型的 `capabilities`，不要在前端或 `AgentTask` 构造时读**
- 若图省事在前端 `accept` 处按「用户选的模型」判断，就会复刻这条 issue

### 4.5 相关 issue #45986

`session: pasted/dropped images are persisted but silently stripped from the model request on v2 beta` —— 「存了但被静默剥离」。与本项目 `§2 #22`（两表无桥）同型。⇒ **「落库成功」不等于「送到模型」**，验证必须在**请求体**上断言，不能在 DB 上断言。

## 5. deepseek-harness（本机）：超限不截断，走 offload + 重试 `[源码]`

### 5.1 能力位在发送前判定，替换为占位符而非丢消息

`packages/llm/llm/src/index.ts:1087-1092`：

```typescript
if (modelInfo.inputModalities !== undefined
  && !modelInfo.inputModalities.includes('image')
```

`packages/llm/llm/src/content.ts:354-367`：`projectImagesForTextModel` **只把 image block 换成稳定占位文本，消息结构与条数不变**。⇒ 切模型不破坏消息序列。

### 5.2 硬约束：图只在 user / tool 角色

`packages/llm/llm-deepseek/src/images.ts:66-68`：

```typescript
if (messages.some(message => message.role !== 'user' && message.role !== 'tool' && contentHasImage(message.content))) {
  throw new LlmError('DeepSeek Messages supports images only in user messages and tool results', 'UNSUPPORTED_CONTENT')
}
```

与 Copilot 的「user 消息 + tool result 两路」**完全一致**（§3.4）。⇒ 本项目 `VU-9` 只需 `user` 一条即可满足；将来做多轮图历史须补这条校验。

### 5.3 超预算：抛专用错误码 → 上层把最老的图换占位 → 重试

`packages/llm/llm-deepseek/src/images.ts` + `packages/compaction/compaction-image-offload/src/index.ts:1-41`：

```typescript
// A durable surface repair, not a provider retry: it spends no retry budget and logs no retry event.
if (!offloadOldestImages(agent.session, agent.session.surface.nodes, failure.offloadImages)) return next()
return Promise.resolve<RequestErrorAction>({ kind: 'retry' })
```

**要点**：超限不走「截断/丢弃/报错」，而是**把最老的图片降级成占位文本后重发**，且注释明确「不消耗重试预算」。⇒ 这解决了「多轮对话里图片越积越多最终超限」的问题，但**依赖会话可回写**，本项目暂无对应设施（不采纳，记录备查）。

## 6. Octop（本机）：三档降级 + 存储/请求分离 `[源码]`

### 6.1 三档降级（最清晰的一份实现）

`src/octop/infra/gateway/media/attachment_hints.py:330-352`：

```python
def _image_unavailable_block(*, locale="en"):
    return {"type": "text", "text": attachment_image_unavailable(locale)}

def _image_as_path_hint(part, *, workspace, locale="en"):
    path = inbound_rel_path(part.local_path) if part.local_path else ""
    if not path:
        return _image_unavailable_block(locale=locale)
    return path_hint_content_block(InboundAttachmentMeta(path=path, filename=Path(path).name or "image",
                                  media_type=part.mime_type or "image/png"), workspace=workspace, locale=locale)
```

`format_attachment_path_hint`（`:121-137`）产出的提示**只含文件名 / 路径 / MIME / 大小**，docstring 明写 `never inline file bytes`。

三档：**有字节 → vision block｜有路径 → path hint｜皆无 → 显式 unavailable**。

### 6.2 存储态与请求态分离（写在一句话里）

`src/octop/infra/agents/middleware/workspace_image.py:1-10` 模块 docstring：

> Checkpoint / history keep path-only `workspace://` refs or the original inline bytes. This middleware expands refs and **fits images that exceed the vision byte or edge caps onto the model request only, so base64 and resized copies never land in LangGraph state or the dashboard history payload**.

⇒ **base64 与缩放副本永不落状态**。这是「只存引用」这一判据的最强表述。

### 6.3 限额单点定义，并写明向谁让路

`attachment_hints.py:36-51`：

```python
VISION_MAX_BYTES = 2 * 1024 * 1024
VISION_MAX_COUNT = 4
# 8000 px is inside Anthropic's 8000 px limit and DeepSeek's 8192 px limit,
# so images already under it are left byte-identical for every provider.
VISION_SAFE_MAX_SIDE = 8000
VISION_MAX_SIDE = 1568        # byte-budget fallback only
VISION_JPEG_QUALITY = 85
```

**注释写清「取最严者」**——多 provider 共存时的正确姿势：先按最严的公共上限过，不足再按单 provider 放宽。

### 6.4 能力位参与自动路由

`src/octop/infra/agents/providers/store.py:253-254` + `:459`：

```python
def _model_dict_supports_image(model): return is_vision_model(model)
...
if needs_multimodal and not _model_dict_supports_image(model):
    continue          # 直接从候选里跳过
```

⇒ 能力位不仅门禁，还**参与路由选型**：带图请求不会落到非视觉模型上。

## 7. 跨项目收敛：四条不变量

四个实现（Aider / Copilot / OpenCode / Octop，deepseek 部分吻合）在下面四条上**完全一致**，可视为行业定稿：

| # | 不变量 | 证据 |
|---|---|---|
| **I-1** | **图片字节永不进文本通道** | Aider `get_files_content` 的 `if not is_image_file`；OpenCode 走 `MediaPart`；本项目 `§2 #20` 同判据 |
| **I-2** | **能力位在请求装配层按「实际调用模型」解析** | OpenCode #60736 维护者判定；deepseek `index.ts:1087`；Copilot「Check vision support first」；Octop 路由跳过 |
| **I-3** | **存储只存引用，字节与缩放副本不落历史** | Octop `workspace_image.py:1-10` 明文；Copilot `blob` vs `file` 两形态；OpenCode 存 `file.data` 但请求时才转 `MediaPart` |
| **I-4** | **降级必须显式，禁止静默丢图** | Octop 三档；Copilot「跳过」；deepseek 抛 `UNSUPPORTED_CONTENT`；OpenCode 注入 note |

**两处行业分歧**（本项目需自行拍板）：

| 分歧 | 选项 A | 选项 B | 本项目取舍 |
|---|---|---|---|
| 图文是否同条消息 | Aider：独立 user 消息 + `assistant:"Ok."` | 本项目 `VU-1`：同条消息多 part | **取 B**（用户意图与图不可分；且 `VU-1` 已交付并验证） |
| 超限处理 | Aider/Copilot：跳过或直接 base64 不处理 | OpenCode：渐进重编码；deepseek：offload+重试 | **取 OpenCode 的渐进重编码**（不依赖会话回写设施）；deepseek 路线待有持久化投影后再议 |

## 8. 对本项目的具体结论（供 `VU-9` / `VU-8` 直接采用）

1. **能力位必须读，且读在 `AgentChatClientService` 这一层**（I-2）。取的是**本次实际要调用的模型**的 `capabilities`，不是前端选中的、也不是 `AgentTask` 构造时缓存的。`§2 #18` 的 `CAP_SUPPORTS_IMAGE_UNDERSTANDING` 只写不读，正是 OpenCode #60736 的成因形态。
2. **能力不适合只做布尔**（Copilot §3）：至少要「是否支持 + 支持的 MIME + 张数上限 + 单图字节上限」四元组。本项目 DB `llm_provider_model.capabilities` 已有 `input:["text","image"]`，需扩到限额字段或在平台侧配置常量并注释「向最严 provider 让路」。
3. **MIME 判型必须嗅探字节**，不能用扩展名（Aider 短板，OpenCode 已纠正）。本项目 `AttachmentContentPolicy` 现有判据需核对是否只看扩展名。
4. **限额是处理参数，不是安全边界**（OpenCode §4.3 明文）。不要把它和上传鉴权混写。
5. **`internal_read_attachment` 应返回 `file`/`image` 块而非文本**（OpenCode 通道 B 的实证做法），这条直接支撑 `§2 #21`（归 `VU-6`）的修法。
6. **验证必须在请求体上断言**，不能在 DB 上断言（OpenCode #45986：「存了但被静默剥离」）。
7. **图片 token 不能按文本估算**（Aider §2.5），`VU-7` 的成本模型需单列。

## 9. 不做的事

- **不引入 `workspace://` 引用机制**（Octop）：依赖工作区对模型侧可见，本项目容器形态未挂载（`GT-10`），照搬会引入隐性耦合。
- **不做图片 offload + 重试**（deepseek）：依赖会话 surface 可回写，本项目暂无该设施。
- **不采纳 Aider 的「按扩展名判型」与「完全不 resize」**：前者的缺陷已被 OpenCode 纠正，后者会直接顶到 provider 限额。
- **不参考 Qoder 的实现**：闭源，产品文档只体现交互（AppShot 截图 + accessibility 文本成对送入、需屏幕录制与辅助功能两项系统权限），**无实现可借鉴**。
- **不再为「图片能不能送」单独造第二份清单**：本文件只作 `VU-9`/`VU-8` 的依据，事实源仍是 `plan/` 与差距表 `G-038`。
