# 联网搜索效果差距分析与优化调研（2026-10-18）

> 用户反馈：平台联网搜索效果不理想。本文档回答三问：  
> ① 平台现有实现的效果瓶颈在哪（代码 + 真实日志实据）；  
> ② 与成熟产品（Perplexity / DeepSeek / Kimi 等）的能力差距；  
> ③ GitHub 上使用博查 API 的开源项目如何优化。
>
> 依据：`BochaWebSearchServiceImpl` / `AiSearchWebSearchServiceImpl` / `ClarifyWebSearchOrchestrator` /  
> `SearchQueryPlannerServiceImpl` / `WebSearchOutcome` / `logs/helloai.log` 实测记录 +  
> 外部调研（博查官方 MCP / 开源工具包 / Perplexity 检索机制拆解）。

## 一、平台现状：执行链路与效果实据

### 1.1 当前执行链路

```
用户消息
  → ClarifyWebSearchOrchestrator.doWebSearch
      → URL 分离（消息含 http(s) 链接则直取页面）
      → SearchQueryPlannerService.planQueries（规则清洗 + LLM 条件改写，产出 1~N 候选词）
      → 逐候选词调 web_search 工具 → WebSearchServiceRouter → 激活实现
      → （当前 provider=bocha-ai-search）AiSearchWebSearchServiceImpl
          POST https://api.bochaai.com/v1/ai-search
          {query, freshness:"noLimit", count:15, answer:false, stream:false}
      → 解析 messages[].content.value[]（网页结果）
      → 结果截断 200 字/条，按 URL 去重合并
  → 可选缺口补搜（SearchGapAssessor，ai-search-max-rounds=2）
  → WebSearchOutcome.toContextText() 渲染注入澄清 prompt
```

### 1.2 效果实据（`logs/helloai.log`，2026-10-18 00:21 真实任务）

```text

澄清联网搜索：候选词命中 15 条: query=制定减脂计划

```

**实据揭示的 4 个瓶颈**：

| # | 瓶颈             | 实据                         | 根因                                                                                                                                           |
| - | -------------- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | **搜索词质量差**     | 「膝盖旧伤 减脂训练计划 饮食方案 建议」→ 0 条 | `QUERY_CHAR_LIMIT=20` 硬截断，把多主题长句前 20 字切碎（漏了「膝盖旧伤」后的关键限定）；规则拆分靠 `[+＋]、以及、，、、` 等连接符，中文长句常拆不干净                                                  |
| 2 | **无时效过滤**      | 所有请求 `freshness:"noLimit"` | 代码硬编码 noLimit；用户问「最新/今年/上周」时无时效语义                                                                                                            |
| 3 | **answer 被关掉** | `answer=无`                 | 配置文件 `ai-search-answer` 默认 true（注释态），但实现 `AiSearchWebSearchServiceImpl` 请求体写死 `answer:false`（「避免与澄清主回复职责重复」的旧决策）——博查侧大模型总结没启用，少了「搜索后先给总结」的能力 |
| 4 | **慢（45.9s）**   | costMs=45963               | AI Search 单次 25s 超时；两个候选词**串行**搜索，第二个词吃到预算上限。配置 `search-budget-ms=30000` 但 AI Search 一次就逼近它                                                  |

### 1.3 结构性短板（对照成熟产品）

| 能力    | 平台现状                            | 成熟产品（Perplexity/DeepSeek/Kimi）  |
| ----- | ------------------------------- | ------------------------------- |
| 查询分解  | 规则拆分 + LLM 条件改写（≤3 词、每词 20 字截断） | 3~5 个**子查询并行**执行（query fan-out） |
| 检索源   | 单一博查                            | 多引擎并行（Google/Bing/自建索引 + 垂直源）   |
| 结果重排  | **无**（取 API 原始顺序）               | 三层 ML 重排（相关性/权威性/时效性）           |
| 时效    | **硬编码 noLimit**                 | freshness 打分 + 30 天时间衰减         |
| 正文抓取  | **仅用户主动给 URL 时**                | 对候选结果自动抓正文/摘要                   |
| 上下文注入 | title + snippet（200 字截断）        | 抽取段落（passage extraction）+ 来源约束  |
| 引用溯源  | URL 列表（无句级引用）                   | **句级引用**（每句标注来源）                |
| 多轮迭代  | 1 轮 + 最多 1 轮补搜（LLM 评估缺口）        | 3~5 轮 Deep Research 迭代          |
| 大模型总结 | **关闭**（answer=false）            | 搜索后先给总结 + 追问                    |

## 二、与成熟产品的差距根因（5 条）

1. **「搜索词」与「用户问题」之间的语义鸿沟没填平**  
   Perplexity 用 LLM 把问题解析成 3~5 个**正交子查询**并行执行；平台靠正则规则 + 条件 LLM 改写，多数场景走规则（短消息直接搜），子查询间不并行、无正交性设计。
2. **检索结果没有「二次精排」**  
   博查返回的原始顺序不是为最终答案设计的。成熟产品都有独立 rerank 层（Perplexity 三层 ML 重排；博查官方也有 Semantic Reranker API `gte-rerank`，80M 参数达 280M 效果）。平台直接透传。
3. **给 LLM 的「料」太少太浅**  
   只给 title + 200 字 snippet。开源工具包（见 §三）用 Jina Reader 抓全文 → 语义分片 → LLM Map-Reduce 摘要 → 把「浓缩后的证据」喂给模型。snippet 常是搜索引擎的「诱饵文本」，不含真正答案。
4. **时效与地域语义丢失**  
   freshness 硬编码 noLimit；问「今天/本周/最新」无差别。成熟产品对时效问题自动收紧时间窗（oneDay/oneWeek），对非时效问题放宽。
5. **answer 关闭 + 无引用约束**  
   博查 ai-search `answer=true` 可让博查侧先给大模型总结（DeepSeek 官方联网就是博查供应的）；平台关掉后，主 LLM 直接看 15 条 snippet 自己综合，既慢又容易「摘要漂移」。同时 prompt 没做「答案必须约束在检索资料内」的 grounding 指令（Perplexity 的核心）。

## 三、GitHub 博查开源项目如何优化（3 个代表）

### 3.1 `JiangNanGenius/Comprehensive-intelligent-search-toolkit`（综合智能搜索工具集，MIT）

**优化点全谱**（架构见 README）：

- **多路搜索**：Kimi 基础搜索 + Bocha 专业搜索 + 用户给定 URL 三源汇入
- **网页正文抓取**：Jina Reader 并发抓全文（HTML→text）
- **语义安全分片**：句子/链接/表格/代码感知的分片（`TARGET_CHUNK_CHARS=2800` + `OVERLAP_SENTENCES=3`）
- **LLM 并发 Map-Reduce 摘要**：每片并发提多条详细摘要 → reduce 去重聚合 top-N（`LLM_MAX_CONCURRENCY=3`）
- **RAG 向量化**（Doubao ARK）：查询/摘要向量化 + 余弦相似度筛选（`SIMILARITY_THRESHOLD=0.08`）
- **语义重排**：Bocha Rerank `gte-rerank` + 多维打分融合（`rerank_score` × `rag_similarity` × `answerability` → `final_score`）
- **引用治理**：可选持久化引用并在后续请求回放（`PERSIST_CITATIONS`）
- **优雅降级**：任一能力缺失（Key 没配）自动跳过，不阻断主流程

**可借鉴**：① 结果注入前先经「抓正文 → 分片 → LLM 摘要 → 打分重排」四步，而不是裸 snippet；② 引用可持久化回放。

### 3.2 `BochaAI/bocha-search-mcp`（博查官方 MCP Server）

**官方推荐用法**：

- 双端点：`web-search`（基础）+ `ai-search`（AI 识别语义 + 模态卡：天气/百科/股票/汇率等几十种结构化卡）
- 参数设计：`freshness`（oneDay/oneWeek/oneMonth/oneYear/noLimit/指定日期区间）+ `count`（1-50）
- **定位差异**：web-search 给链接列表；ai-search 给「结构化模态卡 + 更优时效/语义」，官方明确说 ai-search 在语义识别、时效性、内容丰富性上更好

**可借鉴**：① 用 ai-search 的模态卡处理股票/天气/百科等垂直查询（平台已接 ai-search 但没消费模态卡）；② freshness 按查询语义动态选择。

### 3.3 `jiangxinke/Agentic-RAG-R1`（智能体 RAG，训练中学会搜索）

**独特做法**：

- 模型在推理过程中**自主决定何时搜索**（生成 `<search>查询词</search>` 标签 → 系统拦截 → 调 Bocha → 返回结果 → 继续推理）
- **RAG 质量奖励**：训练时用 `rag_reward` 评估「检索结果是否被正确使用」（RetrievalQualityEvaluator 打分），鼓励模型生成相关查询并有效利用结果

**可借鉴**：让 LLM 在回答过程中**多轮自主搜索**（agentic search），而不是「一轮批量搜完一次性注入」。

### 其他参考

- `1c7/bocha-search`（Claude Skill）：四种 API 全封装，选择指南——绝大多数用 web-search + `summary:true`；需要结构化数据用 ai-search；RAG 重排用 rerank。
- LangChain 集成实践：`freshness=oneMonth` + `site:` 限定 + `rerank:true` + `count:5` 的「优化参数组合」。

## 四、改进建议（按投入产出排序）

### P0：零代码/低代码（当天可做）

1. **开 answer**：`AiSearchWebSearchServiceImpl` 请求体 `answer:false` → `true`（或读配置 `ai-search-answer`）。博查侧先给大模型总结，对齐 DeepSeek 网页版形态。**代价**：单次耗时更长（需同步调预算）。
2. **动态 freshness**：查询词含「今天/最新/本月/今年/上周」等时效词时，`noLimit` → `oneDay/oneWeek/oneMonth/oneYear`（`RelativeTimeNormalizer` 已存在，可复用判定）。

### P1：中等改动（1~3 天）

1. **候选词并行搜索**：`ClarifyWebSearchOrchestrator` 里 `for` 串行改并行（CompletableFuture），把 45.9s 降到 ~25s；配合 `search-budget-ms` 做并发预算。
2. **搜索词质量**：`QUERY_CHAR_LIMIT=20` 截断策略改进——按「语义单元」截断而非硬切前 20 字；LLM 改写放宽触发（当前仅「单候选词 + 长句/疑问句」才触发，多主题长句直接规则拆碎了）。
3. **结果去噪**：snippet 长度 200 → 400~600；过滤广告/聚合站；`siteName` 缺失补 host。

### P2：结构性优化（3~5 天）

1. **正文抓取 + LLM 摘要**（对标开源工具包）：对 top-N 结果用 Jina/自研 fetcher 抓正文 → 语义分片 → LLM 摘要 → 注入。这是从「snippet 拼接」到「证据浓缩」的质变。
2. **博查 Rerank 接入**：对候选结果调 `bocha rerank`（`gte-rerank`），精排后取 top-N 注入——低成本拿到「语义重排」能力（博查 80M 参数模型已够用）。
3. **Grounding 指令**：澄清 prompt 追加「回答必须基于检索资料，无资料支撑的推断需明确标注」约束（对齐 Perplexity 的 grounded generation）。
4. **消费模态卡**：ai-search 返回的天气/股票/百科卡转结构化注入（垂直查询质量质变）。

### P3：远期

1. **Agentic 多轮搜索**（对齐 Agentic-RAG-R1）：让 LLM 在澄清/拆解过程中自主决定多次搜索，而非一次批量。

## 五、结论

平台联网搜索**不是「没有能力」，而是「能力没用满」**：

- 已接入博查（国内最强 AI 搜索供应商之一，DeepSeek 官方供应商），AI Search 已实现；
- 但**结果后处理（抓取/摘要/重排/时效/grounding）基本空白**，搜索词规划偏规则、无并行、answer 被关——这正是「效果不理想」的根因。

**最短路径**：P0 两项（开 answer + 动态 freshness）+ P1 两项（并行 + 搜索词质量）即可感知明显提升；要追平成熟产品体验，P2 的「正文抓取 + Rerank + grounding」是关键三件套。
