## 2. 成熟产品怎么做

### 2.1 Kimi（官方帮助页，2026-10 核对）

- 类型：PDF、Word、Excel、PPT、图片、TXT、视频
- 限额：**单文件 ≤ 100MB，单次 ≤ 50 个**
- 上下文：K2.6 约 128K tokens，K3 最高 1M
- **项目文件「按需读取」**：官方明确「不会在每轮对话中把全部文件正文预加载，而是模型根据你的问题判断需要哪些文件再读取」
- 项目存储配额按套餐（Free 500MB → Ultra 50GB）

⇒ 两个关键产品选择：**① 文件先落库、不每轮全量塞；② 大文件走"按需读取"（工具/检索），小文件才全文注入。**

### 2.2 DeepSeek 网页版

- 回形针上传图片 / PDF / Office / 代码文件；压缩包需先解压
- 扫描版 PDF 走 OCR，识别质量取决于原件清晰度；超长文档官方建议分段
- 上下文 1M tokens，属于「大窗口直接塞」路线

⇒ 大窗口不等于不分层：连 Kimi 都在 128K/1M 窗口上做「按需读取」，说明**注入预算与检索是产品必需，不是省钱手段**。

### 2.3 通用做法（四步）

```
① 上传（multipart / 直传对象存储，返回附件 id）
② 异步解析（文本层提取 / OCR / 视觉理解 → 归一成 markdown 或纯文本）
③ 分层注入（小：全文进 prompt；大：分片 + 检索命中片段）
④ 多轮引用（消息 → 附件关联，气泡显示文件 chip，回答里带可点回源标记）
```

图片两条技术路线：

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 原生视觉 | 图片/PDF 页作为 `Media` 随消息发给视觉模型 | 版面、图表、手写都保留；无需 OCR 基建 | 只有声明 image/pdf 的模型可用；图片 token 贵 |
| 先 OCR | OCR 成文本再按文本注入 | 任何文本模型都能用（DeepSeek 也能） | 表格/版面/图表丢失；中文手写差 |

成熟产品大多**两条都做**：视觉模型在就用原生，否则降级 OCR。

### 2.4 GitHub 生态（含许可，2026-10 核对）

| 工具 | 语言/形态 | 许可 | 强项 | 弱项 |
|---|---|---|---|---|
| Apache Tika | Java 库 | Apache-2.0 | 格式覆盖最广（PDF/DOCX/PPTX/XLSX/HTML…），一个 Reader 全包 | PDF 仅抽文本层，版面/表格散架；无 OCR |
| Apache PDFBox | Java 库 | Apache-2.0 | PDF 文本层抽取 + 页渲染位图（供视觉/OCR） | 无版面分析，无 OCR |
| Apache POI | Java 库 | Apache-2.0 | docx/pptx/xlsx 结构级读取 | 只覆盖 Office |
| MarkItDown（微软） | Python | MIT | Office → markdown 极快、依赖极轻 | PDF 弱、无 OCR |
| Docling（IBM） | Python | MIT | 版面/阅读顺序/表格结构，可插 OCR（EasyOCR/RapidOCR/Tesseract），CPU 可跑，可 `docling-serve` 起 HTTP | 需 sidecar 容器 |
| MinerU（OpenDataLab） | Python | AGPL-3.0（+附加条款） | 中文/公式/表格最强 | 重（模型缓存 20GB 级），AGPL 商用需评估 |
| Marker（Datalab） | Python | GPL-3.0 + 权重条款 | 速度与通用质量均衡 | 许可对商用有限制 |
| PaddleOCR | Python/服务 | Apache-2.0 | 中文 OCR、PP-StructureV3 版面 | 需服务化 |

**Spring AI 侧**：`spring-ai-tika-document-reader`（1.1.8 与项目 `spring-ai.version` 对齐）封装 Tika，可直接产出 `Document` 列表；多模态走 `Media`（image/pdf），与上面第 1.4 节的模型能力元数据正好接得上。

### 2.5 依赖可行性（探针实测，不是推测）

用探针工程（maven 3.9.14 + JDK17）逐一实跑，结论全部来自实测输出：

| 组合 | 结果 | 说明 |
|---|---|---|
| `pdfbox 3.0.5` + `poi-ooxml 5.4.1` | **通过（`-o` 离线）** | 2 个依赖、classpath 约 20 条；只覆盖 PDF + Office |
| `tika-parsers-standard-package 3.1.0`（无 `type=pom`）+ 上述 | **离线失败** | 缺 `jackson 2.18.2`、`bcpkix-jdk18on 1.80.2`、`jcl-over-slf4j 2.0.16`（探针没有 Boot BOM 兜版本，Tika 声明值直接生效） |
| `tika-parsers-standard-package 3.3.1` + `<type>pom</type>` **但只写这一条** | **编译失败**：`程序包 org.apache.tika.parser 不存在` | 3.3.1 实测 classpath 只有 24 个 parser 模块、**没有 `tika-core`** |
| 同上 **+ 显式 `tika-core 3.3.1`** | **通过** | classpath 87 条；`Tika.detect` / 243 种类型可用 |
| **`tika-parsers-standard-package 4.1.0` + `<type>pom</type>`，只写这一条** | **通过（编译 + 解析）** | classpath 86 条；`tika-core 4.1.0` 经 `tika-encoding-detector-html` 传递进来，**不需要单独声明** |
| `tika-core 4.1.0` + `tika-parser-pdf-module` + `tika-parser-microsoft-module` | **通过** | classpath 50 条；`/tmp/sample.pdf` → 45 字符、`/tmp/sample.docx` → 29 字符 |
| 上面两种 4.1.0 组合把 jackson 换成项目现有 `2.18.4.1` | **通过** | 无 `NoSuchMethodError`；PDF / DOCX / HTML 与 Markdown 渲染路径均跑通 |

四条关键修正（都是踩出来的，第 1 条订正了上一版的错误结论）：

1. **README 那条单依赖写法在 4.1.0 上是对的**。源码 `tika-parsers-standard-package/pom.xml` 里 `tika-core` 声明为 `provided`，但 4.x 通过 `tika-encoding-detector-html` 把它带成 compile 传递依赖；3.3.1 没有这条链，所以只写聚合包会缺类。**上一版「必须另加 tika-core」只在 3.x 成立，不能推广到 4.x。**
2. **Tika 4.x 是正式版**（Central 上 `4.0.0` / `4.1.0` 均为 release，最新 release = 4.1.0；3.x 最新 3.3.3）。但 4.x **改了 `Parser.parse` 签名**：入参从 `InputStream` 变成 `TikaInputStream`（3.x 的写法在 4.x 编译不过）。也因此 **`spring-ai-tika-document-reader 1.1.8`（依赖 Tika 3.x）不能配 4.x 用**——本项目不需要它，直接用 Tika API。
3. **离线只是"没预先拉包"，不是"不能用"**：Tika 4.1.0 拉的是 `pdfbox 3.0.8` / `poi-ooxml 5.5.1` / `jackson 2.22.3`，首次引入需要一次联网解析；本机已缓存（`~/.m2/repository/org/apache/tika` 31MB），之后 `-o` 离线构建照常。
4. **`~/Downloads/tika-main` 是 main 分支快照，不是 4.1.0**：`tika-parent/pom.xml` 的 `<revision>` = `4.2.0-SNAPSHOT`。不建议 `mvn install` 后拿它当依赖（快照不可复现、API 可能再变）；源码的价值是**查 API 与官方文档**（`docs/modules/ROOT/pages/`，比官网更全），依赖仍取 Central 的 `4.1.0`。

#### 4.x 现成能力（读源码 + 实测，直接影响 §3.3 实现）

| 能力 | 事实 | 对方案的影响 |
|---|---|---|
| Markdown 输出 | 「4.x 默认输出 Markdown」**只对 `tika-app` / `tika-server` / async-cli 生效**；Java API 的 `Tika.parseToString` 仍是 `BodyContentHandler` 纯文本。要 Markdown 必须显式用 `tika-core` 自带的 `ToMarkdownContentHandler` | 实测 HTML 表格与 **DOCX 表格**都输出 `\|字段\|类型\|` 形式；§3.3 里「表格另用 POI 转 markdown」可以删掉，一个 handler 搞定 |
| 解析限额 | 4.x 在 `ParseContext` 里提供 `EmbeddedLimits`（嵌入文档深度/数量）、`OutputLimits`（字符数、XML 嵌套、zip 炸弹比）、`TimeoutLimits`（`new TimeoutLimits(totalTaskMs, progressMs)`，另有 stall 检测） | 「解析超时 60s / 直读上限 200k」不必自己包 `Future.get`，用官方限额即可，且能防 zip 炸弹这类递归展开 |
| 进程隔离 | 官方文档明确：**不要和应用同进程解析不可信文件**（原文 "Avoid running Tika in the same process as critical infrastructure"），推荐 `tika-pipes-fork-parser`（独立 artifact）在 fork 出的 JVM 里解析 | ATT-1 先同进程 + 限额 + 超时（内网可信来源为主），可选阶段若开放公网上传再换 Pipes；风险章节已登记 |
| OCR | `tika-parser-ocr-module` 在标准包里，但依赖**外部 tesseract 可执行文件**（容器要装） | ATT-2 走视觉直读更省事；若走 OCR 需额外镜像层 |
