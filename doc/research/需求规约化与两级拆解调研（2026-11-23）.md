# 需求规约化与两级拆解调研（2026-11-23）

> Status: Analysis（外部调研，不写排期）
> 背景：端到端场景对照后，用户提出「需求文档 → 粗粒度任务 → 整体 Plan → 细粒度可执行 → 对齐下发」的构想，并补充「项目文档治理模板（doc-template）是否应进入这条链」的问题。本调研回答三个问题：① 开源世界有没有完整实现；② HelloAI 现有底座差什么；③ 治理约束（doc-template）的落点在「需求→任务」还是「任务派发」。**2026-11-23 同日补充：§6 加入「自家 doc 体系机制自评与 doc-template 提炼关系实证」**——用户说明 opensource 的 doc-template 正是从本项目 `doc/`（182 份 md）提炼的，对体系机制做实证对照。

## 0. 结论速览（TL;DR）

1. **开源世界没有完整实现用户构想的组合**（需求自洽校验 + 两级滚动拆解 + 需求级知识库），但每个单点都有成熟的参考：MetaGPT（需求→任务结构）、HTN-Orchestrate（滚动拆解机制）、WeKnora（知识库+Agent+记忆三合一）。
2. **HelloAI 已具备三块底座**：任务树多级字段（`Task.depth/parentTaskId`）、按会话隔离的需求级知识库（`KnowledgeBaseService`，附件已 ingest、拆解期已检索注入）、澄清收敛判据（`ClarifyStallGuard`）。差的是把它们串成「规约化→校验→两级拆解→需求知识库」闭环。
3. **doc-template 的落点不是二选一，而是一主一辅**：主落点在**任务派发/执行约束**（治理契约全文随任务注入执行侧，锚定异质 LLM 的执行一致性）；辅落点在**需求→任务拆解**（只注入「交付契约摘要」引用，不复制全文，防双写漂移）。详见 §4。

## 1. 问题定义：用户构想 = 三栋能力

| 用户诉求（原话提炼） | 系统能力 | 本质问题 |
|---|---|---|
| 丰富需求先拆粗粒度任务、做整体 plan，再看每个粗任务能否一次拆分下发 | 两级拆解 + 整体规划 | 「做什么」的分层 |
| 不能一次达标则二次拆分 | 滚动拆解（执行中按需细化） | 规划粒度动态化 |
| 需求文档能执行的前提是自洽且业务闭环，否则像最初 planner 一样生成无效子任务、浪费 token | 需求规约化 + 自洽性/闭环校验闸门 | 「值不值得做」的前置拦截 |
| 执行需求文档时要有新的 RAG 知识库/上下文记录沟通细节 | 需求级知识库（按需求会话隔离） | 「依据什么做」的上下文供给 |
| （本次补充）不同 AI agent / LLM 结果要在预期内，代码质量靠文档治理约束 | 项目级行为契约注入 | 「按什么标准做」的一致性锚定 |

## 2. 开源调研：按能力维度对照

### 2.1 需求 → 任务拆解（最贴近需求起点）

**MetaGPT**（FoundationAgents/MetaGPT，原 geekan，~69K ⭐，MIT）
- 形态：一句话需求 → PM 写 PRD → 架构师出设计 → PM 拆任务 → 工程师写码 → QA 测试，SOP 串行多角色流水线。
- 与构想的关系：**需求→任务结构的参考**，但①拆解只有一层（PM 拆完即下发给工程师），无两级滚动；②角色 SOP 保证「流程不跳步」，**不做需求语义自洽校验**——社区长期反馈正是「大需求喂进去拆出一堆互相矛盾的子任务」，是用户担忧的活案例。
- 借鉴点：PRD 作为拆解的中间规约制品（文档先行、逐角色产出结构化工作），但必须在 PM 拆解前加自洽闸门。

### 2.2 两级滚动拆解（最独特的一块）

**HTN-Orchestrate**（ycdeng-ntu/htn-orchestrate，2026 论文，Apache-2.0）
- 形态：HTN 分层任务网络，全局 Planner **执行中增量展开任务网络**（不预拆到底，每个展开决策吸收已执行结果）；叶子子任务交给 Orchestrator 调度 worker；AND 语义向上传播；当前拆解无法解决时，基于部分结果**重建**任务网络。
- 与构想的关系：**「滚动拆解」机制最贴切的开源实现**——恰好是「粗任务先出整体 plan，执行中发现不能一次达标再细化」的工程化表达。但场景是 research agent（fso100 基准），非需求文档驱动。
- 借鉴点：增量展开 + 部分结果驱动的重建，可直接映射到「粗粒度任务执行失败/不达标时二次拆分」。

**ReAcTree**（Choi-JaeWoo/ReAcTree，AAMAS 2026）
- 形态：动态 agent 树 + 控制流节点 + 双记忆（episodic 示例记忆 + working 环境观察共享）。
- 与构想的关系：分层规划 + 记忆系统的组合形态，但面向具身家居任务（WAH-NL/ALFRED），非软件工程需求。借鉴点：任务粒度与记忆范围随树深关联的机制。

**XAgent**（OpenBMB/XAgent）
- 形态：双循环架构——外环高层规划 + 子树拆解，内环子任务执行；ToolServer 沙箱；human-in-the-loop。
- 与构想的关系：拆解-执行分层 + 沙箱安全 + 人工接管点，与 HelloAI 现有「任务→子任务→执行→沙箱」形态最接近。无需求文档规约化、无需求级知识库。

### 2.3 框架级（可编排但需自建业务语义）

**CrewAI**（~56K ⭐，MIT）：hierarchical process 由 manager agent 拆任务委派 specialist，内置 short/long-term/entity 记忆。**LangGraph**（~44K ⭐，MIT）：Plan-and-Execute 模式 + 状态图 + checkpointing + interrupt（人工审批点）。两者都是框架：流程结构、记忆、审批都给，但「需求规约化、自洽校验、需求知识库」这些**业务语义要自己搭**——对 HelloAI 的参考价值低于 2.1/2.2 的领域项目。

### 2.4 需求知识库 / 上下文

**WeKnora（腾讯开源）**（Tencent/WeKnora，MIT，Go）
- 形态：**同一个知识库**同时服务 RAG 问答 + ReAct Agent（沙箱/技能/MCP/浏览器）+ 自动 Wiki 三合一；跨会话长期记忆（自动抽取 + 用户确认）；多工作区 RBAC。
- 与构想的关系：**知识库 + Agent + 记忆三合一架构最贴近**用户「需求知识库承载执行上下文」的想法。但它是通用企业知识助手，不做「需求→任务拆解→执行」的工程闭环。
- 借鉴点：①同一语料库三种读法（检索问答 / 推理执行 / 结构化沉淀）；②长期记忆要自动抽取但**用户确认才保留**（与 HelloAI 判据 4「同一事实双写必分叉」同向）。

**rekwai**（rekwai/rekwai）：文档 → 结构化需求知识库 + 完整溯源 + 问卷自动应答。贴近「需求知识库」的形态，但用途是合规问卷，不拆任务。

**ReqRAG**（frickly-systems/reqrag）：RAG 生成技术规格文档，实验性质（Conversation Logging + 多检索策略），仅研究参考。

### 2.5 自洽性 / 执行前校验（用户最独特的一块）

- **awesome-qa-skills 需求一致性分析**（naodeng/awesome-qa-skills）：skill 级提示词包，校验多份材料中术语/状态/规则一致性——思路完整对应「需求自洽校验」，但只是 prompt 级，无工程化组件。
- **planner-critic-engine**（deghosal-2026）：2026 年初 157 个目标实测笔记，核心结论「你的 agent 可以完美执行却仍然失败，因为它拿到的计划从来就不是好的」（规划是第一个安全边界）+ 确定性前置条件检查。与用户「自洽且闭环才进拆解，否则纯浪费 token」完全同向。
- **VerifyLLM**（2026）：LLM 将自然语言指令转 LTL 后执行前验证（机器人领域），学术性质。

**结论**：自洽/闭环校验在开源里只有 skill 与论文级参考，**工程化组件基本空白**——这是 HelloAI 可以做出差异化的位置。

### 2.6 开源调研小结

| 能力维度 | 最强参考 | 形态成熟度 | 直接可用性 |
|---|---|---|---|
| 需求→任务结构 | MetaGPT | 高（69K⭐ 生产可用） | 需补自洽闸门、改两级 |
| 两级滚动拆解 | HTN-Orchestrate | 论文级代码 | 机制可移植 |
| 需求级知识库 | WeKnora / HelloAI 自有 | 高 | 自有底座已具备大半 |
| 自洽校验 | （开源空白） | skill/论文级 | 需自研 |
| 执行一致性锚定 | doc-template（用户自有） | 用户项目实测两年 | 见 §4 |

## 4. 治理约束（doc-template）的落点分析 ★（本次核心补充）

### 4.1 doc-template 的本质：项目级行为契约，不是文档模板

「doc-template」仓库（gitee.com/undefined_404/doc-template）实际内容远超「模板」二字，它是一套**面向 AI agent 的行为契约体系**：

- **六份根文档划清角色**：项目基线（现状）/ 目标架构（边界+非目标）/ 实现差距表（唯一定量事实源）/ `CODE_STYLE`（判据式代码规范）/ `AI开发协作规约`（AI 改代码生命周期+红线）/ 文档体系治理（元规则）。
- **唯一事实源 + 冲突裁决优先级**：`代码事实 > 基线 > 目标架构 > 差距表 > 实施计划 > 归档`；「进度只认差距表，双写必分叉」。
- **AI 接入硬约束**：改代码前必须按序读 8 份文档；archive 不得作为当前依据；改码后同步差距表 + 当月 log。
- **判据是机器可校验的契约**（状态词枚举、目录↔索引一致性自检），而不是散文式建议。

本质判断：**doc-template 把「项目」这个实体的状态描述成了可校验的事实集与行为契约**——这与用户构想的「需求规约化」是**同一个思想的两个层级**：doc-template 规约化的是「项目代码怎么写」，需求规约化要规约化的是「这个需求要做什么、怎么验证」。用户已经在项目级实践了这套方法并验证了它锚定异质 agent 的效果，现在的问题是如何把它下沉到「需求→任务」链。

### 4.2 为什么「不同 agent/LLM 结果一致性」成立：契约锚定，而非模型能力

用户实测「用多个不同 agent、不同 LLM 协助，整体结果在预期内」——这正是 doc-template 设计生效的机制：

- 执行 agent 是**异质**的（不同模型、不同上下文窗口、不同工具习惯），单靠提示词无法保证行为一致；
- 唯一能锚定它们的是**注入一份共同的、机器可校验的行为契约**（判据式条款 + 状态机约束 + 断言式验证要求），让「结果是否合格」由契约判定而非模型主观；
- doc-template 的判据式条款（如「目录文件集 == 索引行集」）之所以有效，是因为它**可机械校验**——这与 HelloAI 记忆判据 31「守卫脚本必须 checked==0 必红」同向。

推论：**这条经验要复用到「需求→任务→执行」链，契约必须随任务到达执行侧，且以「可校验条款」形式存在**，而不是写成叙事性建议——否则换一个 LLM 就漂移一次。

### 4.3 落点结论：主在派发约束，辅在拆解引用（一主一辅，非二选一）

**主落点：任务生成/派发 → 执行的约束注入（执行侧契约全文）**

- 位置：任务下发时，把「治理契约」（`CODE_STYLE` 判据 + 协作规约红线 + 文档体系权限位 + 差距表指针）注入执行 agent 的上下文/System，作为**项目级不变量**随每次执行生效。
- 理由：代码质量由**执行侧**决定，异质 agent 的一致性只能靠执行侧契约锚定；用户实测已经证明这条路有效。
- 承载位（HelloAI）：`Task.agentPolicy`（现有 Map 字段，天然是「随任务下发的策略包」）+ 现有 `requiredSkills` 之外的「契约引用」；拆解提示词引用治理文档作为**唯一事实源指针**而非复制。

**辅落点：需求 → 任务拆解（规划侧契约摘要，只引用不复制）**

- 位置：拆解输入中注入**交付契约摘要**：本项目的交付义务（文档回填、验证门禁 `ci-gate`、差距表更新、日志条目）、产出物形态（任务要带验收判据）、规范引用路径。
- 为什么只引用不复制：①拆解关注「做什么」，全量规范注入污染拆解上下文、浪费 token；②规范是项目级不变量，若复制进任务描述则形成双写——违背 doc-template 自己的「唯一事实源」判据（写两处必分叉）。
- 效果：拆出来的任务自带「交付义务 + 规范指针」，执行 agent 按指针取全文。

**两级之间的传递：契约沿任务树继承（粗带摘要、细取全文）**

- 粗粒度任务（EPIC 级）：承载**交付契约摘要 + 规范引用清单**；
- 细粒度可执行任务（二次拆分产物）：**继承**摘要，执行时由派发侧解析为**契约全文注入**；
- 好处：摘要不随树深膨胀，全文只在执行点展开一次，token 成本可控。

### 4.4 与「需求级知识库」的分层（两层知识，不要混为一池）

| 层 | 内容 | 生命周期 | 注入方式 |
|---|---|---|---|
| **系统级契约库**（doc-template） | 代码规范/协作规约/文档治理/验证门禁 | 项目级恒定 | 静态契约注入（每次执行都带） |
| **会话级需求库**（用户构想的 RAG） | 需求文档原文 + 澄清问答 + 决策沉淀 | 随需求会话存续 | 动态检索（按需取，防上下文膨胀） |

- 两层**不可合并**：契约库回答「按什么标准做」，需求库回答「做什么、依据是什么」，生命周期不同（项目级 vs 会话级）。
- 现状核对：HelloAI 的 `KnowledgeBaseService` 已按 conversationId 隔离——正好可作**会话级需求库**底座；系统级契约库目前主要靠「doc/ + prompt_template 兜底」，是否已形成可注入的契约包待后续核对。

### 4.5 自洽性闸门与 doc-template 的关系

- doc-template 的「唯一事实源 + 冲突裁决」解决的是**文档间一致性**；需求自洽闸门解决的是**需求内语义一致 + 业务闭环**——两者互补：闸门验收过的需求文档，其规约化产物（规约要点、能力域清单）天然可以作为拆解的事实源，避免「writer 与 inspector 各执一词」。
- 实现形态建议（调研级，非排期）：拆解前先产出「需求规约摘要」（结构化：目标/边界/非目标/验收判据/能力域清单），复用 `ClarifyStallGuard` 的收敛闭环嵌入自洽校验；校验不过回澄清追问，不过度引入人工。

## 5. 后续建议（research 口径，不写排期）

1. **需求规约化 + 自洽闸门**：在既有澄清链路上增加「规约摘要产出 + 自洽/闭环校验」，复用 `markReady` 前的附件全文位置与 `ClarifyStallGuard` 收敛机制；校验不过自动回澄清追问（用户侧选项 a），人工裁定（选项 b）作为兜底策略待用户拍板。
2. **两级拆解 + 滚动细化**：以 `G-027` 交付编排设计为实施承载体，其「Plan 双表示/滚动拆解」与 HTN-Orchestrate 的增量展开机制同构；粗任务执行不达标触发二次拆分，最终落点仍是现有 SubTask 执行引擎（对齐任务下发）。
3. **治理契约注入**：将 doc-template（`CODE_STYLE` + 协作规约 + 差距表指针）整理为「项目级契约注入包」，随任务派发到达执行侧（承载位 `Task.agentPolicy`）；拆解侧只引用指针。先行核对现有执行上下文（`AgentRuntimeContextAssembler`）是否已注入相关文档，避免重复建设。
4. **开源可借鉴三件**：MetaGPT 的 PRD-中间规约制品形态、HTN-Orchestrate 的增量展开/重建机制、WeKnora 的「一库三读 + 记忆需确认」——均作为设计文档编写时的输入，不直接引入代码。

## 6. 自家 doc 体系机制自评与 doc-template 提炼关系实证（2026-11-23 补充）

> 用户补充背景：「我开源的 doc-template 就是从这个项目的 doc 文档提炼出来的」。本节对 `<项目根>/doc/`（182 份 md、11 个目录，2026-11-23 实测）做一次机制级自评，并实证 doc-template 的提炼关系——回答「这套体系为什么能锚定不同 agent/LLM 的行为一致，以及模板做了哪些减法」。

### 6.1 提炼关系实证：模板声明的三处「剔除」精确对应源头真实现状

doc-template 自述「被证明是负担、已剔除」的三项，在 HelloAI `doc/` 中均有精确历史对应（[实测] `doc/文档体系分类与治理规则.md`、`doc/log/`、差距表 §0）：

| 模板声明剔除项 | HelloAI 源头实证 | 剔除判据（源头规则原文） |
|---|---|---|
| 独立「订正留痕」文件 | `log/HelloAI 差距表订正留痕.md`（承载 `C-1`~`C-42`）已于 2026-10-09 取消，全部并入对应月 Log，`C-NN` 编号退役 | 「一次订正 = 一条 Log」：订正与产出它的迭代同源，分两处存必然漂移（§3.4） |
| 过多编号前缀（`C-NN`/`P0-P3` 双关） | 差距表 §0 注册 `B1~B5`/`RM`/`P0~P3`/`PR`/`REF`/`BASE`/`W`/`TD`/`G`/`AQ`/`MA`/`ARCH`/`ADR` 等十余套；协作规约仍残留 `P0-A/B/C` 阶段标签 | 同号不同义、跨体系复用是历史事故根源；模板只保留 `G-` 与 `LOG-` 两套 |
| 每份文档自带版本变更史 | 治理规则 §6 命名规范 3「版本信息放文档头」+ DOC 体系自身「V2.1/V2.2 演进只在治理文档头」 | 与 `log/` 重复且更早腐烂 |

**结论：模板不是目录结构搬运，而是带两年实战教训的减法蒸馏**——这正是它区别于普通文档模板（只给目录树）的核心价值。

### 6.2 机制内核：为什么这套体系能锚定异质 AI agent 行为一致

用户实测「换多个 agent、多个 LLM，结果仍在预期内」——由四个机制支撑（对照 `doc/README.md` §1 权威文档表与治理规则全篇）：

1. **权威优先级裁决**：`代码/可验证事实 > 基线 > 目标架构 > 差距表 > 实施计划 > 归档`。任何 agent 遇到「计划写已完成、代码里没有」→ 规则直接裁决「没完成」，**冲突裁决规则化**是异质 LLM 行为收敛的第一层；
2. **唯一事实源矩阵**：进度只认差距表、当前事实只认基线、「能算就别存」（判据：两处写同一数字，必有一个错）。**结构上消灭多 agent 各写一套事实的漂移**；
3. **文档头 State 枚举**：状态词是机器可校验的契约（`plan/` 九态 + `verify-plan-status.sh` 停机判据），已从「人遵守」走向「半自动校验」；
4. **生命周期强制流转**：`plan/` 完成必须离场进 `archive/implemented/`——防止「已完成方案」被后来的 agent 当作待办。**语义形态上正是用户担忧「planner 拆出一堆前后矛盾子任务」所缺的闸门**（见 §4.5）。

### 6.3 模板 vs 源头：三个改进点 + 三个未带走项（双向对照）

**模板优于源头（提炼过程产生了新认知）**：

| 改进点 | 源头现状 | 模板做法 |
|---|---|---|
| README 位置 | `doc/README.md` 承担索引，与项目根 README 双入口 | 索引移**项目根** README，`doc/` 不留 README——单一入口，消除「两份 README 读哪个」 |
| 编号数量 | 实战满配十余套（见 6.1） | 理想化最简两套（`G-` + `LOG-`） |
| 项目特有文档 | `产品定位与对比.md` / `参考与致谢.md` / `技术概览.md` 等 | 剥掉，只留可迁移骨架 |

**源头有、模板未带走（反向补进模板的机会）**：

1. **机械守卫脚本族**——`verify-doc-gap-table.sh` / `verify-plan-status.sh` / `verify-event-key-parity.sh` / `check-arch-freeze.sh` 等 110+ 脚本（`scripts/`），把「规则」变成「可执行校验」。模板只提「五态状态词 + 机械校验脚本」一句，未打包脚本层——**这恰是「不同 agent 行为一致」从口号变成工程现实的最后一环**；
2. **九态状态词 vs 模板五态**——源头 `plan/` 用九态（含 `部分完成`/`阻塞`），每个状态有停机判据（状态=`已完成`⇒剩余动作=`—`），模板简化为五态，丢失「部分完成」这类中间态表达；
3. **引用完整性例外细分**——源头区分「路径过期（导航，改）」vs「对象删除（找不到，必改）」、`archive/**`与`log/**`不改史，模板并成一条判据 06，实战颗粒度更细。

### 6.4 对本调研主题的结论衔接

- 印证 §4 判断：**doc 体系 = 「系统级契约库」的现成原型**（§4.4 分层的左边），缺的只是「人手动遵守 → 随任务自动注入」一步；
- 落点优先级再确认：**一级（保质量）** = `CODE_STYLE` 判据 + 协作规约红线 + 差距表指针随任务注入执行侧；**二级（控范围）** = 拆解只注入契约摘要引用、不复制全文——「唯一事实源」判据已经论证了为什么全文复制必漂移；
- 最该先自动化的层 = **6.3 未带走项 1（守卫脚本族）**，对应 §5 建议 3 的「治理契约注入包」——两者结合的最小落地形态：`AgentRuntimeContextAssembler` 核对是否注入契约 + 把 `verify-*` 判据随任务带进执行验收。
