> **Status**: Analysis

>
> **方法**：主会话直接核查 `helloai-core` / `helloai-api` / `helloai-ui` / Flyway 迁移与 `doc/` 体系（因模型 429，专家团子任务未执行，改由主会话完成全部核查）；开源项目先 WebFetch 核验仓库与 LICENSE，用户下载 5 个仓库源码到本地后（`E:/workspace/{LobsterAI-main, Yuxi-main, QwenPaw-main, dify-main, langgraph-main}`），由 1 个成功代理 + 主会话直接采证源码（LobsterAI / Dify / LangGraph / Yuxi 由主会话采证，QwenPaw 由 Explore-2 代理分析）。

> **结论一句话**：**可实现，且比「再做一个管理后台」对平台更友好**——现有 `requirement_conversation → task → planner/executor/reviewer → artifact` 链路已经覆盖了个人助理 80% 的执行内核，**不建议另起执行内核**；真正的缺口是「用户级归属与隔离」「用户级长期记忆」「统一工作台」三件事，而不是聊天本身。

## 1. 结论摘要

| 维度 | 结论 |
|---|---|
| 业务契合 | ✅ 更友好。把「AI 开发管理平台」变成「个人 AI 助理」，用户心智从「操作台」转为「对话即服务」；现有需求对话已是事实上的个人助理雏形 |
| 技术可行性 | ✅ 可实现。执行链路（会话→澄清→拆解→子任务→Agent 执行→评审→产物）已闭环且经真实回归验证 |
| 建议架构 | 复用现有编排内核，新增**助理入口层**（归属模型 + 工作台聚合 API），不另起执行内核 |
| 最大前置缺口 | **用户级归属（owner）与数据隔离**——`BaseEntity` 无 `createdBy`，会话/任务/产物均无用户维度，全局共享 |
| 其次缺口 | 用户级长期记忆（现有为摘要式 + 会话标题关键词召回）、统一工作台、产品化定时任务、IM 绑定 |
| 开源参考 | **LobsterAI（网易有道，MIT）**形态最接近截图；QwenPaw（Apache-2.0）记忆分层；Yuxi-Know（MIT）前端形态；Dify/LangGraph 作编排范式参考（注意 Dify 多租户授权限制） |
| 不建议优先做 | 自动化定时任务、IM 多渠道绑定、助理人格市场、移动端 |

## 2. 业务视角：为什么对平台更友好

### 2.1 用户心智的变化

截图的「个人助理」与 HelloAI 现有「需求对话」本质上都是**对话驱动任务**，但产品叙事不同：

- **现有形态**：需求对话是「开发流程的一个前置步骤」，做完就进入任务列表、计划、执行、评审等管理视图——用户是**操作者**。
- **个人助理形态**：对话是**常驻入口**，任务/产物/历史被收纳进助理的工作台——用户是**委托人**。

同一套执行引擎，后者对非技术用户（业务人员、小团队负责人）友好得多：不需要理解「任务拆解」「子任务」「评审」这些管理概念，只需「说需求 → 拿结果」。

### 2.2 与现有产品的关系（不是替代，是包装）

| 现有能力 | 个人助理中的角色 |
|---|---|
| 需求对话（澄清/流式/附件/直答） | 助理的对话本体 |
| 任务编排（planner/review/task/agent 域） | 助理执行需求的后台 |
| 产物（ExecutionArtifact / 会话附件 / 技能产物） | 助理交付的「工作产物」 |
| Agent 管理 / 插件 / MCP | 助理的「能力来源」，管理界面保留为高级功能 |

信息架构建议：**助理工作台 = 首页**，管理后台（Agent/任务/插件/监控）退居「高级管理」入口。这样既不破坏现有产品，又让新用户第一眼看到的是「助理」而不是「管理台」。

### 2.3 业务风险（关键三条）

1. **预期管理**：个人助理形态会让用户期待「像人一样记住我」。若长期记忆不做成用户级，用户会很快感到「换了个人」——这是体验塌方点，不是技术塌方点。
2. **成本可见性**：对话驱动会让「一句话=一次多轮执行」变得隐蔽，费用感知弱于显式建任务。现有成本画像（Paperclip ⑥成本闸门）应接到助理入口。
3. **多用户边界**：若做多用户产品，数据隔离是安全红线（会话/任务/产物/记忆全链路），不是 UI 问题。

## 4. 技术可行性分析

### 4.1 建议目标架构（复用内核，新增入口层）

```
┌─────────────────────────────────────────────────────────┐
│  个人助理工作台（helloai-ui 新视图，非新项目）             │
│  对话区（复用 RequirementChat 交互）＋ 右栏工作台          │
│  （身份卡 / 最近任务 / 工作产物 / 项目历史）               │
└──────────────────────┬──────────────────────────────────┘
                       │ REST + SSE（复用 chatStream 通道）
┌──────────────────────▼──────────────────────────────────┐
│  助理入口层（新增，helloai-api 扩展，不新起微服务）        │
│  AssistantProfile（助理身份/命名）                        │
│  OwnerContext（当前用户 → 会话/任务/产物归属过滤）         │
│  WorkbenchAggregate（最近任务/产物聚合查询）               │
└──────────────────────┬──────────────────────────────────┘
                       │ 复用现有服务接口
┌──────────────────────▼──────────────────────────────────┐
│  现有执行内核（不动）                                     │
│  planner（拆解/澄清）→ task（编排/Timeline）              │
│  → agent（执行/评审/事件）→ artifact（产物交付）          │
│  → long_term_memory（会话摘要入库）                       │
└─────────────────────────────────────────────────────────┘
```

关键决策：

1. **不另起执行内核**——现有链路已闭环并经真实回归（`LOG-20261025-*` 等）验证；另起内核 = 双轨维护、能力分裂。
2. **不新起微服务**——助理入口层作为 `helloai-api` 的新 controller + `helloai-core` 新服务包，符合现有单应用→分布式演进中的模块边界（9 域依赖链之外新增，需按架构守卫登记）。
3. **归属模型先行**——`owner` 落 `requirement_conversation`/`task`/`long_term_memory`（迁移 + 存量数据回填 + 查询全链加过滤），这是后续一切用户级功能的地基。
4. **前端复用**——`RequirementChat.vue` 改造为工作台主视图（左对话 + 右工作台），不是新写聊天。

### 4.2 可行性分项

| 截图能力 | 可行性 | 路径 |
|---|---|---|
| 持续对话、直接说需求 | ✅ 现成 | 现有 clarify 链路 |
| 助理可命名/身份 | ✅ 低难度 | 新表 `assistant_profile` + 对话页头部 |
| 项目/项目历史 | ⚠️ 中难度 | 会话列表已有，需加 owner + 分组（按项目标签） |
| 最近任务 | ⚠️ 中难度 | `Task` 加 owner + 聚合查询 |
| 工作产物 | ⚠️ 中难度 | `ExecutionArtifact` + 会话产物聚合 + 下载 |
| 自动化（定时） | ❌ 高难度 | 全新领域（调度表 + 触发 + 执行器接线）→ PR1/PR2 |
| 插件/模板市场 | ⚠️ 中难度 | MCP/技能已有底座，市场形态待定 → PR1 |
| IM 绑定 | ❌ 高难度 | 外部渠道适配器 → PR2 |

## 5. 关键技术问题（按优先级）

| # | 问题 | 影响 | 处置建议 |
|---|---|---|---|
| 1 | **用户归属缺失**（`BaseEntity` 无 owner） | 多用户隔离红线 | PR0：迁移 + 查询全链过滤 + 存量回填；在差距表登记新号段 |
| 2 | **长期记忆无用户维度** | 「记住我」承诺落空 | PR0：`long_term_memory` 加 owner；召回升级为语义检索（可复用现有 LLM 通道） |
| 3 | **统一工作台缺失** | 截图形态差最远的一块 | PR1：聚合 API + `RequirementChat.vue` 改造 |
| 4 | **事件推送是拉取式** | 工作台「过程可见」体验打折 | PR1：SSE 已有，扩展事件订阅 |
| 5 | **成本可见性** | 一句话=一次执行，费用无感 | PR1：成本闸门（PC-6）接入助理入口 |
| 6 | **权限粒度** | owner 过滤与现有 RBAC（Sa-Token 角色）如何叠加 | PR1：先 owner 直滤，后角色矩阵 |
| 7 | **产物生命周期** | 个人产物与任务产物的删除语义（unlink 回收站守卫） | PR1：沿用现有删除语义 |
| 8 | **会话并发** | 多会话并发互斥（RC-1~6 已落地）需在助理入口延续 | PR2：沿用 Redisson 互斥 |
| 9 | **自动化调度** | 全新领域，复杂度高 | PR2：登记不启动，等任务执行面稳定 |
| 10 | **IM 渠道** | 外部渠道适配器工作量大 | PR2：门铃机制演化为渠道适配器 |
| 11 | **记忆隐私** | 用户级记忆的展示/删除/导出 | PR1：随 owner 落地配套 |
| 12 | **分布式一致性** | 助理入口跨域调用遵守依赖链（planner→…→shared） | 持续：架构守卫组 2b/3c |

  - **召回注入**：`MemoryMiddleware.on_model_call()`（L125）每次 user turn 调用 `auto_memory_search()`，结果作为**合成 tool 消息插入消息序列**注入；`max_results` 默认 3（显式工具调用 5）；查询词 = 最后一条 user 消息前 50 字符；结果带 `path:start_line-end_line` 定位（可渐进展开）。

## 8. 风险与注意

1. **「只有聊天壳」风险**：截图形态最容易做成「换皮聊天页」。判定：工作台必须接**真实任务状态与产物**（复用现有 TaskTimeline/Artifact），而非静态卡片。
2. **记忆承诺风险**：UI 上给用户「记住我」的暗示前，必须先有用户级记忆；否则是虚假承诺。
3. **归属改造的回归面**：全链路加 owner 过滤会触到 planner/task/agent 多个域的查询——需要按「补闸门四式」逐入口核对（判据 1：规则存在 ≠ 全路径强制）。
4. **架构守卫**：新增「助理入口层」需登记依赖方向（顺向依赖现有 9 域），过 `check-arch-freeze.sh`。
5. **文档治理**：若立项，在差距表 §0 登记新号段（如 `PA-`）+ 计划/设计文档三件套；本评估为调研性质，落 `research/`。
