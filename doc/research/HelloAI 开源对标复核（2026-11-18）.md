## 2. 三家定位订正

### 2.1 DeepSeek Harness：不是「单 Agent 内核」，也不是「不管互操作」

原文定位「单 Agent 运行时内核，对应你的内部 LLM 执行链，不对标平台层」——**前半句对，后半句要收回**。

**它做互操作，而且是主动设计成「可被别人驱动」** `[实测]`：

- `packages/acp/acp/`：把 agent 暴露为 **ACP（Agent Client Protocol）over JSON-RPC stdio** 服务端，能力含 create/list/resume/close session、attach MCP、permission prompts、cancel。
- `packages/subagent/` 下 **7 个后端**：`subagent-acp`、`subagent-claude-code`、`subagent-codex`、`subagent-dsh-sdk`、`subagent-fork-in-process`、`subagent-spawn-in-process`，外加 `tool-subagent` / `tool-subagent-control`。
- `tool-subagent` 里有 `assertSubagentMaxDepth`，即它有**受深度约束的子代理派生**，不是「只跑一个循环」。

所以「单 Agent 内核」的准确说法是：**单进程内核 + 可派生受控子代理 + 可被 ACP 驱动**。

### 2.2 AgentTeams：有代码强制的九态状态机（推翻原文三处）

这是本轮最重要的订正。原文三处（§1 定位表、§4.1、§5 反向对照）都写「没有状态机、靠 Manager LLM 自由裁量、无状态收敛保证」——**与代码不符**。

**① 九态与转移表外化成跨语言契约** `[实测]`

`plugins/teamharness/contracts/task-transitions.json`：

```text
states  = planned, prepared, assigned, in_progress, submitted,
          completed, revision, blocked, cancelled          （9 态）
terminal= completed, revision, blocked, cancelled
transitions:
  planned     → prepared | assigned | in_progress | submitted | cancelled
  prepared    → assigned | cancelled
  assigned    → in_progress | submitted | cancelled
  in_progress → submitted | cancelled
  submitted   → completed | revision | blocked | cancelled
```

同一张表在 Python 侧另有一份 `mcp/common/constants.py:26-32`（`TRANSITIONS`），`TERMINAL_TASK_STATUSES` 在 `constants.py:19`。文件头注明这是**跨语言黄金契约**，Go 与 Python 两侧在测试里互校——这与我们 `scripts/ci/check-arch-freeze.sh` 的「唯一事实源 + 守卫」是同一思路，但**它把状态机本身做成了可被两种语言读取的数据**。

**② 转移是强制的，不是声明** `[实测]`

`mcp/lifecycle/transitions.py:197-249` 的 `_assert_transition` 做四件事：

- 同态重入 = 合法 no-op（幂等重试不需要额外放行）；
- 终态不可变 ⇒ 报 `task is in terminal state ... (immutable)`；
- 非法转移 ⇒ 抛 `IllegalTransitionError`，且**回带 guidance**（告诉调用方「当前态允许去哪」）；
- 每次拒绝都发 `illegal_transition_rejected` 信号，带 `from|to|action` 判别位。

**③ 还有一个覆盖在九态之上的决策子态** `[实测]`

`constants.py:45`：`DECISION_STATUS_VALUES = (open, blocked, frozen, paused, spec_conflict)`，**只由协议层单点写入**（`_set_decision_status`）。配套：

- 催办阶梯：`ATTENTION_STALL_BLOCKED = 2`、`ATTENTION_STALL_FROZEN = 3`（`constants.py:51-52`）——同一条待答复记录被重复催到第 2 次升 `blocked`、第 3 次升 `frozen`；
- `frozen` 是**吸收态**（`transitions.py:1-14`）：只能由「带审批的关闭」解锁（`unfreeze_authority='approval'`），其它任何写入都被拒，且拒绝本身以 `decision_status_history` 的 `refused` 条目留痕；
- 这套语义**在协议开关关闭时也成立**——文件里明确写「refusal 是状态不变量，不是策略闸门」。

**结论**：AgentTeams 的「决策」确实有 LLM 自由裁量的一面（派给谁、要不要拆），但**任务的流转与收敛是代码保证的**。原文把「Manager 派单靠 LLM」外推成了「整个任务生命周期靠 LLM」，这是溯源不足导致的过度概括。

### 2.3 Octop：定位判断成立，但漏了 ACP 出站

原文定位「多用户个人 AI 助手平台，没有任务拆解/调度/验收这一层」——**成立** `[实测]`：全仓 `subtask|sub_task|decompos|acceptance` 检索只命中 `src/octop/api/routers/mbti.py`（人格量表，与任务无关）。

但原文漏了一条对互操作判断有影响的事实：**Octop 的 ACP 是双向的** `[实测]`

- `docs/acp.md:1-9`：**Inbound** = Octop 作 ACP server，被 Zed / OpenCode 驱动；**Outbound** = Octop 用 `acp_runner` 工具驱动外部编码 CLI。
- 出站后端见 `src/octop/infra/agents/acp/session_modes.py:92-127`：`codebuddy`、`claude_code`、`opencode`、`kimi_code`、`codex`（经 `@zed-industries/codex-acp` 适配器）。

### 3.3 不能把 DSH 当安全权威

`SAFETY.md` 自述（`:7`、`:13`、`:15`）`[实测]`：

| DSH | 「只做资产规范」 | **已过期**：`packages/connector/upstream-skills/` 在运行时**从 GitHub 归档下载**上游技能（`src/archive.ts:1` 注释：kept files / path checks / size bound / digest），另有 `packages/skill/tool-workspace-dependencies` `[实测]` |

⇒ **「运行时获取技能」这一环，DSH 与 AgentTeams 已经追平**。原文「技能获取仍是空白」的表述要限定为「**自进化**（从执行历史产出/修订技能）仍是空白」——这一条在三个仓里确实零命中 `[实测]`。

### 4.2 SK-1 不是纯报表：缺 join 键

原文说「你的事件流和台账基建已经够，这是纯报表工作」——**前置不成立** `[实测]`：

- `chat_skill_run` 表存在（`skill_name` / `status` / `phase` / 时间戳），但 **0 行数据**；
- 表里**只有 `conversation_id`，没有 `task_id` / `sub_task_id`**；
- `sub_task.required_skills` 记的是「计划要求什么技能」，不是「实际跑了什么技能」。

⇒ 要算「技能 × 子任务一次通过率」，当前**没有可 join 的键**。必须先在技能执行侧补埋点（把 `chat_skill_run` 关联到 `sub_task_id`），才谈得上报表。这条改写优先级：**它不是「做报表」，是「补数据契约」**。

> **口径订正（2026-11-18 二次核验）**：`chat_skill_run` 属 **planner 澄清域**（`core/planner/entity/ChatSkillRun.java`，注释自述「对话内技能执行运行记录」），`agent` 域对它**零引用**——两边是两条独立的链，「加个关联」不成立。
>
> 反过来，子任务侧技能执行有唯一入口 `SkillExecutionSupport.run(subTaskId, target, command, timeoutSeconds, round)`（`agent/runtime/sandbox/impl/`）：**子任务 ID、技能名、版本、轮次全在入参里**，埋点位置是现成的。
>
> ⇒ 缺口不是「给旧表加一列」，而是「子任务维度压根没有技能执行台账」。形态更可能是**新建表**（或把台账落到已有的沙箱调用记账体系），而不是复用 `chat_skill_run`。

### 4.3 DC-1 已有一半：缺的是候选集

原文说要从零「记录完整候选集 + 各自得分 + 中选者」——**后两项已有** `[实测]`：`sub_task` 已存在 `assigned_agent_id` / `composite_score` / `score_grade` / `score_factors`（五维因子）。

⇒ 真实缺口只是**被淘汰候选的分数没留**。「评分怎么算的」已有数据，「为什么选了 A 而不是 B」没有数据。这个缺口比原文暗示的小得多，且与 SK-1 共用同一批埋点（都要「子任务维度的事实」）。

> **口径订正（2026-11-18 二次核验）**：缺口判断成立，但**成本被高估了**。
>
> 选人逻辑 `AgentSelector.pickFromCandidates`（`agent/executor/`）里，候选列表 `candidates`、质量排名 `qualityRanks`、成本排名 `costRanks`、在飞数 `inFlight`、分档比较器 `tierComparator` **全部已算好**，只是算完就丢；回退路径 `SubTaskDispatchServiceImpl.pickApiKeyLlmAgent` 同样是「筛完取分数最高」（`filter` → `max`）。
>
> ⇒ 改造 = 在「取最高」之前把候选池序列化，**不需要新建选人链路，也不需要重新算分**。这也让它成为八项里改动最小的一项。

### 4.4 我们已有一个同构先例：技能是懒加载，工具不是

这是本轮最可立即借鉴的一条。DSH 0.2.2-rc.4 给 MCP 客户端加了工具加载策略 `[实测]`：

- `packages/mcp/mcp-client/src/config.ts:67`：`toolLoading: 'eager' | 'on-demand'`，**默认 `eager`**；
- `packages/mcp/mcp-client/src/connection.ts:142`：按策略选择 loader；
- `packages/mcp/mcp-client/src/config.ts:23`：`DEFAULT_CATALOG_DESCRIPTION_MAX_LENGTH = 160`（目录摘要封顶）。

`on-demand` 的含义是：**不把服务端全部工具定义塞进提示词，只给一张带摘要的目录，由模型按需加载**。

而**我们自己的技能侧已经是这个模式** `[实测]`：`InternalLlmExecutorTools.java:473` 的 Javadoc 写的是

> 「REF-8.3 全量目录注入，对齐 DSH `tool-skill` 全量目录 + 惰性加载」

## 5. 决策与治理（本轮最大订正）

### 5.1 原文的自我评价要改两处

原文 §4.1 说「相比之下，AgentTeams 的『决策』是 Manager LLM 看 SOUL.md 自由裁量，没有任何结构化的验收判据」——**前半句部分成立，后半句不成立**。

**成立的**：Manager 的**派单对象选择**确实是 LLM 读 prompt 裁量（`SOUL.md` 里没有打分公式、没有候选集排序规则）。
**不成立的**：**任务的流转、验收、完成判定全部有代码判据**，见下。

### 5.2 验收闸：三道拒收 + 自审禁止 + 身份溯源

`plugins/agentteams-teamharness/mcp/lifecycle/review.py:202-250` 的 `_protocol_guard_for_accept` `[实测]`：

| 拒收码 | 触发条件 |
|---|---|
| `review_missing` | 没有 review 记录，或记录畸形 ⇒ 不许 accept |
| `review_not_passed` | review 的 `verdict` 不是 `pass` ⇒ 不许 accept |
| `approval_required` | r1 类（任务结果验收）缺「已解决的审批记录」⇒ 不许 accept |

配套三条更细的约束 `[实测]`：

- **驳回永远可能**：`accepted=False` 直接放行，不受闸门约束（「必须允许打回」是设计前提）；
- **自审禁止**：审批人账号必须 ≠ 任务受派人。注意它做了**身份归一**——Matrix MXID 的 localpart 与运行时 member name 视为同一身份，避免「换个写法绕过自审」；
- **身份溯源**：记录里带 `submitted_by_source` / `reviewer_source`，取值 `runtime`（可信运行时身份）或 `payload`（调用方自报）。**只有 `runtime` 来源才按严格身份比对**；`payload` 来源退回兼容规则（`default`/`unknown`/空永不相等）。判据原话：*a record without the server-written marker is not an approval (fail closed)*。

对照我们：我们有他审/自审、有 `SelfReviewGate`，但**没有「身份来源（runtime vs payload）」这一层**——我们的身份来自 token/鉴权上下文，天然是可信源，所以这一层对我们不是缺口；真正可借鉴的是**「fail closed 的标记式判定」**：不是「字段看起来像审批」，而是「必须是服务端写的那个标记」。

### 5.3 交付物登记闸：状态不等于交付

`plugins/agentteams-teamharness/mcp/project/flow.py:191-213` 的 `_completion_artifact_registered` `[实测]`，注释原文：

> *a completed task counts only if a real artifact was registered. … The status alone is not evidence of delivery — that is exactly the fake-completion loophole this gate removes.*

判据两条，满足任一即可：任务产物文件真实存在（默认 `result.md`），或任务记录带**已校验**且**非空**的 deliverables。项目完成判定处（`flow.py:1369`、`:1383`）强制要求它，否则不许 `complete_project`。

**这条正中我们的软肋**：我们的 `DONE` 是状态迁移的结果，而不是「产物存在性」的结果。`submitResult` 允许空 output 成功（有「空回复归因」逻辑），交付物存在性校验在别处、且不是完成态的前置。这是「状态与事实脱钩」的同类问题——与「无读取方的列 = 反模式」同源。

#### 5.3.1 补漏：DSH 有整套 `packages/deliverables/`，是第三种范式

> **本节为 2026-11-18 二次核验补入**。首版只引了 AgentTeams 的「文件存在/字段非空」判据，漏了 DSH 的三件套——而三件套恰好说明**「交付物」这件事有三种互不相同的做法**。

`deepseek-harness-master/packages/deliverables/` 下三个子包，各解决一半问题 `[实测]`：

| 子包 | 做法 | 范式 | 证据 |
|---|---|---|---|
| `tool-present` | 模型调用工具把文件**主动声明**为交付物，成功后发会话事件 `deliverables/presented`（带 `turn` / `callId` / `files[]`） | **声明式**：我说我交了什么 | `tool-present/src/types.ts:1-16` |
| `workspace-changes` | turn 开始时给工作区打 git 树快照，turn 结束做 diff；记录每个文件的增删改（`WorkspaceChangedFile` / `WorkspaceChangesSummary`），带字节上限与 diff 超时降级 | **事实式**：实际改了什么 | `workspace-changes/src/recorder.ts:1-50` |
| `deliverable-file-references` | 提示词侧把交付物文件引用给模型看 | 辅助 | `deliverable-file-references/src/index.ts` |

**三种范式对照**：

| 范式 | 谁在说 | 代表 | 能不能造假 | 代价 |
|---|---|---|---|---|
| 声明式 | 模型自己声明 | DSH `tool-present` | 能（模型说交了但文件不存在） | 低 |
| 登记式 | 平台查记录/文件存在 | AgentTeams `_completion_artifact_registered` | 较难（要真造出文件） | 中 |
| 事实式 | 平台自己比对前后状态 | DSH `workspace-changes` | 很难（不依赖模型自述） | 高（要快照 + diff） |

⇒ **对我们的直接含义**：`B-2` 不能只抄 AgentTeams 的「查文件在不在」。我们已有的 A 档 `parts` 本质是**声明式**（模型自报分片），如果只配一个存在性检查，仍然依赖模型的诚实。更稳的组合是「**声明（parts）+ 事实（附件落库 / 工作区回读）双查**」，且事实那一侧应当允许按任务类型豁免（纯分析类子任务没有文件产物）。详见 `design/HelloAI 深度审核改造蓝图.md` `MA-4`。

### 5.4 契约文件自带「已定义 / 已强制」标注

AgentTeams 的 `plugins/teamharness/contracts/*.json` 每份都带 `status` 字段 `[实测]`：

| 契约 | status | 含义 |
|---|---|---|
| `task-transitions.json` | （无 status 字段） | 被代码强制 |
| `attention.json` | `enforced-when-protocol-enforce-on` | 有开关，开则强制 |
| `decision-classes.json` | `defined-not-enforced` | **仅数据，无运行时代码引用** |
| `claim-lease.json` | `defined-not-enforced` | 明确写「no lease mechanism exists」 |
| `durability.json` | `defined-not-enforced` | 全部写操作都是同步级 |
| `retry.json` | `defined-not-enforced` | 无自动重试，靠幂等 |
| `error-codes.json` | `defined-not-enforced` | 错误词表，自述 *Data only - the server does not read this file* |
| `team-protocol.json` | `defined-not-enforced` | 角色/工具协议从代码**抽取**成数据；自述 `critic`/`writer`/`coordinator` **无任何角色闸**、默认全放行 |

`decision-classes.json` 的描述甚至写明：*Data only - no runtime code references this file.*

**这是极值得借鉴的诚实机制**：它把「我们设计了」与「我们强制了」写成**机器可读的一个字段**，而不是靠读者去猜。我们的差距表有九态中文口径管「做到没有」，但**代码契约层面没有等价物**——比如 `design/` 的设计文档可能写了某个机制，代码里没有，两者不会互相报错。

### 5.5 信号 `event_id` 的确定性幂等规则

`contracts/signal-mapping.json` 定义 14 个事件的 id 规则 `[实测]`：

```text
event_id = 'ev_' + sha256(team_id|project_id|task_id|loop_id|event_type|
                           source_event|iteration|fingerprint|attempt|audit_seq)[:16]
```

三条值得记的设计：

1. **时钟不参与身份**——*No raw timestamp is ever part of the identity*；区分「同一操作的两次发生」用**持久化的 `audit_seq`**（每次提交 +1），不用时间戳。理由写得很清楚：同一秒内的 pause/resume/pause 在秒级精度下状态字节完全相同，用时间戳会撞号。
2. **重试必落回同一 id**——重放同一操作读同一 `audit_seq` 与同一状态字节 ⇒ 哈希相同 ⇒ 消费方按 id 去重。
3. **拒绝类要额外判别位**——拒绝不提交状态，`ref` 字节在多次不同拒绝间完全相同；因此发 `action|from|to` 追加进哈希输入，把「不同拒绝」区分开。

这与我们的判据「同一事实双写必分叉」互补：**确定性 id 让「同一事实」在多次重试里保持同一身份**。我们的事件流若也用内容哈希做 id，这条规则可直接对齐。

### 5.6 HelloAI 对照：12 态 vs 9 态

| 维度 | HelloAI | AgentTeams |
|---|---|---|
| 状态数 | **12**（`SubTaskStatus.java:3-40`：PENDING / ASSIGNED / IN_PROGRESS / PAUSED / REVIEW / DONE / REWORK / BLOCKED / CANCELLED / DEAD_LETTER / AWAITING_DERIVED / RESTRUCTURING）`[实测]` | **9**（planned / prepared / assigned / in_progress / submitted / completed / revision / blocked / cancelled）+ **5** 个决策子态覆盖 |
| 状态机落点 | 代码（`SubTaskStateMachine.java`、`FinalReportStateMachine.java`）`[实测]` | 代码（`transitions.py`）+ **跨语言数据契约**（`task-transitions.json`） |
| 非法转移处理 | 抛异常 | 抛异常 + **回带 guidance** + 发拒绝信号（带判别位） |
| 终态 | DONE / CANCELLED（DEAD_LETTER 非终态，可人工再指派） | completed / revision / blocked / cancelled（`revision` 是终态，与我们 `REWORK` 可重跑不同） |
| 卡住升级 | BLOCKED → DEAD_LETTER（重分配熔断） | decision_status：催办 2 次 → `blocked`，3 次 → `frozen`（吸收态，仅审批可解） |
| 机器可读契约 | **无**（`find *transition*.json` 零命中）`[实测]` | 有 |

**结论**：状态机这一项我们是**同一量级、不是领先**。真正的差异在：**他们把状态转移表做成跨语言数据并有互校测试，我们把它焊在 Java 里**。这不影响功能正确性，但影响「状态语义能否被非 Java 侧（前端 / 外部执行器 / A2A 投影）共享同一份事实」——这恰好是我们 A2A 投影要解决的那一类问题（ADR-009 D3「无对应态挤 WORKING」就是靠人工维护的映射）。

## 8. 建议先后顺序（调研建议，不构成排期）

> **声明**：下列只是基于「技术依赖 + 验证前置 + 风险」给出的**粗粒度先后建议**，供后续 `design/` 收敛边界、`plan/` 立任务与编号时参考。**不含任何时间承诺与分期口径，不构成承诺**。

**建议先后**：

1. **B-2 交付物登记闸** —— 依赖最少（只需一个存在性判据），且能立刻堵住「状态说完成、产物不存在」的漏洞。它是后面所有质量度量的前提：度量口径若建立在不可信的 `DONE` 上，报表全废。

   > **口径订正（2026-11-18 二次核验）**：「只需一个存在性判据」过于乐观，两点要收：① 纯分析类子任务本来就没有文件产物，先要定义「什么算产物」，否则闸门会误伤；② 我们的落点 `ExecutionResultHandler#handleReport` 是**内外执行链共用**的唯一写点，在此加硬闸会连内部链一起卡。⇒ 实际做法应先「单侧 + 只告警」，见 `design/HelloAI 深度审核改造蓝图.md` `MA-4`。另外它已不再是第一位——`MA-1`/`MA-2` 更便宜且更急。
2. **B-1 工具面按需加载** —— 与 B-2 无依赖，可并行。放在前面的理由是它**降低后续每个工具增量的边际成本**，越晚做，被写死计数的地方越多。
3. **数据契约补齐（`chat_skill_run` 关联 `sub_task_id` + 候选集快照）** —— 这是 SK-1 与 DC-1 的共同前置。**两件事实是一件事**：都需要「子任务维度的事实完整」。原文把它们排在 P1 是对的，但要先把「补埋点」而不是「做报表」写进任务名。
4. **B-3 状态契约外化** —— 前置依赖是 A2A 投影口径稳定（ADR-009 D3 的三条投影原则），因为一旦状态表外化，投影映射就该由数据驱动而不是散在代码里。
5. **B-4 / B-5 / B-6** —— 治理与幂等增强，可在任一步之后插入，不阻塞主线。
6. **ACP 适配器可行性验证** —— 独立于以上全部。它的价值是**可能一票改变「外部执行器怎么接」**，成本远低于等 A2A 生态；建议以「最小 demo 跑通一次会话」为验证目标，而不是先做完整适配层。
7. **安全项（输入扫描 / 出站扫描 / 命令守卫 / 出口收敛）** —— 原文把 SEC 排在最前，理由是「ToB 门票 + 成本最低」。**本复核对成本判断有保留**：规则库 + 误报调优 + 三态交互（脱敏/阻断/放行留痕）并不便宜，且收益依赖「真有用户贴敏感文档」这一前提。更稳的做法是**先只做审计不阻断**（log-only），跑出误报率再决定是否升级为阻断——直接阻断的误报会卡住正常需求，比不做更糟。

**可并行**：B-1 与 B-2；数据契约补齐与 ACP 验证。
