## 2. Archify v3.1 本体实测

取证对象：`E:\workspace\archify-main\archify`（上游原版，`package.json` `version: 3.1.0`）。另见 §2.7 本地补丁副本。

### 2.1 包结构：不是「一份 md」，是「一个运行时目录」

`[外部]` 实测结构（`ls` / `du` / `find`）：

| 目录 | 体积 | 文件数性质 | 运行必需 |
|---|---|---|---|
| `bin/` | 484K | 6 个 `.mjs`（`archify.mjs` 275KB、`visual-check.mjs` 114KB、`finalize.mjs` 46KB 等） | ✅ 主链 |
| `renderers/` | 2.4M | 11 类图的渲染器 | ✅ |
| `schemas/` | 100K | 12 份 JSON Schema | ✅ |
| `references/` | 144K | 9 份说明书（模型按需读） | ✅ |
| `assets/` + `locales/` | 928K | 图标 / 语言包 | ✅ |
| `examples/` | **13M** | 各类型样例 | ⚠️ 参考质量，裁剪不影响可运行性 |
| `scripts/` | 160K | 7 个构建期脚本（`generate-*`） | ❌ 出图不需要 |
| 合计 | **17M / 158 文件** | | |

`[外部]` `SKILL.md` 明写运行前提：「Replace `bin/archify.mjs` in the commands below with the installed package's absolute path」——**它要求可执行的绝对路径，不是一段文本**。

### 2.2 ★零 npm 运行时依赖（决定性利好）

`[外部]` `bin/*.mjs` 与 `scripts/check-render-output.mjs` 的全部非相对 import（`grep -h -oE "from ['\"][^.'\"][^'\"]*['\"]"`）：

```text
from 'node:child_process'   from 'node:crypto'   from 'node:fs'
from 'node:http'            from 'node:os'       from 'node:path'
from 'node:url'
```

**全部是 Node 内置模块，零第三方包。** `package.json` 的 `devDependencies`（`ajv` / `simple-icons`）只被 `scripts/generate-brand-marks.mjs` / `generate-validators.mjs` 这类**构建期**脚本引用，出图主链不加载。

⇒ **只要宿主有 `node >= 18`（`engines`），整包拷过去即可运行，不需要 `npm install`、不需要联网拉包。**

这一点直接改变了部署形态的代价：沙箱镜像只需预装 node，无需 npm registry 可达。

### 2.3 ★门禁分层：四段门禁里只有一段需要浏览器

`[外部]` `bin/finalize.mjs:22`：

```javascript
export const FINALIZE_STAGES = Object.freeze(['validate', 'deliver', 'check', 'browser-check']);
```

`[外部]` 但 `bin/archify.mjs:7079-7110` 显示这四段**各自也是独立子命令**（`case 'deliver'` / `'finalize'` / `'validate'` / `'check'` / `'browser-check'`）；`COMMAND_USAGE`（`:2191-2209`）给出各自签名。

`[外部]` **依赖隔离实测**：`bin/validate` / `bin/deliver` / `bin/check` **均不存在**，它们是 `archify.mjs` 内联实现；对这三个名字的文件做 `grep -n visual-check|browser` **0 命中**；`visual-check.mjs` 只被 `finalize.mjs`（`from './visual-check.mjs'`）引用。

`[外部]` 浏览器需求只出现在 `bin/visual-check.mjs:1334-1336`（命令探测 `chrome` / `google-chrome` / `google-chrome-stable` / `chromium` / `chromium-browser`），失败时 `finalize.mjs:838-846` 产出 `code: 'viewer/browser-check-runtime'`。

⇒ **`browser-check` 与前三段是正交的**：前三段纯 Node 内置模块，第四段要真实 Chromium。

### 2.4 实测：无浏览器、无 npm install 也能出图

`[外部]` 本机实测（Windows，`node v24.14.0`，**未执行任何 `npm install`**），用自带样例 `examples/brand-aware-delivery.architecture.json`：

```text

> node bin/archify.mjs check .tmp/archify-c1/out.html

```

产物（`[外部]` 实测）：

| 产物 | 大小 | 性质 |
|---|---|---|
| `out.html` | 834,609 B | 自包含交互式 HTML |
| `out.delivery.json` | 570 B | 交付回执：`specification.sha256/bytes` + `artifact.sha256/bytes` |

`[外部]` 自包含性实测：`(src|href)="https?://…` 全文件**仅 1 条命中**，且是 `href="https://github.com/tt-a1i/archify"` 署名链接（非资源加载）；内联 `<svg` 1 个、`<script` 3 个。

⇒ **产物离线可看、无需 CDN、无需 egress 放行**；且回执自带 sha256，天然可作「产物完整性证据」。

### 2.5 工作目录语义：需要跨调用保留的可写工作区

`[外部]` `SKILL.md` 正文要求：每次请求建独立目录 `.archify/<type>-<slug>-<YYYYMMDD-HHMMSS>/`，在其中写 `candidate.json`、产出 `<slug>.html`，**修复重跑复用同一目录**；`meta.output` 用相对工作目录的路径。

⇒ 这是「写文件 → 跑 CLI → 读回执 → 定点修改 → 重跑」的多步闭环，**不是一次命令执行**。它要求工作区的**跨调用持久性**。

### 2.6 与平台技能包约定的三处硬冲突

`[实测]` 平台技能包 frontmatter 是**9 字段封闭白名单**（`helloai-core/.../skill/SkillPackageParser.java:17-19`）：`name / version / description / requiredTools / requiredBaseCapabilities / dependencies / inputSchema / outputSchema / validationRules`；未知字段与缺必填一律 `SkillCorruptException`。

`[外部]` Archify `SKILL.md` frontmatter 实际为：

```yaml
name: archify
description: "..."
license: MIT              # 未知字段
metadata:                 # 未知字段
  version: "3.1"          # 顶层缺 version（且非三段式）
```

⇒ **三处冲突（`license` / `metadata` 未知 + 顶层缺 `version`）**，原样放入 `skills/plugins/` 必被判坏包。这不是缺陷，是两套约定不同：平台技能包 = 「元数据 + 正文」；Archify = 「清单 + 运行时目录」。

### 2.7 本地已有一份**打过宿主补丁**的副本（新增事实，前文未记录）

`[实测]` `.workbuddy/skills/archify/`（v3.1.0，17M / 158 文件）存在，且：

- **未被 git 跟踪**：`.gitignore:109` 忽略 `.workbuddy/`；`git ls-files .workbuddy/skills/` 为空 ⇒ 这是**本机私有副本**，CI / 部署环境不存在，**不可作为交付来源**。
- **与上游不一致**：`bin/archify.mjs` md5 不同（`finalize.mjs` / `visual-check.mjs` / `package.json` 相同）；`SKILL.md` 148 行 vs 上游 125 行，多出 23 行「Local Windows patch (installed 2026-10-14)」。

`[实测]` 该补丁段（`.workbuddy/skills/archify/SKILL.md:129-148`）自述两条宿主适配：

1. **`renderers/shared/atomic-output.mjs` — `TRUST_LINK_COUNTS` 平台开关**：NTFS 删除硬链接后不递减剩余名的 link count，导致原子发布的 `expectedLinks === 1` 终检**必然失败**；win32 下把精确 link-count 校验降级为「至少一个存活名」，保留 inode/device/mode/content 校验；**POSIX 行为不变**。
2. **`bin/archify.mjs` — 10 处 `stdio: 'pipe'` 改为 `['ignore','pipe','pipe']`**：原文「The sandboxed host rejects pipe-stdin child processes with EBUSY」。

**两条事实**（本文档新增，须进 plan 的输入）：

- **补丁 1 是 Windows 宿主专属**，POSIX 不变 ⇒ 若沙箱镜像为 Linux，**不需要**该补丁；
- **补丁 2 指向「受限宿主拒绝 pipe-stdin 子进程」** ⇒ 说明 archify 的 `spawn` 行为**对宿主环境敏感**。本次实测用的是**未打补丁的上游版**且在普通 Windows 上通过，**不能据此推断它在 OpenSandbox 容器内同样通过**（§6 待核 1）。

## 3. 平台侧落地接口面复核

### 3.1 技能包通道是一条纯文本单文件通道（边界，非缺陷）

`[实测]` 四条边界逐条确认：

| 边界 | 证据 |
|---|---|
| 扫描只收平铺单层 `.md` | `SkillPackageScanner.java:29` `classpath*:skills/plugins/*.md`，注释「只扫平铺一层」 |
| 摄入闸门只解清单一个条目，其余只做安全校验后丢弃 | `SkillPackageZipGate.java:122-131`；清单名硬编码 `skill-package-manifest.md`（`:43-44`，注明「禁止用 SKILL.md」） |
| 存储只有正文一个 TEXT 字段 | `InstalledSkillPackage.java:77-84` `private String body;` |
| 注入给模型的是「速览」（前半段） | `SkillSpeedSummaryRenderer.java:20-34` 按 `\n---\n` 切段 + 剔 `# ` 行 |

⇒ 结论与前文 §2 一致（技能加载 ≠ 技能执行），但**边界更具体**：即使只想要「多文件说明书」，当前通道也承载不了——它没有文件树概念。

### 3.2 平台已有「整目录 ZIP」下发通道（外部 Agent 侧）

`[实测]` `AdminAgentController.java:378-409`（`getMySkillZipByAgentId`）自述：「SKILL.md（占位符已渲染）+ scripts/ 全量脚本 + config.example.json … **zip 内顶层目录为 `<role>-skill/`，整体解压/复制到 IDE 的 skills 目录即可使用**；只下载单个 SKILL.md 会导致 scripts/ 脚本缺失」。

`[实测]` 实现 `PromptTemplateServiceImpl.java:195-241` 用 `classpath:onboarding/<role>/**/*` **递归枚举整目录**，顶层写 `SKILL.md`、其余保持相对路径。

`[实测]` 现有 `onboarding/executor/` 已带脚本：`clock.ps1` / `clock.sh` / `config.example.json` / `pull_tasks.ps1` / `process_one.ps1`。

⇒ **这条通道的落点语义与 `npx skills add` 同构**（把文件夹放对位置 + SKILL.md 躺该层）。它是前文路径①的现成载体，**零改造即可承载多文件技能**（前提：技能不依赖平台执行）。

### 3.3 沙箱执行链已交付（前文的路径③前提已变）

`[实测]` 三条已交付能力：

| 能力 | 证据 |
|---|---|
| 沙箱执行通道 | `SandboxExecutionService`（`execute(subTaskId, command, timeoutSeconds)` / `release` / `readWorkspaceFile`）；工具 `internal_run_in_sandbox` 已接线，默认 `enabled=false` fail-closed（`OpenSandboxProperties.java:22-23`、`SandboxExecutionToolContributor.java:60-63`） |
| **同子任务复用沙箱** | `OpenSandboxProperties.java:39-56` `reuseEnabled=true`（`ADR-005`），注释：「写入的文件跨调用保留，模型可对上一轮产物做增量编辑（`sed -i` / `python` 定点改）」；空闲 TTL 900s，turn 末显式 release |
| 沙箱内文件读写 SDK | `OpenSandboxProbe.java:79-90` `sandbox.files().writeFile / readFile / deleteFiles` 三件套已在探针中使用 |

`[实测]` 诚实边界（`ExecutionPolicy.openSandbox()` 自述）：`filesystem=ISOLATED`、`network=PARTIAL`、`process=PARTIAL`——**不标全 ISOLATED**。

⇒ `ADR-005` 的复用语义**正好是 §2.5 要求的跨调用持久工作区**；`files()` API 也已在探针验证可用。这两项在前文写作时（2026-10-15）**尚不存在**。

### 3.4 产物回传通道已有雏形（只读 `.md`）

`[实测]` `SandboxExecutionService.java:52-70` `readWorkspaceFile(subTaskId)` 自述来历：「平台只采集**对话正文**（`AgentExecutionResult.output`），沙箱文件从不自动上传。实测 MiniMax-M3 两次执行都是『20 轮全在沙箱里写 `/workspace/draft.md`、对话区只剩 604 字节写作过程叙述』⇒ 假成功 ⇒ 评审 3 轮全驳回 ⇒ 死信。正文其实早就写出来了，只是没交出去。」

`[实测]` 其能力边界：只读**篇幅最大的一份 `.md`**、**不创建**沙箱、不承载判定。

⇒ 「沙箱文件 → 平台」这条通道**已被证明可存在**，但当前形态是「单文件 + 仅 `.md` + 按体积猜测」，与 §2.4 要交的 `out.html` + `out.delivery.json`（指定路径、指定 MIME、成对交付）不同。

### 3.5 三处接口面缺口（`[实测]`，精确到签名）

| 缺口 | 现状 | 影响 |
|---|---|---|
| **沙箱规格是全局单例** | `SandboxExecutionService.execute(...)` 无 spec / image 参数（`:28`）；镜像来自 `OpenSandboxProperties.spec.image`（默认 `python:3.12`，`:68`） | 无法让某类技能用专用镜像；且 `ADR-005` 复用槽以 `subTaskId` 为键 ⇒ 同子任务先跑 python 验证再跑 node 出图，**会命中错镜像的旧沙箱** |

## 4. 两条对既有结论的时效性订正

### 4.1 订正一：路径③的触发口径应从「①+②」收窄为「②」

`[外部]` 前文 §5 表格写：路径③「补沙箱执行」⇒ 触发**条件① + ②**。

`[推断]` 该判定写于 `S-7`/`S-8`（2026-10-17 交付）**之前**，当时「补沙箱执行」隐含「新建一个碰宿主的执行能力」。按**前文自己钉死的判据**（§5「看平台侧是否出现一个 *agent 可调用* 且 *碰宿主* 的工具」）重算：

- `internal_run_in_sandbox` 已是**既有**工具（不是新增工具面）；
- 其执行发生在 OpenSandbox **容器内**，`filesystem=ISOLATED`，与 app 物理隔离、不注入 app env、不接 app 网络（`§3.3`）；
- ⇒ **「碰宿主」不成立** ⇒ **不触发条件①**。

但 **条件②「技能包要被执行」仍然独立成立**——本项正是该条件的具体候选（前文 §5 已如此认定）。

**裁定结果（2026-10-26，用户拍板）**：取**候选 A** ⇒ **仅触发条件②**。

| 口径项 | 候选 A（**采纳**） | 候选 B（未采纳） |
|---|---|---|
| 触发判据 | 沿用前文机械判据 ⇒ 仅触发**条件②** | 认定「技能脚本进执行面」本身即需重排期 ⇒ 触发 ①+② |
| 依据 | 判据是「碰宿主」，容器内执行不碰宿主（前文 §5 原文） | 保守口径：判据应扩为「执行不可信代码」 |

`[推断]` 候选 A 与前文判据自洽；候选 B 需先修改前文的判据定义，属于**判据变更**而非本次调查结论 —— **本次裁定不改判据**。

**裁定后果**：`G-005` 的**条件②首次真实命中**（前文写作时条件②只是「该条件的具体候选」，本项使其成立）；条件①/③均不触发。承接见 `plan/HelloAI 技能执行面接入实施计划（2026-10-26）.md`（`SKX-x`）。

### 4.2 订正二：条件③「平台自持浏览器」可与条件②剥离

`[外部]` §2.3 / §2.4 已实测：`validate` / `deliver` / `check` 三段**不依赖浏览器**即可产出 HTML 与交付回执；`browser-check` 是独立子命令。

`[推断]` 因此「让平台执行该技能」存在**两个不同档位**：

| 档位 | 需要宿主提供 | 触发的 `G-005` 条件 | 质量保证的差别 |
|---|---|---|---|
| **执行，不做视觉门禁** | node ≥18 | 仅② | 静态校验通过（实测 9/9 artifact checks + composition showcase pass）；**缺**真实浏览器下的布局/溢出保证 |
| **执行，含视觉门禁** | node + Chromium | ② + ③ | 四段门禁齐全（含 `browser-check`） |

⇒ 前文未区分这两档（当时未做门禁分层实测），本文补上。

**裁定结果（2026-10-26，用户拍板）**：取 **C1 先行**（只上 `node`，不装 Chromium）⇒ **条件③不触发**；`browser-check` 档登记为后续独立缺口，不在首个实施计划的范围。

## 8. 结论

1. **「Archify 类技能」的实质要求是三个而不是一个**：`node` 运行时、**跨调用持久的可写工作区**、可选的真实浏览器。三者中平台**已具备第二个**（`ADR-005` 复用沙箱），第一个是镜像问题，第三个已被实测证明**可与主链剥离**（§4.2）。
2. **平台现状与本项的距离是「四块接线」而非「重造能力」**：沙箱规格分层（§3.5 缺口 1）、技能包文件注入（缺口 2）、产物指定回传（§3.4）、工具面一项（缺口 3）。
3. **三路径框架仍然有效；路径③的触发口径已裁定为「仅条件②」**（§4.1）：`S-7`/`S-8` 交付后「碰宿主」不成立，条件②独立成立 ⇒ **`G-005` 条件②首次真实命中**，条件①/③不触发。
4. **最重要的成本优化是条件③可推迟**（§4.2，已裁定 **C1 先行**：只上 `node`、不装 Chromium）：产出实测通过的 HTML + sha256 回执，代价是放弃真实浏览器布局保证——**这条必须显式声明，不得含糊**。
5. **三个待核事实必须先探**（§6，已裁定**并入实施计划首任务** `SKX-1`~`SKX-3`），其中「容器内 spawn 是否被拒」直接决定要不要带宿主补丁——这一条本次**没有**验证，不能当结论。
