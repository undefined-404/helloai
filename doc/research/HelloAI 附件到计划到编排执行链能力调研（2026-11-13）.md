> **状态：Analysis**
>
> 最后更新：2026-11-15（追加 §10：代码现状二次复核 + 图片识别前置功能与开源借鉴；追加 §11：从工作台起步的整体缺口复核 + 技能自动注入与在线更新可行性；§7 未决口径补充至 8 条；追加 §12：上下文压缩 / RAG 与附件切片 / team 模块价值复核）

> **调研问题**：用户希望平台能做到——在个人工作台与 AI 助手对话时上传需求附件或图片，平台把材料分析整理成**一份可分步执行的计划（Plan）**；计划节点再逐个调用现有拆解能力变成子任务，分派给内部 LLM agent / 外部 AI agent 执行；每个节点执行完成独立验证；最终让复杂的开发/工作任务能被拆成可执行小工作，并实现内外 agent 协同。参考形态见用户提供的四张界面截图（项目 = 动态 / **计划** / 任务 / 资产 四页签 + 右侧项目配置）。

## 0. 一句话结论

**目标链路的 7 段里，中间 5 段（拆解 / 二次拆分 / 分派 / 执行 / 审核）已经真实可跑且能自动闭环，前后是断的**——「图片进模型」完全没有通道、「对话出方案」只是提示词文案不落产物、「计划层实体」根本不存在、「按序执行」只有准入守卫没有编排器。所以这不是「再补几个功能」，而是**要在现有 5 段稳态能力之上，补一层「计划」载体 + 补一条多模态输入通道 + 补一个派发编排器**。

## 2. 逐段现状实测

### 2.1 附件接入：文档半条腿，图片零通道

**能用的**（`[实测]`）：
- 两套附件表刻意分表——子任务产物 `attachment`（`V1__init_all.sql:576`，按 `sub_task_id` 聚合）、会话附件 `chat_attachment`（`V121__chat_attachment.sql:26`）。
- 解析路由 `DocumentParserRouter`（`DocumentParserRouter.java:30-33`）：`TEXT` / `STRUCTURED`（pdf/doc/word/ppt/excel/rtf/odt/epub/html）走 Tika，上限 200k 字符（`DocumentParser.java:13`）。
- 三层 Prompt 注入 `ChatAttachmentPromptRenderer`（`:165`）：`MANIFEST`（恒注入清单）/ `CONTEXT`（按预算注入正文）/ `RETRIEVAL`（超预算走 KB 片段）；决策阶段只给前 500 字预览（`:57`）。
- 预算单源 `AttachmentContentPolicy`（`:25`/`:32`/`:35`）：单文件 64k、总量 200k、按窗口 40% 取小。

**不能用的**：
- `ContentKind.MEDIA`（图片/音视频）源码注释明写「**P0 阶段 `SKIPPED`，P1 接视觉直读**」（`ContentKind.java:17`）；`ChatAttachmentParseWorker` 落库文案是「图片/音视频暂不支持正文提取（P0 阶段），仅登记元信息」（`:136-140`）。
- 全仓业务侧 `Media` / `imageUrl` / `data:image` / vision **零命中**（`base64` 仅 6 处，全与凭证/技能传输/沙箱输出相关）；`ModelCapabilities` 只做能力谓词存取，**不驱动消息构造**（`ModelCapabilities.java:38`）。
- 前端 `accept` 白名单**不含图片扩展名**：`RequirementChat.vue:1023`、`Workbench.vue:312`（后端允许上传但只登记，口径不一致）。
- `requirement_message_attachment` 建表（`V121:65`）后**全仓零 Java 引用**。

**一个被忽略的现成基础**：`spring-ai-commons-1.1.8` 里 `org/springframework/ai/content/Media.class` 与 `MediaContent.class` **存在且已在本仓依赖树内**（`helloai-core/pom.xml:97` 引 `spring-ai-client-chat`）；`llm_provider_model` 的 `capabilities` 已给 `deepseek-v4-flash`、`kimi-k3/k2.7/k2.6` 等回填 `input:["text","image"]`（`V110__llm_provider_model_capabilities.sql:71-88`）。**即：数据层有档位、SDK 有类型，只差「构造消息时读能力表」这一步代码**。这条链没有接通，是纯未实现，不是技术不可行。

### 2.2 对话 → 方案：只有提示词，没有产物

- 工作台四张建议卡「整理成方案 / 拆解任务 / 生成文档 / 指派 Agent」（`Workbench.vue:733-737`），点击只把一段指令塞进 system prompt（`AssistantSkillDirective.java:29-38` 的 `PLANNER_INSTRUCTION`、`:40-52` 的 `TASK_INSTRUCTION`）。**不落库、不建任务、不产生任何可确认实体**。
- 助理 system prompt 甚至明令「除非用户明确要求，**不要生成任务需求草案或替用户建任务**」（`AssistantPromptBuilder.java:13`/`:74`）。
- 「转为任务」= `createTaskFromContext`（`AssistantChatServiceImpl.java:311-334`），只新建一条 `kind=REQUIREMENT / mode=CHAT` 会话 + **一条 seed user 消息**，内容是最近 6 条对话每条约 300 字摘要（`:89-90`、`:711-720`），**附件不随迁**；之后必须跳到 `/requirement-chat` 重来。
- 现有「方案」的唯一结构化产物在任务侧 `task_plan_draft`（`V147__plan_draft_staging.sql:24-64`），但那是「**一个 task 内部的拆解草案**」，不是「跨任务的计划」；且该表**只有读接口**（`PlanDraftController` 仅 `GET /listByTaskId`）。

⇒ 「方案」在产品上被拆成四级跳：附件 → 需求终稿 → 任务 → 草案 → 确认计划，**第一跳（图片）与第二跳（助理转方案）都是断的**。

### 2.3 方案 → 任务：两个独立确认点

| 路径 | 确认 | 位置 |
|---|---|---|
| `POST /finalizeById/{id}` | **需确认**（前端 `ElMessageBox.confirm`） | `RequirementConversationController.java:562`；`RequirementChat.vue:3282` |
| `/task` 斜杠直达 | **无需确认**（LLM 出 final 即自动建） | `ClarifyRoundOrchestratorServiceImpl.java:604-651` |
| 助理侧 `createTaskFromContext` | 只建会话，**不建任务** | `AssistantChatServiceImpl.java:311-334` |

建任务后落 `PENDING`，还必须再触发 `task:plan` → `AWAITING_PLAN_CONFIRM` → `confirmPlan` 才转正（`PlannerAnalysisServiceImpl.java:261`）。**方案确认与任务创建是两个确认点**，与用户期望的「对话中直接产出可执行 plan」相差一层。

### 2.4 拆解 / 二次拆分：能力最强的一段，但「二次」不是嵌套

**这一段是平台真正的资产**（`[实测]`，全部稳态可跑）：
- 草案暂存区 `task_plan_draft`：`code` 定宽（`<yyyyMMdd><seq:04d>[-<seq:03d>…]`）⇒ **字典序 = 树前序**；`depends_on_codes` 存 code 不存 id（位置作废重建后引用不断，`V147:12`）；`node_state` 三态 `ACTIVE/DISCARDED/CONFIRMED`；`round` 多轮只读 `max(round)`。
- 门禁三时机 + 唯一放行口：拆解落库（`PlannerDecomposeAsyncServiceImpl.java:774-796`，**阻断不回滚只 warn**）→ 改造类回滚（`SubTaskServiceImpl.java:257-270`）→ 确认口 `recheckStaged`（`PlannerAnalysisServiceImpl.java:313-334`，有 block 抛 400）。判据下沉 `DraftGateChecker`（`RULE_VERSION = "s5-3"`，`:56`，纯函数零 LLM）；结论写 `sub_task.context.gateFindings`（唯一写点 `SubTaskGateFindingsStore`）。
- 尝试栅栏 `task_plan_attempt` 五态 + 租约 + `attemptId` CAS，堵「跨 attempt 迟到写入」。

**「二次拆分」的真相**（这条最容易被误判）：
- `sub_task` **没有** `parent_sub_task_id` 列，**不支持行内嵌套**。
- 「子任务的子任务」是**派生独立 Task**：锚点 `task.parent_sub_task_id`（执行期）或 `(task.parent_task_id, task.parent_draft_code)`（草案期）（`V148__task_derivation.sql:21-28`），DB 硬约束 `depth ≤ 2`（`:54-55`）⇒ **最多 3 级**。
- 三条落地路径：草案期 `deriveDraftByCode`、执行期 `enterRestructuring`（入口白名单 `BLOCKED/DEAD_LETTER/REWORK/PAUSED`）、反向 `propagateDerivedCompletion`。
- **三处深度判据口径不一致**：应用层 `min(getMaxExpandDepth(), 2)`（`PlannerAnalysisServiceImpl.java:637-648`）、DB `≤2`、门禁按 code 连字符数推算且无 code 行**fail-open 跳过**（`DraftGateChecker.java:328-343`）。

### 2.5 按序执行：只有准入守卫，没有编排器

这是用户期望与现状差距**最结构性**的一处：

| 事实 | 位置 |
|---|---|
| 依赖只有 `sub_task.depends_on`（JSONB id 数组），语义「全部 DONE 后本任务才可分发」 | `V27__add_sub_task_depends_on.sql:18` |
| 就绪判定 `isReady`（依赖全 DONE）+ 批量 `filterReady` | `SubTaskQueryServiceImpl.java:277-289` |
| **`task` 层没有依赖概念**（`Task.java` 无 `depends_on`，全仓无该列） | `[实测]` 已验证为空 |
| 确认后派发是**逐条 `for` 循环串行触发**，依赖未就绪者就地返回 null 交 60s 定时任务重扫 | `PlannerAnalysisServiceImpl.java:448-459` |
| 全仓 `dispatchBatch` / `nextDispatchable` / `topoSort` / `DagScheduler` / `dispatchMode` **零命中**；唯一拓扑算法是 `DraftGateChecker.hasCycle`（Kahn，只做环检测） | `DraftGateChecker.java:277-317` |

⇒ 并发是执行侧线程池（`executionCommandExecutor` 4/16/200）的**副作用**，不是编排决策；「顺序」靠时间轮询**涌现**，不靠调度计划。计划层（跨任务顺序）**完全不存在**。

### 2.6 独立验证：双层齐备，两处已知缺口

- 子任务级 `SubTaskReviewServiceImpl.onSubmittedForReview`（`:186-197`，提交即进核验）+ 终报告级 `FinalReportReviewServiceImpl.evaluate`（`:276`，`fidelity.blocks()` 时**不给 LLM 放过机会**）。
- 审核者**只能** `ACTIVE + API_KEY_LLM`（`ReviewerPickerImpl.isUsableReviewer:176-180`）；`ReviewExecutionEngine` 明写「**不改状态不落库**」（`:33-35`）⇒ **审核者动不了文件**，这正是「独立验证」成立的前提。
- 证据硬检查 fail-close（`reviewEvidenceAssembler.checkEvidence`，`:350-369`）。
- 已知缺口（已登记）：`G-034` 审核侧证据**可见性**（Attachment 注入无 id/无区间、`internal_read_attachment` 被剪枝到约 5k 字符）、`G-030` 自审闸门失败**未** fail-close。

### 2.7 内外 agent 协同：两条通道能力不对称

| | 内部 LLM agent | 外部 AI agent |
|---|---|---|
| 接入 | `API_KEY_LLM`，平台侧发起 | `CLI_CLIENT`，**MCP 主动拉取**（`McpMcpServer` 13 工具，`:70-464`；含 `pullTasks`/`claimSubTask`/`heartbeat`/`uploadArtifact`/`submitResult`/`reportBlocked`/`checkOut`） |
| 门槛 | 无 | **心跳在线才可分派**（`HeartbeatService` TTL 5min）+ `agent_duty_lease` 租约（同一 Agent 同时仅一条 ACTIVE） |
| 手脚 | 进程内 13 个 `internal_*` 工具（含 `internal_run_in_sandbox`） | **自己 OS 环境**，平台只派单 |
| 产物回收 | `internal_register_output_attachment` + 沙箱回读 | `uploadArtifact` + `submitResult` → 同一 `ExecutionResultHandler` |
| 附件可见 | ✅ | ✅（`buildSubTaskDetail` 返回 `attachments`，`McpReadModelServiceImpl.java:246-269`） |
| **代码仓地址** | ❌ | ❌ |

**共享的一面**：提交后走**同一条** `SubTaskSubmittedForReviewEvent`（`ExecutionResultHandler.java:421`）、同一审核域、同一返工/死信预算。⇒ 「同一个任务里内外 agent 协作」在数据与状态层**已经成立**，缺的是「谁做哪一步、产物怎么交给下一个」的角色化编排。

## 3. 三条必须纠偏的事实（决定后续方案形态）

### 3.1 「内部 LLM agent 能访问 gitee/github 拉代码」——在平台沙箱内**不成立**

用户提到实测过内外 agent 都能拉代码。必须区分：

- **外部 agent（trae / qoder / teleagent）成立**：它们跑在用户自己的机器上，有自己的网络、自己的 Git 凭据、自己的项目目录。平台只是派单 + 收结果，**不提供仓库也不提供网络**。
- **内部 LLM agent 在平台沙箱内不成立**，三条独立证据：
  1. 沙箱规格 `network-policy.default-action: deny`（`application.yml:197-198`）；
  2. **全仓唯一 `ProcessBuilder` 是 `PgDumpRunner.java:300`（备份专用）**——平台进程从不执行宿主任意命令，也没有「repo 拷贝进工作区」环节；
  3. 仓地址 `task.context.executionEnv.repo`（`ExecutionEnv.java:323`，四态 `NONE/PREEXISTING/REMOTE/LOCAL`）**读取方只有 planner 域**（`PlannerDecomposeAsyncServiceImpl.java:956-958` 注入 `{{EXECUTION_ENV}}`），**agent 域零读取方**，MCP 13 工具返回里**没有 repo 字段**；`subtask-review.md:138` 还对审核者明说「你**看不到源码仓库**」。

⇒ 若曾在测试中成功，那是外部 CLI agent 在宿主环境做到的效果，**不能据此认为平台沙箱具备该能力**。已登记 `G-033`（执行侧与派发校验未闭环），且「仓库注入」形态经用户裁定「**先调查、不预设形态**」。

### 3.2 工作台「整理成方案」不产生方案

它只是把一段中文指令拼进 system prompt（`AssistantSkillDirective.java:29-38`）。产物仍是**聊天正文**，不是可确认、可编辑、可派发的实体。「转为任务」还要把附件丢掉、只搬 6 条 300 字摘要。**用户在图里看到的「计划」页签，后端没有对应表**。

### 3.3 「二次拆分」不是 `sub_task` 递归

是**派生新 Task**（`task.depth ≤ 2`，最多 3 级）。这一点影响方案设计：如果用户想的是「在一个计划下挂一棵多层的执行树」，现有能力是「多个平级 Task，各自有自己的草案与子任务」，**父子关系在 `task` 表上而非 `sub_task` 表上**。计划层若要做树，应挂在 `task` 派生链上，而不是再造一套嵌套。

## 4. 缺口清单（按「挡不挡目标链路」排序）

| # | 缺口 | 现状 | 影响 | 已有锚点 |
|---|---|---|---|---|
| **1** | **计划层实体不存在** | 无 `project` / `plan` / `phase` 表（`[实测]` 全仓为空）；任务之上无载体 | 整条目标链的**骨架缺失**：没有「计划」就没有「计划节点」，也没有「按计划顺序」 | `G-027`（设计成文 `Planned`，未实现） |
| **2** | **多模态输入零通道** | `ContentKind.MEDIA → SKIPPED`；前端 accept 不含图片 | 「上传需求图片」直接不可用 | `ATT-2`（待开始）；`R14`（条件触发） |
| **3** | **无派发编排器** | 只有 `depends_on` 准入守卫 + 60s 轮询；`task` 层无依赖；无批次/拓扑/并发控制 | 「依次有序执行」靠涌现，长计划会抖动、重复扫描、无法表达跨任务顺序 | 无（新） |
| **4** | **对话方案不落产物** | 「整理成方案」= prompt 文案；助理转任务丢附件、只搬摘要 | 用户要多跳 4 次页面才能拿到计划 | `G-028` 相关 |
| **5** | **代码仓地址不进执行侧** | `executionEnv.repo` 只 planner 读；MCP 返回无该字段；沙箱网络 deny | 内部 LLM 无法「拉代码改代码」；外部 agent 只能靠猜路径 | `G-033` |
| **6** | **派发前无环境校验** | 无 `ExecutionPrereqChecker`，技能 AND 不匹配即静默 `PENDING` | 「无原因停留」比 `BLOCKED` 更难排查 | `G-033` |
| **7** | **审核证据可见性不足** | 注入无附件 id/区间；`internal_read_attachment` 被剪到约 5k | 「独立验证」会因看不见而误判 | `G-034`（`RV-8`~`RV-13`） |
| **8** | **同一任务可写工作区共享** | reviewer 与 executor 共用可写容器；`READ_ONLY` 只平台层 | 审核独立性在差距表里按**缺口**记，不按已解决记 | `SL-10`（待开始） |
| **9** | **二次拆分深度判据三处不一** | 应用 `min(cfg,2)` / DB `≤2` / 门禁按 code 段数且 fail-open | 门禁可能对超深计划静默放行 | `TD-13` |
| **10** | **附件逐消息引用未接线** | `requirement_message_attachment` 建表零消费者 | 「这张图对应哪句话」无法结构化 | — |

## 5. 开源可集成 / 可借鉴

### 5.1 文档与图片理解 —— **建议直接集成，不自建**

用户目标里「上传图片/附件 → 整理成方案」的第一个硬门槛就是「看懂图片」。现仓的 `Tika + PDFBox` 是纯文本路线，补视觉要走「渲染页 → 视觉模型转写」，成本和精度都不如成熟的文档结构化工具。

| 项目 | 许可 | 与目标的相关性 | 建议 |
|---|---|---|---|
| **Docling**（IBM / LF AI & Data）`[推断]` | **MIT**（`Granite-Docling-258M` 权重 Apache 2.0） | PDF/Office/HTML/**PNG/JPG/TIFF 图片** → 结构化 markdown/json；能识别**阅读顺序、表格结构、公式（LaTeX）、代码块、图片分类与标题归属**；提供 CLI / Python / **HTTP 服务（`docling-serve`，可 Docker 起）** / **MCP server**；完全离线可跑 | **最贴合**。以 sidecar 形态接入（HTTP 服务），替换/增强 `DocumentParserRouter` 的 MEDIA 分支；`parser` 字段可直接记 `docling`。这正是 `ATT-4`「版面增强（Docling sidecar，登记不启动）」原本点名的方案 |
| **PaddleOCR**（PP-OCRv5/v6 + PP-StructureV3 + PaddleOCR-VL）`[推断]` | Apache 2.0 | 中文识别强，表格/版面坐标可输出 markdown/JSON | 中文截图、扫描件优先候选（Docling 的 Granite 权重对中文仅「实验性支持」） |
| **MinerU**（OpenDataLab）`[推断]` | 2026 年起由 AGPL 转更宽松条款，条款需自行核实 | 复杂版面 | 备选；许可条款须先核 |
| **Marker**（Datalab）`[推断]` | 代码 Apache 2.0 / **权重 OpenRAIL-M** | 表格转换可选 | 谨慎：权重许可有附加限制 |
| **olmOCR 2**`[推断]` | Apache 2.0 | 纯 OCR，需 ≥12GB GPU | 不优先（部署门槛高） |

**接入形态建议**：不把 Docling 装进 Java 进程，按 `docling-serve` 跑成独立 sidecar，`ChatAttachmentParseWorker` 增加一条 `parser=docling` 分支，失败回落到现行 Tika/视觉转写。理由：Python 依赖与本仓 JDK17 运行环境隔离，也符合既有「沙箱/外部能力不塞进主进程」的口径。

### 5.2 编排 —— **不接框架，只借思想**

| 候选 | 结论 | 理由（本仓判据） |
|---|---|---|
| **Temporal** | **明确不接** | 本仓 `HelloAI 交付编排能力设计.md` §1.3 已裁定「不引入 Temporal 等工作流引擎——与现有 DB 状态机双写**必分叉**」（判据 4「同一事实双写必分叉」）。而且本仓已有比它更贴合的等价物：`task_plan_attempt` 五态栅栏 + 租约 + `attemptId` CAS + 25 个 `@Scheduled` 兜底任务，本身就是 durable execution |
| **LangGraph** | **不接**（Python/TS 生态，Java 平台无对应实现） | 但值得借两点：① **checkpointer** = 「每个超级步后落快照」，本仓对应 `task_plan_draft.round` + `node_state`；② **`interrupt` / `resume`（human-in-the-loop 断点）** = 本仓对应 `AWAITING_PLAN_CONFIRM` + `confirmPlan`，**已经更强**（有 DB 约束与权限） |
| **Airflow / Prefect** | 不接 | 批处理 DAG 调度器，与本仓「带 LLM 与人工确认的非确定性节点」语义不匹配 |
| **ACP（Agent Client Protocol）** | **值得借接口形态** | 设计文档 §3.4 已预留 `CodingAgentProvider` 四方法（`createSession` / `execute` / `getStatus` / `cancel`），外部 Coding Agent 统一接入 |

**一句话**：缺的不是工作流引擎，而是**「计划」这个数据载体**和**「派发编排器」这个循环**。分布式编排框架解决的是「进程崩了怎么恢复」，本仓已经用 DB 状态机解决了；框架解决不了「计划节点该按什么顺序派、派给谁、产物怎么交给下一个」——那是**业务编排**，只能自己建。

### 5.3 代码仓访问 —— **只借「纯 Java Git」一点**

| 方案 | 结论 |
|---|---|
| **JGit**（Eclipse，纯 Java Git 实现）`[推断]` | **可集成**，且是当前最优解：不需要宿主装 git、不需要新增 `ProcessBuilder`、可以在沙箱内或 Java 进程内做 clone/fetch/commit。这能绕开「全仓只有 1 处 `ProcessBuilder`」的既有边界 |
| **git worktree 隔离**（每子任务一工作目录、共享对象库） | 借设计思路（`HelloAI 交付编排能力设计.md` §3.5），但**前置是仓库能进到执行侧** |
| **短期最小权限凭证下发**（凭证不进 agent 环境变量） | 借思路；本仓已有 `credential_vault` + `AgentApiKeyCipher` 可承载 |
| SWE-agent `repo.py` 的 `LocalRepoConfig.copy()` | **慎用**：那是 SWE-bench「模型改具体仓库」场景，与本仓「技能型执行、无 repo 拷贝环节」的架构基准冲突（`G-033` 已记此待调查，用户裁定先调查不预设形态） |

### 5.4 明确**不**建议引入的

- **自建 IDE / diff 编辑器 / 代码索引 RAG**：与本仓「编排 + 验收 + 留痕」的差异化无关（设计文档 §1.3 已裁定）。
- **第二套沙箱**（如把 OpenHands Runtime 接进来）：与现有 `OpenSandbox` 是竞争关系，会变成「两套沙箱、两套回读、两套超时」。设计文档已裁定「只取 ACP 接入思路、不接其运行时」。
- **新 `delivery` 领域**：设计文档 §3.2 已裁定「扩展优于新建」——计划归 `planner`、工作区归 `task`、验收归 `review`、外部接入归 `agent`。

## 6. 粗粒度执行顺序建议（供 `design/` / `plan/` 参考）

> **性质**：本节是调研结论中的**能力先后建议**，回答「先补什么，后面的能力才验证得出来」。它不是承诺排期，不含日期、工期、逐项状态或完成度，也不替代正式任务拆解。
> **使用方式**：`design/` 用 §7 的未决口径收敛技术边界，`plan/` 再把下面的建议拆成正式编号、任务、验收与状态；两者可以调整本顺序，但应说明推翻了哪条依赖判断。
> **排序判据**：「谁的缺失让后面验不出来」，而不是「哪个好改」。同一层中标注「可并行」的事项不必串行等待。

### 6.1 先补输入通道与计划载体

1. **多模态输入通道**：读取 `capabilities.input` 是否含 `image`，成立则构造 `UserMessage(Media)`。
   - **前置**：无。SDK `Media` 已在依赖树，能力表已有 image 档位，模型已注册。
   - **为什么先做**：可独立于计划层验证，先在需求对话里证明「图片能进模型」，再决定工作台如何引用附件。
   - **依据**：`ATT-2` 原口径，对应缺口 2。
2. **计划层实体**：Plan + PlanNode，挂在现有 `task` 派生链上，不新造嵌套。**首轮建议只做「容器」，不做项目级滚动拆解**；后者需要 `baseCommitSha`、版本化与滚动重拆，应在有真实多项目样本后再定形。
   - **前置**：无，但必须复用 `task_plan_draft.code` 定宽树序，不建第二套树。
   - **为什么先做**：它是方案落库、节点拆解、进度汇总和顺序派发的共同载体，也是「计划」页签成立的最小前提。
   - **依据**：`G-027` 设计 §4 数据模型已有草样，对应缺口 1；范围收窄理由见 §9.6。
3. **两项可并行的小修（不必等待上述两项完成）**：
   - **派发前环境校验**：`ExecutionPrereqChecker` 校验 `accessType × executionEnv`，不匹配即 `BLOCKED` 并带原因；无前置，可最早消除「无原因 PENDING」（缺口 6）。
   - **二次拆分深度判据归一**：门禁改读 `task.depth`，删除按 code 段数推算与 fail-open；无技术前置，但必须先统一三处判据口径（缺口 9）。

### 6.2 再把方案变成可派发对象

1. **工作台「整理成方案」落产物**：写 Plan 草稿并提供确认，不再只是 prompt 文案。
   - **前置**：计划层实体。
   - **依据**：§2.2，对应缺口 4。
2. **计划节点触发既有拆解**：复用 `decompose` / `confirmPlan`，门禁与 attempt 栅栏原样沿用。
   - **前置**：计划层实体 + 方案落产物。
   - **依据**：§2.4，对应缺口 1、5。
3. **助理转任务保留附件**：替代「最近 6 条 × 300 字摘要、附件全丢」。
   - **前置**：多模态输入通道；没有图片通道时，仅搬附件元信息仍不能让模型读到图片。
   - **依据**：§2.2，对应缺口 4。

### 6.3 然后让计划按依赖顺序跑起来

1. **派发编排器**：计划节点级「就绪集合 → 并发上限 → 记录派发决策」。
   - **前置**：计划层实体 + 节点触发拆解。
   - **复用**：现有 `isReady` 与 `AgentSelector`，只新增批次选择与决策记录这一层。
   - **依据**：§2.5，对应缺口 3。
2. **最小能力边界**：先实现 `nextDispatchable`（按 `depends_on` 求就绪集合）、子任务级并发上限、派发决策落表；让顺序从时间涌现变成可解释、可审计的调度决策。
   - **本调研不建议纳入首轮**：动态分支（`G-009` 已暂缓）、跨计划优先级抢占、关键路径估算。

### 6.4 最后补齐代码仓执行与隔离证据

1. **仓库进执行侧**：
   - **决策点前置**：先做 `G-033` 仓库注入适用性调查（用户已裁定先调查，不预设形态）。
   - **若内部沙箱路线成立**：沙箱规格放开 `network-policy`（仅指定域名/端口）+ JGit clone。
   - **若外部 agent 路线足够**：外部 agent 通道补 repo 地址下发（MCP 工具返回补 repo 字段）。
   - **前置**：派发前环境校验。此项包含安全边界决策，不是纯代码改造（缺口 5）。
2. **审核隔离**：`/workspace` volume 化 + reviewer 只读挂载（`SL-10`）。
   - **前置**：无强依赖；若与「仓库进执行侧」同动沙箱挂载，可合并验证（缺口 8）。
3. **工时与工程进度视图可随后补**：先做「实际」不做「预估」。实际工时从已有 `agent_execution_record`（`V97` token 用量）+ 子任务起止时间推导，先做只读看板；预估工时需要真实使用样本，否则会成为无读取方的空字段。

### 6.5 顺序之外的两条形态约束

1. **计划层实体若不先定「计划节点与 `task` 的关系」，后续会产出两套并行树**（`task.depth` 派生链一套、Plan 节点一套）——正是判据「同一事实双写必分叉」的形态。建议 Plan 节点**就是**一条 `task` 占位行，或 Plan 节点只存 code + 引用 `task_id`，不另存一份层级。
2. **计划节点触发拆解不得新建第二条拆解路径**。现有 `decompose → 草案 → 门禁 → confirmPlan → 物化 → 派发` 已是多次迭代收敛出的稳态链路（`TD-13` / `TD-14` / `TD-15` 都在这里），另起一条会同时绕开门禁、attempt 栅栏与幂等索引。

**推荐的最短验证主线**：图片能进模型 / 计划有载体 → 方案能确认并复用既有拆解 → 就绪节点能被显式派发 → 仓库访问与审核证据能支撑真实开发任务。环境校验与深度判据两项小修可并行提前，不必等主线。

## 7. 未决口径（决定后续形态；不构成待执行计划）

> 以下是调研过程中暴露出的**形态分歧点**，属调研结论的一部分（「哪些路线被排除」的开放面）。
> 它们**不是** `plan/` 的「前置待决」任务清单——未拍板前不存在计划。拍板后这些分歧点应被 `design/` 的 `Scope` 与「不含项」吸收。

1. **「计划」是什么粒度**：是「一份文档 + 若干计划节点（每个节点 = 一次任务）」？还是「项目级（`G-027` 的 Plan + Phase + 滚动式拆解）」？两者差距很大——后者要 `baseCommitSha`、版本化、滚动重拆。
2. **计划确认几次**：现在是「建任务确认 + 计划确认」两次。用户要「对话中直接产出可执行 plan」⇒ 是否允许**一次确认**（确认即建任务并进入派发）？这会动 `AWAITING_PLAN_CONFIRM` 的现有语义。
3. **图片要不要真多模态**（直接把 `Media` 发给视觉模型，成本高、需视觉模型），还是**先转写文本再进澄清**（`ATT-2` 原口径，成本低、可缓存、可引用回源）？建议后者，但需用户确认。
4. **「内部 LLM 拉代码」到底要不要**？如果要，就必须放开沙箱网络策略 + 引入 Git 凭据管理，这是一次安全边界变更（当前 `network-policy: deny` 是有意为之）。若「外部 agent 拉代码」已够用，则 `G-033` 只需做「repo 地址下发 + 派发前校验」这一半。
5. **工作台形态**：截图的「项目 = 动态/计划/任务/资产 + 右侧指令/连接器/专家/技能」是 **WorkBuddy 的通用助手形态**。HelloAI 定位是「任务编排平台」（有 Agent 管理、审查中心、质量看板）。是否照搬「连接器/专家/技能市场」这一栏，还是只取「计划/任务/资产」三栏 + 保留自有「审查/质量」入口？
6. **G1 起点形态**（第三轮新增）：工作台「整理成方案」先落**单节点 Req 级草案**（最快、不动 Plan 容器，先验证交互），还是直接上 Plan/PlanNode 容器？建议前者（§11.2）。
7. **G3 并行方式**（第三轮新增）：图片进模型 P1~P3 最小切片是否以 probe 形式先行验证一张截图（可与 G1 并行、互不阻塞）？§10 已给五段前置表，P1+P2+P3 是自足最小切片。
8. **技能在线源形态**（第三轮新增）：在线拉取的「来源形态」——GitHub/Gitee 公开仓库 raw zip（对标 `skills-lock.json`）还是私有清单服务？以及**安全边界**（来源白名单 + `checksum_sha256` 强制校验 + 沙箱执行隔离、`network-policy` 白名单默认 deny）须在 `design/` 阶段先定两件事（§11.3.3）。

## 9. 追问议题：是否集成禅道类开源项目管理产品

> 触发：用户追问（2026-11-13）。截图那套「动态 / 计划 / 任务 / 资产」被用户描述为「更像工程进度图，类似禅道这种成熟产品」，并提出两条路：① 集成禅道，把 AI 管理与调度升级到「工程化」；② 找更轻的同类产品，因为禅道「过于丰富过于成熟，内部用得到的功能有限」。
> 本节结论**先于理由**，理由只用本仓已核实事实 + 产品模型常识。

### 9.1 结论

**不建议集成禅道，也不建议集成任何现成的项目管理产品。但用户想要的「工程化」是真实缺口，只是它不在产品里，在三个具体能力上。**

理由不是「禅道太重」（那只是取舍问题，可裁剪），而是一条会直接产生缺陷的结构问题：**引入外部项目管理产品 = 给任务状态造第二个事实源**，正撞判据 4「同一事实双写必分叉」。详见 §9.2。

### 9.2 为什么「集成」这条路在原理上就不成立

**（a）两套状态机的驱动源不同，且都不可让渡。**

- HelloAI 的 `sub_task.status` 由**机器事件**驱动：门禁结论（`DraftGateChecker`）、attempt 栅栏、审核驳回、租约超时兜底、`DEAD_LETTER` 重投。
- 禅道类产品的 `task.status` 由**人点鼠标**驱动：人把「进行中」拖到「已完成」。它的整个价值主张建立在「人负责推进」这个前提上。

这两者没有映射关系。要同步，只能在两边各写一次 → 双写。**禅道不会因为你这边审核驳回就把状态退回，你也不会因为人在禅道点了「已完成」就认为门禁通过了。**任何一侧的写入都会让另一侧失真，而失真无法自动判出（谁是对的？）。这不是工程难度问题，是模型冲突。

**（b）你真正要的那部分「工程化」，禅道里恰好没有。**

禅道的能力边界是「人的协作流程」：需求池、迭代、Bug 生命周期、测试用例、工时。它**没有**：

| HelloAI 独有、且是稳态资产 | 外部产品的对应物 |
|---|---|
| 草案暂存区 + 定宽树 code + `depends_on_codes`（`V147:28,48`） | 无（它有树，但没有「草案→门禁→转正」三段） |
| 拆解门禁结论 `gateFindings` / `acceptanceKindDeclared` | 无 |
| attempt 栅栏 + 幂等键 `batch_key`（`V147:32`） | 无 |
| 沙箱生命周期与台账证据（`SL-1`~`SL-9`） | 无 |
| 审核证据可见性（`G-034` / `RV-8`~`RV-13`） | 有「审批」，但审批依据是人的意见，不是可执行判据 |
| 心跳租约 / 派发熔断退避（`dispatchBlockedSubTask` 闸门） | 无 |

也就是说：**集成后，你要的「工程化」一分没多，反而多了一套要同步的状态、一个 PHP+MySQL 的额外进程、一份跨库无事务的最终一致性负担。**（禅道是 PHP + MySQL，与现栈 PostgreSQL/Java 不共享事务边界——跨库一致性只能靠轮询对账。）

**（c）本仓已就该类问题裁定过，方向一致。**

`doc/design/HelloAI 交付编排能力设计.md` §1.3 已明确：不引入 Temporal 等工作流引擎（`":41"`，理由「与现有 DB 状态机双写必分叉」）、不自建 IDE/代码索引（`":40"`）、不新建 `delivery` 域（`":97"`，「扩展优于新建」）。**同一判据直接适用于外部项目管理产品**——它比 Temporal 的侵入性更强（Temporal 至少还是进程内可编排的，禅道是独立系统）。

### 9.3 但「工程化」这个直觉是对的：缺口在三个具体能力，不在产品

用户说「截图更像工程进度图」——这个判断准确。把它翻成能力项，只有三条，而**三条都有相当比例已存在**：

| 缺口 | 现状（已核实） | 判定 |
|---|---|---|
| **① 容器：一个「计划/项目」把若干任务归到一起，并向上汇总进度** | 全仓 `CREATE TABLE project` / `.*phase` 零命中；`task` 无 `depends_on`。**没有容器层** | 真缺（`G-027`） |
| **② 树与依赖：计划节点的层级 + 依赖边** | **已有**：`task_plan_draft.code` 定宽树编码（`V147:28`，注释明写「字典序 = 树的前序」）+ `depends_on_codes`（`:48`）；`sub_task.depends_on` 是真实 JSONB 列（`SubTask.java:166-167`），读侧强制走 `dependsOnIdList()` 归一化（`:212`） | 已有，不必外求 |
| **③ 进度可视化：分层依赖图、批次、状态着色** | **已有**：`helloai-ui/src/components/SubTaskDagView.vue`（297 行，echarts 自绘），按 `dependsOn` 连线、按状态着色、横轴渲染「第 N 批」（`:163`），点节点跳详情 | 已有，只差「时间维度」（甘特） |
| **④ 调度：谁下一个跑、一次几个、顺序从哪来** | **无**：`dispatchBatch` / `nextDispatchable` / `topoSort` / `criticalPath` 全仓零命中；`maxConcurrentLlmCalls=8` 只是 LLM 调用信号量（`AgentExecutionProperties.java:234`），非子任务级并发；顺序靠 `isReady`（前置全 DONE）+ 60s 轮询**涌现** | 真缺 |
| **⑤ 排期与工时：预估 vs 实际** | 无 `estimate` / `actual` 字段。`task_iteration`（`V42`）看似有 `round_num` / `depends_on`，但实为**报告生成后的回填快照**（`AgentEventContextResolver.java:17-18`：「轮次固定取 1」），不承担排期 | 真缺 |
| **⑥ 人工干预留痕：谁改了什么、为什么** | **已有**：`TaskController` 干预入口齐全——`planById` / `confirmPlanByTaskId` / `rejectPlanByTaskId` / `updateDraftByCode` / `regenerateDraftByCode` / `deriveDraftByCode`（`:186,199,205,219,269,236`）；配套 `timeline_event` / `agent_events` / `activity` | 已有 |

**所以「工程化」的真实差距 = ① 容器 + ④ 调度 + ⑤ 工时**，而②③⑥你比大多数开源项目管理产品做得更深（它们没有「草案→门禁→转正」三段，也没有 attempt 栅栏）。

一件事值得单独指出：**用户截图里的「计划」页签，不集成任何外部产品也能做出来**，因为它要的三样东西里有两样（树/依赖/批次图）已经在仓里，只差①容器把任务串起来。这比接一套 PHP 系统的成本低一到两个量级。

### 9.4 如果仍要外部系统：唯一安全的形态是「单向向外投影」

假设有一个真实诉求必须由外部系统满足（例如客户/PMO 要求在他们已有的系统里看到进度），那么**方向必须反过来**：

> **HelloAI 是唯一事实源（唯一写者）；外部系统是只读镜像。单向流出，永不流入。**

- 实现形态：HelloAI 补一个 `ProjectionPort`（或直接用已就绪的 `/api/mcp` 面），把「计划节点 → 迭代项」按固定节奏**推送**出去（创建/更新），且**不消费对方的状态变更**。
- 判据落点：这样只有一侧写，判据 4 不触发；对方界面上任何人工改动都在下一轮推送被**覆盖回** HelloAI 的真相——需要在文档里写明这条，否则运维会当成 bug。
- 反面形态（**明确禁止**）：把禅道当任务主数据、HelloAI 派发前先读禅道状态。这会让 `isReady`、门禁、attempt 栅栏全部依赖一个无事务的外部库——一次网络抖动就会让子任务永久卡在 PENDING，且无法自愈。

### 9.5 若确需选型：按「能否只做投影」而不是「功能多寡」排序

**说明 `[推断]`：本轮外部检索被环境拦截（敏感内容批准超时），以下为该类产品的模型常识，非 2026 年现行版本/API 现状核实结果。选型前须自行核实当前版本、API 能力与许可。**

| 候选 | 技术栈 / 与现栈关系 | 若只做投影的适配度 | 备注 |
|---|---|---|---|
| **禅道 ZenTao** | PHP + MySQL，独立进程、独立库 | 低：模型是「人推进的迭代/需求/Bug」，字段与 `sub_task` 语义错位大；跨库无事务 | 用户自己也判断「过于丰富，用得到的有限」——这个判断是对的 |
| **OpenProject** | Ruby on Rails + PostgreSQL | 中：`work package` 模型抽象度高、API v3 较成熟、原生甘特 | 与 PG 同库型是唯一优势；但 Ruby 栈对 Java 团队是长期维护成本 |
| **Plane** | Django + PostgreSQL，现代轻量 | 中高：`cycle` / `module` 贴近「计划+批次」，API 友好 | 更接近用户想要的「不要那么重」 |
| **Vikunja** | Go + Vue，轻量 | 中：清单/看板/甘特够用，模型简单 | 功能最薄，适合纯展示 |
| **Taiga** | Python + Django，偏 Scrum | 低：Scrum 语义（用户故事/冲刺）与「AI 拆解任务」不匹配 | 不推荐 |
| **Jira** | 商业、SaaS | 低 | 「过于成熟」问题更严重，且数据出境 |

**关键判据不是上表的分数，而是：无论选谁，都只允许它读你、不允许你读它。**若某候选无法做到（例如它的 API 只提供「双向 webhook」而不提供只读拉取），直接排除。

### 9.6 对 §6 建议顺序的范围修正

不改变 §6 的先后结构，只收窄其中三项的**范围口径**；这些收窄已同步反映到 §6.2~§6.4：

1. **「计划层实体」——建议优先只做「容器」，不做项目级滚动拆解**
   理由：容器是①②③⑥的粘合点，且能立刻让「计划」页签成立；而 `G-027` 的项目级形态（`baseCommitSha` + 版本化 + 滚动重拆）是另一个量级，在没有真实多项目样本前无法定形，过早做会重蹈「先建结构再找用途」。
2. **「派发编排器」——只做三件事**：`nextDispatchable`（按 `depends_on` 求就绪集合）→ 并发上限 → 派发决策落表。
   **不做**：动态分支（`G-009` 已暂缓）、跨计划优先级抢占、关键路径估算。
   判据：让「顺序」从时间涌现变成可解释的调度决策，且决策落表可审计。
3. **「工时」——只做「实际」不做「预估」**
   实际工时从已有 `agent_execution_record`（`V97` token 用量）+ 子任务起止时间**推导**，先做只读看板；预估工时需要人填，在没有真实使用场景前是空字段（判据 2「无读取方的列」）。

**一条反向警告**：不要把「甘特图」当起点。甘特需要「预估工期」，而 AI 执行的真实工期在跑之前不可知——先做甘特会产出一张**用假数据填的图**，比没有更糟。先做「已发生的时间线回放」（数据已有），用它反推合理的预估口径。

### 12.1 上下文压缩：两套实现，都是真 LLM 摘要压缩（不是截断），已默认开启

用户疑虑「没有怎么用过，感觉不一定靠谱或管用」。实测结论：**项目里有两套独立的压缩实现，都是「先确定性剪枝、再 LLM 摘要」的真压缩，且默认开启、已接进主链路**。这与 Claude Code / Aider / DeepSeek Harness 的 summarization 压缩是同一类机制，不是简单丢弃历史。

| 套 | 落点 | 机制 | 触发 | 证据 |
|---|---|---|---|---|
| **运行时压缩**（子任务执行内，一个 turn 的消息列表） | `agent/runtime/loop/impl/ContextCompactor.java`（REF-8.2.3，类注释明写对齐 DSH `compaction-basic` + `compaction-tool-result-pruner`） | **两道**：① `ToolResultPruner` 确定性剪枝（超 8192 码点 → 头 4096 + 标记 + 尾 1024，留可审计标记行，不切代理对）；② 仍超预算才 **LLM 摘要**（替换而非追加） | ① 每轮模型调用前压力检查（估算 token ≥ 窗口 × 0.8）；② provider 报超窗错后压缩并重试本轮（上限 1 次） | `ContextCompactor.java:127-161`（两道+两触发）、`ToolResultPruner.java:37-55`（剪枝算法）；接线点 `ChatModelToolLoop.java:163/179/192/195` |
| **对话压缩**（工作台/需求对话，跨轮历史） | `planner/assistant/service/impl/ContextCompactorServiceImpl.java`（PA-12） | **滚动摘要**：计算占用 → 阈值判定 → 尾部按 `reserveRatio=0.20` 逐字保留 → 中段交 LLM 生成滚动摘要（带上一版摘要累积）→ 更新 `compacted_until_seq` 指针；**原始消息不动、可回查** | 每轮对话自动调用（`compact(conversationId, false)`），也可手动 `/compactById` 强制 | `ContextCompactorServiceImpl.java:54-119`；自动触发点 `AssistantChatServiceImpl.java:505`；手动入口 `RequirementConversationController.java:418-420` |

**运行时压缩的几条硬纪律**（与开源标杆逐条对齐，不是简化版）：

- **头部固定保留** system + 首条 user（任务上下文绝不被压），**尾部按 `retainRatio=0.16` 逐字保留**，只压中段（`ContextCompactor.java:190-237`）。
- **绝不拆开 `assistant(tool_calls) + tool_result` 配对**——以「单元」为单位选区，这是 DSH 的 balanced boundary 纪律（`:266-282`）。
- **净收益守卫**：摘要反而比原文长（实测出现过 4939→6327 的净增）则**回滚原文**，不接受「越压越大」（`:238-250`）。
- **摘要额度**：单次执行封顶 2 次，防「每轮都试一次」的抖动（`:163-166`）。
- **token 估算用 jtokkit**（spring-ai 自带 `JTokkitTokenCountEstimator`），不是字符粗估（`:74`、`:289-307`）。
- **失败纪律**：压缩任何一步失败只告警、不阻断循环（`:156-160`）。
- 默认配置：`context-compaction-enabled: true`、窗口 `64000`、阈值 `0.8`、retain `0.16`、溢出重试 `1`、每 run 摘要上限 `2`（`application.yml:313-319`）。

**与开源能力的真实差距（三条，都不是「没有压缩」而是「参数/精度」）**：

1. **运行时窗口写死 64000**：`application.yml:314` 注释自己承认「须与部署模型实际窗口一致……暂以配置承载」。若实际模型窗口更大则过早压缩、更小则过晚。开源（DSH）是从路由模型信息读的。
2. **对话侧 token 用字符粗估**：`ContextWindowProperties.charsPerToken=1.6` + 每条固定开销 4（`:24-27`），不是真 tokenizer；且对话摘要 prompt 限 **400 字**（`ContextCompactorServiceImpl.java:43`），长对话可能丢细节。
3. **对话侧摘要质量依赖 planner agent**：摘要走 `platformAgentExecutionService.executeSync`（`:139`），planner 不可用时保留上一版、本轮不压缩。

**结论**：「不靠谱」的印象不成立——机制是真压缩且纪律完备（净收益守卫、不拆 tool 对、失败不阻断都是实战修正过的）。真正需要校准的是**窗口配置与估算精度**，不是补功能。

1. **生产默认关闭**：`application.yml:505` `enabled: ${KB_ENABLED:false}`（REF-6.13 新能力默认关）；只有 `application-local.yml:85` 默认开。生产没开 = 工具被摘除、检索降级为空。
2. **全库知识（非会话附件）没有运营入口/数据**：目前 kb 里的数据几乎全部来自「会话附件超预算 ingest」，没有「运维手册/规范文档」这类全库知识的批量导入运营动作——`search_knowledge` 工具因此常常无内容可召回。
3. **预算内附件根本不走 kb（这是设计如此，不是缺陷）**：`ChatAttachmentParseWorker.maybeIngestToKb():115-120` 明确「**只在超预算时做**——预算内附件全量注入更快更准（无召回损失），ingest 是『读不到』的补丁，不是默认路径」。所以「大附件切片只用了一半」的观感，实际是「小附件全量注入、大附件才切片检索」的**有意分层**。

**结论**：RAG 不需要「开发」，需要的是**打开开关 + 补全库知识的运营导入**。附件切片链路是完整且分层合理的。

### 12.3 team 模块：真实角色是「任务级 agent 组合模板（快照展开）」，不到子任务级；开源里 team 是「角色扮演式框架」的一等公民，图编排框架则不需要

用户疑虑「team 没真正接入拆解后的子任务分派」「担心设定完是画蛇添足」。实测结论：**team 不是没接线——它在任务创建时就展开成 `agent_policy` 快照并落库，子任务分派确实在用这份快照**；但 team 本身确实**不到子任务级**，而这恰恰是正确的设计，不需要补。

**team 的真实机制 `[实测]`**：

| 事实 | 证据 |
|---|---|
| team = 成员槽位组合（PLANNER / EXECUTOR / REVIEWER），一 agent 一槽位，weight 预留**不参与派发排序** | `TeamMember.java:19-30`、`V70__create_team.sql` |
| **唯一消费点**：任务创建时 `expandAgentPolicy` 把 team 成员按槽位展开成 `agent_policy.executorAgentIds / plannerAgentId / reviewerAgentId`，**快照落库**，后续派发不受 team 成员变更影响（快照隔离） | `TaskServiceImpl.java:150-162`、`TeamPolicyExpander.java:30-53` |
| 子任务分派确实消费这份快照：`executorAgentIds` 白名单 + `required_skills` AND 匹配 | `SubTaskDispatchServiceImpl.java:322/693-697` |
| `sub_task` / `task_plan_draft` **无 team_id 列**——team 不到子任务级 | 全 migration 无 `team_id`（除 team 自身两表） |
| 空池行为：Team 无成员**抛异常**（不可作展开源）；缺某槽位（如 EXECUTOR）则不写白名单 = **不限定（回退全局池）** | `TaskServiceImpl.java:159-161`、`TeamPolicyExpander.java:34-39` |
| 选人算法仍是 `max(score)`，与 team weight 无关 | `SubTaskDispatchServiceImpl.java:572-580` |

**开源对标 `[推断]`**（2026-11-15 检索）：team 抽象在「角色扮演式」框架里是一等公民——**CrewAI** 的 Crew（团队 = 一组 Agent + 一组 Task + Process）、**MetaGPT** 的软件公司角色阵容（PM/Architect/Engineer/QA 的 SOP 流水线）、**AutoGen** 的 GroupChat（多角色自由对话）。但在「图编排」框架里**没有 team 概念**——**LangGraph** 只有图节点与状态边，分工靠节点拓扑而非「团队」实体。

**结论与建议（回答「是否需要、是否画蛇添足」）**：

1. **team 不是画蛇添足，但它现在的正确定位是「任务级组合模板」**——把「哪几个 agent 适合一起干这类活」沉淀为可复用组合，创建任务时一次展开成快照。这已经接线且有用（省得每个任务手选 executor/planner/reviewer）。
2. **不建议做「子任务级可选 team」**。子任务级已经有 `executorAgentIds` 白名单（继承自 task 快照）做选人约束，再叠一层 team 会变成「同一事实两个来源」（team 一套、白名单一套），正是判据 4「双写必分叉」的形态。要按子任务差异化选人，应该扩展**子任务级白名单/技能约束**，而不是引入子任务级 team。
3. **「team 像流程节点审批人」的直觉是对的，但那该走 reviewer 槽位，不是 team**。team 里的 REVIEWER 槽位已经能指定审核者（`TeamPolicyExpander.java:46-51`）；若要「某节点必须特定人审批」，应扩展 **reviewer 指派/审批流**，而不是把 team 改成审批载体。
4. 若要保留 team 长期价值，真正值得补的是 **`team_member.weight` 参与派发排序 + 团队内改派**（差距表已登记为「后期再做」待办），而不是把 team 下沉到子任务。

### 12.4 三个议题的一句话回答

1. **上下文压缩**：是真压缩（确定性剪枝 + LLM 摘要，两道两触发、净收益守卫、不拆 tool 对），与 Claude Code/DSH 同类机制且默认开启；要校准的是窗口配置与 token 估算精度，不是补功能。
