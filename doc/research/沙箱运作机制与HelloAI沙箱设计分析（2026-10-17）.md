## 0. 结论速览（TL;DR）

1. **两个项目的沙箱是「两个世界」**：
   - **Octop（含 octop-harness）**：**容器/远程世界**。默认 `local_shell`（完整宿主访问），可换 **Docker 沙箱**（`python:3.12-slim`，默认禁网、512MB、1 CPU、256 pids、120s 超时、100KB 输出截断）或 **OpenSandbox 远程沙箱**（按需安装官方 SDK）。Linux 上 `local_shell` + 非宿主 root 且装了 bubblewrap 时，自动升级为 **bwrap 根文件系统监禁**。
   - **DeepSeek Harness（DSH）**：**同主机进程监禁世界**。不提供容器；在**同一台宿主机、同一内核**上用平台原语监禁进程的文件效果——Linux **bwrap → Landlock** 两级、macOS **Seatbelt**、Windows **ACL restricted-token**。策略是**每次调用携带**的 `read-only` / `workspace-write` / `danger-full-access` 三档，**禁止无监禁放行**（fail-closed）。

2. **「沙箱」不是单一技术，而是三条隔离轴**（这是 HelloAI 选型的核心框架）：
   | 轴 | 技术 | 隔离强度 | 典型代表 |
   |---|---|---|---|
   | ① 进程内文件效果监禁 | bwrap / Landlock / Seatbelt / Windows ACL | 弱（共享内核+文件系统） | DSH `sandbox-local` |
   | ② 容器命名空间 | Docker | 中（共享内核） | octop-harness `DockerSandbox` |
   | ③ 用户态内核 / 微虚拟机 | gVisor / Firecracker / Kata | 强（独立内核或半独立） | E2B、Modal、OpenSandbox(可配) |

3. **HelloAI 的 G-005 结论仍然成立，但设计蓝图已经可以画出来**：当前无「平台代执行」对象（外部 agent 跑在自己终端、内部 LLM agent 工具面无 shell、平台无脚本引擎），三个触发条件（碰宿主工具 / 技能包被执行 / 平台自持浏览器）均未命中 ⇒ **仍不排期**。但若条件触发，设计蓝图见 §6：**独立沙箱服务 + 纯声明 spec + fail-closed**，参考 DSH 的策略模型做「每次调用携带策略」，参考 octop-harness 做「探针 + scope 生命周期」。

4. **可直接引入的开源沙箱（供你自行下载分析）**：
   - **首选：OpenSandbox**（`github.com/alibaba/OpenSandbox`，Apache-2.0，~15.9k stars）——Octop 官方已集成（`opensandbox>=0.1.16,<0.2`），自带 Docker/K8s 运行时、多语言 SDK、命令/文件/代码解释器/浏览器/桌面环境、网络策略、可换 gVisor/Kata/Firecracker 强隔离。**与 HelloAI「独立沙箱服务」形态最契合**。
   - **次选（轻量/单机）：bubblewrap**（Linux 根文件系统监禁，DSH 与 Octop 都用它）——无需 daemon，但只在 Linux 有效，且 HelloAI 是 Windows 开发环境。
   - **重隔离候选：E2B**（`github.com/e2b-dev/E2B`，Apache-2.0，Firecracker 微VM，~14k stars，可自托管）——隔离最强、最重，适合多租户生产。
   - **注意坑**：**Daytona 核心 2026-06 转私有**（AGPL-3.0 仓库停更，社区分叉 Nightona），不推荐作为新引入依赖；**Modal 无自托管路径**，不适用。

## 1. Octop 的沙箱运作机制

### 1.1 架构：平台委托，harness 执行

`[实测]` Octop（`Octop-main`）**不自己执行** agent 代码，而是把执行委托给 `octop-harness`（基于 deepagents BackendProtocol 的执行引擎）。沙箱是「后端（backend）」概念，由管理员在存储后端里配置：

- **后端类型 12 种**（`octop-harness-main/src/octop_harness/backends/__init__.py:317-337` `spec_supports_execution`）：`local_shell`（默认）/ `filesystem` / `state` / `store` / `composite` / `s3` / `postgres` / `cos` / `oss` / `obs` / `docker` / `opensandbox`。
- **可执行（shell）的仅 3 种**：`local_shell` / `docker` / `opensandbox`。其余是纯文件/存储后端。

### 1.2 Docker 沙箱默认约束（核心参数）

`[实测]` `octop-harness-main/src/octop_harness/backends/docker_sandbox.py`：

| 项 | 默认值 | 位置 |
|---|---|---|
| 镜像 | `python:3.12-slim` | `:64` |
| 网络 | `allow_network=False` → `network_mode="none"`（**默认断网**） | `:476-477` |
| 内存 | `memory="512m"` → `mem_limit` | `:478-479` |
| CPU | `cpus=1.0` → `nano_cpus=int(1.0*1e9)` | `:480-481` |
| 进程数 | `pids_limit=256` | `:482-483` |
| 命令超时 | `command_timeout=120s` | `:63` |
| 输出截断 | `max_output_bytes=100_000`（100KB） | `:66` |
| 容器主进程 | `["sleep","infinity"]` + detach（长驻等待 exec） | `:462-463` |
| 执行方式 | `exec_create(["bash","-lc",command])` + 线程超时 + `_kill_exec` 兜底 | `:534-594` |

**生命周期**：`_acquire_container` 按 `sandbox_scope ∈ {agent, user, fixed}` + `agent_id` 复用命名容器（`octop_sandbox` 前缀），容器消失自动重建（`_rebind_if_missing`）；`close()` 对持久 agent 沙箱**不删容器**（只丢弃句柄），`destroy()` 才停删（工作区文件随容器删除——**无 named volume，默认不 bind-mount**）。

**工作区模型**：同一抽象路径在容器内是**纯路径参数**（`workspace_path`），非宿主 bind mount；文件 I/O 走 Docker SDK `put_archive`/`get_archive`（`_put_file`/`_get_file`，`tarfile` 打包）。`_map_path` 把所有虚拟路径钳制到容器内 workspace 根之下（`_clamp_to_workspace`），`ls`/`glob` 结果重写回虚拟路径（`_rewrite_ls_result`），防止列出容器 `/`。

### 1.3 local_shell 与 bwrap 自动升级

`[实测]` `octop-harness-main/src/octop_harness/backends/__init__.py`：

- 默认 spec：`DEFAULT_BACKEND_SPEC = {"type":"local_shell","root_dir":"/","virtual_mode":True}` —— **完整宿主 shell 访问**（生产必须 restrict root_dir）。
- `_build_local_shell`（`__init__.py:317-337` 附近）：当 **Linux + virtual_mode + 非宿主 root + bwrap 存在** 时，自动换 `BubbledLocalShellBackend`（`bwrap_shell.py`）。
- **bwrap 监禁**（`bwrap_shell.py:86-131` `build_bwrap_argv`）：`--unshare-pid --unshare-ipc --unshare-uts --die-with-parent --new-session`，`--bind root_dir /`（root_dir 成为监禁根），`--ro-bind /usr /bin /lib /lib64`（只读工具链），`--ro-bind-try /etc/resolv.conf /etc/passwd /etc/group /etc/nsswitch.conf`，`--tmpfs /tmp`，`--proc /proc`，`--dev /dev`。
- Windows 上 `default_agent_backend_spec` 收敛 root 到 workspace（`Octop-main/src/octop/infra/backend/resolver.py`）——因为无 bwrap。

### 1.4 OpenSandbox 远程沙箱

`[实测]` `octop-harness-main/src/octop_harness/backends/opensandbox_sandbox.py`：

- 构造即 `SandboxSync.create(image)` 建远程沙箱（`opensandbox>=0.1.16,<0.2`，按需安装见 `Octop-main/src/octop/infra/backend/opensandbox_deps.py`）。
- `execute` → `sandbox.commands.run(command)`；文件走 `files.write_files` / `files.read_bytes`；`close()`/`destroy()` 销毁远程沙箱。
- Octop 侧 `adapter.py` 把 DB 行转成 spec：`row_to_backend_spec`（`adapter.py:44-155`），`kind=opensandbox` 时从 `row.secret_key` 取 `api_key`、`row.endpoint` 取 `domain`、`row.region` 取 `protocol`。

### 1.5 连接性探针

`[实测]` `octop-harness-main/src/octop_harness/backends/probe.py`：`probe_backend(spec)` 对任意后端做 **write → read → delete 回环**（`.harness-probe-<uuid>.txt`），验证后端真实可用。Octop 侧 `probe.py` 对 docker 额外做「ensure image → 真实容器内写读」。

## 2. DeepSeek Harness（DSH）的沙箱运作机制

### 2.1 定位：同主机进程监禁（不是容器）

`[实测]` `deepseek-harness-master/packages/sandbox/sandbox/README.md`：DSH 沙箱是 **same-world confinement**——进程仍共享宿主内核与文件系统；要隔离整个环境须换容器/microVM/远程执行器。这决定了 DSH 的沙箱**不解决**「凭据主密钥泄漏」这类容器级问题，只解决「文件效果越界」。

### 2.2 三档策略模型（每次调用携带）

`[实测]` `packages/sandbox/sandbox/src/index.ts`：

```ts
type SandboxMode = 'read-only' | 'workspace-write' | 'danger-full-access'
```

- `read-only`：除 `/dev/null` 外禁写；
- `workspace-write`：允许写 workspace 根 + 后端定义的临时区；
- `danger-full-access`：绕过监禁（消费方直接跑原 argv，不调 `ctx.sandbox`）。

**关键设计**：策略**随调用携带**（`SandboxPolicy` 每次执行时由 `ctx.sandboxPolicy.resolve()` 解析），不固定在 provider 上——两个消费方可同时用不同策略；**被拒后只能一次性地申请「严格更宽」一档**（read-only → workspace-write 或 danger-full-access；workspace-write → danger-full-access），需人工审批，`approveEscalation` 校验（`escalation.ts`）。

**Fail-closed**：没有可用后端时抛 `SANDBOX_UNAVAILABLE`，**绝不无监禁放行**（`SandboxUnavailableError`，`index.ts:132-145`）。

### 2.3 平台 runner 链

`[实测]` `packages/sandbox/sandbox-local/src/index.ts` `PLATFORM_CHAINS`（`:160-167`）：

| 平台 | 链（按序探测） | 强制完整性 |
|---|---|---|
| Linux | `bwrap` → `landlock`（Landlock 为 `node-addon-system/landlock-run` launcher） | bwrap=full；Landlock 按 ABI 报 full/partial |
| macOS | `seatbelt`（`sandbox-exec -p` SBPL profile） | full |
| Windows | `windows-acl`（ACL restricted-token runner，`@deepseek-ai/dsh-sandbox-windows-acl`） | **partial**（NTFS 硬链接别名 / 读不监禁 / AppContainer-ACL 边界） |

**探测机制**：多候选才探测（`chainVerdict`），唯一候选不探测直接选；`defaultProbeBwrap` 用 `bwrap <profile> -- true` 实测；Landlock 用 launcher 自带 probe 报告 full/partial。

**profile 构造**（`profiles.ts`）：
- bwrap：`--ro-bind / / --dev /dev --unshare-pid --proc /proc --die-with-parent`，workspace-write 时加 `--tmpfs /tmp` + `--bind workspaceRoot workspaceRoot`；
- Landlock：`landlockGrantArgs({ readOnly: ['/'], readWrite: ['/dev/null'(, '/tmp', workspaceRoot)] })`；
- Seatbelt SBPL：`(allow default) (deny file-write*) (allow file-write* (literal "/dev/null"))` + workspace-write 时 `(subpath ...)`。

### 2.4 Windows ACL 后端（对 HelloAI 最相关——同为 Windows 环境）

`[实测]` `sandbox-local/src/index.ts` `windowsAclRunnerArgv`（`:369-388`）：
- **每 workspace 一个「standing 写 SID」**（`workspaceWriteSid`），ACE 落一次后跨会话复用（O(1) 跳过）；
- **每 session/workspace 对一个「随机私有临时目录 + 临时写 SID」**（`tempWriteSid`），dispose 时吊销；
- runner 收到 `--workspace <root> --temp <tmp> --mode <mode> [--write-sid ... --temp-write-sid ...]`，**runner 自身不再管理 DACL**（SID 存在即 seam 管理的契约标记）；
- 报告 partial 的三大原因：NTFS 硬链接把同一文件对象别名到路径外、读不受监禁、被 AppContainer ACL 的树对 Low-integrity 子进程不可读。

### 2.5 消费方（bash-sandbox）

`[实测]` `packages/shell/bash-sandbox/src/index.ts`：`SandboxBashExecutor` 包装 `LocalBashExecutor`，`execute()` 里对 `danger-full-access` 直接跑；否则 `ctx.sandbox.confine(argv, policy)` 拿 `ConfinedArgv.argv` 替换原 argv 去 spawn；每个进程记录「mode / enforcement / denialSignatures / runnerFailureRules」，用 `classifyDenial` / `classifyRunnerFailure` 分类 stderr（denial = 监禁生效，runner failure = 沙箱坏了——两者可区分，`index.ts:115-121`）。

### 2.6 DSH 的局限（README「Known Limitations」）

- 词汇只有**文件效果**——**无网络/进程/syscall/设备/凭据限制**；
- **same-world only**——不解决凭据/内核级问题；
- denial 报告是 stderr 方言（非类型化通道）；
- 每 context 一个 provider（无法同时用多种机制）。

## 3. 两项目对比：HelloAI 该抄谁

| 维度 | Octop/octop-harness | DSH | HelloAI 应取 |
|---|---|---|---|
| 隔离层 | 容器/远程（真隔离） | 进程监禁（文件效果） | **分层**：先进程监禁，重隔离走容器/远程 |
| 策略模型 | 无显式策略档（靠容器硬参数） | **每次调用携带 3 档策略 + 升级审批** | **DSH 策略模型**（与 HelloAI 审批流契合） |
| 生命周期 | `sandbox_scope ∈ {agent,user,fixed}` 命名容器复用 | per-call wrap，无长驻容器 | **Octop scope 模型**（agent 粒度复用） |
| 可用性探测 | `probe_backend` 写读删回环 | 功能探针 + fail-closed 拒跑 | **两者都要**：配置探针 + 执行前 fail-closed |
| 凭据安全 | 未特别处理（容器内 env 即宿主 env 的镜像） | **不解决**（same-world） | **HelloAI 独有红线**：独立容器 + 不共享 env（§5.2） |
| 后端抽象 | `type` 声明式 spec（DB 行 → spec） | 无（平台内 composition） | **Octop 声明式 spec**（`storage_backends` 表已存在） |

**结论**：HelloAI 应**以 DSH 的策略/升级/fail-closed 模型为「政策层」，以 Octop 的声明式 spec + scope 生命周期为「执行层」，两者叠加**，再叠 HelloAI 特有的凭据隔离红线。

## 4. 可直接引入的开源沙箱（候选清单 + 推荐）

### 4.1 推荐：OpenSandbox（首选）

- **仓库**：`github.com/alibaba/OpenSandbox`（Apache-2.0，~15.9k stars，CNCF Landscape，近 30 天仍更新）。
- **定位**：面向 AI 应用的**通用沙箱平台**：统一 Sandbox API（OAS 协议）+ 多语言 SDK（Python/Java/TS/C#/Go 路线图）+ CLI + **MCP 接口** + Docker/Kubernetes 运行时 + 网络策略（统一 Ingress Gateway + 每沙箱 egress 控制）+ 凭据保管组件。
- **内置环境**：Command / Filesystem / Code Interpreter；示例覆盖 Claude Code、浏览器（Chrome/Playwright）、桌面（VNC/VS Code）。
- **强隔离**：支持 **gVisor / Kata Containers / Firecracker microVM** 安全容器运行时。
- **为何最契合**：① Octop 官方已集成（`opensandbox>=0.1.16,<0.2`），说明协议成熟；② **MCP 接口**——HelloAI 的 MCP 基建可直接对接；③ 自托管（`opensandbox-server`，Docker 即可跑）——正好是 HelloAI G-005 裁定的「**独立沙箱服务**」形态；④ 多语言 SDK 含 Java。

### 4.2 次选：E2B（重隔离、多租户）

- **仓库**：`github.com/e2b-dev/E2B`（Apache-2.0 核心，~14k stars，可自托管）。
- **隔离**：每沙箱一个 **Firecracker 微VM**（独立内核，硬件级），~150ms 冷启动，支持暂停/恢复（内存保留）、快照 fork 并行。
- **网络/凭据**：默认阻断私有/链路本地地址与云 metadata 服务；secret 注入使**代码内读不到凭据值**。
- **适用**：HelloAI 若未来做多租户 / 高安全生产，直接自托管 E2B 作为沙箱控制面。

### 4.3 轻量单机：bubblewrap（Linux 专用）

- **仓库**：`github.com/containers/bubblewrap`（LGPL-2.0）。
- 无 daemon、setuid 安装即可用；DSH 与 Octop 都把它当 Linux 首选手 runner。**局限**：仅 Linux；HelloAI 开发机是 Windows（bwrap 不可用，这正是 DSH 在 Windows 上走 ACL 后端、Octop 在 Windows 上收敛 root 的原因）。

### 4.4 组件级：Firecracker / gVisor / Kata（不直接引入，作 OpenSandbox/E2B 的底层）

- **Firecracker**（`github.com/firecracker-microvm/firecracker`，Apache-2.0）：AWS 开源的 microVM，E2B 的底座；
- **gVisor**（`github.com/google/gvisor`，Apache-2.0）：用户态内核，syscall 拦截；
- **Kata Containers**（`github.com/kata-containers/kata-containers`，Apache-2.0）：容器+VM 混合。
- 这三个是「引擎」不是「平台」——HelloAI 不应直接操作，应通过 OpenSandbox/E2B 的运行时配置选择。

### 4.5 ⚠️ 避坑

- **Daytona**（`github.com/daytonaio/daytona`）：**核心 2026-06 转私有代码库**（社区分叉 Nightona）——license rug-pull 风险，不建议作为新引入依赖（其 71.7k stars 含整个 dev-environment 平台，非纯沙箱）。
- **Modal**：**无自托管路径**（closed cloud），不适用。

## 5. HelloAI 现状与红线（设计约束）

### 5.1 G-005 现状（差距表 §2，`[实测]`）

- **形态已裁定**（`D-2026-10-09-4③`）：**独立沙箱服务**（低权限面），**不走「挂 `docker.sock` 进 app 容器」**路线。
- **不排期**（`D-2026-10-09-6③`）：当前无「平台代执行」对象——外部 agent 跑在自己终端（平台=派单方）、内部 LLM agent 工具面无 shell/文件写、平台无脚本引擎。
- **触发条件（任一成立 ⇒ 重新排期，届时启动专项并出 ADR）**：① 平台增加碰宿主的工具；② **技能包要被执行**；③ 平台自持浏览器。
- **预案**（`plan/HelloAI 借鉴落地实施计划.md` §5）：spec 声明化 / 探针 / scope 生命周期 / 形态 = 独立沙箱服务。

### 5.2 ★安全红线（KIMI 评估 §4，`[实测]`）

> 本仓唯一必须钉死的红线，任何设计不得触碰：

- app 容器**必须**注入 `HELLOAI_CREDENTIAL_AES_KEY_BASE64`（`docker-compose.server.yml:317` 必填）；该密钥可解密 `credential_vault` **全量平台供应商 API Key**（`CredentialCryptoService` AES-GCM 解密），agent 的 `apiKey` 亦为 AES-GCM 密文。
- 若在 **app 容器内** `ProcessBuilder("node", "…第三方脚本")`：脚本可经 `process.env.HELLOAI_CREDENTIAL_AES_KEY_BASE64` 取到密钥 → 解密全部供应商密钥；且同 compose 网络可直连 PG/Redis/MinIO。
- **⇒ 隔离位置必须独立容器**：不注入 app 的 env、不接 app 网络（PG/Redis/MinIO）。这与 G-005 裁定（独立沙箱服务）同向。

## 6. HelloAI 沙箱设计蓝图（条件触发时执行）

> 本蓝图是「预案」，不是排期。触发条件成立后，按《决策承载》规则先出 ADR 再实施。以下设计同时吸收 DSH 策略模型 + Octop 执行层 + HelloAI 红线。

### 6.1 总体形态

```text
┌──────────────┐   HTTP/API    ┌──────────────────┐   控制    ┌────────────┐
│  HelloAI app │ ────────────► │  沙箱服务(独立)    │ ────────► │ Docker/K8s │
│ (Java/Spring)│ 纯声明 spec    │  (沙箱控制面)      │  runtime   │ OpenSandbox│
└──────────────┘               │  OpenSandbox/E2B  │            │ 或 E2B     │
                               └──────────────────┘            └────────────┘
                                     ▲ 不注入 app env / 不接 app 网络
                                     │（凭据主密钥红线）
```

- **形态**：独立沙箱服务（进程/容器），与 app 容器**物理隔离**（不共享 env、不接 PG/Redis/MinIO 网络）。**候选底座 = OpenSandbox server**（自托管 Docker 即可）或 E2B（多租户时）。
- **接缝**：app 通过 HTTP API（或 MCP）下发**纯声明 spec**（无 Docker API 参数内嵌），沙箱服务负责创建/执行/销毁。

### 6.2 策略模型（抄 DSH）

- 三档策略 `read-only` / `workspace-write` / `danger-full-access`，**每次调用携带**，由会话/任务解析；
- 默认档从 `read-only` 起（fail-safe），`workspace-write` 显式配置才开；
- **升级 = 单次、严格更宽一档 + 人工审批**（复用 HelloAI 已有的审批流）；重复同档不重复审批；
- **fail-closed**：无可用后端 ⇒ 拒跑（`SANDBOX_UNAVAILABLE`），绝不无监禁放行。

### 6.3 执行层（抄 Octop）

- **声明式 spec**：`{"type":"docker|opensandbox", "image":…, "resources":…, "network":"none|allowlist", "scope":"agent|user|fixed"}` 存 `storage_backends`（表已存在）或新配置表；spec 不内嵌 Docker API 参数（`docker_spec.py` 的 pass-through keys 是反例，HelloAI 要做**白名单收敛**）；
- **scope 生命周期**：`agent` 粒度命名沙箱复用（长驻），`user` 按用户隔离，`fixed` 固定实例；销毁时工作区随容器/沙箱删除（默认不 bind-mount 宿主）；
- **资源硬参数**（默认，参照 octop-harness `DockerSandbox`）：默认镜像、禁网（或出站白名单）、512MB、1 CPU、256 pids、120s 命令超时、100KB 输出截断；
- **探针**：配置侧 write→read→delete 回环（`probe_backend` 同款）；执行前 fail-closed 探测。

### 6.4 文件工具边界（抄 octop-harness `filesystem_guard.py` + DSH 读限制）

- 文件工具（read/write/edit/ls/glob/grep/delete）路径全部钳制到 workspace 根之下（`_map_path` / `_clamp_to_workspace` 同款）；
- 越界 = 软失败（ToolMessage error + 修复提示），不中断整轮；
- deny 规则（敏感路径）第一匹配优先。

### 6.5 网络边界（HelloAI 已交付项，保持）

- `REF-5.4` 出站 SSRF 守卫已交付（URL 层 + 地址层双层，IP 字面量只在 URL 层拦）——沙箱内出站如需白名单，复用同一套 `OutboundUrlGuard` 逻辑或独立实现（沙箱服务侧）；
- 平台自持浏览器（触发条件③）⇒ 沙箱内跑 Chromium/Playwright，出站受控。

### 6.6 落地阶段划分（触发后）

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 1 | **Provider Contract**（抽象 `SandboxProvider` 接口 + 纯声明 spec + 探针 + fail-closed 骨架） | 无（差距表 §2 原文「第一阶段只完成 Provider Contract」） |
| 2 | 接 **OpenSandbox** 后端（Docker 运行时，本地自托管） | 触发条件①②（技能包执行 / 碰宿主工具） |
| 3 | 接 **E2B** 后端（Firecracker 微VM，多租户/高安全） | 生产规模/合规要求 |
| 4 | 浏览器/桌面环境（触发条件③） | OpenSandbox 自带 chrome/desktop 示例 |

> **注意**：阶段 1 只完成契约，不把 Docker/K8s 当已完成安全隔离（差距表 §2 原文）。
