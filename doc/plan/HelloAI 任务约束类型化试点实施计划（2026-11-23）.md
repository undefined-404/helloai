# 0. 定位与边界（★先读）

## 0.1 问题来源

- 用户实测（2026-11-23）：`doc/HelloAI_CODE_STYLE.md`（3918 行 / 151 章节）约束越详细，不同 agent / LLM 的代码产出越收敛于项目规范；当前执行约束仅是 `sub_task.constraints` 单值 TEXT（拆解时 LLM 即兴生成），「几行字段达不到相同效果」。
- 前序讨论结论：任务约束应**类型化**（`DOCUMENT` 契约引用 + 按需读取，而非只注入几行文字）；落点分析见 `design/HelloAI 任务约束类型化设计（试点）.md`（`G-037`）。

## 0.2 本计划做什么

1. 数据层：`sub_task.constraint_refs` / `plan_draft.constraint_refs` JSONB（V154 迁移）+ 实体 / VO 带出；
2. 约束文档目录：`manifest.json`（白名单，试点登记 `code-style` 一份）+ 章节按标题匹配解析（行号漂移免疫）；
3. 执行侧工具：`internal_list_constraint_docs` / `internal_load_constraint_doc`（目录/正文分离 + fail-open）；
4. 三环节接线：拆解提示词声明 + 执行 D6 段注入引用 + 审查提示词携带引用；
5. 单测 + 文档回填。

## 0.3 本计划不做什么（边界）

| 不做 | 为什么 | 依据 |
|---|---|---|
| `SKILL` 类型实现 | 只预留枚举位，走现成技能通道 | 设计 §0.3 |
| 约束编辑 UI / 管理界面 | 试点为后端链路验证 | 设计 §0.3 |
| 审查侧硬性 fail-close 校验 | 需真机误报率数据支撑 | 设计 §0.3 |
| `TEXT` 与 `constraints` 合并重构 | 现有字段已承载且被多面消费，试点并存 | 设计 §0.3 |

## 0.4 诚实边界

- 链路全通 ≠「约束已自动治理」：产出规范符合率提升属行为验证，需真机对照，另立观察项；
- 目录白名单仅 1 份文档，扩登记须同批维护 manifest；
- 本轮改动不自动 commit（沿用约定）；约束文档目录 manifest 是**平台侧新增的代码资源**，与 `doc/` 文档体系的唯一事实源不冲突（manifest 只登记 path 引用，不复制正文）。
