## 1. 一页概览

- **主干 A（沙箱，`G-032` / `SL-1`~`SL-10`）**：先把「容器能活到任务终态 + 文件有固定位置」修对，再让证据能分清「谁在第几轮验的」，然后才把隐式 `Long` 解耦成显式句柄，接着按职责拆实现，最后做审核只读隔离。
- **支线 B（审核证据可见性，`G-034` / `RV-8`~`RV-13`）**：解决「附件太多被截断，Reviewer 看不见却把看不见写成缺陷」。与主干**无代码依赖**，只共享验收口径。
- **交汇点**：`coverage.method` 的两个取值——`sandbox` 档依赖 `SL-4` 的 `callId`，`attachment` 档依赖 `RV-8` 的附件 id；`RV-11` 的判据同时读两边台账。

排序依据不是「哪个好改先改」，而是**可验证性**：阶段 0~1 不做，后面所有改动在真机上都验不出效果（容器 15 分钟就没了）。

## 2. 主干 A：沙箱（`SL-1`~`SL-10`）

```text
阶段 0  ✅ 已完成
  SL-1 作用域  subTaskId(每轮一清) ──→ taskId(全任务共享)   ┐ 必须同批，
  SL-2 释放点  turn 末释放        ──→ 任务 DONE/取消/删除   ┘ 否则名存实亡

        │  作用域对了，但"能活多久"不对：renew 是绝对过期，
        │  一次命令就把 3600s 压到 900s；无后台回收器；124 超时销毁整块工作区
        ▼
阶段 1  修内部正确性（SL-7 ∥ SL-3，同批验证，不动任何对外签名）
  SL-7 寿命    idle-ttl 900s 只喂回收器 / keep-alive 8h 喂 renew(只补不缩)
               exitCode 124、-1 不再销毁容器 / 新增 SandboxIdleReaper
  SL-3 工作区  创建即 mkdir /workspace + 所有命令 cwd=/workspace
               回读按 mtime / 槽查找纳入规格指纹 / 内联按字符计 / 六处文案同步
        │
        │  ← 本阶段起可与支线 B 的 RV-10、RV-8 并行（改的文件不重叠）
        ▼
阶段 2  先能验收（SL-4 → SL-5）
  SL-4 台账条目加 callId + origin(executor/reviewer/platform) + round，上限 50→200
  SL-5 证据从"自报命令 + 摘要匹配"改为 {"kind":"sandbox_exec","callId":"c17"}
       对账默认只认 origin=executor，跨轮标 evidence_round_crossed

        │  与接口无关，但必须早于隔离 —— 否则隔离做得再好也没有验收依据
        ▼
阶段 3  解耦（SL-8）：把塞在一个 Long 里的三种含义拆开
  旧  execute(Long subTaskId, ...)  ← 一-shot / 会话 / 子任务 三义共用
      运行时 resolveScope() → SubTaskQueryPort.findById 反查业务库
  新  exec(WorkspaceRef ref, ...)   ← 调用方声明，运行时只管执行
      前置：ToolInvocationContext.Ids 补 taskId（现在只有 agentId/subTaskId）
      兼容：SandboxExecutionService 保留老签名，7 个消费者零改动

        ▼
阶段 4  拆实现（SL-9）：1192 行按 5 个职责切，不按行数
  runtime(执行) / registry(身份+槽+TTL+回收) / observation(台账+事件装饰器)
  / installer(技能包) / deliverable-reader(挑最大 .md 挪去消费侧)

        ▼
阶段 5  隔离（SL-10）：reviewer 不再共享可写工作区
  /workspace 从容器可写层改为 volume（原来它就不是卷，所以"只读"无处可挂）
  executor 挂 readOnly=false / reviewer 挂 readOnly=true
  SlotKey 必须纳入 Isolation —— 否则 reviewer 命中的还是执行器那个容器
  一次性校验走 EPHEMERAL_VERIFY（不进槽池，跑完即毁）
        │
        │  ← 只读同时是支线 B 的判定基准：审核者不能改被审对象，
        │     RV-11 判"可见证据与声称矛盾"才成立
        ▼
阶段 6  收口（SL-6）：单测 → IT → 真机六项 → 门禁 → 文档回填 → 回滚演练
        （真机六项不含 G-034 的金标准回放，那条归支线 B 验收）
```

**为什么是这个顺序**

1. 阶段 0~1 是**内部正确性**：容器必须活到任务终态、文件必须在固定位置。不修这两项，后面任何真机验证都跑不满（15 分钟容器消失，验不出跨轮效果）。
2. 阶段 2 是**可验收性**：先能回答「这条证据是谁在第几轮跑的」。它与接口无关，但必须早于隔离。
3. 阶段 3 是**解耦**：不是新增能力，是把一个 `Long` 里挤着的三种含义（一次性 / 会话 / 子任务）拆开交给调用方声明。前置动作是 `taskId` 透传（`ToolInvocationContext.Ids` 现在只有 `agentId` / `subTaskId`）。
4. 阶段 4 是**拆实现**：先有稳定接口才能拆；判据是 `CODE_STYLE` §9.1「两个以上业务职责」，§9.2 明确反对按行数机械拆。
5. 阶段 5 是**隔离**：必须有阶段 3 的 `Isolation` 字段与阶段 4 的 registry，才能挂只读卷。
6. 阶段 6 收口。

## 3. 支线 B：审核证据可见性（`RV-8`~`RV-13`）

```text
  RV-10 表格机械预检（零依赖，可最早做，不依赖任何沙箱改动）
        输出 [MECHANICAL_CHECK] detail=198899 summary=198899 MATCH
                                report_claim=199080 MISMATCH(+181)
        │
  RV-8  证据台账：附件 id + injected 区间 + absent 原因
        随 review_record.snapshot 冻结
        落点 ReviewEvidenceAssembler:222/:305/:318
             + freezeEvidence:197 / frozenEvidenceView:168
        │
  RV-9  按证据族配额（主件与 part-* 算一族；交付物优先；区间注入）
        复用「均分保底 + 余量回收」算法（ChatAttachmentPromptRenderer:559，需抽纯函数）
        │
  RV-11 驳回依据可达性闸：缺陷只引用不可见证据 ⇒ INCONCLUSIVE(evidence_unavailable)
        不计返工次数；复用既有出口 SubTaskReviewServiceImpl:488/:513，不新建状态机
        │
  RV-12 有界取全工具（internal_attachment_digest / read_attachment_range）
        绕开 ToolResultPruner 8,192 码点剪枝
  RV-13 注入规则对执行方同源可见（verify-executor-doc-parity.sh 守卫）
```

**与主干的并行关系**：`RV-10` / `RV-8` 改 `ReviewEvidenceAssembler`、`ReviewCoverageParser`、`AttachmentServiceImpl`；`SL-7` / `SL-3` 改沙箱实现（`SL-9` 后已拆为 `OpenSandboxRuntime` / `SandboxWorkspaceRegistry` / `SandboxFactory` / `SandboxObservation` / `SkillPackageInstaller`）。两组文件无交集，可并行开发；但**同批验收**要等各自链路齐备。

## 4. 两条链的交汇点

```text
                         coverage.method
                      ┌───────┴───────┐
               sandbox │               │ attachment
                       ▼               ▼
          SL-4 callId + SL-5 对账   RV-8 附件 id + 注入区间
                       └───────┬───────┘
                               ▼
                    RV-11 判据要同时读两边：
                    「这条缺陷引用的证据，到底看不看得见」
```

- `sandbox` 档在契约里已存在（`ReviewCoverageParser:45-46`），但 `evidenceRef` 指向的「台账条目」在 `SL-4` 之前没有稳定标识。
- `attachment` 档已存在，但 `evidenceRef` 只能填文件名，没有附件 id 与注入区间，`RV-8` 之后才能定向补读。
- 两档的 `covered` 若指向看不见的内容，由 `RV-11` 统一裁决；沙箱侧只读（`SL-10`）保证「被审对象未被审核者改动」，是 `RV-11` 比对成立的前提。
