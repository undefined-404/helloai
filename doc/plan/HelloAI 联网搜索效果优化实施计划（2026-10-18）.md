## 一、改造前基线（`[实测]` 事实，2026-10-18）

### 1.1 当前执行链路

```
用户消息 → ClarifyWebSearchOrchestrator.doWebSearch
  → URL 分离（消息含 http(s) 链接则直取页面）
  → SearchQueryPlannerService.planQueries（规则清洗 + LLM 条件改写，1~N 候选词）
  → 逐候选词【串行】调 web_search 工具
      → WebSearchServiceRouter → AiSearchWebSearchServiceImpl（provider=bocha-ai-search）
          POST api.bochaai.com/v1/ai-search
          {query, freshness:"noLimit", count:15, answer:properties.isAiSearchAnswer()(默认true), stream:false}
      → 解析 messages[].content.value[]（网页结果）
      → 结果截断 200 字/条，按 URL 去重合并
  → 可选缺口补搜（SearchGapAssessor，1 轮）
  → WebSearchOutcome.toContextText() 渲染注入澄清 prompt
```

### 1.2 实测瓶颈（`logs/helloai.log` 2026-10-18 00:21 真实任务）

```text
候选词命中 0 条: query=膝盖旧伤 减脂训练计划 饮食方案 建议    ← 搜索词被 20 字硬截断切碎
候选词命中 15 条: query=制定减脂计划
结束: provider=router->bocha-ai-search, rounds=1, answer=无, pages=0, results=15, costMs=45963
```

| # | 瓶颈 | 根因（`[实测]`） |
|---|---|---|
| B1 | **搜索词质量差**（0 条） | `SearchQueryPlannerServiceImpl.QUERY_CHAR_LIMIT=20` 硬截断，多主题长句前 20 字切碎 |
| B2 | **串行慢（45.9s）** | `ClarifyWebSearchOrchestrator.doWebSearch` 177-217 行 `for` 串行搜索；AI Search 单次 25s 超时 |
| B3 | **answer 丢失** | `ClarifyWebSearchOrchestrator.callWebSearchTool`（281-301 行）只传 `query`+`maxResults`，**没传 `withAnswer=true`** → 工具侧 `withAnswer` 默认 false → 不调 `answerSummary()` → 博查已生成的 answer 被丢弃。**注意：`AiSearchWebSearchServiceImpl` 请求体已用 `properties.isAiSearchAnswer()`（默认 true），博查侧会生成；丢在工具调用参数层** |
| B4 | **时效硬编码** | 两实现请求体 `freshness:"noLimit"` 写死；`RelativeTimeNormalizer` 已存在但只用于查询词内日期归一，没驱动 freshness |
| B5 | **snippet 太浅** | `maxSnippetChars=200` 默认；只 title+snippet，无正文抓取（用户主动给 URL 才抓） |
| B6 | **无重排** | 结果按博查原始顺序透传，无 `gte-rerank` 语义重排 |
| B7 | **无 grounding** | 澄清 prompt 无「答案必须基于检索资料」约束 |
| B8 | **模态卡未消费** | ai-search 返回的模态卡（天气/股票/百科等）被忽略，只解析 `content_type=webpage` |

## 二、改造项（W-1 ~ W-7）

### W-1【P0】编排器请求 answer（`ClarifyWebSearchOrchestrator.callWebSearchTool`）

- **改**：`callWebSearchTool(String query, int maxResults)` → 参数加 `boolean withAnswer`（或直接用 `webSearchProperties.isAiSearchAnswer()`）；组装 argsJson 时加 `"withAnswer": true`。
- **效果**：博查侧 answer 经工具回传 → `WebSearchOutcome.answer` 非空 → `toContextText()` 渲染「以下是联网检索结果的大模型总结」节（该逻辑已有，88-91 行）→ 澄清 LLM 先读总结再读来源。
- **判据**：日志 `answer=有`；`WebSearchOutcome.answer` 非 null。

### W-2【P1】候选词并行搜索（`ClarifyWebSearchOrchestrator.doWebSearch`）

- **改**：177-217 行 `for` 串行 → `CompletableFuture` 并行（受 `searchBudgetMs` 总预算约束；每词一个 future，全部完成后按候选词顺序合并结果、URL 去重）。
- **效果**：45.9s → ~25s（AI Search 单次超时上限）。
- **风险**：并发下 `AiSearchWebSearchServiceImpl.lastAnswer` volatile 单槽——**多词并行时 answer 取哪个词**？取**首个有 answer 的词**（按候选词顺序）；实现上编排器层先收集各词 answer，不依赖服务层单槽。
- **判据**：多候选词场景 costMs 显著下降；results 合并顺序稳定。

### W-3【P0】动态 freshness（`AiSearchWebSearchServiceImpl` + `BochaWebSearchServiceImpl`）

- **改**：新增 `WebSearchProperties.freshness` 动态判定——查询词含时效词（今天/最新/本月/本周/今年/上周）时映射 `oneDay/oneWeek/oneMonth/oneYear`；否则 `noLimit`。判定逻辑复用/扩展 `RelativeTimeNormalizer` 的时效词表。
- **接口**：`WebSearchService.search(query, maxResults)` 签名不变；freshness 由实现内部按 query 判定（或加 `WebSearchRequest` 携带 freshness——**倾向后者**，语义更清晰，但改动面大；先做实现内判定，P2 再评估）。
- **判据**：含「最新」查询的请求体 freshness=oneMonth/oneYear；普通查询仍 noLimit。

### W-4【P1】搜索词质量（`SearchQueryPlannerServiceImpl`）

- **改**：`QUERY_CHAR_LIMIT=20` 硬截断 → 语义单元截断（按「名词短语/专有名词边界」截断，保留完整词）；LLM 改写触发放宽（多主题长句也应进 LLM 而非规则拆碎）；`LLM_REWRITE_TEXT_LIMIT=30` 调低。
- **效果**：「膝盖旧伤 减脂训练计划 饮食方案 建议」→ 不切碎，或 LLM 拆成「膝盖旧伤 减脂训练」「减脂饮食方案」两个正交查询。
- **判据**：多主题长句 0 条率下降；单测 `SearchQueryPlannerServiceImplTest` 补用例。

### W-5【P2】博查 Rerank 接入（新增 `BochaRerankService`）

- **新**：`BochaRerankService`（`WebSearchProperties.rerankBaseUrl` + `rerankModel=gte-rerank`）；对候选结果（top-N）调 rerank，按 `score` 精排后取 top-N 注入。
- **接线**：`ClarifyWebSearchOrchestrator` 合并结果后、渲染前调用（`rerankEnabled` 开关，默认 false 先灰度）。
- **判据**：rerank 后注入顺序与相关性显著提升；失败降级原始顺序（不阻断）。

### W-6【P2】Grounding 指令（澄清 prompt 模板）

- **改**：`prompts/requirement-clarify.md` + `prompts/requirement-chat.md` + `prompts/requirement-decision.md` 追加「联网检索资料约束」段：回答必须基于检索资料；资料未覆盖的推断需明确标注「基于我的一般知识」；引用以检索结果的 [N] 编号标注。
- **效果**：LLM 不再脱离资料自由发挥（Perplexity grounded generation 同款）。
- **判据**：人工核验回答中事实与检索来源的对应关系。

### W-7【P2】模态卡消费（`AiSearchWebSearchServiceImpl.parseResponse`）

- **改**：`parseResponse` 解析 `messages[]` 中非 webpage 的 source（`content_type` 非 webpage 但含结构化卡）→ 转 `WebSearchResult`（title=卡类型，snippet=卡内容 JSON 摘要）或独立 `ModalCard` 字段。
- **范围**：先消费「天气/百科/股票/汇率」等高频卡；`WebSearchOutcome` 加 `modalCards` 字段（payload 可查验）。
- **判据**：垂直查询（天气/股票）注入含结构化数据。
