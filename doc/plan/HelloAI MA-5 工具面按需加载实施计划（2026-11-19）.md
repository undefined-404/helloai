### ② 本计划做什么

**一句话目标**：把已在**技能侧**验证过「目录 + 按需加载」范式（`internal_list_skills` 只给名字 + 简介、`internal_load_skill` 才取正文）**平移到内部工具面**——模型每次请求不再背全部 8.6k 字符的工具定义，而是拿到一张带摘要的目录 + 一个 `internal_load_tool(name)` 按需取全量。

五条具体产出（逐条对应 §3 任务表）：

1. 新建目录装配器：把 `ToolRegistry.resolve` 的**生效结果**转成「目录条目」（`name` + 摘要，摘要封顶 160 字符，与 DSH `catalogDescriptionMaxLength` 对齐）＋ 高频核心工具白名单（3~5 个，**基于 `agent_event` 工具调用统计，不拍脑袋**）；
2. 新增工具 `internal_load_tool(name)`：返回指定工具的**完整** schema / description（turn 内缓存，避免模型反复取同一个）；
3. `RuntimeTurnExecutor.resolveVisibleCallbacks` 接线：模型可见 = 目录（摘要注入）＋ 白名单全量定义 ＋ `internal_load_tool` 本身；**只动内部面（16 个）**，对外 MCP 面（17 个）零改动；
4. 对比实验（判据 18）：同一批任务（≥10 个）改造前后三指标——单次请求提示词 token 数、工具调用成功率、平均轮次；
5. 对外兼容守卫：`verify-mcp-external-surface.sh` 必须保持绿（对外 `tools/list` 逐字符不变）。

### ③ 本计划不做什么

| 不做 | 为什么 | 依据 |
|---|---|---|
| **不动对外 MCP 面（17 个）** | 对外是**签约面**——`research` 与 `tools/list` 的 schema 已对外公开，2026-11-17 刚验过 `verify-mcp-external-surface.sh`；改了就是破坏兼容，而收益一样能在内部面拿到 | 蓝图 §4 `MA-5` ⑥ |
| **不一次全切 on-demand** | DSH 自己默认 `eager`（`toolLoading: z.union(['eager','on-demand']).default('eager')`）——on-demand 有代价（多一次工具调用往返），不是无脑更优 | 蓝图 §4 `MA-5` ④/⑥；DSH `config.ts:67` |
| **不做第二步「按 `ToolContext` 预筛」** | 按角色 / 任务类型只放「可能用到」的工具，漏了就「模型不知道有这个工具」——风险高；**除非第一步的实验数据支持，否则不做** | 蓝图 §4 `MA-5` ⑤ 第二步 |
| **不改工具清单的散落维护现状** | `@Tool` 注解 / `DEFAULT_EXECUTOR_TOOLS` / `INTERNAL_LLM_TOOLS` / contributor 多处维护是独立问题（蓝图问题 3），本次**不改注册机制**，只改「模型可见形态」 | 蓝图 §4 `MA-5` ② 问题 3；最小改动原则 |
| **目录不基于全量注册表** | `ToolRegistry.resolve` 已会摘除条件不可用工具（沙箱未启用时 `internal_run_in_sandbox` 等被摘）。目录若基于全量表，「模型知道有但调不到」比「不知道」更糟 | 蓝图 §4 `MA-5` ⑦ 条件可用性 |
| **不改 `McpMcpServer` / `McpToolConfig.mcpToolCallbacks()`** | 对外 Bean 是签约面；只动内部面 `internalToolCallbacks()` 的消费方（`RuntimeTurnExecutor`） | 蓝图 §4 `MA-5` ⑦；`InternalToolCallbacks` 职责注释 |

### ④ 诚实边界

**落地后仍有以下不成立，必须同步登记差距表**：

1. **净收益尚未被证明**。目录化省的是「定义字符」，但 `internal_load_tool` 是新增工具、会引入 0~N 次额外往返。**token 有没有真降、成功率有没有降，必须等对比实验两组数据**——在此之前本项不构成「已完成」（对照蓝图停止条件）。
2. **`internal_load_tool` 本身也占位**。它是第 17 个内部工具（目录里要列它、白名单要给它全定义），净收益必须扣掉它的定义与调用开销（蓝图⑦「加载工具本身占位」）。
3. **工具调用统计的覆盖面有限**。白名单选型基于 `agent_event` 的 `TOOL_CALL_STARTED` 统计——该事件只覆盖内部执行链已有任务；统计样本若不足（任务少 / 类型单一），白名单初值可能偏离真实高频集。**白名单必须是配置，不是常量**。
4. **成功率对比存在偶发噪声**。工具调用成功率受模型版本 / Provider 可用性影响，短批对比可能把「噪声」误判成「退化」。对比实验要**同期同批**（同一组任务、紧邻执行），并记录 Provider 版本。
5. **`ToolDefinition` 只有 `name` + `description` 两个字段**（参数 schema 由 `@Tool` 注解在别处派发）。「完整 schema」在内部面上实际 = 完整 `description`；本计划不新增 schema 字段（schema 属于 spring-ai 注解面，改了就是破坏性变更）。

## 2. 现状（勘察结论，`[实测]`）

### 2.1 注入链路：请求集 vs 生效集（蓝图口径订正的落点）

| 层级 | 位置 | 行为 |
|---|---|---|
| **请求集**（模型能看到什么，此处只 set 名字） | `AgentRuntimeContextAssembler`（类注释自述「此处**刻意不做** `ToolRegistry.resolve`——生效形态的唯一接线点是 `RuntimeTurnExecutor`」） | 只装配 `ctx.tools` 名字清单 |
| **生效集**（模型真正可见，唯一判据） | `core/agent/runtime/RuntimeTurnExecutor.java`（`:117`） | `List<String> enabledTools = mergeTools(ctx.getTools(), resolved.requiredTools())` —— 请求集 = 上下文 tools ∪ 命中技能 requiredTools（并集去重保序） |
| 同上（`:119-127`） | `toolRegistry.resolve(enabledTools, toolContext)` → `resolvedTools`（**含条件可用摘除 + 描述重写**）；null 兜底空列表 |
| 同上（`:129-143`） | `TOOL_RESOLVED` 事件：`tools`（请求集原语义不变）/ `effectiveTools`（生效集）/ `removedTools`（被摘除项）/ `resolvedTools`（含描述）——**事件可观测面，外部读取零回归，不可破坏** |
| 同上（`:169`） | `resolveVisibleCallbacks(resolvedTools)` → `VisibleToolCallbacks.select(resolvedTools, all)` —— **这就是「模型可见」的最终入口** |

## 4. 关键设计决策

| 决策 | 选了什么 | 为什么不选另一种 |
|---|---|---|
| 注入点 | **`RuntimeTurnExecutor.resolveVisibleCallbacks`（生效集）** | `AgentRuntimeContextAssembler` 只 set 请求集、刻意不做 resolve（类注释自述）；改那里等于改错层（蓝图口径订正） |
| 目录依据 | **`resolve` 之后的集合** | resolve 含「条件可用摘除 + 描述重写」；基于注册表会让「模型知道有但调不到」 |
| 摘要封顶 | **160 字符**（与 DSH `DEFAULT_CATALOG_DESCRIPTION_MAX_LENGTH=160` 对齐） | 目录本身不能变成新负担（蓝图⑦） |
| 白名单 | **3~5 个高频核心工具给全定义，基于 `agent_event` 统计 + 配置化** | 全截断会让简单任务先加载一轮（多花往返）；白名单初值必须可调（诚实边界 3） |
| 加载工具 | **`internal_load_tool(name)` 对标 `internal_load_skill`**（严格匹配 + turn 内缓存） | 技能侧同一范式已运行；DSH `on-demand` = 「目录 + 按需 load」，不是「延迟加载代码」 |
| 默认形态 | **只改形态、不改默认语义**——目录始终注入（轻量），完整定义按需取 | DSH 默认 `eager` 提示 on-demand 有代价；两步走让「形态切换」与「默认值决策」解耦，且第一步不引入第二步的风险 |
| 对比实验 | **改造前先采基线，再改代码，同批重跑** | 判据 18：两组只差「注入形态」这一个变量；顺序反了基线就没了 |
| 对外面 | **零改动 + 守卫回归** | 签约面破坏是兼容事故；收益同样能在内部面拿到（蓝图⑥） |

### 4.1 已识别的最高危漏项（实现时逐条对照）

| # | 问题 | 本计划如何覆盖 |
|---|---|---|
| 1 | `TOOL_RESOLVED` 事件的 `resolvedTools` 负载含完整描述——目录化后该字段变短，外部若有消费者按它解析会受影响 | `RuntimeTurnExecutor` 事件负载保持 `resolvedTools` 字段结构不变，**只换内容为目录条目**；全仓 grep 确认无消费者依赖「完整描述」（预期只有诊断用途） |
| 2 | `internal_load_tool` 取全量描述时「新开事实源」 | 描述唯一事实源 = `ToolRegistry` 目录（`ToolDefinition`），load 工具**只读**，不重复解析 `@Tool` 注解 |
| 3 | 白名单写死 → 高频集变了不跟着变 | `MA5-2` 配置化 + 观察期可调；单测覆盖「白名单为空时全截断」路径 |
| 4 | 目录摘要把「条件不可用工具」也列进去 | `MA5-1` 入参是 resolve 结果 ⇒ 摘除项天然不在目录（写进 javadoc + 单测锁） |
| 5 | turn 内缓存泄漏到下一 turn | 缓存挂在 `ToolInvocationContext` 绑定的 turn 维度（与沙箱台账同域）；`MA5-3` 实现时显式按 turn 清 |

## 5. 依赖与实施次序

```text
MA5-2（白名单统计，无代码依赖，可最先做——且要为 MA5-6 采基线）
  ↓
MA5-1（目录装配器，纯组件，依赖白名单口径）→ MA5-3（load 工具，依赖目录取数）
                                                    ↓
MA5-4（接线，依赖 1/3）→ MA5-5（单测，依赖 4）
MA5-6（对比实验：改造前基线 → 改造后同批 → 结论）→ MA5-7（对外守卫）
MA5-8（文档回填，全部完成后）
```

- **`MA5-2` + `MA5-6` 必须最先**：对比实验要「改造前基线」，白名单要「改造前统计」——**顺序反了就没基线了**。这两项是纯读操作，可在改造前并行完成。
- **`MA5-1` → `MA5-3` → `MA5-4`** 是主干：装配器 → 加载工具 → 接线，后一个依赖前一个。
- **`MA5-5` / `MA5-7`** 是两道锁：单测锁行为、守卫锁兼容，都必须在 `MA5-4` 完成后立即跑。
- **停点纪律（对照蓝图 ② 停止条件）**：本批只做「第一步 + 对比实验」。**第二步（按 `ToolContext` 预筛）除非第一步数据明确支持，否则不做**——做了且失败，会让「模型能看见什么」变得不确定、出问题查不出来。

### 5.1 停止条件（本计划在哪停是安全的）

| 停在哪 | 安全吗 | 判定口径 |
|---|---|---|
| `MA5-4` 完成（接线通、单测绿、对外守卫绿） | **勉强安全**：行为没坏，但「值不值」没答案 | 缺对比实验数据 = 缺「省了多少 token」的证据；做都做了，必须有结论才收口 |
| `MA5-6` 完成且两组数据齐全 | **安全，是干净停点** | token 降幅 + 成功率无退化 + 轮次无恶化三项齐全；若「无法定论」也须显式记录（诚实边界 4） |
| `MA5-8` 未做 | 安全 | 文档回填纪律（差距表 / 蓝图 / 日志）照旧每次必做，不拖 |
