## 0. 定位与边界（★先读）

**① 问题来源**

- **用户反馈（2026-10-22）**：需求对话里无法挂文件；规划者（planner）完全不认识附件内容。原始记录见 `LOG-20261022-009` / `010` / `011`。
- **差距表锚点**：`G-016`（附件内容注入口径）、`G-017`（对象对账覆盖——会话附件未纳入对账即无法安全清理）、`G-024`（附件与联网检索编排）。
- **设计依据**：`design/HelloAI 需求对话附件设计.md`（数据模型 / 解析分工 / 两层注入 / 限额）。
- **外部对标**：`research/HelloAI 需求对话附件产品对标调研（2026-10-22）.md`。

**② 本计划做什么**

把「需求对话附件」从零做到可用：`ATT-1` 文本 + PDF 文本层 + 两层 Prompt 注入（**已完成**）→ `ATT-2` 图片与扫描件视觉直读 → `ATT-3` 超预算文件 ingest 到 `kb` + 引用回源 → `ATT-4` 版面增强（登记不启动）。逐项产出与验收见 §3 任务表。

**③ 本计划不做什么**（边界，防越界）

1. **不改任务域 `attachment`**——它是子任务产物表，只按 `sub_task_id` 聚合、要求 agent 身份上传；会话附件走 `chat_attachment`。两者共用同一对象桶但前缀不同，改造任务域会把两套生命周期搅在一起（依据：`G-017` 的三类引用源口径）。
2. **不宣称「附件能力已完成」**——`ATT-2` 未做前，图片与扫描件一律 `SKIPPED`（清单里显式写「正文不可读」+ 原因），不得让模型据此臆测内容。
3. **不自建向量库或侧库**——`ATT-3` 复用既有 `kb`（`kb_chunk` + HNSW-cosine，PG 单后端），不引入第二个存储（依据：`G-019` / `ADR-002`）。
4. **不改全局限额契约**——单文件 / 单次 / 单会话限额由 `AttachmentContentPolicy`（shared）单源决定，属 `G-016` 范围；本计划只消费，不调参。
5. **不在 `ATT-1` 引入视觉通道**——视觉模型与规划者模型解耦是 `ATT-2` 的设计口径，`ATT-1` 只做纯文本链路。

**④ 诚实边界**

- `ATT-1` 落地后**超预算文件只能截断**（标注「本次仅注入前 N 字」），**不能**按语义检索命中片段——那是 `ATT-3`。
- 图片 / 扫描件当前**不可读**，表现为 `SKIPPED` 而非静默空文件。
- **会话删除后附件对象不会被主动清理**——孤儿清理开关仍默认关闭，且 `G-017` 未达成项 ③（真机双来源对账验收）未完成。用户删除会话只删记录，不删桶内对象。
- 正文注入预算受 `AttachmentContentPolicy` 约束（单文件 64k / 总计 200k），本计划不承诺更大上下文。

## 2. 现状（勘察结论，`[实测]`）

### 2.1 附件域只服务子任务

| 事实 | 取证位置 |
|---|---|
| `attachment` 表只有 `sub_task_id`，**没有 conversation 维度** | `\d attachment`（字段 sub_task_id / visibility / uploader_agent_id） |
| 上传端点 `POST /api/artifacts/upload` 要求 **agent 身份**（`AuthInterceptor.AUTH_ID_KEY`）且 `subTaskId` 必填 | `ArtifactUploadController#upload` |
| 下载 / 预览 / 删除 / 列表都在 `/api/attachments/**`，只按 subTaskId 聚合 | `AttachmentController` |
| 可见性策略按「子任务 × 任务团队」判定（PERSONAL/TASK/PUBLIC） | `AttachmentVisibilityPolicy` |

⇒ 需求对话（`requirement_conversation`）与 `requirement_message` **没有任何附件关联字段**，也没有任何前端上传代码（`helloai-ui/src` 内 `el-upload` / `FormData` 命中 0 处）。

### 2.2 解析能力：PDF / Office / 图片都不读

| 事实 | 取证位置 |
|---|---|
| 无 PDF / Office 解析依赖 | 三个 `pom.xml` 中 `pdfbox` / `tika` / `poi` 命中 0 处 |
| 注入口径**明确把 PDF 排除在文本类之外** | `AttachmentContentPolicy.isTextual()` 只认 `text/*` 与 json/xml/yaml/sql + 一组代码扩展名 |
| 图片只在「媒体族」判定里出现，**不读取内容** | 同文件 `isMedia()`，仅用于决定「不注入正文」 |
| 注入限额已存在且已调优 | `ATTACHMENT_CONTENT_PER_FILE_LIMIT = 64000` 字符、`ATTACHMENT_CONTENT_TOTAL_LIMIT = 200000` 字符 |

⇒ 现状：附件在报告链 / 核验链里只是「文件名 + 类型 + 大小 + 文本型正文」，**PDF 进来就是一张白纸**。

### 2.3 规划者（planner）完全不认识附件

```
grep "Attachment|attachment" helloai-core/src/main/java/com/helloai/core/planner  →  0 files
```

需求对话的 Prompt 模板（`prompts/requirement-clarify.md`、`requirement-chat.md`）只有五个变量：

```
{{CONVERSATION_HISTORY}} {{CURRENT_USER_MESSAGE}} {{LONG_TERM_MEMORY_CONTEXT}}
{{SYSTEM_TIME_CONTEXT}}  {{WEB_SEARCH_CONTEXT}}
```

没有附件层。**结论：给 planner 一个文件，它连"有这个文件"都不知道。**

### 2.4 模型侧能力已有元数据、缺调用通道

`llm_provider_model.capabilities` 已按模型声明输入模态，实测库内：

| provider | 声明 |
|---|---|
| anthropic（claude-sonnet-4-5 / haiku / opus 全系） | `["text","image","pdf"]` |
| dashscope（qwen3.5 系） | `["text","image","video"]`（部分含 audio） |
| deepseek（v4-flash） | `["text","image"]` |
| moonshot（kimi-k2.7-code） | `["text","image","video"]` |

`ModelCapabilities` 解析器已把这套 JSONB 归一成 `inputModalities`（且对 `pdf` 这种非封闭词表做了开放处理）。
但 Java 侧搜 `Media` / `MediaFormat` **0 处** —— 也就是说：**能力有登记，通道没建**。

### 2.5 RAG 零件已就位（可复用，不必新建）

| 零件 | 现状 |
|---|---|
| 向量存储 | PG `kb_chunk`，pgvector `vector(1024)` + HNSW 余弦（`KnowledgeRepository`） |
| 嵌入 | `KnowledgeEmbedder` 走 DashScope OpenAI 兼容端点（复用 `spring-ai-openai`，不新增依赖） |
| 检索 | `KnowledgeBaseService#search`（query 嵌入 → top-k → 预算截断） |
| 给 Agent 的工具 | `search_knowledge`（`SearchKnowledgeToolCallback implements ToolCallbackContributor`） |
| 引用溯源 | `GET /api/kb/chunk/{source}/{chunkIdx}`（前端可点开原文分片） |
| 摄入接口 | `POST /api/kb/ingest`（source 幂等覆盖）、`DELETE /api/kb/source/{source}` |

### 2.6 限额现状

| 层 | 现值 | 出处 |
|---|---|---|
| multipart 单文件 / 单请求 | 8MB / 8MB | `spring.servlet.multipart`（注释说明"略高于 storage 5MB 留边界余量"） |
| 存储层单文件 | 5MB | `storage.max-file-size`（同注释） |
| 单附件注入正文 | 64000 字符 | `AttachmentContentPolicy` |
| 单轮注入合计 | 200000 字符 | 同上 |

## 3. 任务表（ATT-1 ~ ATT-4）

### ATT-1（可离线，1~2 天）：文本 + PDF 文本层 + 注入

> **状态**：已完成 ｜ **剩余动作**：—

| 项 | 内容 |
|---|---|
| 依赖 | **Tika 4.1.0 标准解析包**（`tika-parsers-standard-package` + `<type>pom</type>` 一行，实测 86 条 classpath，含 pdf / microsoft / html / image / ocr 模块，见 §2.5）；首次引入需一次联网解析，之后照旧 `-o` |
| 后端 | `chat_attachment` 建表 + 上传/清单/删除/预览 4 个端点 + `@Async` 解析 worker；`DocumentParser` 端口两个实现：`TextParser`（直读 + `TextCharsetResolver` 判码）、`TikaParser`（`AutoDetectParser` + `ToMarkdownContentHandler` + 三组限额） |
| 单测 | `TextCharsetResolver`：UTF-8 / GBK / GB18030 / UTF-16 BOM / 纯 ASCII 五例；`TikaParser`：pdf 文本层、docx 表格 → `\|a\|b\|`、损坏文件 → FAILED 不抛穿 |
| Prompt | 三模板加 `{{ATTACHMENT_MANIFEST}}` / `{{ATTACHMENT_CONTEXT}}`，渲染器补两个变量 |
| 前端 | 「＋」菜单加「文件」组、拖拽 + 粘贴、胶囊展示与解析态 |
| 验收 | ① 上传 1 个 2MB PDF（20 页）→ 30s 内 READY，问「第三章讲了什么」回答能对上原文；② 上传 15 个文件触发单次上限提示；③ 30MB 文件被拒且提示可读；④ 解析失败的文件在 Prompt 里被标「正文不可读」且模型不臆测；⑤ 渲染结果无残留 `{{…}}`；⑥ **GBK 编码的中文 txt 不乱码**；⑦ **上传的 md 里 `#`、`\|`、反引号原样保留**（不被 Markdown handler 转义） |

### ATT-2 / ATT-3（3~4 天）：视觉直读 + 大文件 RAG + 引用

> **状态**：ATT-2 待开始 · ATT-3 待开始 ｜ **剩余动作**：ATT-2 多模态通道与视觉转写未建；ATT-3 超预算 ingest 与引用回源未接

**ATT-2 视觉直读（已定口径，图片与扫描件共用）**
- provider 适配层补多模态：`ModelCapabilities.input` 含 `image` → `UserMessage(Media)`
- 图片 → 视觉转写（描述 + 全部可读文字）；扫描件 → PDFBox 渲染页 PNG（≤ 20 页）→ 分批视觉转写
- 视觉模型按能力表择一（qwen-vl 优先），与规划者模型解耦；费用闸 + 失败降级 SKIPPED
- 验收：上传一张 UI 截图 → 转写文本能看出「这是个登录弹窗、有两个输入框和一个蓝色按钮」，且进澄清时被引用

**ATT-3 大文件 RAG + 引用**
- 超预算文件自动 ingest（source = `chat:{conv}:{att}`，幂等覆盖，会话删除时清 source）
- 按当前用户消息自动检索 top-k 注入 `{{ATTACHMENT_RETRIEVAL}}`
- 回答里 `[kb:source#chunk]` 可点开原文分片；消息附件关联 + 气泡 chip
- 验收：上传 300 页手册，问其中一个具体参数，回答带可点回源且片段确为原文

### ATT-4（可选，登记不启动）：版面增强

> **状态**：暂缓 ｜ **剩余动作**：Docling sidecar 未接入（登记不启动，待真实表格类附件出现后再评估）

- `DocumentParser` 端口留了第二实现位：Docling sidecar（`docling-serve` HTTP），表格/多栏/公式强的文件按开关路由过去
- 依赖：构建机可联网拉镜像；按需开启，不设默认
- 验收：同一份多栏研报，Tika/PDFBox 与 Docling 输出并排对比，表格列结构不散

### 明确不做（本轮）

- 文档级 ACL / 团队共享文件库（会话级够用）
- PDF 高保真版面还原（表格散架问题交给 ATT-4 的 Docling sidecar 可选件）
- 外置向量库（pgvector 已够，ADR-002 §7 同库同事务是刻意选择）

## 4. 风险与边界

| 风险 | 影响 | 应对 |
|---|---|---|
| 规划者模型是纯文本（DeepSeek） | 图片必须靠视觉通道转写，多一次调用 | 视觉与规划者模型解耦（ATT-2），转写文本再进澄清；无可用视觉模型时显式 SKIPPED 而非静默空文件 |
| 视觉转写有误差（表格数字、条款编号） | 拿错数值写进验收标准 | Prompt 条款要求「数值/条款须标 `[附件i#Page N]`」，前端展示可点回源；关键信息二次核对提示 |
| PDF 文本层质量差（多栏、表格） | 回答引用错位 | 加 `[Page N]` 锚点；ATT-4 起可切换 Docling sidecar |
| 注入把上下文顶爆 | 澄清质量下降甚至报错 | 严格走 3.4 的分层与预算；`extracted_chars` 落库可观测 |
| 附件与会话生命周期不一致 | 孤儿对象/脏数据 | 会话删除级联软删 + 定时对账。**已登记为 `G-017` 未达成项 ③（含验收）**：对账数据源尚未覆盖 `chat_attachment`，且两者同桶不同前缀会被判「会话附件 = 孤儿」——该项是**开启孤儿清理的阻塞前置**，先于清理开关启用完成 |
| 新会话首句上传的归属 | 文件丢归属 | `client_token` + 建会认领，未认领的按 TTL 清理 |
| 离线构建 | 依赖拉不下来 → 主线打包被卡 | ATT-1 引入 Tika 4.1.0 时**第一次允许联网**一次（之后 `-o` 正常）；若构建机确定长期离线，退回「PDFBox 3.0.5 + POI 5.4.1」实测可离线组合 |
| Tika 4.x API 断代 | 抄 3.x 示例编译不过（`parse` 入参改 `TikaInputStream`）；`spring-ai-tika-document-reader` 仍依赖 3.x，**不能与 4.x 同用** | 本项目直接用 Tika API、不用 Spring AI 的 Tika reader；升级 4.x 后禁止再引 3.x 系 reader |
| 依赖版本漂移 | Tika 4 带入 `pdfbox 3.0.8` / `poi 5.5.1` / `jackson 2.22.3`，与项目固定版本可能不一致 | 解析路径实测在项目 jackson 2.18.4.1 下正常；PDFBox 以 Tika 带入版本为准，不另行声明 |
| PDFBox 线程安全 | 并发解析偶发异常 | `PDDocument` 强约束单线程使用，解析 worker 内部串行 per-document，线程池隔离 |
