## 0. 定位与边界（★先读）

**① 问题来源**

- **用户反馈（2026-10-22）**：需求对话里无法挂文件；规划者（planner）完全不认识附件内容。原始记录见 `LOG-20261022-009` / `010` / `011`。
- **差距表锚点**：`G-016`（附件内容注入口径）、`G-017`（对象对账覆盖——三类引用源已接入并真机验收，清理开关仍默认关）、`G-024`（附件与联网检索编排）。
- **设计依据**：`design/HelloAI 需求对话附件设计.md`（数据模型 / 解析分工 / 两层注入 / 限额）。
- **外部对标**：`research/HelloAI 需求对话附件产品对标调研（2026-10-22）.md`。

**② 本计划做什么**

把「需求对话附件」从零做到可用：`ATT-1` 文本 + PDF 文本层 + 两层 Prompt 注入（**已完成**）→ `ATT-2` 图片与扫描件视觉直读 → `ATT-3` 超预算文件 ingest 到 `kb` + 引用回源 → `ATT-4` 版面增强（登记不启动）。

同日追加两项能力（2026-10-23，回答「附件该不该读、该不该搜、搜什么」）→ `ATT-5` **附件意图三态判定**（决定是否注入正文、是否联网）→ `ATT-6` **分析后检索**（先分析附件产不确定点，再用不确定点整理检索词，补搜支持多变体）。逐项产出与验收见 §3 任务表。

**③ 本计划不做什么**（边界，防越界）

1. **不改任务域 `attachment`**——它是子任务产物表，只按 `sub_task_id` 聚合、要求 agent 身份上传；会话附件走 `chat_attachment`。两者共用同一对象桶但前缀不同，改造任务域会把两套生命周期搅在一起（依据：`G-017` 的三类引用源口径）。
2. **不宣称「附件能力已完成」**——`ATT-2` 未做前，图片与扫描件一律 `SKIPPED`（清单里显式写「正文不可读」+ 原因），不得让模型据此臆测内容。
3. **不自建向量库或侧库**——`ATT-3` 复用既有 `kb`（`kb_chunk` + HNSW-cosine，PG 单后端），不引入第二个存储（依据：`G-019` / `ADR-002`）。
4. **不改全局限额契约**——单文件 / 单次 / 单会话限额由 `AttachmentContentPolicy`（shared）单源决定，属 `G-016` 范围；本计划只消费，不调参。
5. **不在 `ATT-1` 引入视觉通道**——视觉模型与规划者模型解耦是 `ATT-2` 的设计口径，`ATT-1` 只做纯文本链路。

**④ 诚实边界**

- `ATT-1` 落地后**超预算文件只能截断**（标注「本次仅注入前 N 字」），**不能**按语义检索命中片段——那是 `ATT-3`。
- 图片 / 扫描件当前**不可读**，表现为 `SKIPPED` 而非静默空文件。
- **会话删除不触碰附件**——`delete(conversationId)` 只删消息与会话行（`RequirementClarifyServiceImpl#delete`），`chat_attachment` 行与桶内对象都留着；且这些行 `deleted` 仍为 0 ⇒ 对账把它们当**有效引用**，永远不会被判孤儿，孤儿清理开关也清不到。只有单条附件删除（`deleteById`）才走 `afterCommit` 回收对象。`G-017` 未达成项 ③（真机双来源对账验收）已于 2026-10-26 通过（`LOG-20261026-028`），但它补的是「对账看得见」，不改这条生命周期缺口。
- **当前没有「附件意图判定」**——会话里有附件时，无论本轮问什么，附件正文都按预算注入。`ATT-5` 落地前，问「今天天气」也会带上附件（占上下文，且可能干扰回答）。
- 正文注入预算受 `AttachmentContentPolicy` 约束（单文件 64k / 总计 200k），本计划不承诺更大上下文。

## 2. 现状（勘察结论，`[实测]`）

### 2.1 附件域只服务子任务

| 事实 | 取证位置 |
|---|---|
| `attachment` 表只有 `sub_task_id`，**没有 conversation 维度** | `\d attachment`（字段 sub_task_id / visibility / uploader_agent_id） |

### 2.2 解析能力：PDF / Office / 图片都不读

| 事实 | 取证位置 |
|---|---|
| 无 PDF / Office 解析依赖 | 三个 `pom.xml` 中 `pdfbox` / `tika` / `poi` 命中 0 处 |

### ATT-3（3~4 天）：大文件 RAG + 引用 + 片段重排

> **状态**：已完成 ｜ **剩余动作**：—

**ATT-3 大文件 RAG + 引用**
- 超预算文件自动 ingest（source = `chat:{conv}:{att}`，幂等覆盖，会话删除时清 source）
- 按当前用户消息自动检索 top-k 注入 `{{ATTACHMENT_RETRIEVAL}}`
- 回答里 `[kb:source#chunk]` 可点开原文分片；消息附件关联 + 气泡 chip
- 验收：上传 300 页手册，问其中一个具体参数，回答带可点回源且片段确为原文

**ATT-3 的设计前置（借鉴 `E:\yhzx\1027\springai` 的实现，2026-10-23）**：

1. **检索必须带作用域三重过滤**：`file_id ∈ 本轮选中集合` + `conversation_id` + `user_id`，三者缺一不可。参考实现是在 kNN 检索的 `filter` 里一次性给全（`terms(file_id)` + `term(user_id)` + `term(conversation_id)`），**先过滤再算相似度**，不是捞回来再筛。

   **这条是硬前置，不是优化项**：我们的 `kb` 是**全平台共享**的向量表（`kb_chunk`），若检索不带 `conversation_id` / `user_id`，A 会话能检索出 B 会话的附件正文——**跨会话泄漏**。`source = chat:{conv}:{att}` 前缀只是命名约定，**不能被当作访问控制**。

   **现状缺口（2026-10-23 实测 `kb_chunk` 字段）**：表里只有 `id / source / chunk_idx / content / embedding / create_time / create_by / update_by / deleted`——**没有 `conversation_id`，也没有 `user_id`**。所以三重过滤里的两项在表结构上并不存在，只有 `source` 前缀可依赖。

   **因此 ATT-3 须先补一次 Flyway 迁移**：`kb_chunk` 加 `conversation_id` / `user_id` 两列 + 复合索引，回填时从 `source` 解析（`chat:{conv}:{att}` 结构固定）。只靠 `source LIKE 'chat:{conv}:%'` 也能跑，但前缀 `LIKE` 需要 `text_pattern_ops` 索引才不退化，且表达不了「谁上传的」——不如直接加列。**版本号在落地时按当时最大迁移号顺延，不在本计划里预占。**
2. **每文件配额 + 总量上限**：参考实现取「每文件 ≤ 5 片 + 总 ≤ 20 片 + 按文件分组输出并加 `【文件：xxx】` 头」。我们 `buildContext` 目前是**先到先得**（第一份吃满 64k，第四份可能「预算已用尽」），多文件场景会饿死后面的文件。ATT-3 落地时须改为「先给每文件保底份额，剩余预算再按需分配」。
3. **单次参与文件数上限**：参考实现限 5 个（`MAX_FILES`），超限直接拒。我们 `AttachmentContentPolicy` 已有「单次 5 个」口径，落地时复用，不新增常量。

**ATT-3 片段重排（2026-11-07 方案）**：

- **复用**：`BochaRerankService` 的 HTTP 契约（`POST /v1/rerank`、`gte-rerank`）已由 `W-5` 真机验证。抽出通用入口 `rerankOrder(String query, List<String> documents)`，返回按 `relevance_score` 降序的**原下标**；`rerank(query, List<WebSearchResult>)` 改为委托该入口，行为与日志口径不变。
- **接线点**：`ChatAttachmentPromptRenderer#buildRetrieval`——`KnowledgeBaseService.search` 返回 top-k（16 片）后、拼 `{{ATTACHMENT_RETRIEVAL}}` 前，以 `hit.content()` 送排；按重排顺序注入，`[kb:source#idx]` 锚点与文件名映射不变。
- **开关**：`helloai.attachment.retrieval-rerank-enabled`（默认 `false`）——与 `W-5` 的 `helloai.web-search.rerank-enabled` **分开**，避免「开启网页重排 ⇒ 附件检索也自动计费」；两者共用博查 Key。
- **降级契约**：开关关 / 无博查 Key / 片段 < 2 / 请求失败 / 响应不可解析 → 原顺序注入（检索是附加值，重排失败不得让本轮读不到附件）。
- **边界**：`doSearch` 的字符预算截断发生在重排前；128K 窗口下 16 片 × 600 字 ≈ 检索预算 9,600 字，正常不触发截断；仅极端长片段场景下重排只能调整已返回片段的顺序。
- **验收**：① 单测锁定重排顺序、降级与空片段路径；② 真机开启后日志出现 `附件片段重排完成: in=…, out=…, filtered=…`，关闭时无该日志且注入顺序与向量序一致。
- **实现落地（2026-11-07）**：`BochaRerankService#rerankOrder(String, List<String>)` 返回按分降序的**原下标**（`<2` 条 / 无 Key / 失败 / 不可解析返回 `null`），`rerank(query, results)` 改为委托该入口、日志口径不变；`parseReranked` 收敛为 `parseOrder(body, size)`。接线落在 `ChatAttachmentPromptRenderer#rerankHits`（`buildRetrieval` 内、字符预算截断之后），开关 `helloai.attachment.retrieval-rerank-enabled` 默认 `false`，与 `helloai.web-search.rerank-enabled` 分离。单测：`BochaRerankServiceTest` 10 项（`rerankOrder` 无 Key / 不足 2 条 / 网络失败 / 本地 `HttpServer` 断言顺序 `[2,0,1]` / **网页开关关闭但 Key 就绪仍重排**）、`ChatAttachmentPromptRendererTest` 27 项（重排生效 / 关闭零交互 / 失败回退向量序）。
- **真机缺陷与修复（2026-11-07）**：首轮真机附件检索命中 16 片但无重排日志。根因：`BochaRerankService#isAvailable()` 将「网页重排开关」当作通道可用性，`rerankOrder` 复用它 ⇒ 附件独立开关单独开启被静默吞掉。修复：抽出 `hasCredential()`（只判博查 Key），`rerankOrder` 仅按 Key 判定；`rerank(query, results)` 自身显式判定 `isAvailable()`，网页入口的开关约束不变。新增回归单测 `rerankOrder_webSwitchOff_stillReranks` 锁定「网页开关关闭、Key 就绪时通用入口仍重排，网页入口仍返回原序」。
- **真机证据（2026-11-07）**：开关开启（临时配置）后同一附件提问出现 `博查 Rerank 完成: in=16, out=16, filtered=0` 与 `附件片段重排完成: conversationId=2113486948265484290, in=16, out=16, filtered=0`（检索 16 片后确实调用重排）；临时开关回滚为默认 `false` 并重启后，同一提问仅出现 `附件检索命中: hits=16`，无重排日志、无博查调用（保持向量序）。临时配置已回滚，`git diff` 为空。

### ATT-5（1~2 天）：附件意图三态判定

> **状态**：已完成 ｜ **剩余动作**：—

**目标**：每轮先判定本轮提问与附件的关系，避免两种极端——「有附件就带全文」与「有附件就不敢搜」。

| 取值 | 含义 | 系统行为 |
|---|---|---|
| `none` | 本轮不涉及附件（如「今天天气怎么样」） | **不注入附件正文**（省上下文），附件清单仍可见 |
| `answerable` | 附件本身能答（如「这份手册第 3 步说什么」） | 不联网，基于附件作答 |
| `needs_external` | 附件需外部核验（如「这个方案合不合规」） | 进 `ATT-6`，检索词只能来自附件里的外部锚点 |

**落点**：

- `prompts/requirement-decision.md` §三：`need_search` 布尔 → 增 `attachment_intent` 三态；兼容期保留 `need_search` 双写
- `ChatRoundDecisionParser`：`SearchDecision` record 加字段；缺失时按 `need_search` 推导（向后兼容，老模板不炸）
- 三个消费方按三态分支：`ClarifyCommandSearchServiceImpl`（`resolveChatSearchOutcome`）/ `ClarifyStreamServiceImpl:144,285`（进度文案）/ `ClarifyRoundOrchestratorServiceImpl`（`runChatSearchRound`）

**验收**：同一会话三段验证 —— ① 带附件问「这份手册第 3 步说什么」→ `answerable`，不触发联网；② 次轮问「今天天气」→ `none`，Prompt 里无附件正文；③ 带附件问「这个方案合不合规」→ `needs_external`，检索词含附件里的法规名。

**边界**：不新增 LLM 调用（复用既有决策调用，只加字段）；不改 `AttachmentContentPolicy` 限额。

### ATT-6（2~3 天）：分析后检索（方案 A）

> **状态**：已完成 ｜ **剩余动作**：—
> **真机证据（2026-11-06）**：上传附件提问后，检索词为附件外部锚点、补搜产出 3 条不同角度查询、回答区分「附件结论」与「外部核验」，见 `LOG-20261106` F 域。

**目标**：检索词来自「附件分析后整理出的不确定点」，既不是用户原话，也不是附件原文。

三步链路：**分析**（基于附件产初步结论）→ **提不确定点**（附件没给依据 / 与常识冲突 / 需外部核验）→ **整理检索词**（每个不确定点 → 1 条查询，多条变体）。

**落点（不引入 Spring AI，改自建链路）**：

| 改动 | 位置 | 说明 |
|---|---|---|
| 缺口模板产出多变体 | `prompts/websearch-gap-assess.md` | 由「给出 1 个补充查询」改为「给出 1~3 个不同角度的补充查询」 |
| 解析取全数组 | `SearchGapAssessor.parseGapQuery` | `arr.get(0)` → 取前 N 条（上限 3），返回 `List<String>` |
| 补搜支持多条 | `ClarifyWebSearchOrchestrator` | 补搜循环遍历多条，去重后并入结果 |
| 不确定点显式化 | 决策模板附件区（`renderForDecision` 已给锚点区） | 要求模型先写「未决点」再给 `search_query` |

**为什么不引入 Spring AI**：`MultiQueryExpander` / `QueryTransformer` 均需 `ChatClient` 驱动，而本平台调用走 `PlatformAgentExecutionService.executeSync`（agent 层管模型路由 / 成本记账 / 故障转移）。硬接会出现两套模型抽象并存；且 `RetrievalAugmentationAdvisor` 是**线性流**，满足不了「先分析再判不确定点」的自适应要求。判据与取舍见 `LOG-20261023-014`。

**验收**：上传一份自编手册，问「这个方案合不合规」—— ① 检索词含附件里的法规名 / 标准号，而非「我上传的附件」；② 补搜轮次产出 ≥ 2 条不同角度查询；③ 回答区分「附件结论」与「外部核验结果」。

**依赖**：`ATT-5` 先落地（否则无法确定何时该进这条链）。
### ATT-7（1 天）：附件预算窗口化（防撑爆）

> **状态**：已完成 ｜ **剩余动作**：—
> **真机证据（2026-11-06）**：128K 窗口下 120,010 字文档注入 25,600 字、截断提示含「拆分为多个文件分批上传」，见 `LOG-20261106` F 域。

**问题**：`ATTACHMENT_CONTENT_TOTAL_LIMIT = 200,000` 字是按「1M 窗口模型」拍的，用在 128K 窗口模型上必然溢出。

按 Kimi 官方 FAQ 的换算基准（K2.6 单轮 128K token ≈ 5~6 万汉字 ⇒ **1 汉字 ≈ 2 token**）：

| 模型窗口 | 200,000 字折合 | 结论 |
|---|---|---|
| 128K token | 约 400,000~500,000 token | **超窗口 3~4 倍** |
| 1M token | 约 400,000 token | 勉强安全 |

且 `llm_provider_model.capabilities` 里**没有 `contextWindow` 字段**，平台根本不知道模型能吃多少 token——预算与窗口完全脱钩。失败形态是**静默截断到窗口之外**（回答缺内容或请求失败），不是显式报错。

**做法（不改注入方式，只改预算算法）**：

1. **配置项** `helloai.attachment.context-window-tokens`（默认 `128000`）——取平台现役模型的**最小值**作为保守默认，不按 per-model 动态取（`ChatAttachmentPromptRenderer` 拿不到模型信息，链路改造收益不抵成本）。
2. **预算计算公式**：

   ```java
   // 附件最多占窗口 40%，剩余 60% 留给会话历史 / 检索结果 / 输出
   int budgetChars = contextWindowTokens * 40 / 100 / 2;   // 2 = 每汉字 token 数（保守）
   int totalLimit  = Math.min(ATTACHMENT_CONTENT_TOTAL_LIMIT, budgetChars);
   ```

   | 窗口 | 算出预算 | 对比现状 |
   |---|---|---|
   | 128K | 25,600 字 | 现值 200,000，**超 7.8 倍** |
   | 256K | 51,200 字 | |
   | 1M | 200,000 字 | 与现值一致（现值即按此设计） |
3. **触顶文案补处置建议**（对齐 Kimi 的做法）：现行文案只写「缩小范围」，补一句「或拆分为多个文件分批上传」。
4. **单文件上限同时收紧**：`perFileLimit = min(64,000, totalLimit)`，避免单文件吃掉全部预算。

**不做的事**：

- **不做向量化**（结论见 `LOG-20261023-018`：超 64k 的附件占比 0%，向量化是过度设计）
- **不做 per-model 动态窗口**（需要模型元数据 + 链路改造；先用保守全局值兜住「不撑爆」这个底线）

**验收**：把配置调到 `128000`，上传一份 10 万字文档——① 注入正文字数 ≤ 25,600；② Prompt 里出现截断提示且字数吻合；③ 请求不因超窗口失败。

**风险**：收紧后大文件可用内容变少。缓解：截断提示里明确原文长度与本次注入量，用户可自行拆分上传。

### ATT-8（0.5 天）：进度文案取真实候选词

> **状态**：已完成 ｜ **剩余动作**：—

**问题**：`RoundProgressText.searching(String)` 直接把用户原始消息当「检索词」展示（`ClarifyStreamServiceImpl:192` / `AssistantChatServiceImpl:419`），而真实候选词要到检索阶段才生成。用户看到「正在联网检索：帮我分析一下我上传的附件这个手册方案是否正确」——这既不是检索词，也不像进度。selection 模式下传入的 `userMessage` 甚至不是真正的检索锚。

**做法**：

1. `ClarifyWebSearchOrchestrator` 拆出 `planCandidates(userMessage, priorityQueries)`：URL 分离 + 优先词合并 + 规则/LLM 规划 + 兜底关键词 + 相对时间归一化，**只规划、不搜索、不抓页面**；
2. `doWebSearch(..., plannedCandidates)` 新增重载：候选非 null 时跳过重复规划（LLM 规划只跑一次），仍执行抓页面 / 域名前置 / 候选检索 / 补搜 / 重排 / 合并；
3. `ClarifyCommandSearchService` 增 `planChatSearch(...)` / `planClarifySearch(...)`（返回 `null` 表示本轮不检索）与 `executeChatSearch(...)`，`resolveChatSearchOutcome` 改为调用两者；
4. 澄清与助理两条流式链路改为「先规划 → 用真实候选词发进度帧 → 再执行」；不检索时按原因发「会话搜索开关关闭」或「附件内容可回答 / 无需外部资料」。

**边界**：

- 不新增 LLM 调用（规划结果复用，不重跑）；
- 域名前置发生在抓页面失败之后，进度帧里的检索词可能比最终实际检索词少一个 `site:` 前缀；
- 规划本身失败（异常/超时）时回退为空候选，进度帧显示「正在联网检索」，行为与改造前一致。

**验收**：① 进度帧文本与结果帧「（检索词：…）」逐词一致；② 助理链路同样生效；③ 搜索开关关闭时进度帧显示跳过原因而非伪检索词。

**实现落地（2026-11-07）**：`ClarifyWebSearchOrchestrator` 新增 `planCandidates(userMessage, priorityQueries)` 与 `planCandidates(userMessage, priorityQueries, anchor)`，`doWebSearch(String, List, LocalDate, List<String> plannedCandidates)` 在候选非 `null` 时跳过重复规划（纯 URL 的域名前置兜底同时从执行阶段移入规划阶段，并加 `startsWith(host)` 防重复前置）；`RoundProgressText.searching(String)` 换为 `searching(List<String>)`（`null`/空 → 「正在联网检索」，否则拼前 60 字）。`ClarifyCommandSearchService` 以 `record PlannedChatSearch(String source, List<String> queries)` 承载规划结果，`planChatSearch` 保留 `ATT-5` 的 `vetoesWebSearch` 否决与 `ALWAYS_ON`/`OFF`/`AUTO`/降级分支，`planClarifySearch` 在开关关闭时返回 `null`。澄清 CHAT/CLARIFY 与助理流式两条链路均改为「先规划 → 发进度帧 → 再执行」，跳过时分别显示「会话搜索开关关闭」「附件内容可回答 / 无需外部资料」。单测：新增 `ClarifyWebSearchOrchestratorTest` 4 项（含 `verify(searchQueryPlannerService, never()).planQueries(...)` 锁定「规划不重跑」）与 `RoundProgressTextTest` 3 项；`RequirementClarifyServiceTest` 中旧断言「正在联网检索：你好」按新语义改为「本轮未联网检索（无需外部资料）」。

**真机证据（2026-11-07）**：需求对话 CHAT 联网轮进度帧检索词与结果帧「（检索词：…）」逐词一致；搜索开关关闭轮显示「本轮未联网检索（会话搜索开关关闭）」而非伪检索词；助理链路进度帧同样取真实候选词并按 60 字截断，结果帧同源。见 `LOG-20261107`。

## 4. 风险与边界

| 风险 | 影响 | 应对 |
|---|---|---|
| 规划者模型是纯文本（DeepSeek） | 图片必须靠视觉通道转写，多一次调用 | 视觉与规划者模型解耦（ATT-2），转写文本再进澄清；无可用视觉模型时显式 SKIPPED 而非静默空文件 |
| 视觉转写有误差（表格数字、条款编号） | 拿错数值写进验收标准 | Prompt 条款要求「数值/条款须标 `[附件i#Page N]`」，前端展示可点回源；关键信息二次核对提示 |
| PDF 文本层质量差（多栏、表格） | 回答引用错位 | 加 `[Page N]` 锚点；ATT-4 起可切换 Docling sidecar |
| 注入把上下文顶爆 | 澄清质量下降甚至报错 | 严格走 3.4 的分层与预算；`extracted_chars` 落库可观测 |
| 附件与会话生命周期不一致 | 孤儿对象/脏数据 | 会话删除级联软删 + 定时对账。**`G-017` 未达成项 ③ 已于 2026-10-26 验收通过**（`LOG-20261026-028`）：三类引用源（含 `chat_attachment`）并入同一被引用集合，会话附件对象不再被判孤儿，悬空方向真机复现。**残留缺口**：会话删除不触碰 `chat_attachment`（行 `deleted` 仍为 0 ⇒ 永不判孤儿、也无 TTL 清理任务），需另行定「会话删除级联附件 + 对象回收」口径，见 §0④ |
| 新会话首句上传的归属 | 文件丢归属 | `client_token` + 建会认领，未认领的按 TTL 清理 |
| 离线构建 | 依赖拉不下来 → 主线打包被卡 | ATT-1 引入 Tika 4.1.0 时**第一次允许联网**一次（之后 `-o` 正常）；若构建机确定长期离线，退回「PDFBox 3.0.5 + POI 5.4.1」实测可离线组合 |
| Tika 4.x API 断代 | 抄 3.x 示例编译不过（`parse` 入参改 `TikaInputStream`）；`spring-ai-tika-document-reader` 仍依赖 3.x，**不能与 4.x 同用** | 本项目直接用 Tika API、不用 Spring AI 的 Tika reader；升级 4.x 后禁止再引 3.x 系 reader |
| 依赖版本漂移 | Tika 4 带入 `pdfbox 3.0.8` / `poi 5.5.1` / `jackson 2.22.3`，与项目固定版本可能不一致 | 解析路径实测在项目 jackson 2.18.4.1 下正常；PDFBox 以 Tika 带入版本为准，不另行声明 |
| PDFBox 线程安全 | 并发解析偶发异常 | `PDDocument` 强约束单线程使用，解析 worker 内部串行 per-document，线程池隔离 |
| 意图三态误判（涉及附件却判 `none`） | 不注入正文 → 答非所问 | `ATT-5` 落地后按 §3 三段验收；误判时用户可显式说「看附件」重判 |
| 变体扩展推高延迟 | 补搜从 1 条变 3 条，单轮多 5~10s | `ATT-6` 只在首轮命中不足时触发；补搜受 `searchBudgetMs` 约束，超时丢弃不重试 |
