## 0. 定位与边界（★先读）

**① 问题来源**

- **用户裁定（2026-10-24）**：明确要求「草案生成与拆解，**不仅仅是针对于代码开发的**」。原始记录见 `LOG-20261024-034`。
- **自查认定的基准错位**：同日早前的对照分析（`LOG-20261024-033`）以 `spec-kit` / `claude-task-master` / Qoder 为基准，三者均为编码工具，只能得出「交互层缺什么」，得不出「能力模型缺什么」——本文档与设计文档是对该基准错位的修正。
- **代码级根因**：`planner-decompose.md` 的「拆解原则」整段是软件交付语法（`planner-decompose.md:60-93`）；`GRANULARITY` 只控制「拆多细」，不控制「按什么维度拆」（`planner-decompose.md:34-38`）；`task` 表无任何领域 / 交付物类型维度（`V1__init_all.sql:24-36`）。
- **差距表锚点**：`G-025`（本轮登记）；正交相邻项 `G-010`（`GRANULARITY` 出处）、`G-011`（`uncertainties` 字段出处）。

**② 本计划做什么**

把「按什么维度拆」与「谁来判怎么判」变成显式声明，使拆解从「只有一档（静态 DAG + 软件交付语法）」变为「按判据分档」。具体产出七条：

1. **两个字段**：`task.task_archetype`（六类拆分维度）+ `sub_task.acceptance_kind`（四类验收判据）。
2. **提示词按 archetype 分支**：`planner-decompose.md` 注入 archetype，输出对应的拆分维度与终止锚；BUILD 保持现全行为（含契约先行）。
3. **archetype 判定链**：终稿产出时判（`final_package.archetype`）+ 用户可改 + 判不出回落 `BUILD`。
4. **验收校验按 kind 分流**：`AUTOMATED` / `STRUCTURAL` / `REVIEWED` / `ATTESTED` 各走各的文本写法校验，把「假可判定」挡在落库前。
5. **拆解期上下文快照**：`{{TASK_CONTEXT_SNAPSHOT}}`（附件清单 / 知识库命中 / 历史同类任务），解决「拆解输入只有 title + description」。
6. **验收契约可满足性标注**（`TD-11`）：同一子任务内 `acceptance` 与 `uncertainties` 交叉校验——量化验收若依赖一个「只能问人」的缺口，则登记前置条件。**只标注、不拒绝、不改 kind**。
7. **核验侧前置条件豁免**（`TD-12`）：核验逐条判定时读前置条件，未满足则记 `SKIPPED(blocked_by)` 而非 `FAIL`；前置满足则照常严格判。

**③ 本计划不做什么**（边界，防越界）

1. **不做「通用任务拆解」**——不存在这种东西；拆解维度与验收判据由交付物性质决定，方案是分档不是统一。依据：`design/HelloAI 任务拆解领域无关化设计.md` §8。
2. **不做 archetype 自动学习**——样本量为 0 时任何学习都是噪声。依据：同设计 §8；先靠「模型判 + 人工可改」积累标注。
3. **不引入第二套执行调度器**——ledger 走单步派发复用现有分发链。依据：本项目「同一事实双写必分叉」判据。
4. **不改 `sub_task` 四要素契约与 DAG 校验**——`content`/`deliverable`/`acceptance`/`priority` 仍必填；Kahn 拓扑与环检测（`PlannerDecomposeAsyncServiceImpl:557` / `:614`）原样保留。依据：设计 §7 第 1、2 条。
5. **不改 `TaskBaseline` 初始化时机**——它的时机对它自己是正确的；缺的是拆解期快照，不是把 baseline 提前。依据：设计 §5.3。
6. **不改澄清链路的门控与交互**——`progress` 自评门控化、`Recommend` 一键采纳等属交互层，与本计划的「能力模型」是两件事。依据：`LOG-20261024-033` 的 P0 建议已明确降级，不在本计划范围。
7. **不做形式化求解（PDDL / SMT）**——`TD-11` 的可满足性判定走**机械规则 + 窄模式匹配**，不把验收标准建模成状态机或一阶逻辑。依据：本项目的验收是自然语言条目（`STRUCTURAL：1) … 2) …`），形式化建模成本远超收益；开源参照（NASA FRET、`plan-lint`）均只借概念与骨架，不移植其求解器，见 §7。
8. **不在拆解侧降级验收强度**——命中 `TD-11` 不把 `STRUCTURAL` 改成 `REVIEWED`（那是永久放宽标准，映射补齐后也不会自动变严）。豁免只在核验侧、且仅在前置未满足时生效（`TD-12`）。

**④ 诚实边界**

- **`TD-1`/`TD-2` 落库 ≠ 能力可用**：若 `TD-3`（提示词分支）未落地，`archetype` 恒为 `BUILD`、`acceptance_kind` 恒为 `AUTOMATED`，**系统行为与今天完全一致**，只是多了两个常量列。判断「本计划是否生效」的唯一标准是 §3 中 `TD-3` 与 `TD-5` 的状态，不是 `TD-1`/`TD-2`。
- **archetype 判定准确率未知**：`TD-4` 依赖模型判断，首期**没有任何准确率数据**。落地后不得宣称「已支持非代码任务」，只能说「提供了分档通道，判定质量待观测」。
- **存量任务不会被追溯修正**：迁移默认值使历史任务一律 `BUILD` + `AUTOMATED`，它们的行为不变，也不会自动变成正确的 archetype。
- **`RESEARCH` / `DECIDE` 类任务的核心差距不因本计划关闭**：`TD-10`（ledger 通道）不启动前，这两类任务仍是「用静态 DAG 硬拆」，拆出来的步骤在执行时照样作废。本计划只到「拆解骨架对得上」，到不了「计划未知的任务也能自适应」。
- **`STRUCTURAL` 校验器覆盖有限**：它只能判可数的结构断言（章节数 / 条目数 / 字数 / 字段齐全），**判不了内容质量**。写作质量仍只能靠 `REVIEWED` 或 `ATTESTED`。
- **`TD-11` 的「可满足性」是启发式判定，不是证明**：它只能识别「验收里要求实证型来源（URL / 原文摘录 / 页面 / 截图）× 存在只能问人的 `UNCONFIRMED` × 无豁免措辞 × 无澄清依赖」这一种组合。**规则刻意收窄（宁可少标）**——不覆盖「语义上等价但措辞不同」的表达，也不覆盖非来源型的不可满足（如「同一子任务既要求全量又要求零改动」）。漏标时不阻断任何链路，结果仍由核验侧兜底。
- **`TD-12` 的豁免会让「缺输入」类子任务以 SKIPPED 收尾**：这类子任务最终可能停在 `REVIEW` 等人工补映射，而不是自动 `DONE`。这是**有意的**——比"编数据后 DONE"或"零产出后死信"都更接近真实状态，但会提高人工介入频次。
- **`ACCEPTED` 类验收无法自动化**：`ATTESTED` 只能留痕，不能防「人随便点通过」。

## 5. 关键设计决策

| # | 决策 | 取舍理由 |
|---|---|---|
| 1 | **archetype 在 task 级单值，acceptanceKind 在 sub_task 级** | 拆分维度必须由主交付物统一决定，否则骨架是混的；子任务差异只影响「怎么判」，用 kind 表达已足够 |
| 2 | **archetype 在终稿阶段判，不在拆解阶段判** | 拆解时模型只见 title + description，判不准；终稿时已看过完整对话 |
| 3 | **判不出回落 `BUILD`，不做猜测性判定** | 猜错比不猜更贵——错误的拆分维度会产出看起来合理但结构错位的计划 |
| 4 | **`acceptanceKind` 复用 review 域，不新建链路** | `REVIEWED` 本来就是 `subtask-review.md` 轨道 A 的职责，显式声明即可，无需新能力 |
| 5 | **ledger 走单步派发，不引入第二套调度器** | 两条执行路径会让「任务当前状态」的事实源分叉 |
| 6 | **`TaskBaseline` 时机不动，另补拆解期快照** | 两者用途不同（运行基准 vs 输入视图），合并会让语义互污染 |
| 7 | **快照只给「有什么」，不给「是什么」** | 全文注入既撑爆预算，又会让 Planner 抄历史产出而非重新拆解 |
| 8 | **`GRANULARITY` 与 `archetype` 正交互不替代** | 一个管「拆多细」一个管「按什么维度拆」，是两维不是一维 |
| 9 | **stall counter 用净值计数（有进展 −1），不用累加** | 累加实现会在长任务上被历史抖动拖到误重规划；净值计数给的是「有限恢复预算」——小错误不至于立刻重规划，但也不会被后续进展完全抹掉（`[实测]` `_magentic_one_orchestrator.py:393-399`） |
| 10 | **`facts` / `plan` 存自由文本，`progress` 存结构化** | 事实的类型跨领域无法枚举，结构化反而限制表达；progress 五问 schema 固定且需逐次比对趋势 |
| 11 | **`facts` 提取与 `plan` 生成必须两次调用** | 混在一次会让模型「先想计划再倒推事实」，facts 被计划污染（`[实测]` `_prompts.py:26` 明文禁止在一次输出里列 next steps） |
| 12 | **重生成只动内容字段，`title` / `id` / `dependsOn` 不动** | 改这三样会让审计线索断裂——外部引用、依赖图、时间线全部对不上（`[实测]` `update-task.json` 硬规则） |
| 13 | **`TD-11` 可满足性校验「只标不拒」** | 可满足性判定是启发式（文本推断），误判率远高于 `kind ↔ 写法`（后者有确定正则特征）。fail-close 会大面积拒合法拆解并阻塞主链路（风险 2 的同型事故）；且「存在不确定」本身不是错误，正确产出是**标注**而非拒绝 |
| 14 | **豁免在核验侧（`TD-12`），不在拆解侧降级** | 拆解侧把 `STRUCTURAL` 改 `REVIEWED` 是**永久放宽**标准，映射补齐后不会自动变严；核验侧豁免只在「前置未满足」期间生效，条件解除即恢复严格 |
| 15 | **前置条件引用用显式 `ref`（`U1`/`U2`），不用数组下标或内容哈希** | 下标随重拆 / 单条 `regenerateById` 漂移；哈希稳定但不可读，排障时人眼对不上。`ref` 可读且随 JSONB 落地无需迁移 |
| 16 | **规则只咬「实证型来源要求」，不咬所有量词** | `STRUCTURAL` 天然要写量词（`≥3 章节`、`≤300 字`、`5 个字段`），这些不依赖任何外部对象；一律标注会大面积误标并让豁免失控。真正会与 `UNCONFIRMED` 冲突的只有「必须指向某个尚未确定的外部实体去取回证据」 |
