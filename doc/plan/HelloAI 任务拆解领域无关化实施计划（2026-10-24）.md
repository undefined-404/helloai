## 0. 定位与边界（★先读）

**① 问题来源**

- **用户裁定（2026-10-24）**：明确要求「草案生成与拆解，**不仅仅是针对于代码开发的**」。原始记录见 `LOG-20261024-034`。
- **自查认定的基准错位**：同日早前的对照分析（`LOG-20261024-033`）以 `spec-kit` / `claude-task-master` / Qoder 为基准，三者均为编码工具，只能得出「交互层缺什么」，得不出「能力模型缺什么」——本文档与设计文档是对该基准错位的修正。
- **代码级根因**：`planner-decompose.md` 的「拆解原则」整段是软件交付语法（`planner-decompose.md:60-93`）；`GRANULARITY` 只控制「拆多细」，不控制「按什么维度拆」（`planner-decompose.md:34-38`）；`task` 表无任何领域 / 交付物类型维度（`V1__init_all.sql:24-36`）。
- **差距表锚点**：`G-025`（本轮登记）；正交相邻项 `G-010`（`GRANULARITY` 出处）、`G-011`（`uncertainties` 字段出处）。

**② 本计划做什么**

把「按什么维度拆」与「谁来判怎么判」变成显式声明，使拆解从「只有一档（静态 DAG + 软件交付语法）」变为「按判据分档」。具体产出七条：

1. **两个字段**：`task.task_archetype`（六类拆分维度）+ `sub_task.acceptance_kind`（四类验收判据）。
2. **提示词按 archetype 分支**：`planner-decompose.md` 注入 archetype，输出对应的拆分维度与终止锚；BUILD 保持现全行为（含契约先行）。
3. **archetype 判定链**：终稿产出时判（`final_package.archetype`）+ 用户可改 + 判不出回落 `BUILD`。
4. **验收校验按 kind 分流**：`AUTOMATED` / `STRUCTURAL` / `REVIEWED` / `ATTESTED` 各走各的文本写法校验，把「假可判定」挡在落库前。
5. **拆解期上下文快照**：`{{TASK_CONTEXT_SNAPSHOT}}`（附件清单 / 知识库命中 / 历史同类任务），解决「拆解输入只有 title + description」。
6. **验收契约可满足性标注**（`TD-11`）：同一子任务内 `acceptance` 与 `uncertainties` 交叉校验——量化验收若依赖一个「只能问人」的缺口，则登记前置条件。**只标注、不拒绝、不改 kind**。
7. **核验侧前置条件豁免**（`TD-12`）：核验逐条判定时读前置条件，未满足则记 `SKIPPED(blocked_by)` 而非 `FAIL`；前置满足则照常严格判。

**③ 本计划不做什么**（边界，防越界）

1. **不做「通用任务拆解」**——不存在这种东西；拆解维度与验收判据由交付物性质决定，方案是分档不是统一。依据：`design/HelloAI 任务拆解领域无关化设计.md` §8。
2. **不做 archetype 自动学习**——样本量为 0 时任何学习都是噪声。依据：同设计 §8；先靠「模型判 + 人工可改」积累标注。
3. **不引入第二套执行调度器**——ledger 走单步派发复用现有分发链。依据：本项目「同一事实双写必分叉」判据。
4. **不改 `sub_task` 四要素契约与 DAG 校验**——`content`/`deliverable`/`acceptance`/`priority` 仍必填；Kahn 拓扑与环检测（`PlannerDecomposeAsyncServiceImpl:557` / `:614`）原样保留。依据：设计 §7 第 1、2 条。
5. **不改 `TaskBaseline` 初始化时机**——它的时机对它自己是正确的；缺的是拆解期快照，不是把 baseline 提前。依据：设计 §5.3。
6. **不改澄清链路的门控与交互**——`progress` 自评门控化、`Recommend` 一键采纳等属交互层，与本计划的「能力模型」是两件事。依据：`LOG-20261024-033` 的 P0 建议已明确降级，不在本计划范围。
7. **不做形式化求解（PDDL / SMT）**——`TD-11` 的可满足性判定走**机械规则 + 窄模式匹配**，不把验收标准建模成状态机或一阶逻辑。依据：本项目的验收是自然语言条目（`STRUCTURAL：1) … 2) …`），形式化建模成本远超收益；开源参照（NASA FRET、`plan-lint`）均只借概念与骨架，不移植其求解器，见 §7。
8. **不在拆解侧降级验收强度**——命中 `TD-11` 不把 `STRUCTURAL` 改成 `REVIEWED`（那是永久放宽标准，映射补齐后也不会自动变严）。豁免只在核验侧、且仅在前置未满足时生效（`TD-12`）。

**④ 诚实边界**

- **`TD-1`/`TD-2` 落库 ≠ 能力可用**：若 `TD-3`（提示词分支）未落地，`archetype` 恒为 `BUILD`、`acceptance_kind` 恒为 `AUTOMATED`，**系统行为与今天完全一致**，只是多了两个常量列。判断「本计划是否生效」的唯一标准是 §3 中 `TD-3` 与 `TD-5` 的状态，不是 `TD-1`/`TD-2`。
- **archetype 判定准确率未知**：`TD-4` 依赖模型判断，首期**没有任何准确率数据**。落地后不得宣称「已支持非代码任务」，只能说「提供了分档通道，判定质量待观测」。
- **存量任务不会被追溯修正**：迁移默认值使历史任务一律 `BUILD` + `AUTOMATED`，它们的行为不变，也不会自动变成正确的 archetype。
- **`RESEARCH` / `DECIDE` 类任务的核心差距不因本计划关闭**：`TD-10`（ledger 通道）不启动前，这两类任务仍是「用静态 DAG 硬拆」，拆出来的步骤在执行时照样作废。本计划只到「拆解骨架对得上」，到不了「计划未知的任务也能自适应」。
- **`STRUCTURAL` 校验器覆盖有限**：它只能判可数的结构断言（章节数 / 条目数 / 字数 / 字段齐全），**判不了内容质量**。写作质量仍只能靠 `REVIEWED` 或 `ATTESTED`。
- **`TD-11` 的「可满足性」是启发式判定，不是证明**：它只能识别「验收里要求实证型来源（URL / 原文摘录 / 页面 / 截图）× 存在只能问人的 `UNCONFIRMED` × 无豁免措辞 × 无澄清依赖」这一种组合。**规则刻意收窄（宁可少标）**——不覆盖「语义上等价但措辞不同」的表达，也不覆盖非来源型的不可满足（如「同一子任务既要求全量又要求零改动」）。漏标时不阻断任何链路，结果仍由核验侧兜底。
- **`TD-12` 的豁免会让「缺输入」类子任务以 SKIPPED 收尾**：这类子任务最终可能停在 `REVIEW` 等人工补映射，而不是自动 `DONE`。这是**有意的**——比"编数据后 DONE"或"零产出后死信"都更接近真实状态，但会提高人工介入频次。
- **`ACCEPTED` 类验收无法自动化**：`ATTESTED` 只能留痕，不能防「人随便点通过」。

> 判据是**结论与样本分布无关**：字段空不空、依赖图闭不闭合，判的是「有没有」与「图结构」；文本启发式（名词包含、覆盖矩阵、定性矛盾）依据是某一时点的样本快照，分布一变就误拦合法产出，而 `block` 的代价是整批拆解失败、重试必复现 ⇒ **一律不得 `block`**。落地要求：规则在调用点**显式声明 `severity`**（不再由工厂方法默认 `block`），`Result` 按 `severity` 分区，`hasBlocking()` 只看 `block`。
>
> **阈值型规则的可 block 条件（`s4-5`，取代 `s4-4` 的绝对禁令）**：`s4-4` 原文写「任何阈值型规则不得 block」，却与 `G2_LEN_MIN`（`acceptance` 10 字符仍 block）自相矛盾。改为可校验条件 ——
> **阈值 ≤ 存量分布最小值 / 3（`DraftGateChecker.BLOCK_THRESHOLD_MARGIN`），且每次改阈值须重跑存量回放并核对倍数。** 余量 ≥3 倍时分布小幅漂移不会把合法产出推到阈值以下；不足 3 倍说明阈值贴着当前分布，随时会误拦。历史两例均被本条件正确判定：
> - `deliverable`：存量 5 / 阈值 8 = **0.6 倍** ⇒ 不满足，**阈值已整体删除**（`s4-4`，`P1-C` 事故：11 月的验证/夹具类任务把最小值从 10-24 的 17 拉到 5，119 条存量中 4 条合法草案被整批拦死）；
> - `acceptance`：存量 39 / 阈值 10 = **3.9 倍** ⇒ 满足，**保留 block**。
>
> 推论：`S5` 门 3a 的三条规则（覆盖矩阵 / 输入未产出 / 定性矛盾）无「存量分布最小值」可言，余量条件不成立 ⇒ 只能 `warn`，不得沿用名义上的「确定性」去 block。

**门 2 明确不做「空泛检测」**：中文「内容是否空泛」没有可靠正则，强写只会制造假阳性（把短而准的草案判空）。真正的空泛归门 4。门 2 的「不规定写法」直接抄 `subtask-review.md:71` 的既有口径——「技能只用于判断交付形态是否缺失，不用于比较实现手段，等价实现同样算达标」，保证拆解侧与核验侧对「合规」的定义一致。

**门 4 的触发条件是风险命中，不是「门 3 不通过」**：门 3a 的确定性规则只能发现「引用解不开 / 有环 / 覆盖映射缺失」，**发现不了语义矛盾**——`LOG-20261025-014` 那类缺陷（验收要求取回外部实证，而该实证在另一草案被标 `UNCONFIRMED`）在确定性规则下全绿。按「不通过才跑」的触发，门 4 一次都不会被调用。正确触发：**本草案验收含证据型动词 ∧ 全任务存在 `UNCONFIRMED` ∧ 本草案有跨草案依赖，三条同时成立才调**。

**门 4 不复用 reviewer 的判据**：`subtask-review.md:57` / `:138` 的轨道 A 判的是「产出对验收标准的符合性」，证据必须来自物化附件正文或沙箱一手结果，且明文写「你看不到源码仓库」。拆解期**没有任何产出，只有计划文本**，输入形态、证据纪律、失败语义三者皆不同。可复用的是**角色选择方式、`findings` 结构化 schema、从严的默认姿势**；判据必须独立成一份 rubric。`门 4` 与 `TD-12` 也不可合并：前者是计划期问「这条验收能否被满足」，后者是核验期问「产出是否因上游缺口而豁免」——时点、输入、处置都不同，只能共享同一份依赖数据。

**LLM 结果永无 block 权**：凡 LLM 结论（门 3b / 门 4）只能 `warn` / `annotate`。否则同一批草案两次拆解结论不同，会出现「有时能确认、有时不能」；模型误判还会把正确计划卡死。**block 权只给确定性规则**。

**建议（未排期，`S3` 前定）**

- 门 1/2 是纯函数、纯内存，**在 `confirmPlan` 里对 DB 现有草案重建 `PlanDraftItem` 再跑一次，成本可忽略**（草案数 ≤10）；有 `blocking` 则拒绝确认并提示具体草案。

#### 三分类处置（修复动作的选择依据）

| 类 | 缺陷形态 | 修复动作 | 可用性 |
|---|---|---|---|
| **A** | 验收不可满足 / 正文空泛 | `regenerateById` | ✅ 现成：只重写 `content`/`deliverable`/`acceptance`/`acceptanceKind` 四字段（`PlannerDecomposeAsyncServiceImpl:214`） |

| **C** | 根因在需求本身（需求自相矛盾 / 关键事实缺失） | **不重生成**：澄清或写显式假设 | ❌ 任何重生成都只是猜 |

> **这是本方案最大的隐性风险**：少了这三分类，局部重修会系统性地把「不可满足的验收」重写成「可满足但更弱的验收」——表面收敛，实际**降低了契约强度**。它比误报一条告警严重得多，因此 A/B/C 必须在 `findings` 里显式标注（`fixClass`），并对 A 类修复设「验收强度不得下降」的比对检查。

#### 收敛守卫（防「验 → 修 → 验」震荡）

1. 一轮修复后 **`findings` 总数不得增加**（按 `ruleId` 计数）；
2. **最多 2 轮**；
3. 到顶仍不收敛 → **转人工**，未解 `findings` 全量落 timeline；
4. 整批重跑会**重新分配 `ref` 与 `dependsOn` 序号，已建立的引用全部失效** ⇒ 局部重修除了省时间（单次拆解约 48s），也是**保住已通过门禁结果的唯一方式**。

### TD-14 拆解生命周期：状态单一含义 + 租约判活 + 幂等落库

> **状态**：已完成 ｜ **剩余动作**：—
> **建号理由**（2026-11-08，迁移 `V146`）：`TD-13 S4` 把门禁落点后移到「落库之后」后，暴露出三个与门禁判据无关、但同处拆解生命周期的缺陷。它们不属于 `TD-13` 任何切片（`S0`~`S6` 全部关于「判什么」），故续建号 `TD-14`（续号、未新增前缀）。

#### 问题（`[实测]`）

| # | 缺陷 | 现场 | 后果 |
|---|---|---|---|
| 1 | `PLANNING` 一义两用 | `TaskStatus`（改前注释：「拆解进行中**或草案待确认**」） | 「机器在跑」该被超时回收，「等用户确认」不该；混用一个状态后，所有判定只能靠 `NOT EXISTS (草案)` 打补丁 |
| 2 | 判活用 `update_time` 心跳 | `TaskMapper.selectTimedOutPlanning`（改前 `update_time < deadline`） | 拆解线程调模型的十几分钟里**一次库都不写**，无法自证活着 ⇒ 跑得比阈值久必然被判死。dev 的 provider 读超时 `600000ms` 与阈值 10 分钟**正好相等**，误杀不是偶然 |
| 3 | 落库段无事务 | `doDecompose`（改前无 `@Transactional`，而同类的 `expandById` / `regenerateById` 都有） | `saveDrafts` 之后五步（重加载 / 依赖回写 / 契约归一 / findings / 状态推进）各自独立，任一步抛异常即留「半批草案」；失败分支 `rollbackToPending` 只改状态**不清草案** ⇒ 确定性产出「草案在库 + `task=PENDING`」死结（confirm 与 re-decompose 双向拒绝，现场靠 `.tmp/sql-set-planning.sql` 手工改库救回） |
| 4 | 无幂等键 | `executeDecompose` 只在入口查一次 `status != PLANNING` | 异步段被重投 / 补偿重跑时 status 仍是 PLANNING，照样通过 ⇒ 落第二批草案 |

#### 决策

| # | 决策 | 取舍 |
|---|---|---|
| 1 | **`PLANNING` 纯化为「拆解中」，新增 `AWAITING_PLAN_CONFIRM`** | **加 1 个而不是加 2 个**：拆分后 `PLANNING` 自动只剩「机器在跑」一义，不需要再为它另造状态 |
| 2 | **判活改租约 `task.decompose_lease_until`，删 `NOT EXISTS` 补丁** | 与 `OrderExpireTask` 扫 `expire_time`、`TccFreezeTimeoutTask` 扫 `TRY_SUCCESS` 冻结痕迹同构：**超时任务扫痕迹、不扫业务主体状态**。租约是「进入 PLANNING 时就写好的约定到期时刻」，不是心跳 |
| 3 | **状态 / 租约 / `attemptId` 三者同一条 UPDATE（`beginDecompose`）** | 分步写会留「已 PLANNING 但租约或 `attemptId` 为空」的窗口：租约为空被巡检漏检（永久卡死），`attemptId` 为空让幂等键失效 |
| 4 | **`attemptId` 在入口生成，不在异步段生成** | 幂等的本质是「同一件事有同一个名字」。异步段每次执行都生成新 UUID ⇒ 唯一索引永不冲突 ⇒ 幂等形同虚设 |
| 5 | **落库段用 `TransactionTemplate` 包住，LLM 调用留在事务外** | `@Transactional` 会把十几分钟的模型调用也圈进事务（占连接）；抽独立方法又会因同类自调用绕过代理而失效。边界写在代码里最直接（与 `AssistantChatServiceImpl` 同构） |
| 6 | **findings 在整批拆解走同事务版，在展开 / 重生成 / 编辑仍走独立事务** | 判据是「结论描述的主体还在不在」：整批拆解若回滚，草案都没了，孤儿 findings 无意义；改造类操作要「回滚草案变更但留诊断」 |
| 7 | **CAS 失败按「已被回收 → 推回待确认 / 已取消 → 回滚 / 已是待确认 → 幂等」三分流** | 静默跳过 = 草案变孤儿（缺陷 3 的形态）；一律作废 = 白扔用户等了十几分钟的结果；一律推回 = 给已取消任务留孤儿数据 |
| 8 | **唯一索引 `(task_id, decompose_attempt_id, draft_seq)` 带 `WHERE decompose_attempt_id IS NOT NULL AND deleted = 0`** | 部分索引让非拆解路径（展开 / 重生成 / 人工）不受约束；软删行不参与，重新拆解不会撞历史行 |
| 9 | **状态推进与失败回退的 CAS 一律带 `attemptId` 比对（`casStatusForAttempt`）** | 唯一索引只约束「同一 attempt 的第 N 条」，**跨 attempt 完全挡不住**。真实时序：A 跑超租约被巡检推回 `PENDING` → 用户重新拆解得到 B、状态又回 `PLANNING` → A 苏醒落库，只比状态的 CAS 会命中 **B 的** `PLANNING`，两批草案同时入库。把 `attemptId` 比进 CAS 后，A 的推进失败 ⇒ 抛异常回滚 ⇒ 那批草案一条不剩（新增 1 例 `shouldRollbackWhenAttemptSupersededByNewDecompose` 守住该时序） |

| 10 | **「只持 patch 的写入方」必须走按键合并，且事务边界要与主体同生共死**（新增 `SubTaskService.mergeContextInTx`） | 决策 8 把门禁 findings 改成同事务写入时，复用了 `updateContext`——它的契约是**整段覆写**，而 findings 交出去的是只含 `gateFindings` 一个键的 patch。后果：草案落库后 `context` 只剩 `gateFindings`，`plannerAgentId` / `planGeneratedAt` / `acceptanceKindDeclared` / **`acceptancePreconditions`** 全被擦掉。真机实测（2026-11-08）：时间线记了 `task_plan_acceptance_precondition_unmet{preconditionRefs:["U2"]}`，草案 1 的 `context` 里却只剩 `gateFindings` —— `TD-11` 的标注被自己人擦掉，弹窗那栏永远空 |

> **决策 9 的三处调用点**（缺一处即漏一个窗口）：`advanceAfterDecompose` 的 `PLANNING → AWAITING_PLAN_CONFIRM`、`advanceAfterDecompose` 的 `PENDING → AWAITING_PLAN_CONFIRM`（回收后推回）、`rollbackToPending` 与 `PlannerAnalysisServiceImpl.decompose` 的线程池拒绝回退（`PLANNING → PENDING`）。后两者只带状态时会**误伤新一轮拆解**——把别人刚进去的 `PLANNING` 推回 `PENDING`。

> **原计划写「`attemptId` 放草案 `context`」，实施时改为独立列**：唯一索引只能建在列上。若坚持只放 JSONB，就得用表达式索引 `(context->>'decomposeAttemptId')`——那样每次更新 `context`（如写 findings）都会重算索引项，且键名写错时索引**静默失效**（判据 1：规则存在 ≠ 全路径强制）。列为唯一事实源后不再往 `context` 重复写同一事实（判据 4）。

> **决策 10 的分工判据**（`SubTaskService` 三个 context 写入口，按「写成败要不要与调用方同生共死」划）：`updateContext` = 整段覆写 + 跟随事务（只给持有完整 map 的调用方）；`updateContextInNewTx` = 按键合并 + 独立事务（审计要活过回滚）；`mergeContextInTx` = 按键合并 + 跟随事务（只改几个键、但必须与业务同生共死）。**错配的形态是「持 patch 却调覆写」**，所以守门测试钉在调用点（`SubTaskGateFindingsStoreTest`：同事务分支必须调 `mergeContextInTx`、且永不调 `updateContext`）。
>
> 存量影响已量化：2026-11-08 15:36（该改动生效）之后落的草案共 **18 条 / 4 个任务**丢了这批键；其中仅 1 条（任务 `2119361967457947650` 草案 1）本应带 `acceptancePreconditions`，可从时间线事件 payload 复原（`draftSeq` + `preconditionRefs` 都在）。`plannerAgentId` / `planGeneratedAt` / `acceptanceKindDeclared` **全仓无读取方**（`acceptanceKindDeclared` 的唯一读取方 `PlanGateRunner` 在同批判定时读的是内存草案，不受落库后覆写影响），故不回填。

### TD-15 重新拆解前的物理清理越界

> **状态**：已完成 ｜ **剩余动作**：—
> **触发**（2026-11-08）：`TD-14` 收尾时穷举「拆解链路还有哪些出口没收敛」，翻出这条**既有**隐患（不是 `TD-14` 引入的）。

**缺陷**：`decompose` 入口在「该任务下所有子任务都是 `CANCELLED`」时调 `physicalDeleteByTaskId`，其 SQL 是

```sql
DELETE FROM sub_task WHERE task_id = #{taskId}
```

**无状态过滤**。安全性 100% 依赖调用点上方那句 `countByTaskIdExcludingStatus(taskId, CANCELLED) > 0 → 抛错`。这是判据 1 的标准形态：**规则存在 ≠ 全路径强制**——换个调用点忘了那句 count，就会把 `IN_PROGRESS` / `DONE` 连执行痕迹一起删掉。

注释里那句「该场景草案从未执行，无关联执行记录」也不是约束，是**假设**：子任务执行过再被取消（取消前已派发 / 已跑过一轮）时它就不成立，而 `task_timeline` / `review_record` 的 `sub_task_id` 是**无外键的软引用**，删行只会留下指向不存在子任务的孤儿引用，DB 不报错、也不回收。

**改动**：

| 项 | 内容 |
|---|---|
| 新 SQL | `SubTaskMapper#physicalDeleteNeverExecutedCancelled`：`WHERE task_id=? AND status='CANCELLED' AND NOT EXISTS (SELECT 1 FROM agent_execution_record r WHERE r.sub_task_id = st.id)` |
| 出口 | `SubTaskService#physicalDeleteNeverExecutedCancelled`（跨域物理删除仍由 task 域收口，§7.1）；原 `physicalDeleteByTaskId` 保留不动，**只服务任务级联删除**（那里删全部行是对的） |
| 调用方 | `PlannerAnalysisServiceImpl#decompose`；删除数 < CANCELLED 数时记 `task_plan_cancelled_draft_retained`（payload `{cancelled, deleted, retained}`）+ WARN 日志 |
| 事件码 | `TASK_PLAN_CANCELLED_DRAFT_RETAINED` |

**两条约束都下沉到 SQL 的理由**：状态过滤让「非取消态删不掉」对任何调用方成立；`NOT EXISTS` 把「从未执行」这个假设变成条件。二者都不依赖调用方记性。

**取舍（不对称代价）**：保留有执行痕迹的行，会让 §6.100 要解决的「幽灵依赖」在新一轮里仍可能残留——但那只影响新草案的依赖解析（可见、可重拆）；错删执行痕迹是**不可恢复**的。两者不对称，故选保留。

**真机核验（2026-11-08，只读 SQL，不改数据）**：

```
cancelled_total=25  would_delete_new=24  would_keep_new=1
保留行: sub_task.id=2119277757896400897（定义订单系统接口契约）
        agent_execution_record=1 条，所属 task 2119277597539770370 状态=CANCELLED
```

⇒ **这条不是纸面加固**：旧 SQL 在真实数据上会删掉 1 条有执行记录的取消草案。当前不构成现实事故（所属任务本身已 `CANCELLED`，而 `decompose` 要求任务为 `PENDING`），属**潜伏缺陷未触发**——如实登记，不夸大成「已发生过」。

**验收**：`PlannerAnalysisServiceTest#shouldRecordRetainedWhenSomeCancelledDraftsNeverDeleted`（3 条 CANCELLED 只删 2 条 → 记保留事件且 payload 三项齐全）；另两条既有用例改断言新方法名，锁住「不碰旧的无过滤入口」。

**诚实边界**：

## 5. 关键设计决策

| # | 决策 | 取舍理由 |
|---|---|---|
| 1 | **archetype 在 task 级单值，acceptanceKind 在 sub_task 级** | 拆分维度必须由主交付物统一决定，否则骨架是混的；子任务差异只影响「怎么判」，用 kind 表达已足够 |
| 2 | **archetype 在终稿阶段判，不在拆解阶段判** | 拆解时模型只见 title + description，判不准；终稿时已看过完整对话 |
| 3 | **判不出回落 `BUILD`，不做猜测性判定** | 猜错比不猜更贵——错误的拆分维度会产出看起来合理但结构错位的计划 |
| 4 | **`acceptanceKind` 复用 review 域，不新建链路** | `REVIEWED` 本来就是 `subtask-review.md` 轨道 A 的职责，显式声明即可，无需新能力 |
| 5 | **ledger 走单步派发，不引入第二套调度器** | 两条执行路径会让「任务当前状态」的事实源分叉 |
| 6 | **`TaskBaseline` 时机不动，另补拆解期快照** | 两者用途不同（运行基准 vs 输入视图），合并会让语义互污染 |
| 7 | **快照只给「有什么」，不给「是什么」** | 全文注入既撑爆预算，又会让 Planner 抄历史产出而非重新拆解 |
| 8 | **`GRANULARITY` 与 `archetype` 正交互不替代** | 一个管「拆多细」一个管「按什么维度拆」，是两维不是一维 |
| 9 | **stall counter 用净值计数（有进展 −1），不用累加** | 累加实现会在长任务上被历史抖动拖到误重规划；净值计数给的是「有限恢复预算」——小错误不至于立刻重规划，但也不会被后续进展完全抹掉（`[实测]` `_magentic_one_orchestrator.py:393-399`） |
| 10 | **`facts` / `plan` 存自由文本，`progress` 存结构化** | 事实的类型跨领域无法枚举，结构化反而限制表达；progress 五问 schema 固定且需逐次比对趋势 |
| 11 | **`facts` 提取与 `plan` 生成必须两次调用** | 混在一次会让模型「先想计划再倒推事实」，facts 被计划污染（`[实测]` `_prompts.py:26` 明文禁止在一次输出里列 next steps） |
| 12 | **重生成只动内容字段，`title` / `id` / `dependsOn` 不动** | 改这三样会让审计线索断裂——外部引用、依赖图、时间线全部对不上（`[实测]` `update-task.json` 硬规则） |
| 13 | **`TD-11` 可满足性校验「只标不拒」** | 可满足性判定是启发式（文本推断），误判率远高于 `kind ↔ 写法`（后者有确定正则特征）。fail-close 会大面积拒合法拆解并阻塞主链路（风险 2 的同型事故）；且「存在不确定」本身不是错误，正确产出是**标注**而非拒绝 |
| 14 | **豁免在核验侧（`TD-12`），不在拆解侧降级** | 拆解侧把 `STRUCTURAL` 改 `REVIEWED` 是**永久放宽**标准，映射补齐后不会自动变严；核验侧豁免只在「前置未满足」期间生效，条件解除即恢复严格 |
| 15 | **前置条件引用用显式 `ref`（`U1`/`U2`），不用数组下标或内容哈希** | 下标随重拆 / 单条 `regenerateById` 漂移；哈希稳定但不可读，排障时人眼对不上。`ref` 可读且随 JSONB 落地无需迁移 |
| 16 | **规则只咬「实证型来源要求」，不咬所有量词** | `STRUCTURAL` 天然要写量词（`≥3 章节`、`≤300 字`、`5 个字段`），这些不依赖任何外部对象；一律标注会大面积误标并让豁免失控。真正会与 `UNCONFIRMED` 冲突的只有「必须指向某个尚未确定的外部实体去取回证据」 |
| 17 | **LLM 结论永无 `block` 权，block 只给确定性规则** | 同批草案两次拆解结论可能不同 ⇒ 会出现「有时能确认、有时不能」；模型误判会把正确计划卡死。`warn` 只影响人工注意力，不改变可执行性 |
| 18 | **门 4 触发按「风险命中」而非「门 3 不通过」** | 门 3a 的确定性规则发现不了语义矛盾（`LOG-20261025-014` 那类在确定性视角下全绿）⇒ 「不通过才跑」等于永不调用 |
| 19 | **门 4 用独立 rubric，不复用 reviewer 判据** | reviewer 判「产出对标准的符合性」，证据须来自物化附件或沙箱一手结果（`subtask-review.md:57`/`:138`）；拆解期无产出、只有计划文本，输入形态与证据纪律皆不同。可复用角色选择、`findings` schema、从严姿势，不可复用判据本身 |
| 20 | **局部重修按 A/B/C 三分类选择动作，并对 A 类查「验收强度不得下降」** | `regenerateById` 的白名单只覆盖四字段（`:214`）；缺分类会系统性地把「不可满足」重写成「可满足但更弱」，表面收敛、实际降低契约强度 |
| 21 | **一轮修复后 `findings` 总数不得增加，最多 2 轮，到顶转人工** | 没有收敛守卫，「验 → 修 → 验」会震荡；整批重跑还会重排 `ref`/`dependsOn` 使既有引用全部失效 ⇒ 局部重修是保住已过门禁结果的唯一方式 |
| 22 | **`TD-13` 施工前必须先回退 2026-10-25 的任务级补偿补丁** | 那次把判据从单条改任务级，本质是为掩盖「模型把缺口贴错草案」打的补偿。生成侧修好后该补丁变纯负资产：它会继续把含 `URL/页面/截图` 的草案无差别标注（带同一 `refs` 全集、无相关性过滤），把刚修好的精确输入重新搅成噪声。**补偿性补丁不随根因回滚 = 修完立刻自伤** |
| 23 | **`TD-13` 拆 7 个切片，施工顺序 `S1 → S4 → S2+S3 → S5 → S6`（`S0` 并行）** | 整块按四道门施工是跨多包的巨型改动，无法独立验收与回滚。先做纯缺陷修复（`S1`）与零迁移纯内存项（`S4`），再补表达力（`S2`）与消费（`S3`）——顺序颠倒会得到「有表达力、没人读」或「有规则、抓不到事故形态」的半成品 |
| 24 | **`TD-14` 把「拆解中」与「待确认」拆成两个状态，而不是给超时任务加白名单** | 加白名单（`NOT EXISTS (草案)`）只在「草案已落库」时成立，而回收发生在落库之前——补丁保护的正是它自己看不见的窗口。状态拆开后「要不要回收」由状态天然回答，补丁与 `decompose` 的状态守卫一起消失 |
| 25 | **判活从「多久没写库」改成「约定到期时刻」，因为前者对 IO 型长任务无效** | 心跳判活的铁律是「活着的人必须持续证明自己活着」；拆解线程在调模型期间没有能力写库。租约是**进入时就承诺**的到期时刻，跑得再久也不会被误判，除非真的超时 |
| 26 | **幂等键必须在入口生成并落库，且由数据库唯一索引兜底** | 应用层「先查再插」有 TOCTOU 窗口，跨节点时必然漏；唯一索引是唯一跨进程成立的约束。配套铁律：`DuplicateKeyException` 必须被当作「已消费」而非失败——否则虽然没落重复数据，却会走失败分支把成功的那次结果回退掉 |

## 6. 风险与边界

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | `TD-4` archetype 判定准确率低 | 用错拆分维度 ⇒ 计划结构错位，且外观合理难以发现 | 首期只观测不设阈值；判定结果进日志；人工可改作兜底 |
| 2 | `TD-5` 校验过严 | 大面积拒绝合法拆解，阻塞主链路 | 先用 `TD-3` 真实样本回归；校验失败提示必须说明「哪一条不满足哪个 kind 要求」 |
| 3 | `TD-3` 改动破坏 `BUILD` 零行为 | 当前唯一可用的任务类型被改坏 | 验收硬要求：同一输入两版 diff = 空 |
| 4 | `TD-6` 跨域取数越界 | 违反 §7.1 / §7.2（跨域禁直捅 Mapper、取数据走服务接口投影） | 只经 Service 端口；`check-arch-freeze` 必须全绿 |
| 5 | 两个常量列被误认为「能力已交付」 | 夸大完成度（本项目历史事故类型） | §0 ④ 已点名；差距表 `G-025` 状态写 `部分完成` 而非 `已完成`，直到 `TD-3`+`TD-5` 落地 |
| 6 | `TD-11` **误标**（把不依赖外部对象的量化验收当成冲突） | 豁免扩大化 ⇒ 该严的子任务被放宽 ⇒ 质量下滑，且看起来「一切正常」 | 规则只咬「实证型来源」（决策 16）+ 两条反例单测（§3 `TD-11` 验收 2/3）+ WARN 可观测、不阻断 |
| 7 | `TD-11` **漏标**（措辞不同、语义等价） | 本次事故原样重现：不可满足契约仍放行 ⇒ 执行者无解 ⇒ 死信 | 漏标不阻断任何链路，仍由核验兜底；`TD-12` 推进前先看标注率；`B1a` 保证驳回理由可查（§4.4） |
| 8 | `ref` 漂移（重拆后模型换了 `ref` 或不再输出） | `acceptancePreconditions` 指向空白 ⇒ 豁免失效或错配 | `ref` 只当标签不当主键；**解析不到即不豁免**（fail-safe：保持现状严格），并记 WARN 而非静默 |
| 9 | `TD-13` 局部重修把「不可满足的验收」重写成「可满足但更弱」 | 表面收敛，契约强度静默下降，且看起来「已修复」 | `findings.fixClass` 强制分类；A 类修复加「验收强度不得下降」比对（判据数 + 字符级）；C 类禁止重生成 |
| 10 | `TD-13` 门 3b / 门 4 误判带来人工噪音 | 确认草案的人工频次上升；若给 block 权则会把正确计划卡死 | LLM 规则**只 warn**；按 `ruleId` 灰度统计「warn → 真缺陷」比例后再议升级；规则与阈值不同批变 |
| 11 | 门 3a 覆盖矩阵依赖「需求要点清单」，而该清单未产品化 | 覆盖检查落空，或要点由模型临时抽取、口径漂移 | 覆盖矩阵**不得**以「一句话检查」立项：先定要点由谁生成、存哪、与草案如何对齐，再实现规则（`S0`） |
| 12 | 门 3b / 门 4 是额外 LLM 调用，会把拆解耗时从约 48s 推高 | 确认草案的等待时间接近翻倍，用户体验崩 | 机械可判的（门 1/2、门 3a）**全部交给代码**；门 4 只在「风险命中」三条同时成立时调；单次调用设超时，超时降级为 `warn` 不阻塞；耗时随 `findings` 一起落 timeline 以便观测 |
| 13 | `TD-14` 的拆解仍是**进程内 `@Async`**，不是分布式队列 | 发起节点崩溃 ⇒ 本次拆解丢失（草案与状态同事务，库里不会留半批，但 LLM 的十几分钟白花）；多节点下**能**保证「不重复落库」，但**不保证「恰好执行一次」** | 「不重复落库」由两层共同保证（跨节点有效）：DB 唯一索引挡「同 `attemptId` 的第 N 条」，`casStatusForAttempt` 挡「跨 `attemptId` 的迟到写入」（见决策 9）；「执行中丢失」由租约回收 + 用户重拆兜底。要做到「恰好一次」需把拆解投到 `helloai-mq`，属独立工程，不在 `TD-14` 范围 |
| 14 | `AWAITING_PLAN_CONFIRM` 状态**永不超时** | 用户一直不处理 ⇒ 任务永久停在待确认（这是设计，不是缺陷：草案不参与 claim/分发，无错误数据） | 但缺「已等待 N 天」的可见性与提醒；若要做，只能做**提醒 / 通知**，不得自动作废草案（用户可能已经改了一半）。**2026-11-08 已补展示层**（任务列表「已等待 N 分钟/小时/天」），自动处置仍明确不做 |
| 15 | **`blockedBy` 与 `dependsOn` 会被当成同一件事**（字段名都在表达「关系」） | 有人把 `blockedBy` 反写成依赖边，或反过来用 `dependsOn` 判断影响面 ⇒ 造出并不存在的执行顺序 / 漏掉真实阻塞 | 语义写死两条：`dependsOn` = 谁先做（受「只能引用更早序号」约束），`blockedBy` = 谁被卡（可指向任意草案、**不含自身**）。服务端**不据 `blockedBy` 改 `dependsOn`**；归一化丢弃自引用正是这条的机械保证 |
| 16 | **`TD-15` 保留有执行痕迹的 CANCELLED 行**会让 §6.100 的「幽灵依赖」在新一轮里残留 | 新草案的 `dependsOn` 可能指向一条已取消但仍存在的行 | 代价不对称：残留只影响新草案依赖解析（**可见、可重拆**），错删执行痕迹**不可恢复**。故选保留，并以 `task_plan_cancelled_draft_retained` 事件把「保留了 N 条」摊到时间线上，不静默 |

- **`FRET` 这条参照的实战结论（2026-10-25 晚，`LOG-20261025-018`）**：我一度据「realizability」这个提法设计了
  「**甲判据**」——单条 `acceptance` 内部自相矛盾（要求真实来源 ∧ 禁止出现真实主体）即判不可满足。真机数据
  把它推翻了：同一条第 5 条在另一条草案上**要么不触发、要么触发后仍被通过**，说明「禁的是指认、不是引用」，
  可满足路径存在。⇒ **「realizability」这个概念值得借，但「自然语言正则能判出不可满足」这个跨越不成立**——
  形式化需求工程能判，是因为它先把需求转成了形式模型；我们没有那一步，正则只能判「措辞像不像矛盾」。
  这条留在这里，是为了下一个想走同一条路的人先看到它已经失败过一次。
