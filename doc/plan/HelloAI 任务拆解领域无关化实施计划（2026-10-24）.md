## 0. 定位与边界（★先读）

**① 问题来源**

- **用户裁定（2026-10-24）**：明确要求「草案生成与拆解，**不仅仅是针对于代码开发的**」。原始记录见 `LOG-20261024-034`。
- **自查认定的基准错位**：同日早前的对照分析（`LOG-20261024-033`）以 `spec-kit` / `claude-task-master` / Qoder 为基准，三者均为编码工具，只能得出「交互层缺什么」，得不出「能力模型缺什么」——本文档与设计文档是对该基准错位的修正。
- **代码级根因**：`planner-decompose.md` 的「拆解原则」整段是软件交付语法（`planner-decompose.md:60-93`）；`GRANULARITY` 只控制「拆多细」，不控制「按什么维度拆」（`planner-decompose.md:34-38`）；`task` 表无任何领域 / 交付物类型维度（`V1__init_all.sql:24-36`）。
- **差距表锚点**：`G-025`（本轮登记）；正交相邻项 `G-010`（`GRANULARITY` 出处）、`G-011`（`uncertainties` 字段出处）。

**② 本计划做什么**

把「按什么维度拆」与「谁来判怎么判」变成显式声明，使拆解从「只有一档（静态 DAG + 软件交付语法）」变为「按判据分档」。具体产出七条：

1. **两个字段**：`task.task_archetype`（六类拆分维度）+ `sub_task.acceptance_kind`（四类验收判据）。
2. **提示词按 archetype 分支**：`planner-decompose.md` 注入 archetype，输出对应的拆分维度与终止锚；BUILD 保持现全行为（含契约先行）。
3. **archetype 判定链**：终稿产出时判（`final_package.archetype`）+ 用户可改 + 判不出回落 `BUILD`。
4. **验收校验按 kind 分流**：`AUTOMATED` / `STRUCTURAL` / `REVIEWED` / `ATTESTED` 各走各的文本写法校验，把「假可判定」挡在落库前。
5. **拆解期上下文快照**：`{{TASK_CONTEXT_SNAPSHOT}}`（附件清单 / 知识库命中 / 历史同类任务），解决「拆解输入只有 title + description」。
6. **验收契约可满足性标注**（`TD-11`）：同一子任务内 `acceptance` 与 `uncertainties` 交叉校验——量化验收若依赖一个「只能问人」的缺口，则登记前置条件。**只标注、不拒绝、不改 kind**。
7. **核验侧前置条件豁免**（`TD-12`）：核验逐条判定时读前置条件，未满足则记 `SKIPPED(blocked_by)` 而非 `FAIL`；前置满足则照常严格判。

**③ 本计划不做什么**（边界，防越界）

1. **不做「通用任务拆解」**——不存在这种东西；拆解维度与验收判据由交付物性质决定，方案是分档不是统一。依据：`design/HelloAI 任务拆解领域无关化设计.md` §8。
2. **不做 archetype 自动学习**——样本量为 0 时任何学习都是噪声。依据：同设计 §8；先靠「模型判 + 人工可改」积累标注。
3. **不引入第二套执行调度器**——ledger 走单步派发复用现有分发链。依据：本项目「同一事实双写必分叉」判据。
4. **不改 `sub_task` 四要素契约与 DAG 校验**——`content`/`deliverable`/`acceptance`/`priority` 仍必填；Kahn 拓扑与环检测（`PlannerDecomposeAsyncServiceImpl:557` / `:614`）原样保留。依据：设计 §7 第 1、2 条。
5. **不改 `TaskBaseline` 初始化时机**——它的时机对它自己是正确的；缺的是拆解期快照，不是把 baseline 提前。依据：设计 §5.3。
6. **不改澄清链路的门控与交互**——`progress` 自评门控化、`Recommend` 一键采纳等属交互层，与本计划的「能力模型」是两件事。依据：`LOG-20261024-033` 的 P0 建议已明确降级，不在本计划范围。
7. **不做形式化求解（PDDL / SMT）**——`TD-11` 的可满足性判定走**机械规则 + 窄模式匹配**，不把验收标准建模成状态机或一阶逻辑。依据：本项目的验收是自然语言条目（`STRUCTURAL：1) … 2) …`），形式化建模成本远超收益；开源参照（NASA FRET、`plan-lint`）均只借概念与骨架，不移植其求解器，见 §7。
8. **不在拆解侧降级验收强度**——命中 `TD-11` 不把 `STRUCTURAL` 改成 `REVIEWED`（那是永久放宽标准，映射补齐后也不会自动变严）。豁免只在核验侧、且仅在前置未满足时生效（`TD-12`）。

**④ 诚实边界**

- **`TD-1`/`TD-2` 落库 ≠ 能力可用**：若 `TD-3`（提示词分支）未落地，`archetype` 恒为 `BUILD`、`acceptance_kind` 恒为 `AUTOMATED`，**系统行为与今天完全一致**，只是多了两个常量列。判断「本计划是否生效」的唯一标准是 §3 中 `TD-3` 与 `TD-5` 的状态，不是 `TD-1`/`TD-2`。
- **archetype 判定准确率未知**：`TD-4` 依赖模型判断，首期**没有任何准确率数据**。落地后不得宣称「已支持非代码任务」，只能说「提供了分档通道，判定质量待观测」。
- **存量任务不会被追溯修正**：迁移默认值使历史任务一律 `BUILD` + `AUTOMATED`，它们的行为不变，也不会自动变成正确的 archetype。
- **`RESEARCH` / `DECIDE` 类任务的核心差距不因本计划关闭**：`TD-10`（ledger 通道）不启动前，这两类任务仍是「用静态 DAG 硬拆」，拆出来的步骤在执行时照样作废。本计划只到「拆解骨架对得上」，到不了「计划未知的任务也能自适应」。
- **`STRUCTURAL` 校验器覆盖有限**：它只能判可数的结构断言（章节数 / 条目数 / 字数 / 字段齐全），**判不了内容质量**。写作质量仍只能靠 `REVIEWED` 或 `ATTESTED`。
- **`TD-11` 的「可满足性」是启发式判定，不是证明**：它只能识别「验收里要求实证型来源（URL / 原文摘录 / 页面 / 截图）× 存在只能问人的 `UNCONFIRMED` × 无豁免措辞 × 无澄清依赖」这一种组合。**规则刻意收窄（宁可少标）**——不覆盖「语义上等价但措辞不同」的表达，也不覆盖非来源型的不可满足（如「同一子任务既要求全量又要求零改动」）。漏标时不阻断任何链路，结果仍由核验侧兜底。
- **`TD-12` 的豁免会让「缺输入」类子任务以 SKIPPED 收尾**：这类子任务最终可能停在 `REVIEW` 等人工补映射，而不是自动 `DONE`。这是**有意的**——比"编数据后 DONE"或"零产出后死信"都更接近真实状态，但会提高人工介入频次。
- **`ACCEPTED` 类验收无法自动化**：`ATTESTED` 只能留痕，不能防「人随便点通过」。

> **门 2 的 block 权只给 ① ②**：③ ④ 名义上「确定性」，实际是对中文文本的启发式匹配，误报会直接阻断合法拆解（比 `TD-5` 风险 2 更硬——那是拒绝，这是整批拆解失败）。反例：`deliverable="分析报告"` + `acceptance="STRUCTURAL：输出 5 个章节，每章 ≥1 条结论，总计 ≤3000 字"` 名词交集为 0，但完全合法；本次事故草案的验收也含「抽查 3 条来源URL可打开」（核实语义），可能被 ④ 误判。跑满 3 批真实样本、按 `ruleId` 统计「warn → 人工确认为真缺陷」达阈值后再议升 block。
>
> **🟥 原则（2026-11-07 `s4-5` 量化，门 1~4 通用）：`block` 权只给「结论与样本分布无关」的规则。**
> 判据是**结论与样本分布无关**：字段空不空、依赖图闭不闭合，判的是「有没有」与「图结构」；文本启发式（名词包含、覆盖矩阵、定性矛盾）依据是某一时点的样本快照，分布一变就误拦合法产出，而 `block` 的代价是整批拆解失败、重试必复现 ⇒ **一律不得 `block`**。落地要求：规则在调用点**显式声明 `severity`**（不再由工厂方法默认 `block`），`Result` 按 `severity` 分区，`hasBlocking()` 只看 `block`。
>
> **阈值型规则的可 block 条件（`s4-5`，取代 `s4-4` 的绝对禁令）**：`s4-4` 原文写「任何阈值型规则不得 block」，却与 `G2_LEN_MIN`（`acceptance` 10 字符仍 block）自相矛盾。改为可校验条件 ——
> **阈值 ≤ 存量分布最小值 / 3（`PlanBatchGateChecker.BLOCK_THRESHOLD_MARGIN`），且每次改阈值须重跑存量回放并核对倍数。** 余量 ≥3 倍时分布小幅漂移不会把合法产出推到阈值以下；不足 3 倍说明阈值贴着当前分布，随时会误拦。历史两例均被本条件正确判定：
> - `deliverable`：存量 5 / 阈值 8 = **0.6 倍** ⇒ 不满足，**阈值已整体删除**（`s4-4`，`P1-C` 事故：11 月的验证/夹具类任务把最小值从 10-24 的 17 拉到 5，119 条存量中 4 条合法草案被整批拦死）；
> - `acceptance`：存量 39 / 阈值 10 = **3.9 倍** ⇒ 满足，**保留 block**。
>
> 推论：`S5` 门 3a 的三条规则（覆盖矩阵 / 输入未产出 / 定性矛盾）无「存量分布最小值」可言，余量条件不成立 ⇒ 只能 `warn`，不得沿用名义上的「确定性」去 block。

**门 2 明确不做「空泛检测」**：中文「内容是否空泛」没有可靠正则，强写只会制造假阳性（把短而准的草案判空）。真正的空泛归门 4。门 2 的「不规定写法」直接抄 `subtask-review.md:71` 的既有口径——「技能只用于判断交付形态是否缺失，不用于比较实现手段，等价实现同样算达标」，保证拆解侧与核验侧对「合规」的定义一致。

**门 4 的触发条件是风险命中，不是「门 3 不通过」**：门 3a 的确定性规则只能发现「引用解不开 / 有环 / 覆盖映射缺失」，**发现不了语义矛盾**——`LOG-20261025-014` 那类缺陷（验收要求取回外部实证，而该实证在另一草案被标 `UNCONFIRMED`）在确定性规则下全绿。按「不通过才跑」的触发，门 4 一次都不会被调用。正确触发：**本草案验收含证据型动词 ∧ 全任务存在 `UNCONFIRMED` ∧ 本草案有跨草案依赖，三条同时成立才调**。

**门 4 不复用 reviewer 的判据**：`subtask-review.md:57` / `:138` 的轨道 A 判的是「产出对验收标准的符合性」，证据必须来自物化附件正文或沙箱一手结果，且明文写「你看不到源码仓库」。拆解期**没有任何产出，只有计划文本**，输入形态、证据纪律、失败语义三者皆不同。可复用的是**角色选择方式、`findings` 结构化 schema、从严的默认姿势**；判据必须独立成一份 rubric。`门 4` 与 `TD-12` 也不可合并：前者是计划期问「这条验收能否被满足」，后者是核验期问「产出是否因上游缺口而豁免」——时点、输入、处置都不同，只能共享同一份依赖数据。

**LLM 结果永无 block 权**：凡 LLM 结论（门 3b / 门 4）只能 `warn` / `annotate`。否则同一批草案两次拆解结论不同，会出现「有时能确认、有时不能」；模型误判还会把正确计划卡死。**block 权只给确定性规则**。

#### 三分类处置（修复动作的选择依据）

| 类 | 缺陷形态 | 修复动作 | 可用性 |
|---|---|---|---|
| **A** | 验收不可满足 / 正文空泛 | `regenerateById` | ✅ 现成：只重写 `content`/`deliverable`/`acceptance`/`acceptanceKind` 四字段（`PlannerDecomposeAsyncServiceImpl:214`） |

> **这是本方案最大的隐性风险**：少了这三分类，局部重修会系统性地把「不可满足的验收」重写成「可满足但更弱的验收」——表面收敛，实际**降低了契约强度**。它比误报一条告警严重得多，因此 A/B/C 必须在 `findings` 里显式标注（`fixClass`），并对 A 类修复设「验收强度不得下降」的比对检查。

#### 收敛守卫（防「验 → 修 → 验」震荡）

1. 一轮修复后 **`findings` 总数不得增加**（按 `ruleId` 计数）；
2. **最多 2 轮**；
3. 到顶仍不收敛 → **转人工**，未解 `findings` 全量落 timeline；
4. 整批重跑会**重新分配 `ref` 与 `dependsOn` 序号，已建立的引用全部失效** ⇒ 局部重修除了省时间（单次拆解约 48s），也是**保住已通过门禁结果的唯一方式**。

##### S1 `ref` 作用域修正 + fail-fast（0.5d）

**现状缺陷**（`TD-11` 断点 ② 本体）：`buildDrafts` 把全批 `uncertainties` 聚合成 `taskLevelUncertainties` 再跑 `ensureRefs`，返回的是**聚合列表序号**；而 `ensureRefs` 的 javadoc 明写「作用域 = 本子任务内」。结果草案 2 落库 `acceptancePreconditions=["U2"]`，它自己的 JSONB 里只有 `U1`。**`AcceptanceSatisfiabilityCheckerTest:137-153` 已把这条悬空行为断言成期望值**。

**改动**：
1. 删除任务级聚合段，恢复「对本子任务自己的 `uncertainties` 跑 `ensureRefs`」；
2. 调用方补一层解析：`acceptancePreconditions` 的每个 `ref` 必须能在**持有它的草案**内解析到，解析不到 → **不落这条标注** + 记 WARN（`acceptance_precondition_unresolvable`）；
3. 同步改单测期望值（把「悬空 `U2` 是期望」改成「悬空即不落标注」），并补一条「本子任务内可解析 → 正常落标注」的正例。

**这条是在回退 2026-10-25 的补偿补丁**：当时把判据从单条改任务级，本质是为掩盖「模型把缺口贴错草案」而做的补偿。补丁不随根因回滚，就会在 `S2` 修好之后继续把所有含 `URL/页面/截图` 的草案无差别标注。

**验收补充**：同一子任务的 `review_record` 与详情页能读到上述 `findings`（`ruleId` / `severity` / `evidence` 三项齐全，中文说明随附）；阻断场景下用户能在任务侧看到「哪条规则拦了哪条草案的哪个字段」，不需要去翻日志。

**刻意不做**：不接豁免判定（那是 `TD-12`，批次 7 单独做）。本切片只解决「有没有人读」，不引入第二个变量。

**验收**：`review_record` 可见 `blocked_by` 与缺口原文；**本切片前后同一子任务的核验结论逐字一致**（这是「只读」的硬判据）。
> 判据原写「`TD-12` 未上线时…」，但 `TD-12` 排在第 7 批、早于 `S3`，届时必然已上线 ⇒ 该条件不可执行。改成「切片前后一致」后两种时序都成立；若 `TD-12` 已在线，用同一份固定台账做前后对照。

##### S5 门 3a 确定性三规则（1.5d）

**落点**：`applyDependsOn`（`:1215`）之后——此刻才有真实 Snowflake ID 与可解析身份。

| `ruleId` | 判什么 | 首轮 severity |
|---|---|---|
| `G3A_COVERAGE_GAP` | 需求要点 → 草案覆盖矩阵，未覆盖项 | warn（**`S0` 未定稿则关闭**） |
| `G3A_INPUT_UNPRODUCED` | 某草案验收要求的输入，全批无人产出 | warn |
| `G3A_STATUS_CONFLICT` | 同一实体一处 `UNCONFIRMED`、另一处当已知（靠 `blockedBy` 定位，不靠 `ref` 跨草案拼接） | warn |

三条全部 warn，写 `context.gateFindings` + timeline。**`G3A_STATUS_CONFLICT` 依赖 `S2`**：没有 `blockedBy` 时这条规则只能做 `note` 文本模糊匹配，误报率高且抓不到本次事故形态（两边都报 `TO_LOOK_UP`、文本自洽）。

> **🟥 `S5` 实现约束（2026-11-07 `s4-4` 原则）**：门 3a 的三条规则**全部是启发式**（覆盖矩阵靠要点抽取、输入产出靠引用词、定性矛盾靠文本比对），因此**只能声明 `severity=warn`**，调用点必须显式传 `SEVERITY_WARN`，不得因「门 3a 名义上属确定性」就沿用 `block`。`P1-C` 的教训是：拿统计快照去否决整批合法产出，代价（拆解失败、重试必复现）与依据完全不成比例。**`S5` 验收须包含存量回放：** 用 119 条存量草案跑新规则，任何 `block` 命中都要逐条人工确认为真缺陷，否则降级。

**`G3A_INPUT_UNPRODUCED` 的判据必须在 `S5` 开工前收窄成可枚举规则**：原表述「某草案验收要求的输入，全批无人产出」没有定义「验收要求的输入」怎么抽取——不定义就实现，结果与 `TD-11` 同型（有规则、无真判据）。`S5` 首版只允许收窄形态，例如「`acceptance` 出现『上游 / 前置 / 基于…结果』等显式引用词 ∧ `dependsOn` 为空」，且**未命中的形态一律不报**；不做语义推断。

##### S6 门 3b / 门 4 影子 + A 类重修 + 收敛守卫（2d）

1. **两份独立 rubric prompt**：`planner-gate3b-rubric.md`（划分合理性 / 粒度 / 缺口归属）、`planner-gate4-rubric.md`（「给定需求 + 上游交付物声明 + 本草案已知/未知，验收在现有输入下是否可满足」）。**不得复用 `subtask-review.md`**——那边判的是产出对标准的符合性、证据须来自物化附件或沙箱一手结果（`:57`/`:138`），拆解期无产出。
2. **门 4 触发按风险命中**：本草案验收含证据型动词 ∧ 全任务存在 `UNCONFIRMED` ∧ 本草案有跨草案依赖，三条同时成立才调。
3. **A 类重修接线**：`regenerateById`（`:214`）只重写四字段，接上后加「**验收强度不得下降**」比对（判据数 + 字符级），不满足则回滚并转 B 类。
4. **收敛守卫**：按 `ruleId` 计 `findings`，一轮后总数不得增加、最多 2 轮、到顶转人工 + 全量落 timeline。
5. **灰度**：门 3b / 门 4 全部 `warn`，按 `ruleId` 统计「warn → 人工确认为真缺陷」比例，达阈值再议升 `block`；**灰度期不得同批改规则与阈值**。

**验收**：同一批草案跑两次 → 结论可有差异但**均不阻断**；草案含证据型动词而全任务无 `UNCONFIRMED` → **门 4 不调用**。

#### 验收

1. 构造一批含环依赖 + 验收不可满足 + 覆盖缺失的草案 → 门 1/2/3a 分别命中且给出 `ruleId`，落库前即阻断——**不产生任何 `sub_task` 行**（`task.context` 的审计写入除外）；
2. 门 3b / 门 4 在同一批草案上跑两次 → 结论可有差异，但**均不得阻断**，`findings` 可读；
3. 触发条件验证：草案验收含证据型动词但全任务无 `UNCONFIRMED` → **门 4 不调用**（成本守卫生效）；
4. 收敛守卫：构造需要 3 轮才能修的样本 → 第 3 轮转人工，`findings` 全量进 timeline；
5. A 类重修后 `acceptance` 强度不下降（字符级 + 判据数比对）；
6. 整批复跑与局部重修的结果等价性：局部重修后的批次通过门禁，且未受影响草案的 `ref` / `dependsOn` **一字未变**。

## 5. 关键设计决策

| # | 决策 | 取舍理由 |
|---|---|---|
| 1 | **archetype 在 task 级单值，acceptanceKind 在 sub_task 级** | 拆分维度必须由主交付物统一决定，否则骨架是混的；子任务差异只影响「怎么判」，用 kind 表达已足够 |
| 2 | **archetype 在终稿阶段判，不在拆解阶段判** | 拆解时模型只见 title + description，判不准；终稿时已看过完整对话 |
| 3 | **判不出回落 `BUILD`，不做猜测性判定** | 猜错比不猜更贵——错误的拆分维度会产出看起来合理但结构错位的计划 |
| 4 | **`acceptanceKind` 复用 review 域，不新建链路** | `REVIEWED` 本来就是 `subtask-review.md` 轨道 A 的职责，显式声明即可，无需新能力 |
| 5 | **ledger 走单步派发，不引入第二套调度器** | 两条执行路径会让「任务当前状态」的事实源分叉 |
| 6 | **`TaskBaseline` 时机不动，另补拆解期快照** | 两者用途不同（运行基准 vs 输入视图），合并会让语义互污染 |
| 7 | **快照只给「有什么」，不给「是什么」** | 全文注入既撑爆预算，又会让 Planner 抄历史产出而非重新拆解 |
| 8 | **`GRANULARITY` 与 `archetype` 正交互不替代** | 一个管「拆多细」一个管「按什么维度拆」，是两维不是一维 |
| 9 | **stall counter 用净值计数（有进展 −1），不用累加** | 累加实现会在长任务上被历史抖动拖到误重规划；净值计数给的是「有限恢复预算」——小错误不至于立刻重规划，但也不会被后续进展完全抹掉（`[实测]` `_magentic_one_orchestrator.py:393-399`） |
| 10 | **`facts` / `plan` 存自由文本，`progress` 存结构化** | 事实的类型跨领域无法枚举，结构化反而限制表达；progress 五问 schema 固定且需逐次比对趋势 |
| 11 | **`facts` 提取与 `plan` 生成必须两次调用** | 混在一次会让模型「先想计划再倒推事实」，facts 被计划污染（`[实测]` `_prompts.py:26` 明文禁止在一次输出里列 next steps） |
| 12 | **重生成只动内容字段，`title` / `id` / `dependsOn` 不动** | 改这三样会让审计线索断裂——外部引用、依赖图、时间线全部对不上（`[实测]` `update-task.json` 硬规则） |
| 13 | **`TD-11` 可满足性校验「只标不拒」** | 可满足性判定是启发式（文本推断），误判率远高于 `kind ↔ 写法`（后者有确定正则特征）。fail-close 会大面积拒合法拆解并阻塞主链路（风险 2 的同型事故）；且「存在不确定」本身不是错误，正确产出是**标注**而非拒绝 |
| 14 | **豁免在核验侧（`TD-12`），不在拆解侧降级** | 拆解侧把 `STRUCTURAL` 改 `REVIEWED` 是**永久放宽**标准，映射补齐后不会自动变严；核验侧豁免只在「前置未满足」期间生效，条件解除即恢复严格 |
| 15 | **前置条件引用用显式 `ref`（`U1`/`U2`），不用数组下标或内容哈希** | 下标随重拆 / 单条 `regenerateById` 漂移；哈希稳定但不可读，排障时人眼对不上。`ref` 可读且随 JSONB 落地无需迁移 |
| 16 | **规则只咬「实证型来源要求」，不咬所有量词** | `STRUCTURAL` 天然要写量词（`≥3 章节`、`≤300 字`、`5 个字段`），这些不依赖任何外部对象；一律标注会大面积误标并让豁免失控。真正会与 `UNCONFIRMED` 冲突的只有「必须指向某个尚未确定的外部实体去取回证据」 |
| 17 | **LLM 结论永无 `block` 权，block 只给确定性规则** | 同批草案两次拆解结论可能不同 ⇒ 会出现「有时能确认、有时不能」；模型误判会把正确计划卡死。`warn` 只影响人工注意力，不改变可执行性 |
| 18 | **门 4 触发按「风险命中」而非「门 3 不通过」** | 门 3a 的确定性规则发现不了语义矛盾（`LOG-20261025-014` 那类在确定性视角下全绿）⇒ 「不通过才跑」等于永不调用 |
| 19 | **门 4 用独立 rubric，不复用 reviewer 判据** | reviewer 判「产出对标准的符合性」，证据须来自物化附件或沙箱一手结果（`subtask-review.md:57`/`:138`）；拆解期无产出、只有计划文本，输入形态与证据纪律皆不同。可复用角色选择、`findings` schema、从严姿势，不可复用判据本身 |
| 20 | **局部重修按 A/B/C 三分类选择动作，并对 A 类查「验收强度不得下降」** | `regenerateById` 的白名单只覆盖四字段（`:214`）；缺分类会系统性地把「不可满足」重写成「可满足但更弱」，表面收敛、实际降低契约强度 |
| 21 | **一轮修复后 `findings` 总数不得增加，最多 2 轮，到顶转人工** | 没有收敛守卫，「验 → 修 → 验」会震荡；整批重跑还会重排 `ref`/`dependsOn` 使既有引用全部失效 ⇒ 局部重修是保住已过门禁结果的唯一方式 |
| 22 | **`TD-13` 施工前必须先回退 2026-10-25 的任务级补偿补丁** | 那次把判据从单条改任务级，本质是为掩盖「模型把缺口贴错草案」打的补偿。生成侧修好后该补丁变纯负资产：它会继续把含 `URL/页面/截图` 的草案无差别标注（带同一 `refs` 全集、无相关性过滤），把刚修好的精确输入重新搅成噪声。**补偿性补丁不随根因回滚 = 修完立刻自伤** |
| 23 | **`TD-13` 拆 7 个切片，施工顺序 `S1 → S4 → S2+S3 → S5 → S6`（`S0` 并行）** | 整块按四道门施工是跨多包的巨型改动，无法独立验收与回滚。先做纯缺陷修复（`S1`）与零迁移纯内存项（`S4`），再补表达力（`S2`）与消费（`S3`）——顺序颠倒会得到「有表达力、没人读」或「有规则、抓不到事故形态」的半成品 |
