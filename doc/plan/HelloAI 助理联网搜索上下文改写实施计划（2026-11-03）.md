## 一、触发与实测

用户消息：

```text
最近的 AI 相关新闻，这次联网查询后，展开详细说说吧
```

`logs/helloai.log` 实测：

```text
博查 AI Search 失败（已降级为空列表）: query=最近的 AI 相关新闻, err=request timed out
博查 AI Search 失败（已降级为空列表）: query=展开详细说说, err=request timed out
web_search 工具调用完成: query=展开详细说说, maxResults=5, hits=0, withAnswer=true, modalCards=0
候选词命中 0 条: query=最近的 AI 相关新闻
候选词命中 0 条: query=这次联网查询后
候选词命中 0 条: query=展开详细说说
结束: queries=[最近的 AI 相关新闻, 这次联网查询后, 展开详细说说], rounds=1,
      answer=无, pages=0, results=0, costMs=25014
```

三个叠加问题：

1. **分句规则把整句拆碎**：`SearchQueryPlannerServiceImpl` 按 `，` 拆分，元词表没有覆盖“这次”“联网查询后”“展开详细说说”，三条候选全部进入检索。
2. **LLM 改写被门槛跳过**：规则已产出 3 条候选且原文 27 字 ≤ 40，命中 `shouldLlmRewrite` 的“多候选 + 短文本”跳过分支。
3. **助理链路只把原始 message 传给检索**：`AssistantChatServiceImpl` 已加载 `recentConversation`、上下文摘要、`attachmentContext`，但这些只进入最终回复 Prompt，没有进入检索；因此“这次”无法指代上一轮，附件也无法参与检索决策。
4. **博查 AI Search 本轮超时**：`answer=true` + 25s 超时已贴着边界（历史成功调用约 22–25s），即使查询词正确也可能 0 命中。

## 二、目标与非目标

### 目标

- 原话不再产出“这次联网查询后”“展开详细说说”这类检索词。
- 单独的“最近”有明确时效档位，且搜索词内可转绝对日期。
- 助理检索前能结合：最近对话历史、上下文摘要、附件决策视图、系统当前时间，生成独立搜索词。
- 附件能独立回答时优先附件、跳过联网；附件需要外部核验时，用附件锚点检索。
- 决策 LLM 失败、博查超时等路径全部降级，不阻断对话。
- 不改变澄清链路既有语义（共享的规则/时效改动需回归）。

### 非目标

- 不引入新搜索供应商。
- 不做 Agentic 多轮搜索（W 计划 P3 仍登记不启动）。
- 不做前端改动、不改 DB / MQ / Flyway。
- 本期不做“独立 standalone question 改写 + 多查询 rerank”的完整 C 方案；若 B 上线后跨轮指代仍频繁，再单独立项。

## 四、A 方案详细

### A1 查询规划器：指代碎片过滤与改写门槛

文件：`helloai-core/src/main/java/com/helloai/core/planner/service/impl/SearchQueryPlannerServiceImpl.java`

**改动**

1. 新增 `FOLLOWUP_FILLER_PATTERN`，只用于“候选是否全是对话碎片”的判定，不复用为全局清洗，避免误伤实体：
   - `这次 / 本次 / 此次 / 再次 / 重新 / 接着 / 刚才 / 刚刚 / 上面 / 上述 / 之前`
   - `展开 / 详细 / 说说 / 讲一讲 / 聊一聊 / 综合 / 综合性 / 梳理 / 总结一下 / 总结`
   - `联网查询后 / 联网查询 / 查询后 / 查一下 / 查询`
2. `isMetaOnlyQuery` 的 residual 同时剥离 `META_WORD_PATTERN` 与 `FOLLOWUP_FILLER_PATTERN`；residual < 2 字即丢弃。
3. `shouldLlmRewrite` 增加“不可检索候选”触发：
   - `ruleQueries` 为空，或任一条 `isMetaOnlyQuery` 为真 → 进入 LLM 改写；
   - 其余保持现有“多候选 + ≤40 字跳过”的成本控制。
4. 保留 `dropMetaQueries` 作为 LLM 产物与无 LLM 场景的兜底。

**预期**

- 原话在 `queryRewriteEnabled=false` 时只保留 `最近的 AI 相关新闻`；
- 开启改写时进入 LLM，产出可检索的独立主题词；
- `Redis 缓存，MySQL 调优，Kafka 消息队列` 这类正常多主题不被误杀。

**测试**

- 原话（关闭改写）→ 仅 `最近的 AI 相关新闻`；
- 原话（开启改写，mock 返回 `["2026-11 AI 行业最新动态"]`）→ LLM 被触发；
- `这次联网查询后` / `展开详细说说` → 空候选；
- `总结 React 19 新特性` / `结合附件分析机场许可规定` → 保留实体；
- 现有 W-4 多主题长句、元词过滤用例全部保持通过。

### A2 相对时间：单独“最近”归一化与 freshness

文件：`helloai-core/src/main/java/com/helloai/core/planner/clarify/RelativeTimeNormalizer.java`

**改动**

1. 新增 `RECENT_BARE_PATTERN`（负向排除更长表达）：
   `最近(?!一周|7天|30天|一年|几年|\d)`
2. `normalize` 在 `RECENT_WEEK_PATTERN` / `RECENT_DAYS_PATTERN` 之后替换裸“最近”为近 30 天区间（常量 `BARE_RECENT_DAYS = 30`，可调）。
3. `freshnessFor` 档位顺序调整：
   - 先保留今天/本周/本月/今年/“最新”等既有档位；
   - `最近一年` 归入 `oneYear`；
   - 裸“最近”最后归入 `oneMonth`。
4. 保持幂等：已归一化的绝对日期不被二次替换。

**预期**

- `最近的 AI 相关新闻` → `2026-08-02 2026-08-31的 AI 相关新闻`（以 2026-08-31 为锚点时），freshness=`oneMonth`；
- `最近一周` 仍为 `oneWeek`，`最近一年` 仍为 `oneYear`。

**待确认**

- 裸“最近”默认按 30 天还是 7 天。建议先 30 天（召回优先），按实测再收紧。

### A3 博查 AI Search 超时兜底与延迟配置

文件：
- `helloai-core/src/main/java/com/helloai/core/planner/service/impl/AiSearchWebSearchServiceImpl.java`
- `helloai-start/src/main/resources/application.yml`

**改动**

1. `search()` 在 AI Search 返回空列表（含超时、非 2xx、解析为空）后，回退基础 Web Search：
   - 端点：`properties.getBochaBaseUrl()`（`/v1/web-search`）；
   - 请求体：`query / summary=true / count=limit / freshness`（freshness 复用 `RelativeTimeNormalizer.freshnessFor`）；
   - 响应解析复用现有 `parseResponse` 的 `data.webPages.value` 兼容路径；
   - 回退超时取 `min(timeoutMs, 8s)`，失败仍返回空列表，不抛异常；
   - 日志：`AI Search 无结果，回退基础 Web Search: query=..., costMs=...`。
2. 配置评估（先改配置、再观察真实链路）：
   - `ai-search-answer: false`（降低博查侧总结带来的 25s 边界延迟；最终回复仍由主 LLM 总结）；
   - `ai-search-timeout-ms: 15000`（为回退留预算）；
   - 若质量下降或仍超时，再调整 `ai-search-max-results` / 回退超时。
3. 不新增 Bean、不改 `WebSearchService` 路由：在 AI Search 实现内部完成回退，避免 `provider=bocha-ai-search` 时基础 Bocha Bean 不存在的问题。

**预期**

- AI Search 超时后仍能通过基础 Web Search 拿到结果；
- 最坏耗时控制在 `searchBudgetMs=30s` 内（15s + 8s + 余量）；
- 若回退也失败，日志能明确区分“AI Search 失败”和“基础搜索失败”。

**测试**

- 抽出 `buildFallbackRequestBody` 做包级单测（字段、freshness、count）；
- 解析路径复用现有 `parseResponse` 单测；
- 真实链路观察回退日志与 costMs。

## 五、B 方案详细

### B1 新增助理检索决策组件

新增：`helloai-core/src/main/java/com/helloai/core/planner/assistant/AssistantSearchQueryPlanner.java`

职责：只做“助理本轮检索词 + 附件关系”决策，不生成用户可见回复。

**依赖**

- `ClarifyPromptRenderService`：复用 `renderDecisionPrompt(conversation, userMessage)`，它已注入最近历史、上下文摘要、附件决策视图、系统当前时间与搜索策略。
- `ChatRoundDecisionParser`：复用既有严格解析（intent / attachment_intent / attachment_targets / web_search）。
- `PlatformAgentExecutionService` + `PlannerAgentPicker`：与澄清链路同一执行链与凭证。
- `AgentTask.context.scene = "assistant_search_query"`，便于日志与测试定位。

**场景约束**

在 `renderDecisionPrompt` 输出末尾追加助理检索约束（不改模板、不改接口）：

```text
## 场景约束（助理检索，必须遵守）
- 本调用只用于助理本轮联网检索决策；intent 必须为 chat，clarification_question 必须为 null。
- 搜索开关已开启，web_search.need_search 必须为 true，search_query 必须是非空、可直接检索的独立关键词。
- 历史中的「这次 / 上面 / 刚才」等指代必须结合历史改写为独立主题；相对时间转绝对日期。
- 若附件已能完整回答，attachment_intent 设为 answerable；否则按 needs_external / none 判定。
```

**输出**

```java
record AssistantSearchPlan(
    String priorityQuery,   // LLM 优化搜索词；null/空白表示走规则词
    boolean skipSearch,     // 附件可独立回答且确有附件
    boolean degraded,       // 决策失败，已降级
    String attachmentIntent // 仅日志
)
```

**降级**

- 渲染/执行/解析任一失败 → `degraded=true`、`priorityQuery=null`、`skipSearch=false`，继续走现有规则检索；
- `webSearchEnabled=false` → 不调用 LLM，直接 `disabled`；
- `skipSearch` 仅在 `attachment_intent=answerable` 且 `hasAttachments=true` 时成立，避免无附件时误跳过。

### B2 助理同步/流式链路接线

文件：`helloai-core/src/main/java/com/helloai/core/planner/assistant/service/impl/AssistantChatServiceImpl.java`

**改动**

1. 注入 `AssistantSearchQueryPlanner`。
2. 同步 `doRoundLocked`：
   - `loadPromptContext` 后调用 `resolveSearchPlan(conversation, message, context)`；
   - `resolveWebSearchContext(conversation, message, plan)`，把 `plan.priorityQuery` 作为 `ClarifyWebSearchOrchestrator.doWebSearch(source, priority)` 的优先候选。
3. 流式 `runAssistantRound`：
   - 在 `loadPromptContext` 后、`doWebSearch` 前调用同一 plan；
   - `plan.skipSearch=true` 时进度文案改为“附件内容可回答，本轮跳过联网检索”，直接进入主回复；
   - 否则 `doWebSearch(conversationId, message, plan)`，优先词先行、规则词兜底。
4. 语义边界：
   - 助理 `webSearchEnabled=true` 表示“每轮允许搜索”，因此**不使用** `need_search=false` 跳过搜索；只取 `search_query`；
   - `webSearchEnabled=false` 时不调用决策、不搜索；
   - 决策失败时行为与改造前一致（规则检索），不阻断。
5. 可观测性：
   - 日志：`助理检索决策: conversationId=..., query=..., attachmentIntent=..., skipSearch=..., degraded=..., costMs=...`；
   - 现有 `澄清联网搜索：候选词...` 日志保留，可直接核对最终候选词。

## 七、风险与回滚

| 风险 | 缓解 |
|---|---|
| A1 指代词表过宽，误杀正常查询 | 只用于“全碎片判定”，补实体保留用例；不做全局清洗 |
| 裸“最近”30 天召回偏旧 | 常量可调；必要时改 7 天 |

| B1 多一次 LLM 调用，增加延迟 | 复用现有 Planner 执行链；失败降级；观察 costMs，必要时限制场景 |
| B1 模板输出 clarify，导致解析失败 | 追加场景约束；解析失败自动降级规则词，不阻断 |
| 附件 answerable 跳过联网与用户预期不一致 | 仅在有附件时生效；日志可查；与澄清链路语义一致 |

回滚：
- A1/A2/B1/B2 均为独立改动，按文件回滚；
- B 失败自动降级，无需额外开关；
- A3 可将 `ai-search-answer` / `ai-search-timeout-ms` 恢复原值，或回滚回退方法。
