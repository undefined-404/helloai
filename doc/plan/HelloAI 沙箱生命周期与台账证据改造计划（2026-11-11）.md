## 0. 定位与边界（★先读）

### ① 问题来源

- **S-7 沙箱每轮销毁**：`LocalExecutionCommandConsumer` 在 turn 结束 `release(subTaskId)`（[LocalExecutionCommandConsumer.java:156-171](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/mqconsumer/LocalExecutionCommandConsumer.java#L156)）。真机第 5 轮开工时 `/workspace` 为空（16:00:43 `ls` 只有 `.`/`..`），模型每轮重建上游文档、重复探索；5 轮共 72 条沙箱命令（70 条不同），`ls -la /workspace`、`cat verify_out.txt`、重写 `verify.py` 均出现重复。
- **S-3/S-4 证据对账脆弱**：模型自报 `EVIDENCE` 用「`cat > v7.py <<'PYEOF' ... python3 v7.py`」这类省略式命令，与台账「真实命令前 200 字符」做前缀匹配必然失败（[SelfReviewEvidenceVerifier.java:111-132](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/loop/impl/SelfReviewEvidenceVerifier.java#L111)）；台账每子任务只保留 50 条（[SandboxCallLedger.java:36](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/sandbox/SandboxCallLedger.java#L36)），而本轮 72 条，早轮证据被淘汰。真机 `self_review_evidence_checked` 的 `ledgerCount` 从 15:59 起恒为 50，mismatch 全部指向省略式命令。
- **外部对照结论**：三个参考项目**没有一个**在 turn 边界销毁工作区——DSH 的 cwd 就是项目目录、持久 shell 跨 turn 存活；OpenSandbox 官方用法是 `taskId → sandboxId`、按 ID 重连、不要每轮 destroy；octop 的工作区按 Agent 持久、`close` 与 `destroy` 分离。详见 §9。

**第二轮（2026-11-13，代码复勘——第一轮方案单靠 `SL-1`/`SL-2` 不足）**

`SL-1`/`SL-2` 只解决了「作用域键」与「释放时点」，**没有解决「容器能不能活到任务终态」**。复勘发现 8 条独立根因：

- **R1 `renew` 是绝对 TTL，会把剩余寿命改短**：`renewQuietly` 每条命令执行 `sandbox.renew(Duration.ofSeconds(max(idleTtlSeconds, 60)))`（[OpenSandboxExecutionService.java:1090-1092](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/sandbox/impl/OpenSandboxExecutionService.java#L1090)），语义是 `expiresAt = now + t`（SDK 1.1.1 `Sandbox#renew(Duration)` 实测），**不是叠加**。默认规格 `timeoutSeconds=3600`，第一次命令后即被压到 900s；node 规格 `timeout-seconds: 900` 本身只有 15 分钟。任务一旦超过 15 分钟无命令（人工审查、长任务间隔），容器即被回收，`SL-1` 的 task 级复用名存实亡。
- **R2 没有后台回收器**：`SandboxSlotPool` 的 `idleExpired` 只在**同键再次 acquire** 时判定（[SandboxSlotPool.java:56](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/sandbox/impl/SandboxSlotPool.java#L56)），无 `@Scheduled` 清理。这意味着「TTL 调大」= 容器泄漏（键不再被访问就永远不清），「TTL 调小」= 工作区丢。当前实现两者都占。
- **R3 命令级超时会销毁整个任务工作区**：`exitCode == 124（TIMEOUT） || exitCode == -1（ERROR）` 直接 `pool.remove(key, this::destroy)`（[OpenSandboxExecutionService.java:887-893](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/sandbox/impl/OpenSandboxExecutionService.java#L887)）。默认命令 `timeout` 由 `resolveSandboxTimeoutSeconds(spec)` 取，缺省仅 30s（[:1076-1079](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/sandbox/impl/OpenSandboxExecutionService.java#L1076)）——一次超时的 `npm install` 就把整个任务已产出的文件全带走。
- **R4 没有工作目录、`/workspace` 不保证存在**：`RunCommandRequest` 只设 `command` 与 `timeout`，无 `workingDirectory`（[:904-907](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/sandbox/impl/OpenSandboxExecutionService.java#L904)），命令落在镜像默认 cwd；`/workspace` 仅在技能安装时 `directoryEntries` 里 `mkdir`（[:667-669](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/sandbox/impl/OpenSandboxExecutionService.java#L667)）。模型写 `./x.py` 与写 `/workspace/x.py` 落在两个地方，回读只扫 `/workspace`。
- **R5 槽查找忽略规格指纹**：`pool.findKey(k -> k.matches(resolved))`（[:388](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/sandbox/impl/OpenSandboxExecutionService.java#L388)、[:744](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/sandbox/impl/OpenSandboxExecutionService.java#L744)）只比 `(kind, scopeId)`，`SlotKey` 里的 `specFingerprint` 未参与匹配。同一任务 python 与 node 两个规格时，后一次调用可能命中另一个规格的容器（文件不在一起，且镜像里没有对应运行时）。
- **R6 台账无来源/轮次，reviewer 与 executor 共用同一账本**：`recordCall` 只写 `command/exitCode/truncated/digest`（[:272-295](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/sandbox/impl/OpenSandboxExecutionService.java#L272)），无 `origin`（executor/reviewer/platform）与 `round`。而 reviewer 在 `subtask_review` 场景可取到 `internal_*` 工具（[AgentMcpServerServiceImpl.java:342-364](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/service/impl/AgentMcpServerServiceImpl.java#L342)），并在 [BusinessSurfaceLoopRunner.java:168](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/BusinessSurfaceLoopRunner.java#L168) 绑定被审子任务 ID 执行命令 ⇒ reviewer 的核验命令写进 executor 账本，返工多轮时无法区分「谁在哪一轮验的」。`findMatch` 全账本扫描、只有单趟 `used` 去重（[SelfReviewEvidenceVerifier.java:98-132](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/loop/impl/SelfReviewEvidenceVerifier.java#L98)），跨轮同命令可互相顶替。
- **R7 大产物永远无法内联**：`readArtifact` 把字节数与「8000 字符」常量直接比较（[InternalLlmExecutorTools.java:106](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/tool/InternalLlmExecutorTools.java#L106)、[:559](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/tool/InternalLlmExecutorTools.java#L559)），且 `maxBytes < size ⇒ truncated`。中文产物按 UTF-8 3 字节/字，2300 字即被判 truncated，模型按现状文案无法内联大文件。
- **R8 六处 Prompt/工具说明仍写「子任务结束即销毁」**：`AgentRuntimeContextAssembler:1024/1029/1032`、`InternalLlmExecutorTools:407/411/466/572`。模型按说明行为，S-7 的「每轮重建」部分由此固化。

### ② 本计划做什么

1. **沙箱寿命改为任务级、终态销毁**（`SL-1` + `SL-2`，**已完成**）：槽键从 `(subTaskId, spec)` 改为 `(taskId, spec)`；删除 turn 结束释放；任务 `DONE` / `CANCELLED`（含级联删除）时经事件在事务提交后释放该任务全部沙箱。会话内技能执行（非子任务 ID）继续走原 `scope:{id}` 语义。
2. **容器寿命正确性**（`SL-7`，新增）：拆分「空闲回收 TTL」与「容器绝对寿命」两个量——`idle-ttl 900s` 只用于回收器判活，`keep-alive 28800s` 作为 `renew` 的绝对目标；`renew` 改为「剩余不足才补」；`exitCode 124/-1` 不再销毁容器；新增 `SandboxIdleReaper` 定时回收，让「大 TTL」安全。
3. **工作区语义与回读修正**（`SL-3`）：容器创建后预建 `/workspace`，所有命令注入 `workingDirectory=/workspace`；回读改为按 mtime 取最近 `.md`；`findKey` 纳入规格指纹；大产物内联改为按字符计；六处过期说明同步。
4. **证据改为台账条目引用**（`SL-4` + `SL-5`）：台账条目加平台生成 `callId` 与 `origin`/`round`；围栏 `EVIDENCE` 从「自报命令 + 摘要」改为 `{"kind":"sandbox_exec","callId":"c17"}`；新增 `internal_list_sandbox_calls`；对账按 `origin=executor`、本轮优先过滤；旧格式保留一版兼容。
5. **沙箱运行时接口化**（`SL-8`，新增，P2）：把隐式 `Long`（一-shot / 会话 / 子任务三义）替换为调用方构造的 `WorkspaceRef(kind, ownerId, specFingerprint, isolation, access, lifetime)`；新增五方法接口 `SandboxRuntime`（`exec` / `readFile` / `stat` / `writeFile` / `release`），`OpenSandboxExecutionService` 降为实现、`SandboxExecutionService` 退为薄适配层（老签名保留给 7 个消费者）；删除 `runtime` 层对 `agent.port.SubTaskQueryPort` 的查库——前置条件是 `taskId` 透传（见 §2.8）。
6. **职责拆分**（`SL-9`，新增，P2）：1192 行实现类按现有职责切为 `SandboxRuntime`（执行）/ `SandboxWorkspaceRegistry`（身份 + TTL + 终态回收 + 后台回收器）/ `SandboxObservation`（台账 + 时间线，协作对象）/ `SkillPackageInstaller` / `DeliverableReader`（「挑最大的 `.md`」搬回消费侧）/ `SandboxFactory`（建销与规格映射，拆构造环）。判据是 `CODE_STYLE` §9.1「两个以上业务职责」，不是行数（§9.2 明确反对按行数机械拆）。
7. **审核隔离**（`SL-10`，新增，P1）：审核不与执行器共享**可写**工作区——`/workspace` 挂 volume + `readOnly` 给 reviewer；一次性校验走 `EPHEMERAL_VERIFY`（跑完即毁，不进槽池）。在此之前 `READ_ONLY` 只是平台层建议，不构成隔离。
8. **验证与灰度收口**（`SL-6`）：单测 / 集成 / 真机（返工续作、跨子任务可见、终态销毁、证据引用、20 分钟空闲存活、reviewer 只读）与 `scope=task|subtask` 回滚开关。

### ③ 本计划不做什么

1. **不把任务级沙箱当成「子任务隔离」**：同一 Task 的子任务共享 `/workspace`，这是**有意放宽**（上游产物天然可见、返工可续作），安全边界从「子任务」上移到「Task」。子任务子目录隔离列入 §8 挂起项，不在本批。**依据**：用户 2026-11-11 口径「task 级沙箱」；ADR-005 既有「同子任务复用」语义上移一层。
2. **不在无 volume 的前提下假装只读**：SDK 1.1.1 存在 `Volume.Builder#readOnly(boolean)` 与 `Sandbox.Builder#snapshotId`（反射实测），但 `/workspace` 当前是容器可写层、**不是 volume**。审核隔离要真隔离，故单列 `SL-10`（volume 挂载 + `readOnly`）承载；`SL-8` 的 `access=READ_ONLY` 只做平台层，**不冒充**容器级只读——`internal_run_in_sandbox` 仍可 `rm` / 重定向写文件。快照（`snapshotId`）仍列 §8。
3. **不把对象存储附件水合进沙箱**：上游已物化附件仍在对象存储，本批只解决「沙箱内产生的文件跨轮/跨子任务可见」；`storageUrl` 可满足性问题另批处理。**依据**：差距表 `G-029` 已登记「上游附件 storageUrl 不可达」，其修复面大于沙箱生命周期。
4. **不做 G-030 自审 fail-close**：本批先把「证据是否可信」修好（`SL-4`/`SL-5`），`self_review_failed → 不提交` 的出口收口必须在证据链可靠后再上，否则误判会把正常任务全拦。**依据**：差距表 `G-030`；用户 2026-11-11 要求本批只做沙箱与证据引用。
5. **不做跨进程重启的沙箱重连**：槽池仍是进程内内存；重启后工作区丢失、旧容器由绝对 TTL 回收。持久化映射列入 §8。**依据**：ADR-005 将沙箱定义为进程级资源，本批不改变该边界。
6. **不按 PID 杀命令**：OpenSandbox 未暴露进程句柄，命令级超时只能靠 `RunCommandRequest.timeout`；`SL-7` 只能做到「超时不再销毁容器」，做不到「精确终止某个后台进程」。后台残留进程由容器终态销毁兜底。
7. **不改外部 Agent 的沙箱**：外部 CLI Agent（trae / qoder）自带工作区，不在本链。**依据**：外部执行者职责手册（`doc/manual/executor-duty/`）与 `G-014` 外部通道口径。
8. **不改 Action/状态机语义**：`DEAD_LETTER`、`RESTRUCTURING`、任务重派/重构仍按既有状态机流转。**依据**：ADR-008 与「状态迁移唯一入口」约束（`SubTaskStateMachineServiceImpl`）。
9. **不做审核侧附件证据可见性**：附件注入预算（`AttachmentContentPolicy` 64k/200k）、证据台账（`EvidenceLedger`）、表格机械预检、驳回依据可达性闸、有界分页工具，均属**对象存储附件 → Prompt** 装配链，不在本计划；已登记 `G-034`（拟 `RV-8`~`RV-13`）。本计划只保证**沙箱内**证据可被引用与归因（`callId` + `origin`/`round`），两条链在 `coverage.method=sandbox|attachment` 汇合。**依据**：2026-11-13 用户提供的三例审核失败复盘——第 1、2 轮是执行方数字与 CSV 矛盾（真实缺陷），第 3 轮才是平台不可见；把前者放宽会放行真错误。

### ④ 诚实边界

- **任务级共享 ≠ 数据隔离**：同任务的不同**执行者**可以读/改彼此的文件；首期用「同槽命令串行」防止并发写坏，但语义上不隔离。子任务间强隔离走 §8 子目录方案；审核侧只读隔离走 `SL-10`。落地后**不得在差距表把 `G-032` 标为「已完成」直到真机验证通过**。
- **同任务多规格 = 多个沙箱**：python 与 node 规格键不同，文件不互相可见；跨规格共享必须走对象存储导出，不在本批。`SL-3` 只保证「同一规格不会被错配」。
- **`READ_ONLY` 在 `SL-10` 落地前不构成隔离**：reviewer 与执行器共用同一可写容器，`internal_run_in_sandbox` 的任意 shell 都能改文件；平台层「不给写工具」只约束工具清单，挡不住命令。`SL-10` 之前，审核独立性在差距表里**按缺口记**，不按已解决记。
- **`runtime` 去查库依赖不是免费的**：`ToolInvocationContext.Ids` 只有 `(agentId, subTaskId)`（[ToolInvocationContext.java:70](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/tool/ToolInvocationContext.java#L70)），**没有 `taskId`**；`SL-8` 必须先把 `taskId` 透传进绑定（[RuntimeTurnExecutor.java:159](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/RuntimeTurnExecutor.java#L159)、[BusinessSurfaceLoopRunner.java:177](file:///E:/yhzx/1027/helloai/helloai-core/src/main/java/com/helloai/core/agent/runtime/BusinessSurfaceLoopRunner.java#L177)），否则 `TASK` 类句柄在工具层构造不出来，只能退回查库。
- **`renew` 的绝对 TTL 语义依赖探针确认**：本计划按「`renew(Duration)` 设置绝对过期时刻」实现，落地前用一次性探针（创建容器 → `renew(60s)` → 等 70s → 重连）确认；若实测为叠加语义，`SL-7` 的 `keepAlive` 计算需改为「延展量」。该探针是 `SL-7` 的第一个动作，结论回写本节。
  - **`[实测] 2026-11-13 结论：确认为绝对语义**（本地 OpenSandbox 1.1.1，REST 探针 `POST /api/v1/sandboxes/{id}/renew`）：创建 300s 后可 renew 到 600s（延长），再把 15:24 的过期改到 06:24（**缩短**，且到期后 `GET` 401/404），证明 `expiresAt = now + t`，不叠加、可提前回收。故 `keepAlive` 按「目标绝对寿命」实现；同时把计划内「探针等 70s 后重连」简化为「缩短到 80s 后实测 404」，省去等待长 TTL。
- **销毁是「尽力而为」**：任务终态事件丢失、进程崩溃、SDK 不可达时，由空闲回收器与沙箱绝对 TTL 兜底回收；不承诺即时。
- **`callId` 只证明「这条命令确实执行过且输出摘要一致」**，不证明命令验的是对的东西；内容正确性仍归 reviewer。
- **旧证据格式保留兼容**：`command + exitCode + truncated + digest` 仍可解析、仍走旧匹配，但只做一版过渡，后续可删。
- **本计划完成不关闭 `G-029` / `G-030`**：`G-029` 的附件水合与 `G-030` 的出口 fail-close 仍是独立差距；`G-032` 只覆盖沙箱生命周期与证据引用本身。

  5. **新增 `SandboxIdleReaper`**：每分钟遍历槽池，`idleSince > idleTtl` 且能 `tryLock` 的槽 ⇒ `destroy` 并移除；拿不到锁跳过。使「大 `keep-alive`」不再等于泄漏。

- **实现口径（与上文步骤的差异，需保留）**：
  - 步骤 3 的台账 `timedOut=true` **本批未加**：`exitCode == 124` 已无损编码「超时」，显式字段随 `SL-4` 的 `Entry` 扩展（`callId`/`origin`/`round`）一次落，避免两次改 record 构造。
  - 步骤 5 的回收阈值**按键区分**（本批修正计划内部矛盾）：任务级槽（`task:{taskId}`）按 `keep-alive` 判活，`scope:{id}` 与子任务级回滚槽按 `idle-ttl` 判活。原因：任务级槽有终态释放点、空闲常是「等人工审查」，按 900s 销毁会丢整个任务工作区，且与已续期到 8h 的真实寿命脱节；非任务级槽没有终态释放点，只能按短空闲上限收敛。`acquire` 同键淘汰也改用同一 `slotTtlMillis`，否则「空闲 20 分钟再下命令」会先被 acquire 淘汰、验收项不可能通过。

  - 步骤 2 的「`renew(max(remaining, keepAlive))`」实现为**半衰期判据**：剩余 ≥ 目标一半就不发 `renew`（每轮都补等于每条命令白付一次 RPC），剩余不足才补到 `now + keepAlive`。
- **验收**：任务空闲 20 分钟后下一条命令仍命中原容器（`sandboxId` 不变、`/workspace` 文件仍在）；`exitCode=124` 后下一条命令仍命中原容器且文件仍在；空闲超过 `idle-ttl` 的槽在 60~120s 内被回收（日志 `sandbox reaped idle=...`）；`activeSandboxes()` 不随时间单调增长。
- **测试（已落）**：`SandboxSlotPoolTest` +4 例（到期回收 / `ttl<=0` 豁免 / 槽锁被占用跳过 / null 与空池幂等，合计 14 例）；`OpenSandboxExecutionServiceTest` +6 例（默认值拆分 / 300s 默认与钳制 / 半衰期续期判据 / 按键 TTL / 未启用与空池回收，合计 23 例）；两类 37 例 0 失败。

> - **偏差 ③：适配层落地为独立 `SandboxRuntimeAdapter`（`@Component`），实现类不再 `implements SandboxExecutionService`。** 若让实现类自己当适配层，查库与执行仍在同一个类里，「运行时零业务查询」就只是约定。现在 `OpenSandboxExecutionService` 的构造器只有 `(properties, loader, ledger, timeline)`，`SubTaskQueryPort` 在编译期就拿不到。
> - **偏差 ④：解析顺序改为「绑定 `taskId` 优先于查库」。** 计划只要求 `taskId` 透传，实现额外把它当作**短路条件**：执行链已绑定时直接构造 `TASK` 句柄，一次执行 20 轮就省 20 次查询；未绑定（turn 末释放 / 非执行链调用）才走 `SandboxScopes`。`scope=subtask` 回滚模式在查库前短路（行为回到 2026-11-11 前）。
> - **偏差 ⑤：`writeFile` 只按默认规格建槽。** `SandboxRuntime#writeFile` 不带 `spec` 参数（计划给的五方法里也没有）：当前唯一写入方是跨文档证据落盘（`SL-10`），其规格与命令执行默认规格一致。需要专用规格时再扩签名，不提前在接口上挂一个无人使用的参数。
> - **架构守卫扩为组 4（2 条硬拦截）：** `impl` 不得 import `SubTaskQueryPort` / `SandboxScopes`，目标恒为 0，已锁入 `arch-baseline.txt`。规则名 `sandbox.impl->SubTaskQueryPort` / `sandbox.impl->SandboxScopes`。

- **落点**：新增 `WorkspaceRef` / `SandboxRuntime`（`agent/runtime/sandbox/`）、`SandboxExecutionService`（退为适配层）、`OpenSandboxExecutionService`（降为实现）、`SandboxScopes`（退出 runtime 调用链）、`ToolInvocationContext`、`RuntimeTurnExecutor`、`BusinessSurfaceLoopRunner`、7 个消费者。
- **做法**：
  1. `WorkspaceRef(Kind kind, Long ownerId, String specFingerprint, Isolation isolation, Access access, Lifetime lifetime)`：
     - `Kind`：`TASK` / `SUBTASK` / `SCOPE` / `ONESHOT`；
     - `Isolation`：`TASK_WORKSPACE`（进槽池、按任务终态回收）/ `EPHEMERAL_VERIFY`（不进槽池、跑完即毁）；
     - `Access`：`READ_WRITE` / `READ_ONLY`；
     - `Lifetime`：`TASK` / `TURN` / `CALL`。
  2. 新增 `SandboxRuntime`：`exec(ref, command, timeoutSec)` / `readFile(ref, path, maxBytes)` / `stat(ref, path)` / `writeFile(ref, path, bytes)` / `release(ref)`。沙箱对 executor / reviewer / 自审**一无所知**，角色差异全部由 ref 承载。
  3. **`taskId` 透传先行**：`ToolInvocationContext.Ids` 扩为 `(agentId, taskId, subTaskId)`，`bind` 由 `RuntimeTurnExecutor`（`ctx.getTaskId()`）与 `BusinessSurfaceLoopRunner`（被审子任务的 `taskId`）注入。不先做这步，工具层构造不出 `TASK` 句柄，只能退回查库。
  4. `SandboxExecutionService` 保留全部老签名（7 个消费者零改动），内部只做 `subTaskId → WorkspaceRef` 一次映射；**只有适配层允许查库**，`SandboxRuntime` 实现里零业务查询。
  5. 调用侧显式给 ref：执行器 = `TASK/TASK_WORKSPACE/READ_WRITE/TASK`；reviewer = `TASK/TASK_WORKSPACE/READ_ONLY/TASK`；会话技能 = `SCOPE/TASK_WORKSPACE/READ_WRITE/TASK`；`FinalReportFidelityGate` = `ONESHOT/EPHEMERAL_VERIFY/READ_ONLY/CALL`。
  6. `SandboxScopes` 保留为 legacy 适配（一版后删），从 `SandboxRuntime` 的调用链上摘除。
- **验收**：`SandboxRuntime` 实现与 `WorkspaceRef` 之间无 `SubTaskQueryPort` / `SandboxScopes` 调用（Grep 零命中）；7 个消费者编译零改动；日志能区分 executor 与 reviewer 的 ref。
- **测试**：`WorkspaceRefTest`（工厂 / 非法组合 / legacy 转换）；`SandboxRuntimeAdapterTest`（老签名 → ref 映射，含 `null` ⇒ `ONESHOT`）；`check-arch-freeze.sh` 新增规则「`runtime.sandbox` 不得依赖 `agent.port`」。
- **依赖**：在 `SL-3` 之后（cwd / 指纹稳定后再改签名，避免两次冲突）；与 `SL-4`/`SL-5` 无耦合（`origin` 改由 ref 推导反而更准）。

### SL-10 审核隔离（P1，新增）

> **状态**：已完成（代码 + 单测 + 真机） ｜ **剩余动作**：—

> **实现偏差**（2026-11-13 落地后回填）：
> 1. **槽键纳入 `Access` 而非 `Isolation`（对「纳入 `Isolation`」的精确化）**：`WorkspaceRef` 的 `task()` 与 `taskReadOnly()` 隔离形态都是 `TASK_WORKSPACE`，区别只在 `Access`（`READ_WRITE` / `READ_ONLY`）。故 `SlotKey` 在 `(Kind, ownerId, specFingerprint)` 之外再纳入 `Access`（`SL-10` 对 `SL-8` 槽键字段的精确化）——executor（`READ_WRITE`）与 reviewer（`READ_ONLY`）各自一个槽实例，否则 reviewer 复用的仍是执行者那个可写容器。`Isolation` 只承担「是否进槽池」（`TASK_WORKSPACE` / `EPHEMERAL_VERIFY`）。

  3. `EPHEMERAL_VERIFY`：不进槽池，创建→执行→销毁。现有的 `execute(null, ...)` 一-shot 就是它，只是没有建模（`FinalReportFidelityGate:132`）。

  5. 卷清理：任务终态销毁时删卷；异常路径由 registry 的任务登记表 + 回收器清理。
- **验收**：reviewer 执行 `touch /workspace/x` 返回非零且文件不存在；executor 写同一文件成功；任务终态后卷目录为空。
- **测试**：单测（ref → 卷参数映射 / 槽键含 `Isolation`）；真机（reviewer 写入被拒 + 终态卷清理）。

## 4. 关键设计决策

| 决策 | 选择 | 理由 / 备选 |
| --- | --- | --- |
| `D1` 作用域 | **Task 级**（`task:{taskId}`），会话技能保留 `scope:{id}` | 用户口径；OpenSandbox 官方 `taskId→sandboxId`；比子任务级更能解决上游可见与返工续作。备选：子任务级（不改上游可见性） |
| `D2` 工作区布局 | **首期共享 `/workspace`**，不做子任务子目录 | 改动最小、与现有 Prompt 路径兼容；代价是跨子任务可见（有意为之）。子目录 + cwd 注入列入 §8 |
| `D3` 销毁时点 | 任务 `DONE/CANCELLED`（含删除），事件 AFTER_COMMIT | `DEAD_LETTER` 子任务仍可能重派；turn 结束不销毁。备选：显式管理端点（增加运维负担） |
| `D4` 证据标识 | 平台生成 `callId`，模型只引用 | 消灭「手抄命令」这一脆弱环节；比 digest 自算可靠；`digest` 仍保留用于防伪 |
| `D5` 台账容量 | 200 条/子任务，查询工具只列 50 | 覆盖单次长执行；内存可控（512 子任务 × 200） |
| `D6` 兼容 | 旧 `EVIDENCE` 四字段保留一版 | 避免存量任务与旧模型立即失效；日志标记 legacy，下一版删 |
| `D7` 并发 | 同槽命令串行（既有 `Slot.lock`）+ 回收器 `tryLock` | 跨子任务共享时至少不并发写；语义隔离不做 |
| `D8` 容器寿命 | **两个量**：`idle-ttl=900s`（判空闲，回收器用）/ `keep-alive=28800s`（`renew` 的绝对目标）；`renew` 只在剩余不足时补 | **撤回首版「900 → 7200 + 每次 renew」**：`renew` 是绝对语义，写大值会被后续小值改短；且无回收器时大 TTL = 泄漏。备选：不 `renew`、只靠容器创建参数（会随命令失败一起丢） |
| `D9` 灰度 | `sandbox.opensandbox.scope` 取 `task` 或 `subtask`（默认 `task`） | 出问题可一键回退；回滚分支保留 turn 末释放 |
| `D10` 证据来源与轮次 | 台账 `origin` + `round`；对账默认只认 `executor`，跨 origin/跨轮打标不静默通过 | reviewer 与 executor 共用被审子任务 ID 执行命令（`BusinessSurfaceLoopRunner:168`），无来源字段就无法区分；跨轮同命令会互相顶替 |
| `D11` 工作区句柄 | `WorkspaceRef(kind, ownerId, specFingerprint, access, lifetime)` 显式化；`runtime` 不再反查业务库 | 现有 `Long` 背负「一-shot / 会话 / 子任务」三义，靠 `SubTaskQueryPort` 查库区分 = 运行时层依赖业务层（架构倒挂）。`access` 只做平台层，容器级只读需 volume，列 §8 |
| `D12` 大产物内联 | 按**字符**计数，超限截断并标 `truncated`；删除不可达建议文案 | 现实现字节比字符常量（中文 3 倍偏差），且 `maxBytes < size ⇒ truncated` 让大文件永远进不了上下文 |

## 5. 依赖与实施次序

```
SL-7（容器寿命） ∥ SL-3（工作区） ──→ SL-4（callId/origin） ──→ SL-5（证据引用）
                                        └──→ SL-8（接口化 + taskId 透传）──→ SL-9（职责拆分）
                                                                             └──→ SL-10（审核只读挂载）
SL-1 ✅ ──→ SL-2 ✅ ──────────────────────────────────────────────────────→ SL-6（收口，最后）
```

- `SL-7` 与 `SL-3` **同批优先**：只修作用域不修寿命 = 容器 15 分钟后消失；只修 cwd 不修寿命 = 真机验不出跨轮效果。二者可并行开发、同批验证。
- `SL-4` 必须在 `SL-5` 之前（无 `callId` 无法引用）；`SL-4` 与 `SL-7`/`SL-3` 无代码依赖，可提前。
- `SL-8` 在 `SL-3` 之后（cwd/指纹稳定后再改签名）；其第一动作是 `taskId` 透传，否则 `TASK` 句柄构造不出来。
- `SL-9` 在 `SL-8` 之后（先有接口再拆实现）；`SL-10` 依赖 `SL-9` 的 `SandboxWorkspaceRegistry`（卷挂载点），建议同批。
- **证据归属先于隔离**：`SL-4`/`SL-5` 的 `origin`/`round` 不依赖 `SL-10`，先做——台账现在连「谁执行的」都没记，隔离做得再好也无法验收。
- `SL-6` 是收口，必须最后；「20 分钟空闲」项只能在 `SL-7` 之后验，「reviewer 只读」项只能在 `SL-10` 之后验。
- **G-030 自审 fail-close 不在本计划**：待 `SL-5` 真机验证「证据引用零 mismatch」后单独一批上线。
- 本计划不动 DB schema、不新增迁移；`SL-1`/`SL-2` 的未提交改动与后续改动按用户节奏同批审核提交。

## 6. 风险与边界

1. **跨子任务文件污染**：任务级共享后，B 可能误读/覆盖 A 的文件；靠命令串行与 Prompt 约束，不做强制隔离（§8 子目录方案）。
2. **多规格不共享**：同一任务 python/node 两个沙箱，文件不互通；跨规格交付应走 `internal_export_artifact`。
3. **重启丢工作区**：进程重启后槽池清空，旧容器靠 TTL 回收；任务若需继续，会新建沙箱、旧文件丢失（已有行为，不恶化）。
4. **终态释放与在跑命令竞争**：`releaseByTask` 用 `tryLock`；拿不到锁的槽交给 TTL，避免杀正在执行的命令。
5. **对话作用域误判**：`SubTaskQueryPort.findById(scopeId)` 未命中即按 `scope:{id}`；需加单测防「conversationId 恰好等于某个 subtaskId」的极端碰撞（雪花 ID 概率可忽略，但保留判据）。
6. **台账内存增长**：200×512 上限（`SL-4` 已落）；任务终态主动清理需要 task 域「按任务列子任务 ID」的端口，本批未接（见 §3 `SL-4` 实现偏差），判据：`SL-6` 真机观察长任务进程堆内存是否随任务数单调增长。
7. **证据引用不校验内容**：`callId` 只证明执行事实；报告内容仍需 reviewer。
8. **容器泄漏（`SL-7` 引入的新平衡）**：`keep-alive` 拉长后，若回收器失效（`@Scheduled` 未启用、池被绕开），容器会堆积到 8h。判据：`SL-6` 真机观察 `activeSandboxes()` 是否随时间单调增长；回收器单测覆盖「到期必删」。
9. **僵尸容器（进程崩溃）**：槽池是内存态，进程崩溃后 `releaseByTask` 不会执行，容器活到 `keep-alive`。这是 `SL-7` 有意的取舍（宁可 8h 后回收，也不让正常任务中途丢文件）；远端清理列入 §8。
10. **`renew` 语义误判**：若 SDK 实为叠加语义，`SL-7` 的 `max(remaining, keepAlive)` 会变成无限延长。故 `SL-7` 第一步必须是探针，结论回写 §0④ 后才实现。
11. **`origin` 依赖调用侧正确注入**：若某条路径漏注入，会退化为 `executor`，导致 reviewer 命令被当作者证据。判据：`SL-4` 单测穷举调用点 + `SL-6` 真机检查 `origin` 分布。
12. **连续三步改结构**：`SL-8` 改接口、`SL-9` 拆实现、`SL-10` 改槽键，若字段分三次扩，会产生三批冲突与回归。规避：`SL-8` 一次性把 `WorkspaceRef` 的 `Isolation` 定全，`SL-9` 只搬不改语义，`SL-10` 只加挂载参数。
13. **槽键加 `Isolation` 使实例数翻倍**：同任务变成 executor 一个可写实例 + reviewer 一个只读实例，内存与启动延迟上升。`EPHEMERAL_VERIFY` 不进池、不占常驻；容量按并发上限评估（§7 真机观察 `activeSandboxes`）。
14. **volume 化后工作区脱离容器生命周期**：节点磁盘、跨节点调度、清理失败都会留下孤儿卷。卷登记与清理归 `SandboxWorkspaceRegistry`，任务终态与回收器双路清理，§7 加「终态后卷目录为空」判据。

## 8. 挂起项（明确不启动）

1. **子任务子目录隔离**（`/workspace/subtasks/{id}` + 每子任务 `workingDirectory`）：`SL-3` 统一 cwd 后仍可扩展，但需要迁移现有 Prompt 路径与回读规则，单独评估。
2. **工作区快照（`snapshotId`）**：SDK 1.1.1 支持 `Sandbox.Builder#snapshotId`（反射实测），但「按轮次/按子任务快照回放」需要快照存储与命名策略，且与 volume 方案能力重叠；先把 `SL-10` 的只读挂载做完，快照远期。只读挂载本身**不再挂起**（已升为 `SL-10`）。
3. **对象存储附件水合进沙箱**（S-6 的另一半）：`storageUrl` 可见性/验收可满足性另批。
4. **G-030 自审 fail-close**：待 `SL-5` 真机稳定后单独一批。
5. **S-1 雪花 ID 精度**：agent 面 ID 统一字符串，独立小批（优先级高于 G-030）。
6. **S-8 交付物清洗**：物化前剔除 provider 模板/工具调用残迹，独立小批。
7. **沙箱跨重启重连**：需要持久化 `taskId → sandboxId` 映射与启动对账（含僵尸容器清理），远期。
8. **命令级 PID 终止**：OpenSandbox 未暴露进程句柄；如需精确终止后台进程需 SDK 支持或容器内自治脚本，远期。
