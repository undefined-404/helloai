# HelloAI 需求对话附件（添加文件 / 引用文件）设计方案（2026-10-22）

> 状态：**口径已定（2026-10-22 拍板，见 §6），待实施**；代码未动。编写：2026-10-22，2026-10-22 补 Tika 依赖实测
> 关联：`PRODUCT.md` 需求对话、`G-016`（附件内容注入口径）、`ADR-002`（RAG 选型）、`Requirement_Package_Uncertainty.md`
> 结论先行：**当前平台不支持在需求对话里挂文件，规划者（planner）也完全不识别附件内容**；能力缺口有三处（数据模型、解析链、Prompt 注入），但底层零件（对象存储、pgvector RAG、模型能力元数据、离线可用的解析依赖）都已具备，实施不需要新增外部基础设施。

## 1. 现状取证

### 1.1 附件域只服务子任务

| 事实 | 取证位置 |
|---|---|
| `attachment` 表只有 `sub_task_id`，**没有 conversation 维度** | `\d attachment`（字段 sub_task_id / visibility / uploader_agent_id） |
| 上传端点 `POST /api/artifacts/upload` 要求 **agent 身份**（`AuthInterceptor.AUTH_ID_KEY`）且 `subTaskId` 必填 | `ArtifactUploadController#upload` |
| 下载 / 预览 / 删除 / 列表都在 `/api/attachments/**`，只按 subTaskId 聚合 | `AttachmentController` |
| 可见性策略按「子任务 × 任务团队」判定（PERSONAL/TASK/PUBLIC） | `AttachmentVisibilityPolicy` |

⇒ 需求对话（`requirement_conversation`）与 `requirement_message` **没有任何附件关联字段**，也没有任何前端上传代码（`helloai-ui/src` 内 `el-upload` / `FormData` 命中 0 处）。

### 1.2 解析能力：PDF / Office / 图片都不读

| 事实 | 取证位置 |
|---|---|
| 无 PDF / Office 解析依赖 | 三个 `pom.xml` 中 `pdfbox` / `tika` / `poi` 命中 0 处 |
| 注入口径**明确把 PDF 排除在文本类之外** | `AttachmentContentPolicy.isTextual()` 只认 `text/*` 与 json/xml/yaml/sql + 一组代码扩展名 |
| 图片只在「媒体族」判定里出现，**不读取内容** | 同文件 `isMedia()`，仅用于决定「不注入正文」 |
| 注入限额已存在且已调优 | `ATTACHMENT_CONTENT_PER_FILE_LIMIT = 64000` 字符、`ATTACHMENT_CONTENT_TOTAL_LIMIT = 200000` 字符 |

⇒ 现状：附件在报告链 / 核验链里只是「文件名 + 类型 + 大小 + 文本型正文」，**PDF 进来就是一张白纸**。

### 1.3 规划者（planner）完全不认识附件

```
grep "Attachment|attachment" helloai-core/src/main/java/com/helloai/core/planner  →  0 files
```

需求对话的 Prompt 模板（`prompts/requirement-clarify.md`、`requirement-chat.md`）只有五个变量：

```
{{CONVERSATION_HISTORY}} {{CURRENT_USER_MESSAGE}} {{LONG_TERM_MEMORY_CONTEXT}}
{{SYSTEM_TIME_CONTEXT}}  {{WEB_SEARCH_CONTEXT}}
```

没有附件层。**结论：给 planner 一个文件，它连"有这个文件"都不知道。**

### 1.4 模型侧能力已有元数据、缺调用通道

`llm_provider_model.capabilities` 已按模型声明输入模态，实测库内：

| provider | 声明 |
|---|---|
| anthropic（claude-sonnet-4-5 / haiku / opus 全系） | `["text","image","pdf"]` |
| dashscope（qwen3.5 系） | `["text","image","video"]`（部分含 audio） |
| deepseek（v4-flash） | `["text","image"]` |
| moonshot（kimi-k2.7-code） | `["text","image","video"]` |

`ModelCapabilities` 解析器已把这套 JSONB 归一成 `inputModalities`（且对 `pdf` 这种非封闭词表做了开放处理）。
但 Java 侧搜 `Media` / `MediaFormat` **0 处** —— 也就是说：**能力有登记，通道没建**。

### 1.5 RAG 零件已就位（可复用，不必新建）

| 零件 | 现状 |
|---|---|
| 向量存储 | PG `kb_chunk`，pgvector `vector(1024)` + HNSW 余弦（`KnowledgeRepository`） |
| 嵌入 | `KnowledgeEmbedder` 走 DashScope OpenAI 兼容端点（复用 `spring-ai-openai`，不新增依赖） |
| 检索 | `KnowledgeBaseService#search`（query 嵌入 → top-k → 预算截断） |
| 给 Agent 的工具 | `search_knowledge`（`SearchKnowledgeToolCallback implements ToolCallbackContributor`） |
| 引用溯源 | `GET /api/kb/chunk/{source}/{chunkIdx}`（前端可点开原文分片） |
| 摄入接口 | `POST /api/kb/ingest`（source 幂等覆盖）、`DELETE /api/kb/source/{source}` |

### 1.6 限额现状

| 层 | 现值 | 出处 |
|---|---|---|
| multipart 单文件 / 单请求 | 8MB / 8MB | `spring.servlet.multipart`（注释说明"略高于 storage 5MB 留边界余量"） |
| 存储层单文件 | 5MB | `storage.max-file-size`（同注释） |
| 单附件注入正文 | 64000 字符 | `AttachmentContentPolicy` |

## 2. 成熟产品怎么做

### 2.1 Kimi（官方帮助页，2026-10 核对）

- 类型：PDF、Word、Excel、PPT、图片、TXT、视频
- 限额：**单文件 ≤ 100MB，单次 ≤ 50 个**
- 上下文：K2.6 约 128K tokens，K3 最高 1M
- **项目文件「按需读取」**：官方明确「不会在每轮对话中把全部文件正文预加载，而是模型根据你的问题判断需要哪些文件再读取」
- 项目存储配额按套餐（Free 500MB → Ultra 50GB）

⇒ 两个关键产品选择：**① 文件先落库、不每轮全量塞；② 大文件走"按需读取"（工具/检索），小文件才全文注入。**

### 2.2 DeepSeek 网页版

- 回形针上传图片 / PDF / Office / 代码文件；压缩包需先解压
- 扫描版 PDF 走 OCR，识别质量取决于原件清晰度；超长文档官方建议分段
- 上下文 1M tokens，属于「大窗口直接塞」路线

⇒ 大窗口不等于不分层：连 Kimi 都在 128K/1M 窗口上做「按需读取」，说明**注入预算与检索是产品必需，不是省钱手段**。

### 2.3 通用做法（四步）

```
① 上传（multipart / 直传对象存储，返回附件 id）
② 异步解析（文本层提取 / OCR / 视觉理解 → 归一成 markdown 或纯文本）
③ 分层注入（小：全文进 prompt；大：分片 + 检索命中片段）
④ 多轮引用（消息 → 附件关联，气泡显示文件 chip，回答里带可点回源标记）
```

图片两条技术路线：

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 原生视觉 | 图片/PDF 页作为 `Media` 随消息发给视觉模型 | 版面、图表、手写都保留；无需 OCR 基建 | 只有声明 image/pdf 的模型可用；图片 token 贵 |
| 先 OCR | OCR 成文本再按文本注入 | 任何文本模型都能用（DeepSeek 也能） | 表格/版面/图表丢失；中文手写差 |

成熟产品大多**两条都做**：视觉模型在就用原生，否则降级 OCR。

### 2.4 GitHub 生态（含许可，2026-10 核对）

| 工具 | 语言/形态 | 许可 | 强项 | 弱项 |
|---|---|---|---|---|
| Apache Tika | Java 库 | Apache-2.0 | 格式覆盖最广（PDF/DOCX/PPTX/XLSX/HTML…），一个 Reader 全包 | PDF 仅抽文本层，版面/表格散架；无 OCR |
| Apache PDFBox | Java 库 | Apache-2.0 | PDF 文本层抽取 + 页渲染位图（供视觉/OCR） | 无版面分析，无 OCR |
| Apache POI | Java 库 | Apache-2.0 | docx/pptx/xlsx 结构级读取 | 只覆盖 Office |
| MarkItDown（微软） | Python | MIT | Office → markdown 极快、依赖极轻 | PDF 弱、无 OCR |
| Docling（IBM） | Python | MIT | 版面/阅读顺序/表格结构，可插 OCR（EasyOCR/RapidOCR/Tesseract），CPU 可跑，可 `docling-serve` 起 HTTP | 需 sidecar 容器 |
| MinerU（OpenDataLab） | Python | AGPL-3.0（+附加条款） | 中文/公式/表格最强 | 重（模型缓存 20GB 级），AGPL 商用需评估 |
| Marker（Datalab） | Python | GPL-3.0 + 权重条款 | 速度与通用质量均衡 | 许可对商用有限制 |
| PaddleOCR | Python/服务 | Apache-2.0 | 中文 OCR、PP-StructureV3 版面 | 需服务化 |

**Spring AI 侧**：`spring-ai-tika-document-reader`（1.1.8 与项目 `spring-ai.version` 对齐）封装 Tika，可直接产出 `Document` 列表；多模态走 `Media`（image/pdf），与上面第 1.4 节的模型能力元数据正好接得上。

### 2.5 依赖可行性（探针实测，不是推测）

用探针工程（maven 3.9.14 + JDK17）逐一实跑，结论全部来自实测输出：

| 组合 | 结果 | 说明 |
|---|---|---|
| `pdfbox 3.0.5` + `poi-ooxml 5.4.1` | **通过（`-o` 离线）** | 2 个依赖、classpath 约 20 条；只覆盖 PDF + Office |
| `tika-parsers-standard-package 3.1.0`（无 `type=pom`）+ 上述 | **离线失败** | 缺 `jackson 2.18.2`、`bcpkix-jdk18on 1.80.2`、`jcl-over-slf4j 2.0.16`（探针没有 Boot BOM 兜版本，Tika 声明值直接生效） |
| `tika-parsers-standard-package 3.3.1` + `<type>pom</type>` **但只写这一条** | 依赖能解析，**编译失败**：`程序包 org.apache.tika.parser 不存在` | 聚合 POM 只带 24 个 parser 模块，**不带 `tika-core`**（实测 classpath 里无 tika-core） |
| 同上 **+ 显式 `tika-core`** | **通过** | classpath 87 条；`Tika.detect` / 243 种类型可用 |
| **`tika-core 4.1.0` + `tika-parser-pdf-module` + `tika-parser-microsoft-module`** | **通过** | classpath 50 条；实测解析 `/tmp/sample.pdf` → 45 字符、`/tmp/sample.docx` → 29 字符，内容正确 |
| 同上，但把 jackson 换成项目的 `2.18.4.1` | **通过** | 无 `NoSuchMethodError`，说明 Tika 4 的 jackson 声明（2.22.3）与项目版本可共存于我们这条解析路径 |

三条关键修正（都是踩出来的）：

1. **`tika-parsers-standard-package` 是 pom 打包的聚合件**，`<type>pom</type>` 必须写；但**只写它编译不过**——聚合 POM 只引入 24 个 parser 模块，`tika-core`（`Tika`、`AutoDetectParser` 所在）要单独声明。
2. **Tika 4.x 是正式版**（Central 上 `4.0.0` / `4.1.0` 均为 release，最新 release = 4.1.0；3.x 最新 3.3.3）。但 4.x **改了 `Parser.parse` 签名**：入参从 `InputStream` 变成 `TikaInputStream`（3.x 的写法在 4.x 编译不过）。也因此 **`spring-ai-tika-document-reader 1.1.8`（依赖 Tika 3.x）不能配 4.x 用**——本项目不需要它，直接用 Tika API。
3. **离线只是"没预先拉包"，不是"不能用"**：Tika 4.1.0 拉的是 `pdfbox 3.0.8` / `poi-ooxml 5.5.1` / `jackson 2.22.3`，本机 `~/.m2` 没有这些版本 ⇒ 首次引入需要一次联网解析；之后照旧 `-o` 离线构建。

## 3. 方案

### 3.1 数据模型

**推荐新增 `chat_attachment`，而不是给 `attachment` 加 `conversation_id`**：

| 理由 | 说明 |
|---|---|
| 语义不混 | `attachment` 的可见性策略、补偿任务、交付物判定都建立在「子任务」这个锚点上；塞进会话维度会让 `AttachmentVisibilityPolicy` 出现第四种情形 |
| 生命周期不同 | 会话附件绑定会话，会话删除即回收；子任务附件绑定交付审计，需长期留存 |
| 迁移风险低 | 新表 + 新端点，不动既有 T1/T2 链路 |

```sql
CREATE TABLE chat_attachment (
    id                bigint PRIMARY KEY,
    conversation_id   bigint,              -- 可空：新会话首句先上传、会话尚未创建
    client_token      varchar(64),         -- 新会话挂载期临时归属（前端生成 UUID），建会话后回填
    file_name         varchar(255) NOT NULL,
    file_type         varchar(64)  NOT NULL,   -- 归一扩展名
    mime_type         varchar(128) NOT NULL,
    file_size         bigint       NOT NULL,
    content_hash      varchar(64),             -- sha256，同会话内去重
    bucket_name       varchar(64)  NOT NULL,
    object_key        varchar(255) NOT NULL,
    parse_status      varchar(16)  NOT NULL,   -- PENDING / PARSING / READY / FAILED / SKIPPED
    parse_error       varchar(512),
    extracted_text    text,                    -- 文本层/解析结果（≤ 解析上限）
    extracted_chars   integer,
    page_count        integer,
    parser            varchar(32),             -- pdfbox / tika / plain / vision / ocr
    kb_source         varchar(160),            -- 已入 RAG 时的 source（chat:{conv}:{att}）
    create_by         varchar(64) NOT NULL DEFAULT '',
    create_time       timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time       timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    deleted           smallint NOT NULL DEFAULT 0
);
CREATE INDEX idx_chat_att_conv  ON chat_attachment (conversation_id) WHERE deleted = 0;
CREATE INDEX idx_chat_att_token ON chat_attachment (client_token)   WHERE conversation_id IS NULL AND deleted = 0;

CREATE TABLE requirement_message_attachment (
    id            bigint PRIMARY KEY,
    message_id    bigint NOT NULL,
    attachment_id bigint NOT NULL,
    seq           integer NOT NULL DEFAULT 0,
    create_time   timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE UNIQUE INDEX uk_msg_att ON requirement_message_attachment (message_id, attachment_id);
```

> `client_token` 是刚需：新会话是「先上传文件 → 再发第一句」的顺序，此时还没有 `conversation_id`。建会时按 token 认领并回填。

### 3.2 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/clarify/attachments/upload` | multipart：`file` + 可选 `conversationId` / `clientToken`；**平台账号通道**（不要求 agent 身份） |
| GET | `/api/clarify/attachments?conversationId=&clientToken=` | 本会话/本临时批次的文件清单（含 parseStatus，前端轮询解析进度） |
| POST | `/api/clarify/attachments/deleteById/{id}` | 删除（软删 + 异步回收对象） |
| GET | `/api/clarify/attachments/previewById/{id}` | 内联预览（复用 `AttachmentService#isPreviewable` 的白名单口径，扩 pdf/图片） |
| POST | `/api/clarify/attachments/reparse/{id}` | 解析失败重试（幂等，供运维与用户自助） |

请求侧变化：`POST /api/clarify/create` 与 `/send` 增加可选 `attachmentIds: number[]`（不传则沿用消息体里的 `[file:xxx]` 反解，二者取并集）。

### 3.3 解析流水（异步）

```
upload ─► 落对象存储 + 落 chat_attachment(PENDING) ─► 返回 id（不等解析）
                                   │
                                   ├─ 魔数校验：Tika.detect(bytes) 与声明 mimeType 对照（不一致即拒）
                                   │
                                   ├─ @Async 解析 worker
                                   │    ├─ 统一入口：Tika AutoDetectParser（pdf 模块 = PDFBox、microsoft 模块 = POI）
                                   │    │    text/*, md, json, csv, 代码 → 直读 UTF-8（截断 200k 字符，不经 Tika）
                                   │    │    pdf → Tika 抽文本层（按页拼，带 [Page N] 锚点）
                                   │    │           文本层空/字符密度过低 → 判定扫描件 → PDFBox 渲染每页 PNG → 视觉直读（3.3.1）
                                   │    │    docx/pptx/xlsx → Tika 抽文本（标题/段落；表格另用 XWPF/XSSF 转 markdown 表格）
                                   │    │    图片 → 视觉直读（3.3.1）：转写文本落 extracted_text，parser=vision
                                   │    └─ 写 extracted_text / page_count / parser / parse_status
                                   └─ 前端 2s 轮询清单直到终态（或 SSE 推，复用现有流式通道）
```

**pom 里到底怎么写**（按 §2.5 实测，少一行就编译不过）：

```xml
<dependency>                                                 <!-- 只要 PDF/Office 就用这三条，50 条 classpath -->
  <groupId>org.apache.tika</groupId><artifactId>tika-core</artifactId><version>4.1.0</version>
</dependency>
<dependency>
  <groupId>org.apache.tika</groupId><artifactId>tika-parser-pdf-module</artifactId><version>4.1.0</version>
</dependency>
<dependency>
  <groupId>org.apache.tika</groupId><artifactId>tika-parser-microsoft-module</artifactId><version>4.1.0</version>
</dependency>

<!-- 若要用聚合包（全格式），必须同时写 type=pom 与 tika-core，否则编译期找不到 Tika 类 -->
<!--
<dependency>
  <groupId>org.apache.tika</groupId><artifactId>tika-parsers-standard-package</artifactId>
  <version>4.1.0</version><type>pom</type>
</dependency>
-->
```

> 4.x 的 `Parser.parse` 入参是 `TikaInputStream`（3.x 是 `InputStream`）；从 3.x 示例抄代码会编译失败。
> `tika-parser-pdf-module` 已把 `pdfbox 3.0.8` 作为传递依赖带进来，渲染扫描件页不需要再单独声明；若后续要与 PDFBox 直接交互（`PDFRenderer`），版本以 Tika 带入的为准，避免双版本共存。

判定阈值（可配 `chat.attachment.*`）：

| 项 | 建议值 | 理由 |
|---|---|---|
| 单文件 | 20MB | 覆盖绝大多数 PDF/PPT；multipart 上限同步抬到 30MB |
| 单次上传 | 5 个 | 与「一轮对话挂 5 个文件」的用户心智一致 |
| 单会话累计 | 20 个 / 100MB | 防滥用，超出提示删除旧文件 |
| 直读全文上限 | 200k 字符 | 超过即转 RAG（见 3.4） |
| 解析超时 | 60s | 超时标 FAILED 可重试，不阻塞会话 |
| PDF 扫描件判定 | 每页平均字符 < 50 且总页数 ≥ 3 | 经验阈值，日志留实际值便于回调 |
| 扫描件转图像 | 最多 20 页、每页长边 1568px | 控视觉 token 与费用；超出只处理前 20 页并在清单标注 |

#### 3.3.1 视觉直读（已定口径：图片与扫描件都走这条）

统一成一条链：**图片 / 扫描件页 → 视觉模型 → 文本 → 与普通附件同一条注入路径**。

| 环节 | 做法 |
|---|---|
| 模型选择 | 读 `llm_provider_model.capabilities.input` 里含 `image` 且 `enabled=1` 的模型择一（优先 dashscope qwen-vl 系，其次 anthropic / openai）；**不复用规划者模型**，避免把每轮澄清成本抬到视觉档 |
| 传输通道 | Spring AI `UserMessage` + `Media`（`MediaFormat.IMAGE_PNG/JPEG`，base64 内联）。这是平台**首条多模态通道**，需在 provider 适配层补齐（`spring-ai-openai` 与 `spring-ai-anthropic` 都已支持，不新增依赖） |
| 调用形态 | 单图一次调用，输出分两段：「客观描述」+「图中全部可读文字」；扫描件按页批量（每批 ≤ 5 页）后拼接，保留 `[Page N]` 锚点 |
| 落库 | `extracted_text` 存转写结果，`parser=vision`，`parse_status=READY`；原图仍存对象存储供预览 |
| 降级 | 无可用视觉模型 / 调用失败 / 超费用闸 → `parse_status=SKIPPED`，清单显式写「图片未识别」，Prompt 条款要求不得臆测（不静默当空文件） |
| 费用闸 | 每会话每日视觉调用次数 + 单文件页数双上限，超限走 SKIPPED 并提示 |

> 为什么选视觉而不是 OCR：OCR 对截图（UI 稿、报错弹窗、图表）只拿到文字，丢掉布局与颜色语义，而这类截图正是需求澄清里最常见的图片输入。代价是必须先把多模态通道建起来——它同时是后续「子任务执行带图」的前置能力，属一次性投入。


### 3.4 注入策略（三层，按预算降级）

新增模板变量，CLARIFY / CHAT / FINALIZE 三模板统一（与 N-012 的 Context 分层一致）：

```
{{ATTACHMENT_MANIFEST}}     恒注入：文件清单表（名称/类型/大小/页数/解析状态/是否已入检索）
{{ATTACHMENT_CONTEXT}}      小文件全文层（复用 G-016 限额：单文件 64k、合计 200k 字符，超限截断标注）
{{ATTACHMENT_RETRIEVAL}}    大文件检索层（按当前用户消息 embedding → top-k → 带 chunk 锚点）
```

分层规则：

| 场景 | 处理 |
|---|---|
| 文本总字符 ≤ 200k | 全部进 `{{ATTACHMENT_CONTEXT}}`，顺序按上传顺序，每文件前加 `### 附件 i：文件名（页数/字符）` |
| 有文件 > 64k 或超总计 | 该文件 **ingest 到 kb**（`source = chat:{conversationId}:{attachmentId}`），只把 **检索命中片段** 放进 `{{ATTACHMENT_RETRIEVAL}}`，清单里标注「已入检索」 |
| 图片 / 扫描件（视觉转写成功） | 转写文本按普通文本走同一套预算；清单标注 `来源=视觉识别`，Prompt 条款要求「转写可能有误差，涉及数值/条款需注明出处页码」 |
| 解析失败 / 跳过（无视觉模型、超费用闸、类型不支持） | 清单里显式写 `状态=正文不可读（原因）`，并在 Prompt 条款里要求「不得据此臆测内容」（与 G-010 的「缺形态点名驳回」同源，避免模型瞎猜） |
| 无附件 | 三个变量都渲染成「（无）」，保持模板无残留占位符（延续 `ReviewPromptRenderTest` 的反向完备判据） |

**为什么不全塞**：单轮 200k 字符 ≈ 130k+ tokens，DeepSeek 64K 上下文直接爆；而一次澄清往往只看文件的一两节。检索层解决的是「大窗口也塞不下」和「塞了也不准」两个问题。

### 3.5 多轮与引用

- 每条 user 消息落 `requirement_message_attachment`，气泡内显示文件 chip（图标 + 文件名 + 大小，点击预览）
- 后续轮次默认**继续可见**（同一会话的附件集合进 `{{ATTACHMENT_MANIFEST}}`，正文按需检索），与 Kimi「文件跟会话走」一致
- 「引用对话中的文件」= composer「＋」菜单第二组「文件」，列出本会话已有文件；选中即加进本轮 `attachmentIds`（不重新上传）
- 助手回答需要指向 PDF 具体位置时，用 `[附件i#Page N]` 形式；RAG 命中用 `[kb:source#chunkIdx]`，前端渲染为可点标记（`/api/kb/chunk` 已支持）

### 3.6 前端交互（对齐现有「＋」菜单与技能胶囊）

```
＋
├─ 技能       方案整理 / 直接拆解            （已上线）
└─ 文件       添加文件…                      → 系统文件选择器 / 拖拽
              引用本会话文件…                → 子弹层列表（多选）
```

- 已挂文件 → 复用技能的胶囊样式，排在技能胶囊之后；`解析中` 态显示转圈 + 禁发提示（或允许发送但标注「该文件仍在解析」）
- 输入区支持拖拽上传 + 粘贴截图（`paste` 事件取 `image/*`），这两种是最高频入口，比点两次菜单快
- 超限/类型不支持 → 前端先拦（`accept` + `size` 校验），后端再兜（双校验）
- 解析失败 → 胶囊变红 + tooltip 显示原因 + 「重试解析」

### 3.7 安全与成本

| 项 | 措施 |
|---|---|
| 类型白名单 | 扩展名 + MIME + **魔数校验**（`tika-core` 的 `Tika().detect()` 一行搞定，避免改扩展名绕过） |
| 解压炸弹 | 若支持 zip：限制条目数 / 解压后总量 / 递归深度；一期可不支持压缩包 |
| 病毒扫描 | 阶段三接 ClamAV sidecar；当前至少不做可执行文件（`.exe/.sh/.jar` 直接拒） |
| 私有内容提示 | 上传区常驻一句「文件内容会发给模型服务处理」，与 Kimi 同款告知 |
| 越权 | 会话附件按 `conversationId` + 创建者校验；预览/删除走同一条判据，不再复制策略 |
| 成本 | 同会话内按 `content_hash` 去重（同一文件重复上传不重复解析/嵌入）；解析 token 与检索 top-k 全可配 |

## 4. 分期与验收

### P0（可离线，1~2 天）：文本 + PDF 文本层 + 注入

| 项 | 内容 |
|---|---|
| 依赖 | **Tika 4.1.0 子模块**（`tika-core` + `tika-parser-pdf-module` + `tika-parser-microsoft-module`，实测可编译可解析，见 §2.5）；首次引入需一次联网解析，之后照旧 `-o` |
| 后端 | `chat_attachment` 建表 + 上传/清单/删除/预览 4 个端点 + `@Async` 解析 worker（txt/pdf/docx/pptx） |
| Prompt | 三模板加 `{{ATTACHMENT_MANIFEST}}` / `{{ATTACHMENT_CONTEXT}}`，渲染器补两个变量 |
| 前端 | 「＋」菜单加「文件」组、拖拽 + 粘贴、胶囊展示与解析态 |
| 验收 | ① 上传 1 个 2MB PDF（20 页）→ 30s 内 READY，问「第三章讲了什么」回答能对上原文；② 上传 15 个文件触发单次上限提示；③ 30MB 文件被拒且提示可读；④ 解析失败的文件在 Prompt 里被标「正文不可读」且模型不臆测；⑤ 渲染结果无残留 `{{…}}` |

### P1（3~4 天）：视觉直读 + 大文件 RAG + 引用

**P1-a 视觉直读（已定口径，图片与扫描件共用）**
- provider 适配层补多模态：`ModelCapabilities.input` 含 `image` → `UserMessage(Media)`
- 图片 → 视觉转写（描述 + 全部可读文字）；扫描件 → PDFBox 渲染页 PNG（≤ 20 页）→ 分批视觉转写
- 视觉模型按能力表择一（qwen-vl 优先），与规划者模型解耦；费用闸 + 失败降级 SKIPPED
- 验收：上传一张 UI 截图 → 转写文本能看出「这是个登录弹窗、有两个输入框和一个蓝色按钮」，且进澄清时被引用

**P1-b 大文件 RAG + 引用**
- 超预算文件自动 ingest（source = `chat:{conv}:{att}`，幂等覆盖，会话删除时清 source）
- 按当前用户消息自动检索 top-k 注入 `{{ATTACHMENT_RETRIEVAL}}`
- 回答里 `[kb:source#chunk]` 可点开原文分片；消息附件关联 + 气泡 chip
- 验收：上传 300 页手册，问其中一个具体参数，回答带可点回源且片段确为原文

### P2（可选）：版面增强

- `DocumentParser` 端口留了第二实现位：Docling sidecar（`docling-serve` HTTP），表格/多栏/公式强的文件按开关路由过去
- 依赖：构建机可联网拉镜像；按需开启，不设默认
- 验收：同一份多栏研报，Tika/PDFBox 与 Docling 输出并排对比，表格列结构不散

### 明确不做（本轮）

- 文档级 ACL / 团队共享文件库（会话级够用）
- PDF 高保真版面还原（表格散架问题交给 P2 的 Docling sidecar 可选件）
- 外置向量库（pgvector 已够，ADR-002 §7 同库同事务是刻意选择）

## 5. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 规划者模型是纯文本（DeepSeek） | 图片必须靠视觉通道转写，多一次调用 | 视觉与规划者模型解耦（P1-a），转写文本再进澄清；无可用视觉模型时显式 SKIPPED 而非静默空文件 |
| 视觉转写有误差（表格数字、条款编号） | 拿错数值写进验收标准 | Prompt 条款要求「数值/条款须标 `[附件i#Page N]`」，前端展示可点回源；关键信息二次核对提示 |
| PDF 文本层质量差（多栏、表格） | 回答引用错位 | 加 `[Page N]` 锚点；P1 起可切换 Docling sidecar |
| 注入把上下文顶爆 | 澄清质量下降甚至报错 | 严格走 3.4 的分层与预算；`extracted_chars` 落库可观测 |
| 附件与会话生命周期不一致 | 孤儿对象/脏数据 | 会话删除级联软删 + 定时对账（与 G-017 悬空附件对账同源，可合并做） |
| 新会话首句上传的归属 | 文件丢归属 | `client_token` + 建会认领，未认领的按 TTL 清理 |
| 离线构建 | 依赖拉不下来 → 主线打包被卡 | P0 引入 Tika 4.1.0 时**第一次允许联网**一次（之后 `-o` 正常）；若构建机确定长期离线，退回「PDFBox 3.0.5 + POI 5.4.1」实测可离线组合 |
| Tika 4.x API 断代 | 抄 3.x 示例编译不过（`parse` 入参改 `TikaInputStream`）；`spring-ai-tika-document-reader` 仍依赖 3.x，**不能与 4.x 同用** | 本项目直接用 Tika API、不用 Spring AI 的 Tika reader；升级 4.x 后禁止再引 3.x 系 reader |
| 依赖版本漂移 | Tika 4 带入 `pdfbox 3.0.8` / `poi 5.5.1` / `jackson 2.22.3`，与项目固定版本可能不一致 | 解析路径实测在项目 jackson 2.18.4.1 下正常；PDFBox 以 Tika 带入版本为准，不另行声明 |
| PDFBox 线程安全 | 并发解析偶发异常 | `PDDocument` 强约束单线程使用，解析 worker 内部串行 per-document，线程池隔离 |

## 6. 已定口径（2026-10-22 拍板）

| 项 | 决定 | 落地含义 |
|---|---|---|
| 解析路线 | **纯 Java 为主，Docling 留接口位** | P0 用 Tika 4.1.0 子模块（core + pdf + microsoft）；`DocumentParser` 端口留第二实现位，Docling sidecar 不排期 |
| 图片与扫描件 | **视觉模型直读** | 需新建平台首条多模态通道（`Media`）；视觉模型与规划者解耦；失败降级 SKIPPED，不静默当空文件 |
| 限额 | **单文件 20MB / 单次 5 个 / 单会话 20 个、累计 100MB** | multipart 上限抬到 30MB；解析超时 60s；扫描件转图 ≤ 20 页 |

> 与 §2.5 的关系：解析路线确定"纯 Java"后，Tika 版本选择也随之确定——**4.1.0 子模块组合**（50 条 classpath、单一解析 API、自带魔数检测），而不是全聚合包（87 条）或裸 PDFBox+POI（只覆盖两类）。
