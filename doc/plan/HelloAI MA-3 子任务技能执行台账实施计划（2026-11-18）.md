## 0. 定位与边界（★先读）

### ① 问题来源

| 来源 | 具体指向 |
|---|---|
| `design/HelloAI 深度审核改造蓝图.md` §4 `MA-3` | 八项改造的第 3 项 |

| `SL-5`（`SandboxCallLedger`）的局限 | 进程内内存台账，重启即清空；只有 `callId` / 命令前缀 / `exitCode` / `origin` / `round` / `at`，**无 `skillName`** ⇒ 不能作为跨会话统计源 |
| 实际运维痛点 | 「这个技能到底提升了多少成功率」无法回答；技能包该保留还是淘汰只能靠感觉 |

### ② 本计划做什么

**一句话目标**：让**每一次技能执行**（成功 / 失败 / 超时）都在库里留一行，且带 `sub_task_id` 可 join。

四条具体产出：

1. 新建表 `sub_task_skill_run`（子任务维度技能执行台账）；
2. 收口技能执行**唯一入口**的签名，使 `subTaskId` / `taskId` / `agentId` / `round` **全部显式入参**；
3. 在 `finally` 里 best-effort 落库（独立事务），**写失败绝不影响技能执行结果**；
4. 提供按 `sub_task_id` / `task_id` 查询的基础能力（mapper 方法），不做报表、不做界面。

### ③ 本计划不做什么

| 不做 | 为什么 | 依据 |
|---|---|---|
| **不复用 / 不修改 `chat_skill_run`** | 它在 **planner 澄清域**（`planner/entity/ChatSkillRun.java`，自述「对话内技能执行运行记录」），语义是「用户在对话里点了技能」；往上加 `sub_task_id` = 一张表两种语义，即「一列两义」反模式 | 判据 3（枚举/归因纪律）+ 蓝图 §4 `MA-3` ⑤ |
| **不做报表 / 不做看板 / 不做前端页面** | 本计划交付的是**数据契约**。报表要有消费场景再做；现在做界面等于给空表做 UI | 判据 2 |
| **不改 `SandboxCallLedger`** | 它是「当前子任务内引用证据」的进程内台账，服务模型不同（引用 vs 统计）。**两者并存，不是重复** | `SL-5` 设计目的 |
| **不记完整命令** | 完整命令可能含密钥 / 令牌。只记前 200 字符前缀，与 `SandboxCallLedger` 同口径 | 安全边界，`SL-5` 既有口径 |
| **不记录非技能命令** | `internal_run_in_sandbox` 跑的是随手命令，不是技能执行。混进来会让「技能成功率」失真 | 一张表一种语义 |
| **不做保留期清理任务** | 表增长策略要等真实数据量；先记录，量级明确后再定清理 | 避免过早优化 |
| **不改沙箱执行链** | `sandboxExecutionService.execute(...)` 一行不动，只在外层包计时与落库 | 协作规约 §2.1 最小改动 |

### ④ 诚实边界

**落地后仍有以下不成立**：

1. **上线前的历史数据永远缺失**。报表必须能区分「没跑过」与「没记录」，只能以上线时间为切点。**这不是缺陷，是不得不接受的事实。**
2. **`task_id` 是冗余列**（从 `sub_task_id` 可 join 得到）。这是刻意的反范式取舍（报表按任务聚合时省一次大表 join），代价是**两处可能不一致**——写入时从同一份事实取，不做二次查询。已在迁移注释里写明理由。
3. **`command_prefix` 不是命令指纹**。截断到 200 字符，长命令的差异可能落在截断之后 ⇒ **不能用来判断「同一条命令」**。要判重必须用 `ExitCode` + `skill_name` + `round` 组合。
4. **技能包注入失败（`ensureInstalled` 失败）不落台账**。它发生在 `execute` 之前、属于「没跑起来」；要不要记成一次尝试是产品口径问题，本期**不记**，登记为待定。
5. **沙箱未启用时表恒为空**。`internal_run_skill` 被 `SkillExecutionToolContributor` 从模型可见列表摘除，空表是**正常状态**，不是故障。

## 2. 现状（勘察结论，`[实测]`）

勘察日期 **2026-11-18**。行号会漂移，实现前以**方法名**为准。

### 2.1 技能执行唯一入口（改造半径极小的根本原因）
| 位置 | 事实 |
|---|---|
| `core/agent/runtime/sandbox/impl/SkillExecutionSupport.java` `run(Long subTaskId, SkillTarget target, String command, Integer timeoutSeconds, int round)` | **生产代码唯一调用点**：`InternalLlmExecutorTools.java:701`（全仓 grep 确认，另一处命中是单测 mock） || 同上 `SkillTarget(name, version, spec)` | `name` / `version` 都在，**版本号无需额外查询** |
| 同上，内部实现 | 只做两步：拼 `cd <rootDir>; export TMPDIR=...` 包装 + 转调 `sandboxExecutionService.execute(subTaskId, spec, wrapped, timeout, EXECUTOR, round)` |
| `core/agent/runtime/sandbox/ExecuteResponse.java` | `record ExecuteResponse(String output, int exitCode, boolean truncated, String callId)`；`EXIT_CODE_TIMEOUT = 124`、`EXIT_CODE_ERROR = -1`；`succeeded()` = `exitCode == 0 && !truncated` |

> **口径订正（2026-11-18 实现时更正）**：「生产代码唯一调用点」不成立——全仓共有**两处**：
> ① `InternalLlmExecutorTools`（内部执行链，`scopeId = subTaskId`，**落台账**）；
> ② `SkillPackageExecutionServiceImpl.run(skillName, scopeId, ...)`（业务面对话技能执行，
> `scopeId` 是**会话级工作区键、不属于任何子任务**，其记录在既有 `chat_skill_run`，**不落本台账**）。
> 因此 `SkillRunContext` 比原计划多一个 `scopeId` 字段，并提供两个工厂：`ofSubTask(...)` / `ofConversationScope(...)`。
> 若把两者塞进同一字段，台账会写出一批「子任务 ID = 会话 ID」的假行。

## 4. 关键设计决策

| 决策 | 选了什么 | 为什么不选另一种 |
|---|---|---|
| 表的归属 | **新建 `sub_task_skill_run`**，放 `agent` 域 | `chat_skill_run` 在 planner 澄清域、语义是「对话里点技能」；加 `sub_task_id` = 一列两义。且新表成本只是「一条迁移 + entity + mapper」，比改一张有 5 个读方的表安全 |
| 埋点位置 | **`SkillExecutionSupport.run`**（唯一入口） | 埋在工具层（`internalRunSkill`）会漏掉将来任何新入口；判据 1「穷举所有入口」，埋最里层才不漏 |
| 身份字段传递 | **显式入参 `SkillRunContext`**，不走 `ToolInvocationContext` ThreadLocal | `SkillExecutionSupport` 是编排门面，不该知道工具调用上下文；隐式依赖会让这个类无法在非工具场景复用。且 ThreadLocal 在异步 / 线程切换时会静默失效 |
| 事务 | **`REQUIRES_NEW` 独立事务** | 技能执行可能在外层事务内（`submitResult` 链路），共用事务会让「业务回滚 ⇒ 台账也回滚」，而台账需要如实记录「跑过但失败了」。这也是 `SubmissionActivityRecorder` 的既有理由 |
| 失败也记 | **success / 非零退出 / 超时 / SDK 异常全部记** | 只记成功 ⇒ 失败率永远算不出来，而失败率是技能能不能用的核心指标 |
| `task_id` 冗余 | **冗余一列**，写注释说明 | 报表按任务聚合时 `sub_task_id → task_id` 的 join 在大表上多余。反范式取舍，代价（两处可能不一致）显式登记 |
| 记 `command_prefix` | 只记前 200 字符 | 完整命令可能含密钥；`SandboxCallLedger` 已确立此口径，沿用不发明 |

## 6.1 实现记录（2026-11-18，落地后订正）

**结果**：`MA3-1`~`MA3-6` 全部落地；`SkillRunLedgerTest` 8 例 + `InternalLlmExecutorToolsTest` 43 例全绿；
本地库已手工执行 `V152` 正文（幂等）并实测：建表 + 两条索引齐全、按 MyBatis-Plus 的列清单 insert 成功
（含 `round` 列，PG 非保留字，无需引号）、聚合 SQL 结果正确。

**实现中确认/更正的事实**：

| # | 计划里怎么写的 | 实际是什么 | 处置 |
|---|---|---|---|
| 1 | `SkillExecutionSupport.run` 只有一处调用点 | **两处**（多一个业务面对话技能执行） | `SkillRunContext` 增 `scopeId` + 两个工厂，见 §2.1 口径订正 |
| 2 | `record SkillRunContext(subTaskId, taskId, agentId, round)` | 加 `scopeId` 后才能同时表达「按子任务复用沙箱」与「按会话复用沙箱」 | 五个分量，`subTaskId == null` ⇒ 不落台账 |
| 3 | 只列了 `exit_code` / `command_prefix` / `duration_ms` | 另加 `truncated` / `call_id` | 截断的成功与完整成功必须能分开统计（与 `ExecuteResponse.succeeded()` 同口径）；`call_id` 与 `SandboxCallLedger` 互查 |
| 4 | 未定义「`execute` 直接抛异常」怎么记 | 记 `exit_code = -1`（即 `EXIT_CODE_ERROR` 的既有语义），异常照旧外抛 | 台账在 `finally` 里写，所以「抛了异常」同样留痕 |

**表的可用性验证（本地库实测，非推演）**：

- `pg_indexes` 结果 = `idx_stsr_sub_task_id`、`idx_stsr_task_id`、`sub_task_skill_run_pkey`；
- 用 MyBatis-Plus 同款列清单 `INSERT`（含未加引号的 `round`）成功，随后按 `task_id + skill_name` 聚合
  得到 `total=1 / succeeded=1`，清理后表行数回到 0。

**仍未做（明确属另一批）**：`SK-1` 技能效果报表 / 看板 / 前端页面；保留期清理任务；
`ensureInstalled` 失败是否记为一次「尝试」（产品口径待定，本期不记）。
