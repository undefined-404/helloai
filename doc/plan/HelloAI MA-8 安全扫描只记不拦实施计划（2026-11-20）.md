### ② 本计划做什么

**一句话目标**：在四条最可能把用户密钥带进模型 / 带出产物 / 进知识库的链路上，加一层**只记录、不阻断**的敏感内容扫描——命中时写一条时间线事件，payload 只留「规则名 + 偏移 + SHA-256 指纹」，**结构上不含原文**。

四条具体产出（对应 §3 任务表）：

1. **规则集唯一事实源**（`SensitiveScanRule`，7 条）与**挂点枚举**（`SensitiveScanPoint`，4 个）；
2. **纯判据组件** `SensitiveContentScanner`（不脱敏、不阻断、不打日志），含校验位算法抗误报；
3. **唯一「扫 + 记」入口** `SensitiveScanRecorder`（绝不抛出 + payload 无原文位）；
4. **四挂点接线**：用户消息入库 / 子任务产物落库 / LLM 出站 prompt 装配 / **附件正文进 prompt 前（2026-11-20 追）**。

### ③ 本计划不做什么

| 不做 | 为什么 | 依据 |
|---|---|---|
| **不做拦截（fail-close）** | 误报会直接卡住正常业务，比不做更糟。第一版只产生事件 + 日志 | 蓝图 §2.2 `MA-8` 停止条件；判据 9（约束强弱看 fail-open/fail-close） |
| **不做脱敏 / 打码** | 脱敏会让「原文」这条事实在链路上消失，反而无法判断误报；且改写用户内容属于未授权的语义变更 | 蓝图 §4 `MA-8` ⑤ |
| **不记录原文（任何形态）** | 扫描器如果把原文写进日志 / 事件 payload，**它自己就变成新的泄露源**。只留 SHA-256 指纹用于「同一份泄露是否重复出现」的聚合 | 判据 4（同一事实双写必分叉）+ 本条自身的安全语义 |
| **不做 `MA-9` 的询问 / 恢复** | 那是 `MA-9`；本项一旦开始问用户就变成本项无法独立回滚 | 蓝图 §4 `MA-9` 定位 |
| **不加第三方 DLP 库** | 引入依赖会让「规则集即判据源」这件事跑出仓外，`MA-9` 查表就失去单一事实源 | 蓝图 §4 `MA-8` ⑥ |
| **不扫 system prompt / 历史消息全文** | system 段是平台模板（不可能含用户密钥）；历史消息已在对话域被扫过。全扫纯属浪费且拖慢主链 | 判据 1（规则存在≠全路径强制，必须说清覆盖边界） |

### ④ 诚实边界

1. **本项不拦任何东西**。命中只写事件与日志，链路照常执行——「泄露」仍然会发生，只是**开始被记录**。
2. **误报率是未知数**。6 条规则的判据精度靠「校验位 + 词边界 + 载荷长度」压低误报，但真实分布要靠观察期采出；在观察期结论出来前，本项**不标「已完成」**。
3. **规则覆盖有限**。6 条规则只覆盖「高置信度的结构化密钥形态」，不覆盖自定义口令、内部代号、非标准格式的凭据——这不是缺陷，是刻意的精度取舍。
4. **`MAX_SCAN_CHARS` 截断**意味着超长文本尾部不被扫描；`truncated` 标记会被记进事件 payload 以便事后识别。

勘察日期 **2026-11-20**。以下行号会漂移，实现前以**方法名**为准重新定位。

### 2.1 现状：完全空白

| 位置 | 行为 |
|---|---|
| 全仓 grep `id_card` / `bank_card` / `api_token` / `private_key` / `LTAI` / `AKIA` | **零命中**——无任何扫描 / 检测实现 |
| `core/shared/util/` | 已有 `DeliveryEvidenceEvaluator` 这类「纯判据组件」先例（`MA-4` 建），但无敏感内容判据 |
| 产出链 `ExecutionResultHandler.handleReport` | 直接把 `report.getOutput()` 落库，无任何内容检查 |
| prompt 装配 `AgentRuntimeContextAssembler` | `userPrompt` 装配完直接进 `AgentLoopInput`，无检查 |
| 消息入库 `RequirementMessageServiceImpl.addMessage` | 四条路径（澄清 / 助理 / 流式 / 编辑重跑）共用，无检查 |

### 2.2 挂点选择依据（为什么恰好这四个）

| 挂点 | 落点 | 为什么是这里（而不是别处） |
|---|---|---|
| `INPUT` | `RequirementMessageServiceImpl.addMessage` 的 `"user".equals(role)` 分支 | 澄清 / 助理 / 流式 / 编辑重跑四条路径都经此。**挂在各 Controller 会漏「编辑消息重跑」**（判据 1：规则存在≠全路径强制，必须穷举入口） |
| `ARTIFACT` | `ExecutionResultHandler` 成功分支 | 子任务产物落库的唯一写点。扫 `output` 而非 `parts` 全文：`parts` 可能含多份大文件正文，逐份全扫会拖慢提交主链 |
| `LLM_OUTBOUND` | `AgentRuntimeContextAssembler` 的 `userPrompt` 装配之后 | 覆盖最易漏的一条路径——**依赖产物把上游密钥传到下游**。扫 `userPrompt` 而非整条消息数组：system 段是平台模板（不可能含用户密钥），历史消息在对话域已被 `INPUT` 覆盖 |
| `ATTACHMENT`（2026-11-20 追） | `ChatAttachmentParseWorker.parse` 的 `markReady` **之前** | **三洞实测**：对话/澄清链附件正文经 `ChatAttachmentPromptRenderer` 的 `{{ATTACHMENT_CONTEXT}}` 拼装绕过 `LLM_OUTBOUND`；`internal_read_attachment` 直读对象存储亦绕过；`INPUT` 只扫消息 content 不扫附件。`markReady` 之后正文即注入 Prompt / ingest 进 KB ⇒ `markReady` 前是唯一能拦到附件完整原文的位置 |

### 2.3 抗误报的判据设计（为什么不是纯正则）

| 规则 | 抗误报手段 | 不这么做会怎样 |
|---|---|---|
| `ID_CARD` | 必过 **GB 11643 校验位**（`ID_WEIGHTS` + `ID_CHECK_CODES`） | 18 位订单号 / 快递单号 / 设备号会全部命中，误报率接近 100% |
| `BANK_CARD` | 必过 **Luhn 校验** | 16 位任意数字（时间戳、主键）会全部命中 |
| `MOBILE` | 词边界 + 11 位 + `1[3-9]` 前缀 | 长数字串的中间 11 位会命中 |
| `PRIVATE_KEY` | PEM 头字面量 | 几乎无假阳性 |
| `CLOUD_AK` | 厂商前缀白名单（阿里云 `LTAI` / 腾讯云 `AKID` / AWS `AKIA`·`ASIA`） | 泛化「20 位大写字母数字」会命中一切 ID |
| `API_TOKEN` | 前缀 + **足够长的载荷**（`sk-learn` 这类短词不命中）；前缀按**长到短**排列（`sk-ant-` 先于 `sk-`） | `sk-` 单独匹配会把变量名 `sk-learn`、`sk-image` 全判成密钥 |
| `CONFIG_SECRET`（2026-11-20 追） | 只认**键值赋值**形态（`password`/`secret`/`token`/`api_key` 等键后紧跟 `=`/`:` + 值载荷 ≥4 位）；排除占位值（`changeme` / `xxx` / `$VAR` 引用 / 空值 / `<占位>`) | 配置文件名 / 变量名本身含 `secret` 字样常见，单认关键词会整文件误报；只认赋值形态把误报压到「确实存在一个密钥字段」 |

### 2.4 现状结论

`[实测]` **结论**：判据所需的数据源全部现成（链路上文本已在手边），无需新增表 / 无需新增查询。工程量集中在 `common`（常量 + 配置）+ `core`（两个组件 + 三处接线），**零 schema 变更**。

## 4. 关键设计决策

| 决策 | 选了什么 | 为什么不选另一种 |
|---|---|---|
| 组件形态 | **纯判据 + 独立记录器**（判据不依赖 Spring 上下文，记录器负责 I/O） | 把扫描与写事件塞进一个组件，判据就无法被单测直接用「纯函数」方式验证（与 `DeliveryEvidenceEvaluator` 同范式） |
| `enabled` 默认值 | **`true`** | 默认 `false` 意味着部署后零数据——观察期永远开始不了。log-only 本身零行为变化，默认开没有风险 |
| 命中信息形态 | **规则名 + 偏移 + SHA-256**（无原文） | 存原文等于让扫描器成为新的泄露源；不存指纹则无法判断「同一份泄露是否在多个挂点重复出现」 |
| 规则名解析 | `parseDisabled` 返 `ParseResult(disabled, unknown)` | 静默忽略写错的规则名，会让运维以为「关了 A 规则」实际没关 |
| 挂点① 位置 | `addMessage` 的 user 分支 | 挂各 Controller 会漏「编辑消息重跑」（判据 1） |

## 5. 风险与回滚

| 风险 | 处置 |
|---|---|
| 扫描拖慢主链 | `maxScanChars=8000` 上限 + `MAX_HITS_PER_RULE=8` 早停；`scanAndRecord` 全 try-catch，异常不穿透 |
| 误报刷爆时间线 | `MAX_HITS_IN_PAYLOAD=12` + `ruleCounts` 聚合；`enabled=false` 即刻全关（一行配置，无需回滚代码） |
| 正则灾难性回溯 | 6 条规则均为定长 / 短前缀形态，无嵌套量词；`PRIVATE_KEY_HEADER` 用 `[A-Z0-9]{0,32}` 有界量词 |
| `group(1)` 漏写致崩溃 | **已修**：模式加捕获组 + `collect()` 改为 `groupCount() >= 1 ? 1 : 0`——「漏写括号」退化为精度损失而非运行期崩溃（判据：观测不得伤主链） |

**回滚**：`helloai.sensitive-scan.enabled=false` 一行配置即回到改造前行为（组件仍在，但不再扫描）。代码层无需回滚。

## 6. 实现记录与观察期

### 6.1 实现记录（2026-11-20）

全部 9 项已完成。**关键实现取舍**：

1. **规则前缀按长到短排列**：`API_TOKEN` 的 `sk-ant-` 必须先于 `sk-` 匹配，否则 `sk-ant-xxx` 会被切成 `sk-` + `ant-xxx` 两段，载荷长度校验失效。
2. **`collect()` 的 group 兜底**：初版 `PRIVATE_KEY_HEADER` 模式未写捕获组而 `collect()` 硬取 `group(1)` ⇒ `IndexOutOfBoundsException: No group 1`（20 例中 1 例报错）。双保险修复：① 模式加捕获组；② `collect()` 改成 `matcher.groupCount() >= 1 ? 1 : 0`。**后者才是真正的纪律**——观测组件不得因为一条规则写错就崩掉整条扫描。
3. **`sha256Hex` 手写十六进制**：用 `Character.forDigit` 而非 `String.format`，避免格式化开销；`NoSuchAlgorithmException`（SHA-256 必然存在，但签名要求处理）返回空串不抛。
4. **挂点② 扫 `output` 而非 `parts`**：`parts` 可能含多份大文件正文，逐份全扫会显著拖慢提交主链；`output` 是模型自述正文，是密钥泄露最可能的载体。
