## 0. 定位与边界（★先读）

**① 问题来源**

- **用户裁定（2026-10-26）**：选 C 档「让平台自己成为会用它的 Agent」，并追问核心问题——「这技能需要沙箱、内置浏览器、nodejs，不是简单 `skills.md` 能实现的，如果把它变成内置技能、单独处理，还会涉及架构变动么」。
- **本次调查结论**：技能**机制层**不用改（9 字段白名单 / zip 闸门 / `body` 单 TEXT / 速览渲染）；**执行通道层缺四块接线**；`G-005` 条件②真实命中。
- **前文结论**：技能加载 ≠ 技能执行（`REF-8.3` 已交付加载、无执行通道）；凭据主密钥红线——app 容器必填 `HELLOAI_CREDENTIAL_AES_KEY_BASE64`（`docker-compose.server.yml:317`），可解 `credential_vault` 全量供应商 Key ⇒ 第三方脚本不得共享 app env / 网络。
- **差距表锚点**：`G-005`（Sandbox Provider，**条件②命中**）；已完成相邻项 `G-004`（Skill Capability）、`G-022`（技能 ↔ 模型能力引用边）。
- **起点事实**：`internal_run_in_sandbox` 只能执行调用方传入的命令；`execute(...)` 无 spec / image 参数；无「技能包 → 沙箱」文件注入通道；产物回读只认「最大一份 `.md`」（本文 §2.3 第 13~21 条）。

**② 本计划做什么**

把「一份带运行时目录的技能包」变成平台内部 Agent 可实际调用的执行面——**平台自持执行，不依赖外部 Agent 的工具链**。五项产出：

1. **镜像基线**：固定一个预装 `node >= 18` 的沙箱镜像，并把 `node` 版本、资源规格、`spawn` 行为三者实测落定（`SKX-1`~`SKX-2`）。
2. **注入形态**：确定 158 文件进沙箱的通道（逐文件 `writeFile` 还是 `tar` 一次搬运），带耗时与失败率实测（`SKX-3`）。
3. **技能包入库**：把 Archify 裁剪到出图必需的目录集，以版本锚 + 清单 + 许可入库（`SKX-4`）。
4. **四块接线**：沙箱规格按调用分层（`SKX-5`）、技能包文件注入（`SKX-6`）、产物按指定路径回传（`SKX-7`）、工具面新增技能执行入口（`SKX-8`，**生效开关**）。
5. **验收与登记**：C1 档跑通三段门禁并验证回执可作完整性证据（`SKX-9`），再把 `G-005` 条件②命中与四块接线的落地状态回填（`SKX-10`）。

**（2026-10-27 追加）交付后暴露的四类问题，本计划承接范围扩为九项**：

6. **拿到手**：产物导出为可下载附件（`SKX-11`）⇒ 对话内选技能当场出图（`SKX-12`）。
7. **不让人等**：执行异步化，把 377s 从 HTTP 线程摘出去（`SKX-13`）。
8. **少走重试**：spec 落库前预校验 + `$ref` 内联（`SKX-14`）。
9. **装得上**：部署面收口，`SANDBOX_*` 在两条部署路径都贯通（`SKX-15`）。

**③ 本计划不做什么**（边界，防越界）

1. **不新建「技能运行时」第二套引擎** —— 技能的执行是沙箱的事，不是新引擎的事。依据：`research/Octop全库借鉴分析_综合版.md` §4；本次调查 §7.1。
2. **不在 app 容器内 `ProcessBuilder` 跑第三方脚本** —— app 容器持有可解全量供应商 Key 的凭据主密钥。依据：前文 §4 凭据主密钥红线；`D-2026-10-09-4③`（不走 `docker.sock` / 宿主能力挂载路线）。
3. **不装 Chromium、不实现 `browser-check`** —— 用户裁定 C1 先行。依据：本次调查 §4.2；代价见本文件 ④。
4. **不用 Java 重写 archify 渲染器** —— 275KB `archify.mjs` + 11 类渲染器 + 12 份 schema，等价于重写上游并永久失去同步能力。依据：本次调查 §7.3。
5. **不把 Archify 塞进 `skills/plugins/*.md`** —— frontmatter 三处硬冲突（`license` / `metadata` 未知 + 顶层缺 `version`），且塞进去只能得到一份说明书。依据：本次调查 §2.6 + §7.4。
6. **不改技能加载机制**（9 字段白名单 / `skill-package-manifest.md` 清单名红线 / zip 闸门限额 / `body` 单 TEXT / 速览截断）—— 加载与执行正交。依据：前文 §2；本次调查 §3.1。
7. **不做技能商店 / 多租户技能市场 / 技能版本灰度** —— 无需求来源。依据：本计划唯一驱动是「让平台自己会用 Archify」；越界扩张属《治理规则》§3.2 明令防的两类事故之一。
8. **不在本计划内接入第二个技能** —— 先把一个包跑通全链，第二个包的可行性由第一个的结果判断。依据：本次调查 §6 三项待核事实未定前，任何「通用化」都是猜测。
9. **不改 `internal_run_in_sandbox` 的语义** —— 它仍是「执行本调用传入的命令」，技能执行走新入口（`SKX-8`）。依据：既有工具已在业务中被使用，改语义会波及 `S-9` 机械判定（`FinalReportFidelityGate`）。

**④ 诚实边界**

- **C1 档 ≠ 视觉已验证**：`validate` / `deliver` / `check` 三段通过只证明静态校验与产物结构，**不证明**真实浏览器下的布局与溢出。任何产出说明都必须写「自动化检查通过；未经视觉复核」——`SKILL.md` 承诺的四段齐全在跳过第四段时**不成立**。
- **`G-005` 条件②命中是本计划的直接后果，不是副作用**：本计划一旦落地，平台就在执行技能脚本。条件①/③仍不成立（无新增碰宿主工具、平台不自持浏览器）。
- **镜像就绪 ≠ 技能可用**：`SKX-4` 入库了包但 `SKX-8` 未交付时，模型仍然调不到它——判断「本计划是否生效」的唯一标准是 `SKX-8` 的状态，不是 `SKX-4`。
- **容器内 `spawn` 行为未验证前，不能保证 archify 在沙箱内跑通**：本次实测用的是**未打补丁的上游版 + 普通 Windows**，而本地补丁副本自述受限宿主会以 EBUSY 拒 pipe-stdin 子进程。`SKX-2` 的结论决定是否带宿主补丁。
- **`SandboxSpec` 的三个字段目前未被执行服务消费**：`resourceLimits` / `networkPolicy` / `scope` / `entrypoint` 只被声明，`Sandbox.builder()` 只拿到 `image`（本文 §2.3 第 15 条）。`SKX-5` 若只换 image 字符串而不喂 builder，「规格分层」是假的。
- **产物回传的价值上限由 `readFile` 的大小天花板决定**：若 SDK 单次读取有上限而 HTML 又超限，只能退化为分段读，此时「一次拿到完整产物」不成立（`SKX-7` 待测）。
- **只覆盖 Archify 一类技能**：需要 `npm install`、需要联网拉包、需要 GUI 的技能不在本计划的可行性结论范围内。
- **技能包入 jar 会增大部署物**：裁剪后预计 4~6MB（`examples/` 13MB 剔除）。多包并存时需重新评估「入 jar vs 挂载」，`SKX-4` 须记录实际体积。

## 4. 关键设计决策

### 4.1 产物回传走 SDK `files().readFile`，不走命令输出通路

**结论**：`readArtifact` 用 `sandbox.files().readFile(...)`。

**理由**：命令输出通路有 `MAX_OUTPUT_CHARS = 100_000` 全局截断（`OpenSandboxExecutionService.java:66` / `:319-322`）；834KB HTML 经 base64 膨胀后约 1.1MB 字符，**必然**被切断，且切断点是任意字节，解码会直接失败（现有 `decodeWorkspacePayload` 已把「疑似输出被截断」列为解码失败的常见原因，`:246-251`）。分段读虽可行，但要拼多次往返 + 临时文件，复杂度与失败面都更高。`files()` 三件套已在探针验证可用（§2.3 第 18 条），不经命令通路。

**被否方案**：① 提高 `MAX_OUTPUT_CHARS` —— 会放大所有命令输出的内存与日志压力，为一个技能改全局闸门不划算；② 命令内 `base64` 分块 + 多次 `execute` —— 受单次 300s 上限与 100K 字符双重约束，834KB 要 12 轮以上，且中间失败无法断点续传。

**待核**：`readFile` 的单文件上限未测。若低于产物大小，退化为「分块写临时文件 + 逐块 `readFile`」，并在 `SKX-7` 明确记录。

### 4.2 槽 key 必须带规格指纹

**结论**：`SandboxSlotPool` key 由 `Long(subTaskId)` 改为复合键 `(subTaskId, specFingerprint)`。

**理由**：`ADR-005` 的复用语义是按 `subTaskId` 缓存。引入 per-call spec 后，同一子任务内「先 python 验算、再 node 出图」会命中同一槽——**拿到的是 python 镜像的容器**，`node` 不存在（§2.3 第 16 条）。这不是极端场景：`SKX-9` 的验收流程本身就是多命令复用同一子任务。

**代价**：`release(subTaskId)` 的语义从「销毁一个槽」变为「销毁该子任务的所有规格槽」，`SandboxSlotPool` 需要新增批量移除能力；内存上同子任务最多驻留「规格数」个容器，需在 `release` 兜底之外确认空闲淘汰仍生效。

### 4.3 技能包入 classpath，不做外部挂载

**结论**：包随代码进 jar（`resources/skills/packages/<name>/<version>/`）。

**理由**：① 离线部署——`docker-compose.server.yml` 拓扑无外网，包不能运行时下载；② 版本可追溯——包版本随 git 提交走，与代码同源；③ 与既有纪律一致——新能力默认关闭、通过配置注入启用（`REF-6.13`），挂载目录需要运维在部署脚本里额外准备，增加部署面对齐成本。

**代价**：jar 增大 4~6MB（裁剪后）。若将来多包并存（5 个以上），需重新评估；本计划在 `SKX-4` 记录实际体积作为该判断的输入。

**被否方案**：对象存储 + 运行时下载（引入外部依赖、离线部署不可用）；宿主目录挂载（运维面成本 + 与 `D-2026-10-09-4③` 不走宿主能力的方向相悖）。

### 4.4 C1 档的对外表述纪律

**结论**：所有产出说明必须写「自动化检查通过；未经视觉复核」。

**理由**：`SKILL.md` 明写「A passing receipt proves the included `validate`, `deliver`, strict `check`, and real-browser `browser-check` gates passed」。跳过第四段时该承诺**不成立**——回执里也确实没有 browser-check 的记录。这是本次调查 §4.2 的诚实标注，属于硬约束而非措辞偏好。

**执行点**：`SKX-8` 的工具描述、`SKX-9` 的验收记录、以及未来任何对外说明。

### 4.5 新增工具不触发的论证（防后人误判）

**结论**：`SKX-8` 新增 `internal_run_skill` **不触发 `G-005` 条件①**。

**理由**：前文 §5 钉死的机械判据是「平台侧是否出现一个 *agent 可调用* 且 *碰宿主* 的工具」，不看是否进程外。本工具满足「agent 可调用」，但执行发生在 OpenSandbox 容器内——`filesystem=ISOLATED`、零平台凭据 env（`HELLOAI_CREDENTIAL_AES_KEY_BASE64` 绝不进沙箱）、egress 默认 deny、app 不加入沙箱网络 ⇒ **「碰宿主」不成立**。对比先例：`D-2026-10-10-2②` 判 `PgDumpRunner` 不触发，也是同一个判据。

**要求**：该论证必须写进 `SKX-8` 的代码注释，否则下一个人看到「新增了 agent 可调用工具」会重新打一遍排期。

## 5. 依赖与实施次序

```text
SKX-1（镜像基线）──→ SKX-2（spawn 行为）
        │                  │
        ↓                  ↓
SKX-3（注入通道）────→ SKX-4（入库形态）
                           │
                           ↓
SKX-5（规格分层）→ SKX-6（文件注入）→ SKX-7（产物回传）→ SKX-8（工具面，生效开关）
                                                              │
                                                              ├──→ SKX-11（导出为附件）──→ SKX-12（对话直出，已完成）
                                                              ↓                              │
                                                   SKX-9（端到端）→ SKX-10（登记）←──────────┤
                                                                                             │
                                        SKX-13（异步化）←──┬── SKX-14（spec 预校验）──────────┘
                                        SKX-15（部署面）←──┘
```

- `SKX-1` / `SKX-2` 无代码依赖，**可立即开工**；二者都需要真实 OpenSandbox 环境（`helloai.sandbox.opensandbox.enabled=true` + 可达 server）。
- `SKX-3` 依赖 `SKX-1` 的镜像；`SKX-4` 依赖 `SKX-2` 的补丁结论与 `SKX-3` 的注入形态。
- **`SKX-3` ↔ `SKX-4` 的表观循环及解法**：`SKX-3` 需要「裁剪后的包」当样本，而 `SKX-4` 才是入库那一步 ⇒ 看起来互为前置。解法：裁剪口径在 `SKX-4` 动作 1 已写死（只剔 `examples/`+`scripts/`），**实验批先手工裁一份本地样本**（实测 103 文件 / 3.95MB）供 `SKX-3` 用；`SKX-4` 再按同一口径正式入库。两者共享口径，不共享产出。
- `SKX-5`~`SKX-8` 是代码改动，**可并行设计但须顺序合并**：`SKX-8` 依赖前三者的接口签稳定。
- `SKX-9` 依赖全部；`SKX-10` 依赖 `SKX-9` 的结论（登记只能写已验事实）。
- **首个可判断「生效」的节点是 `SKX-8`**，不是 `SKX-4`——包入库了但工具没有，模型照样调不到。
- **`SKX-11` 是 2026-10-26 追加项**（原计划漏判，见该条「为什么追加」）：它依赖 `SKX-7` 的回读能力与 `SKX-8` 的工具面，但**不被 `SKX-9` 依赖**——`SKX-9` 验的是「产物对不对」，`SKX-11` 解决的是「用户拿不拿得到」。两者可并行；若要「用户能看到图」，`SKX-11` 是必经项。
- **`SKX-12`（2026-10-27 追加，已完成）**：依赖 `SKX-11`（有产物才有得下）与 `SKX-6`（注入），**不依赖 `SKX-9`**。它把「用户怎么触发」从「等子任务执行者自己决定」改成「对话里显式选」，与 `SKX-9`（模型自己在工具循环里选）是**并行且不互证**的两条路——这是本文最容易误判的一处，见 `SKX-9` 的口径订正段。
- **`SKX-13` / `SKX-14`（2026-10-27 追加，均未启动）**：都依赖 `SKX-12` 已定的链路（前者改调用形态、后者改输入质量），**互不依赖**，可并行。`SKX-13` 的收益是「用户不再等 377s」，`SKX-14` 的收益是「少走重试」——两者叠加才把最坏耗时压下来。
- **`SKX-15`（2026-10-27 追加，部分完成）**：与代码条目解耦，属部署事实。**它不阻塞 `SKX-13`/`SKX-14`，但阻塞「一键部署路径可用」**——`compose.server` 缺 `SANDBOX_*` 时，部署完沙箱实为关闭，技能全部不可用。
- **`SKX-10` 的登记范围因此扩为 4 条新增 + 1 条口径反转**：登记只能写已验事实，故 `SKX-13`/`SKX-14` 只能登记为「未启动/缺口」，不能写成能力。
