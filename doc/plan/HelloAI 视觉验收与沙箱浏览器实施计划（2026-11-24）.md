## ② 本计划做什么

**目标**：让「界面 / 游戏 / 网页」类交付物从「人工肉眼验收」变成「平台可产出证据 + 可读证据 + 可阻断」。

具体产出（逐项对应 §3 任务表）：

1. **`VU-1` 视觉直读通道**——建立平台首条多模态通道（图 → LLM 消息带 `Media`），是 `ATT-2` 视觉转写的**前置基础设施**（但两者用途不同，见 §0④）；
2. **`VU-2` reviewer 看得到图**——把 `ReviewEvidenceAssembler` 的「你看不到媒体、从严核」换成「带来图元的证据」，让 reviewer 能真看；
3. **`VU-3` 截图存储与证据引用**——截图/录屏走 `ArtifactStorage`，证据只留引用，**绝不进 git**；
4. **`VU-4` 浏览器能力面**——沙箱内可载入页面并产截图；独立 `spec-presets.browser`，不动现有 `node` / `default`；
5. **`VU-5` `AcceptanceKind.RUNTIME_UI` 链路**——枚举 + DB 约束 + 提示词 + 前端标签全链路打通；
6. **`VU-6` 失败语义收口**——无视觉能力 / 浏览器不可用时**不假通过**，转人工或 `INCONCLUSIVE`；
7. **`VU-7` 成本与测试分层**——image token / 浏览器启动 / 录屏存储三段成本各自可观测，单测 hermetic；
8. **`VU-8` 执行面输入源**——用户上传的图（`chat_attachment`）能被**子任务执行器**读到；不补则 `VU-1` 的通道在真实使用中只有上游产出图、没有用户输入源（§2 #22）；
9. **`VU-9` 对话面视觉直读**——工作台 / 新建对话 / 澄清这几条 `AgentTask → ChatClient` 链能带图。**这是用户实际最常触达的面**，且与 `VU-1` 修的执行链**无任何共用节点**（§2 #23），`VU-1` 对它零收益。

> **`VU-8` 与 `VU-9` 是两条不同链路，互不替代**：`VU-8` 走 task 域 `attachment`（执行面），`VU-9` 走 planner 域 `chat_attachment`（对话面），各有自己的表与执行器。**修通一条不会让另一条可用**，两者都不是可选优化。

## ④ 诚实边界

- **`VU-1` 做完 ≠ 能看图验收**：它只让消息**能带图元**。reviewer 真正看到图还需 `VU-2`；真机验证「模型确实收到了图」需 `RUI-1` 的实测；
- **`VU-1` 的实施面比初版评估大**：初版只列 `AgentLoopInput` + `AgentTask` + `ChatModelToolLoop` 三个点；实测有**两条进循环的路**（§2 #16），必须 `AgentContext` + `AgentTask` 两处都加，另需两处填值 + 一处解码修复。工期按此重估，不按初版三点的量；
- **两个计划外缺陷必须在 `VU-1` 同批处理，否则本计划会「名义上加了视觉能力、实际上继续误判」**：① `loadUpstreamContent` 把图片当 UTF-8 解码（§2 #17）；② `CAP_SUPPORTS_IMAGE_UNDERSTANDING` 只写不读（§2 #18，读取侧归 `VU-6` 但影响面在 `VU-1` 之后立刻可见）；
- **本计划的根依赖是 `RUI` 清单的事实核对结论**：`RUI-1`（模型是否支持图片输入）、`RUI-4`（沙箱能否跑 Chromium/WebGL）、`RUI-5`（Playwright MCP vs 原生）三项未出结论前，`VU-4` 之后的任务**只能是待开始**，不得预判；
- **`VU-4` 起会触发 `G-005` 条件③**：一旦平台自持浏览器，那个「暂缓重排期」的前提失效 ⇒ 须重新排期并出 ADR（隐性成本远大于写代码）。本计划**不替代**那次重排期决策；
- **★`VU-1` 交付 ≠ 产品里的任何一处能用**：这是本计划最需要说清的一条诚实边界。`VU-1` 只打通了**执行链**（`ExecutionCommand → AgentContext → RuntimeTurnExecutor → AgentLoopInput`），而用户实际触达的三处入口**都不走这条链**——
  - **工作台对话 / 新建对话 / 澄清**走 `AgentTask → ApiKeyAgentExecutor → AgentChatClientService → ChatClient.user(String)`，与执行链**无任何共用节点** ⇒ `VU-1` 零收益（§2 #23，归 `VU-9`）；
  - **需求对话里上传的图**落在 `chat_attachment`（planner 域），执行器只读 `attachment`（task 域），**两表无桥** ⇒ 用户上传的图到不了执行器（§2 #22，归 `VU-8`）；
  - 且前端两个上传入口的 `accept` **至今不含 `image/*`**，用户**连图都选不上**。
  ⇒ 因此「模型多模态能力已具备」与「用户能在产品里传图提问」是**两件事**，前者 2026-11-24 已验证（四模型 DB 实测声明 `input:["text","image"]`，§2 #19），后者要做完 `VU-9`（对话面）与 `VU-8`（执行面）才成立。**在两者交付前，不得对外表述为「平台已支持图片输入」**；★**2026-11-25 追补**：§2 #19 的「四模型均声明 image」已不能作为「模型侧不缺能力」的依据——deepseek 在本平台实际不可达图片输入（SDK 静默丢图），`V155` 已按 fail-close 收为 `["text"]`；能力位语义见 #19 的口径订正
- **`VU-8` / `VU-9` 的排期我先拍板为 `VU-9` 优先**：它与 `VU-2` 共用 `AgentTask.mediaRefs` 字段（一次改动省两次动手 `@Builder` 类），且 planner 域用自己的表、**不涉及跨域读取与两套生命周期的既有约定**，成本明显低于 `VU-8`；而工作台与新建对话又是产品默认入口。`VU-8` 的候选路线 A 需先经 `RUI-1` 结论再定；
- **视觉验收的正确率无数据**：`VU-6` 定的是「失败必须显式」，不是「判定有多准」。误报率 / 漏报率需对照实验（参照 `MEMORY-DETAIL-工程纪律与判据.md` 判据 18 的对照实验口径），本计划不下结论；
- **`ATT-2` 与本计划的关系必须分清（2026-11-24 实测订正）**：两者**共用同一条多模态通道基础设施**（`UserMessage.Builder.media`），但**用途是两条不同路线**，不是同一件事——
  - `ATT-2` = **视觉转写**：图片 → **独立 VLM 调用**（`design/HelloAI 需求对话附件设计.md` §3.3.1 明确「不复用规划者模型」）→ 输出「客观描述 + 可读文字」→ 落 `extracted_text`（`parser=vision`）→ **走普通附件文本注入路径**，主模型**不直接看图**；
  - `VU-1` = **媒体直读**：图片作为 `Media` **直接进执行 / 评审模型的消息**，不转写、不落中间文本。
  - **为什么本计划不能改用转写**：转写丢掉布局与颜色语义，而 UI 截图/游戏画面正是靠这些判定的（§0③ 已排除「好玩/手感/美术」不代表不需要看布局）。设计文档 §3.3.1 选转写是因为「需求澄清」场景要的是**文字需求**，两场景诉求不同，**不可互换**。
  - **正确的依赖方向**：`VU-1` 的通道是 `ATT-2` 的**前置基础设施**（设计文档原文即写「它同时是后续『子任务执行带图』的前置能力」）；但 `ATT-2` 的转写逻辑、视觉模型选择、费用闸、`parser=vision` 落库、降级 `SKIPPED` **都不在 `VU-1` 范围内**，仍归附件计划。
  - **状态唯一事实源**：`ATT-2` 的状态以附件计划为准，本计划不双写。

> **⚠️ 阻塞已于 2026-11-24 解除（`VU-8` 交付后）**：路线 A 只读通道打通后，「执行期看图」不再依赖两表建桥——执行器经 `ConversationMediaRefPort` 直接读 `chat_attachment`。⇒ `RequirementChat.vue` 的 `accept` 与澄清链 `AgentTask` 填值**可立即开工**，两条须同批（先补 `accept` 而不填值仍是「图进库、模型看不到」；先填值而不补 `accept` 是死代码）。本条原「有意不接」的结论**不删、只加此指针**，避免读史时误判为漏做。

- **为什么单独立项**：`VU-1` 修的是**执行链**（`ExecutionCommand → AgentContext → RuntimeTurnExecutor`），而**工作台对话与新建对话走的是另一条链**（`AgentTask → ApiKeyAgentExecutor → AgentChatClientService → ChatClient.user(String)`），中间不经过 `AgentContext`、也不经过 `AgentLoopInput`。两链没有任何共用节点 ⇒ `VU-1` 对对话面**零收益**（§2 #23）。用户感知到的「对话里传图没反应」正是这条链。
- **四个断点（按数据流顺序）**：
  1. **落库即丢**：`ChatAttachmentParseWorker:80-86` 对 `ContentKind.MEDIA` 一律 `markSkipped(...)`，`extractedText` 永远为空；
  2. **渲染只给清单**：`ChatAttachmentPromptRenderer:371/410/496/589` 四处注入点都要求 `parseStatus == READY && extractedText` 非空 ⇒ 图片只以 `:637` 的 `"需识别（无正文）"` 出现在清单里，**正文段零内容**；
  3. **`AgentTask` 无媒体通道**：三处 `builder()` 只填文本；`AgentTask` 至今无 `media` 字段（与 `VU-2` 同一字段，须同批加，否则第二次动 `@Builder` 类）；
  4. **`ChatClient` 只收文本**：`AgentChatClientServiceImpl:97`（同步）/`:153`（流式）都是 `.user(String)`，而 Spring AI 的媒体重载在 `PromptUserSpec` 上（`ChatClientRequestSpec.user(Consumer<PromptUserSpec>)`）。
- **参考实现（跨项目调研结论，全文见 `research/HelloAI 图片输入通道跨项目实现调研（2026-11-24）.md`）**：核对 **Aider（源码）/ GitHub Copilot SDK（官方文档）/ OpenCode（源码+官方 issue）/ deepseek-harness（本机源码）/ Octop（本机源码）** 五处，收敛出**四条不变量**——四家在下面四条上完全一致，可视为行业定稿：
  - **I-1 图片字节永不进文本通道**：Aider `base_coder.py::get_files_content` 用 `if not is_image_file(fname)` 把图片显式排除在文本拼接外；OpenCode 走独立 `MediaPart`。⇒ 与本项目 §2 #20 同一条判据，**交叉验证它不是自创而是共识**。
  - **I-2 能力位在「请求装配层」按「本次实际调用的模型」解析**：这是**最关键的一条**。OpenCode 官方 issue `anomalyco/opencode#60736` 维护者原话：「The note is added each time a request is built, based on the model the request actually uses … **even though `deepseek-flash` looked selected on the client**」——即「前端选中的模型」≠「实际调用的模型」时，能力判定必须取后者。deepseek `packages/llm/llm/src/index.ts:1087-1092` 同位置判定；Copilot 文档明写「Check vision support first — sending images to a non-vision model wastes tokens」；Octop `providers/store.py:253-254`+`:459` 让能力位参与路由跳过。⇒ **本项必须在 `AgentChatClientService` 这一层读能力，不能在前端 `accept` 或 `AgentTask` 构造时读**，否则直接复刻 #60736。
  - **I-3 存储只存引用，字节与缩放副本不落历史**：Octop `middleware/workspace_image.py:1-10` docstring 明文「base64 and resized copies **never land in** LangGraph state or the dashboard history payload」；Copilot 分 `file`（路径）/`blob`（内存 base64）两形态。⇒ `AgentTask.mediaRefs` 只存 `attachmentId`，字节在 `ChatClient` 调用点读。
  - **I-4 降级必须显式，禁止静默丢图**：Octop `attachment_hints.py:330-352` 三档（字节→vision / 路径→path hint，`:121-137` 明写 `never inline file bytes` / 皆无→显式 unavailable）；deepseek 缺能力或缺附件服务时抛 `LlmError(..., 'UNSUPPORTED_CONTENT')`（`images.ts:60-63`）；Copilot 明写超限图「is skipped and not sent」；OpenCode 注入显式 note。⇒ 本项判据③照此做成**三态**。
  - **两处行业分歧（本项目已拍板）**：① 图文同条 vs 独立轮次——Aider 用「独立 user 消息 + `assistant:"Ok."`」，本项目 `VU-1` 用「同条消息多 part」⇒ **取后者**（用户意图与图不可分，且已交付验证）；② 超限处理——Aider/Copilot 跳过或原样直发，OpenCode「渐进重编码直到塞进」、deepseek「offload 最老图 + 不耗重试预算地重试」⇒ **取 OpenCode 渐进重编码**（不依赖会话回写设施；deepseek 路线等有持久化投影后再议）。
  - **三处不采纳**：① Octop `workspace://`（依赖工作区对模型侧可见，本项目容器形态未挂载，`GT-10`）；② deepseek offload（依赖会话 surface 可回写，无对应设施）；③ Aider「按扩展名判型 + 完全不 resize」（前者缺陷已被 OpenCode 用字节嗅探纠正，后者会直接顶到 provider 限额）。
  - **额外可复用的三条工程细节**：① **限额是「处理参数」不是「安全边界」**（OpenCode 文档原话），不要和上传鉴权混写；② **MIME 必须按字节嗅探**，不信扩展名与声明 MIME（OpenCode 原话：改文件名或 `data:` MIME 不能让不支持的二进制变可见）；③ **图片 token 不能按文本估算**（Aider `token_count_for_image` 独立分支），`VU-7` 成本模型须单列。
  - **一条对 `VU-6` 的直接支撑**：OpenCode 的 `read` 工具读到图时返回 **`file` 块（`data:` URI + mime）** 而非文本（`tool/plugin/read.ts`），该块在下一次请求降级为 `image` block 随 `tool_result` 回传。⇒ `§2 #21` 的 `internal_read_attachment` 正解是**返回 file/image 块**，不是「解码成字符串」。本项不修它，但修法已定稿。
- **必避的坑**：
  - **★能力位必须在 `AgentChatClientService` 读，且按「本次实际调用的模型」读**：这是 OpenCode 官方 issue `#60736` 的成因形态——维护者判定「note 是每次构建请求时按实际使用的模型加的，而你前端看着选的是 `deepseek-flash`」。本项目存在模型回落与变体（`default`/`high`），前端选中 ≠ 实际调用 ⇒ **在前端 `accept` 处或 `AgentTask` 构造时判能力，会复刻这条 issue**。
  - **限额是处理参数不是安全边界**：不要把「图片 ≤ N MB」写进上传鉴权（OpenCode 文档原话：「Image settings are therefore processing limits, not an upload or security boundary」）。安全边界应是字节嗅探 + MIME 白名单。
  - **MIME 必须按字节嗅探**：不信扩展名、不信声明 MIME（改文件名不能让不支持的二进制变可见）。
  - **不得把图当文本硬塞**：`new String(bytes, UTF_8)` 塞进 prompt 会得到乱码且污染上下文——与 §2 #17/#20 同一判据。
  - **不得只改同步链**：对话面存在同步（`AssistantChatServiceImpl:357`）与流式（`:451`）两个入口，只改一处会得到「发出去有图、重发一次没图」的错觉；澄清链同样两条（`ClarifyRoundOrchestratorServiceImpl:616/690/768/824` + `ClarifyStreamServiceImpl:356`）；
  - **媒体与文本必须同条 `UserMessage`**（`VU-1` 已验证过的判据，`ChatModelToolLoop` 注释有完整理由），不要图单独成一条消息；
  - **零媒体必须走原路径**：`media` 为空时仍调 `.user(String)`，不调带 `media(List.of())` 的重载——否则请求体与现在不同，回归面会无故放大；
  - **图必须能传到**：本项依赖 `VU-8` 之外的**另一个输入源**——对话面用的是 `chat_attachment`（planner 域自己的表），**不经 task 域**，因此**本项不依赖 `VU-8` 的读取通道**，只需前端 `accept` 补 `image/*`。这是与 `VU-8` 的关键区别，别混为一谈。
- **前置**：`VU-1`（`AttachmentMediaAssembler` 与「图文本同条消息」判据，已达成）；前端 `accept` 补 `image/*`（两步同批）
- **最小可验证闭环**：前端补 `accept` → 用户在工作台传一张截图 + 一句问话 → 模型回答里描述出截图内容。
- **验收判据**：① 对话面发出的请求体含该 `Media`（`ChatModel` 层可断言）；② 图片不再进入 `extractedText` 的文本通道（单测：`markSkipped` 时 `extractedText` 为空且不被当正文注入）；③ 清单文案改为**三态能力分支**（不变量 I-4，deepseek `images.ts:60-63` + Octop `attachment_hints.py:330-352` + Copilot「is skipped and not sent」）：**能看**（不再宣称看不到）/ **只能给路径**（给文件名+路径+MIME，不内联字节）/ **明确看不到**（显式文案或显式报错），禁「假装看过」的第四态；与 `VU-2` 的 `buildMediaVisibilityNote` 反转同判据，**两处措辞不得各写一套**；④ 同/流两条入口行为一致（单测各断言一次）；⑤ 零媒体时请求体与改动前一致；⑥ `AgentTask.mediaRefs` 只存**附件引用**不存字节（不变量 I-3）；⑦ **能力位读取位置有确定性断言**：断言能力解析发生在 `AgentChatClientService` 构建请求时、且取的是**本次实际调用的模型**（不变量 I-2，对应 OpenCode `#60736`）——测试里构造「前端选中视觉模型、实际路由到非视觉模型」的错配场景，断言降级文案命中三态之一而非崩溃；⑧ 验证在**请求体**上断言，不在 DB 上断言（OpenCode `#45986`：「落库成功 ≠ 送到模型」）。
- **与 `VU-2` 的边界**：`VU-2` 是**业务面 reviewer 看图**（`BusinessSurfaceLoopRunner` 那条链）；本项是**对话面问答看图**（`ApiKeyAgentExecutor` 那条链）。两者共用 `AgentTask.mediaRefs` 字段与 `AttachmentMediaAssembler` 判据，**字段必须同批加**（判据 30：加字段后全仓搜该类构造点），但**填值处与文案处各不相同**，可分两批交付。
