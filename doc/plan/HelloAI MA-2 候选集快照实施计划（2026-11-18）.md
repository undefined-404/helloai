### ② 本计划做什么

**一句话目标**：让**每一次派单决策可复盘**——事后能查到当时的候选池、各自分数与排名、中选者、走的是哪条选人路径。

四条具体产出：

1. 定义派单决策快照形状（`DispatchDecisionSnapshot`），由选人器**返回**给调用方，不由选人器自己落库；
2. 在**四条**选人路径上产出快照（三处主选人 + 一处回退），并标记 `path` 区分口径；
3. 快照落 `sub_task.context.dispatchSnapshot`（**不加表不加列**），键名进 `SubTaskContextKeys`；
4. `attempt` 取既有 `sub_task.attempt_total`，重派时旧快照可追溯。

### ③ 本计划不做什么

| 不做 | 为什么 | 依据 |
|---|---|---|
| **不改选人逻辑本身**（不加判据、不调权重、不换比较器） | 一旦同时改判据，就说不清行为变化是快照引起的还是新判据引起的 | 判据 18（对照实验前提 = 两组只差被研究的那一个变量） |
| **不新建表** | 一次派单一份快照，查询模式是「按子任务取最新一条」，正是 JSONB 上下文的形状；`lastExecution` 已证明可行 | 蓝图 §4 `MA-2` ⑥ |
| **不存敏感配置** | 快照只留投影字段（id / name / role / 分数 / 排名 / 在飞数 / 档位），**不存 model、key、prompt、endpoint** | `SandboxCallLedger` 同类口径（只记前缀，防密钥进库） |
| **不做报表 / 不做前端展示** | 快照是数据契约。看板与统计要有第二个消费方时再做，现在做就是「只写不读」 | 判据 2 |
| **不记录 `ReviewerPicker` 的评审人选择** | 它是评审侧选人，语义与派单不同；混进来会让「派单决策」这张表变成两种事实 | 一张快照一种语义 |
| **不改 `composite_score` / `score_grade` / `score_factors` 落库逻辑** | 这三列已存在且是「中选者」的分数事实；快照补的是「候选池」，两者互补不重复 | 蓝图 §4 `MA-2` ② |

### ④ 诚实边界

**落地后仍有以下不成立，必须同步登记**：

1. **快照只覆盖「选人」，不覆盖「为什么不派」**。`ReassignGateDecision` 那一层的拒绝原因（熔断 / 退避窗口 / 策略白名单）走的是 `recordRedispatchSkipped` 事件，**不在本快照里**。要回答「为什么这单一直没派出去」仍要看时间线事件。
2. **不是事件溯源**。快照是「最近一次决策的覆盖式写入」，不是全量历史。`attempt_total` 递增后旧快照被覆盖，**只能追溯最后一次**。要全量历史必须建表，属另一批。
3. **`path` 只区分两条**（`primary` / `fallback`）。三处主选人（`dispatchBlockedSubTask` / `dispatchPendingSubTaskAuto` / `redispatchAssignedTimeout`）在快照里**看不出是哪一处**，除非再加 `trigger` 字段——本期不加，因为加它就要为三种触发各自定义语义，收益不明。
4. **没有消费方**。本计划交付的是**数据契约**，不改任何界面。按判据 2，它在上线时就是「写了没人读」——这是**主动接受的**，因为 `DC-1` 的价值必须靠「事后查」兑现，而事后查天然晚于写入。**但这意味着它必须配一条查询路径**（见 §6 验收 5），否则就是重演 `decision-classes.json` 的错误。

## 4. 关键设计决策

| 决策 | 选了什么 | 为什么不选另一种 |
|---|---|---|
| 快照形状落点 | `sub_task.context.dispatchSnapshot`（JSONB） | 新表要配 mapper / entity / 迁移 / 索引，而查询模式只有「按子任务取最新一条」——正是 JSONB 的形状 |
| 谁写快照 | **`task` 域 `SubTaskDispatchServiceImpl`** | `AgentSelector` 在 `agent` 域，跨域写 `task` 表是「直捅」（协作规约 §5.1~5.2） |
| 覆盖 vs 追加 | **覆盖**（按 `attempt` 递增，每次覆盖） | 追加会让 JSONB 无限膨胀；全量历史要建表，属另一批 |
| `attempt` 来源 | 既有 `sub_task.attempt_total` | 新增计数器 = 同一事实两个来源，必然不同步 |
| 截断 | top 10 + `candidateTotal` + `truncated` | 上百 Agent 的候选池全存会让单行 JSONB 失控；而「总数」这个信息不能丢 |
| 回退路径的排名字段 | 填 `null` | 回退是单维 `max(score)`，没有质量排名 / 成本排名 / 档位——**编造 0 会让人误读成「排第一」** |
| `decidedAt` | 记录 | 便于与时间线事件对齐；但**不参与身份**（不学 AgentTeams 的 `event_id = sha256(...)`，因为我们的快照不是事件、不需要幂等去重） |

### 4.1 与 AgentTeams 的取舍（抄哪一半）

| 抄 | 不抄 |
|---|---|
| 「决策可复盘」这个目标 | `defined-not-enforced` 的形态——**只声明不接线**。我们的快照必须有真实写入点 |
| 「失败尝试也要留痕」的思路（它连拒绝都记 `refused`） | 内容哈希做事件身份（我们没有事件总线，不需要重放幂等） |

## 6.1 实现记录（2026-11-18，落地后订正）

**结果**：`MA2-1`~`MA2-7` 全部落地；定向单测 165 例全绿（`DispatchSnapshotTest` 6 + `SubTaskDispatchServiceTest` 45，
其中新增 2 例）；架构冻结守卫未超基线。

**实现中确认/更正的事实（按发现的先后）**：

| # | 计划里怎么写的 | 实际是什么 | 处置 |
|---|---|---|---|
| 1 | 落库调 `subTaskService.mergeContext(...)` | 公开方法不存在，实际是 `updateContextInNewTx`（按键合并 + `REQUIRES_NEW`） | 已用 `updateContextInNewTx`，并在 §2.3 追「口径订正」 |
| 2 | `attempt` 取 `subTask.getAttemptTotal()` | 调用方手里的实体是 **`incrementAttemptTotal` 自增之前**的快照，直接用会少 1 | 落库前重读一行取真实值；<b>不在内存 `+1`</b>（否则同一事实两个来源） |
| 3 | 快照含「在飞数」 | `SCORE_DESC` 策略**根本不采集**在飞数（只有加权随机拿它当分母），全量采集会给默认路径加 N 次 count 查询 | 该策略下记 `null`；质量/成本维度关闭时同样记 `null`。「不可比」与「最差」必须区分，不编 0 |
| 4 | 候选按「最终比较器」排序 | 加权随机策略原先只有 `tierComparator`（不含 score），排序会产生大量 `dutyRank` 查询 | 排序统一用 `resolveComparator`（分档 + score）；同时把 `dutyRank` 提为**一次预计算**（`resolveDutyRanks`），比较结果逐字不变、查询量从约 2n 降到 n |
| 5 | 三处主选人 + 一处回退 | 正确；另有 `redispatchInProgress`（人工显式指定执行者）——它**不是选人决策** | 该路径不产快照，属 §0④ 已声明的边界 |

**快照字段口径（写进实现，供后续消费方对齐）**：

- `tier` = 「值班 → 接入类型 → 质量 → 成本」分组序号（0 = 最优档），不是「第几档成本」；
- `candidates` 按 `resolveComparator` 降序，`winner` 在快照内唯一；加权随机策略下 winner 未必是第一位
  ——这正是「抽签结果 + 位次」都要留痕的理由；
- `decidedAt` 是 ISO-8601 字符串（不快照 `OffsetDateTime`：JSONB 里存字符串，读侧无需 JavaTimeModule）。

**已知边界（未变）**：覆盖式（只有「最近一次」）；不覆盖「为什么不派」（`ReDispatchGate` 拒绝原因走时间线事件）；
`path` 只区分主/回退，三处主选人互相看不出。

**新增边界（实现时发现）**：`ResilientDispatcher`（熔断降级替代）内部也调 `pickAlternative(agentId, role, constraints)`，
那是**第五条**选人点。本期**不接线**——它在 `agent` 域、且其决策已由熔断事件与 `ResilientDispatcher` 自己的日志承载，
硬塞进 `sub_task.context` 反而要新开跨域写口。若将来要回答「熔断降级时选了谁」，应单开一份「降级决策」记录，
而不是把两种语义混进同一份快照。
