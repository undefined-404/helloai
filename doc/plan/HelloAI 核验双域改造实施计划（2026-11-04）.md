## 0. 定位与边界（★先读）

**① 问题来源**

- **用户裁定（2026-11-04）**：review 应拆为**他审（reviewer）**与**自审（self-review）**两条业务，两处都要调整（原文见文档头）。
- **外部机制对照**：`security-audit-skill`（Cloudflare，MIT）在「证明审全了」上比本项目走得更远——覆盖台账 / 三态裁决 / 确定性 validator / 对立面复核，四项均已代码化；两份独立分析主要结论一致（一份看全局流程，一份看单点判定），其中 3 处细节经代码复核订正（见 §2）。仅借机制，不复制领域内容（安全领域知识库不适用）。
- **代码级根因**（详见 §2）：review 判定从「提示词有约束」到「代码有强制」之间是**空的**——`analysis` / `acceptanceRef` / `nit` vs `blocker` 三条提示词要求都没有对应校验（§2.1 事实 5~7）；自审轮则被**显式关掉工具**（§2.2 事实 12~13），所谓「自审」只是模型自述。
- **差距表锚点**：`G-007`（Rule + Test + LLM 统一决策，状态「待开始」）；正交相邻项 `G-016`（技能注入契约，已关闭）。
- **观测缺口**：抽检只抽 `APPROVED`，驳回侧无独立复核（§2.1 事实 9），「误伤率」不可度量。

**② 本计划做什么**

把「审没审全」「自审跑没跑」从**口径问题**变成**机读事实**。具体产出六条：

1. **`RV-1` 纯静态判定校验器**：`analysis` 非空 / `acceptanceRef` 子串归属 / `pass`↔`score` 双向一致 / 宽松解析标记，全部确定性、零 token。
2. **`RV-2` 三态结论**：`APPROVED / REJECTED / INCONCLUSIVE`，让「证据不足」不再被迫二选一（放行或返工），并与抽检表 `review_recheck_log` 同步放宽约束。
3. **`RV-3` `coverage[]` 结构化 + 静态覆盖批评器**：验收点逐条状态机读，覆盖判据改为 **`criterionRef` 子串归属**（不用「条数相等」，见 §4 决策 D2）。
4. **`RV-4` 抽检独立性**：排除原判定人；LLM 失败/超时补 timeline 事件，与 `UNPARSEABLE` 区分。
5. **`SR-1` ~ `SR-4` 自审走沙箱**：收尾轮放开**仅一个**受限工具、围栏升级为可机读 `EVIDENCE`、闸门只判「证据是否存在且一致」、不合格同 turn 有界重跑、沙箱不可用显式降级。
6. **`SR-5` 沙箱调用台账**（本轮新增）：`OpenSandboxExecutionService` 目前**不留任何执行记录**（§2.3 事实 20），而 `SR-2`/`SR-3` 的「以平台侧记录为准」依赖它——不建台账，自审证据只能退回模型自填，等于没改。

**③ 本计划不做什么**（边界，防越界）

1. **不建第二套 Review Runtime、不新增子任务状态**——沿用 `SubTaskStatus` 与既有 REVIEW→REWORK/COMPLETE 链。依据：`doc/HelloAI 项目基线文档.md:373`「现阶段不建立第二套 Review Runtime」红线。
2. **不搬安全审计的领域模型**——六阶段流程、hunting waves、`attack class` 知识库、severity 分级、`scratch→artifacts` 11 步描述符提升均不适用。依据：本项目的判定对象是**单次子任务产出**，不是**整个代码库的攻击面**；`research/` 借鉴判据「只借机制不复制领域内容」。
3. **不让沙箱成为判定者**——沙箱只提供「命令是否执行、退出码、输出」事实，内容达标仍由 reviewer / LLM 判定。依据：`design/adr/ADR-004-sandbox-execution-chain-and-fidelity-gate.md` §4。
4. **不在本批替换缺陷指纹**——`RepeatedFailureGate` 现有三段式判据（评分停滞 + 文本重复 / 自报停滞）已用真机语料校准，替换需独立立项。依据：§8 挂起项。
5. **不在拆解侧降级验收强度**——`RV-1` 命中只**标注/转人工**，不改 `acceptance`、不改 `acceptance_kind`、不自动 `pass=false`。依据：`TD-11`「只标不拒」同款处置（`LOG-20261025-014`）。
6. **不把自审闸门做成第二个 `FinalReportFidelityGate`**——两者判定对象不同（单子任务收尾 vs 终报告），职责边界见 §4 决策 D4。依据：判据「同一事实双写必分叉」。

**④ 诚实边界**

- **`RV-1` 首批只标不拒 ≠ 四处 fail-open 已关闭**：本计划先落地 `Warn` 档（记事件、不改判定），真机语料从 **n=12** 起步（§2.3 事实 20）。**`Warn` 档上线不得宣称「核验契约已强制」**；只有升 `Block` 后该结论才成立。
- **`RV-2` 落 `INCONCLUSIVE` ≠ 人工介入成本已可控**：该态设计为「停 REVIEW 转人工」。上线后**人工待处理会上升**，这是有意取舍（比「空转返工」或「假 pass」更接近真实），但它确实是**新增作业量**。
- **`RV-3` 的 `coverage[]` 依赖模型填 `criterionRef`**：模型不填或填错时，批评器只能判「未覆盖 → `INCONCLUSIVE`」，判不了「其实覆盖了只是没写」。因此该能力的上限是**「漏判可发现」，不是「漏判不发生」**。
- **`SR-1` ~ `SR-4` 落地后「自审真跑过」只在沙箱开启时成立**：`application-quickstart.yml:112` 默认 `enabled=false`，该档位下自审一律走降级（`degraded_no_sandbox`），**不得统计为「已自审」**。
- **`SR-5` 台账只是调用记录，不是执行正确性证明**：它记 `command/exitCode/truncated/digest`，不证明命令本身验的是对的东西。
- **`RV-6` 的误伤率只覆盖有快照的驳回记录**：`V141` 之前的历史驳回（本机 41 条）无快照、返工已覆盖产出，不入样；该指标样本从 0 起步，**不得用首周数字下结论**。
- **`RV-7` 只做 `Warn` 档观测，不等于乱码已被拦截**：检测命中只进 `sub_task_auto_review_verdict_warn`，不改判定；且检的是「可机读的损坏特征」，不含语义层面的错译/乱序。要真正拦住，须在验收标准里加编码断言（本项已改拆解提示词）或升 `BLOCK`（待真实语料证明零误伤）。
- **`RV-1` Block 与 `RV-3` 两个 BLOCK 分支无真机样本 ≠ 未实现**：`reject_with_full_score` / `coverage_absent` / `unconfirmed_silently_dropped` 均由 reviewer 输出形态触发，执行侧（内部/外部 Agent）只能控制交付内容，正常链路无法稳定制造；按单测/IT 收口，计划已标注「不可自然采样」，不主动构造。
- **`G-007` 不因本计划关闭**：本计划只覆盖「reviewer 判定的确定性与可核对性」，`G-007` 的「Rule + Test + LLM 统一决策」还包含 rule 引擎与 test 执行者的统一调度，那层不在本计划。差距表状态按批次完成后回填，**不提前宣称**。

- **提示词契约**（`prompts/subtask-review.md` 输出 JSON 增 `coverage` 数组）：每条 `{criterionRef, status: covered|failed|not_verifiable, method: attachment|sandbox, evidenceRef, note}`。

- **数据现状（2026-11-04，本机 `15432`）**：`review_record` 83 `APPROVED` / 41 `REJECTED`；V141 之前历史驳回记录 `snapshot` 均为 `NULL`。

**（1）候选口径**

- 查询扩为 `result IN ('APPROVED','REJECTED')`，并加一条**硬前置**：`REJECTED` 记录必须 `snapshot IS NOT NULL`。历史驳回（V141 前）不入样——返工已覆盖产出，复判对象不可信。
- **驳回优先入样**：`ORDER BY (result = 'REJECTED') DESC, create_time ASC`，合池比例仍为 `recheck-sample-ratio`。理由：驳回是少数侧（本机 33%，另一实例 32%），纯「先审先抽」会让小样本侧多轮后才出现；误伤率需要驳回侧尽快有样本。
- **非随机抽样的既有口径不变**：本项只做「按时间顺序的确定性抽样」，误伤率用于趋势与人工复核线索，不作统计推断。
- `INCONCLUSIVE` 不入样（无「原判」可复判）。

**（2）执行器改造（`ReviewRecheckExecutor`）**

- 去掉「仅 APPROVED」早退，允许 `APPROVED` / `REJECTED`；`originalResult` 取 `record.getResult()`，不再硬编码 `APPROVED`。
- `discrepancy` 语义改为「复判与原判不一致」（实体与 V57 注释同批更新，**不加列、不加迁移**）：
  - 放水 = `original=APPROVED & recheck=REJECTED`；
  - 误伤 = `original=REJECTED & recheck=APPROVED`；
  - 方向由 `original_result` 派生，查询侧不产生二义。
- 事件与对话文案按方向生成：`SUB_TASK_RECHECK_DISCREPANCY` payload 增 `originalResult` / `recheckResult` / `direction`（`leak_approved` / `overturned_rejection`）；对话流文案改为「原判通过，复判驳回（放水）」/「原判驳回，复判通过（误伤）」。
- `REJECTED` 记录若被手工直调且无快照 ⇒ 新增跳过原因 `snapshot_missing`（不写 `review_recheck_log`），与 `snapshot_drift` 分开留痕。
- 排除集（`reviewersInvolved`）、`INCONCLUSIVE` 复判跳过、只度量不改状态等既有口径不变。

**（3）误伤率统计**

- 在 `review_recheck_log` 之上按 `original_result` 分组：有效复判数 / 分歧数。公式：
  - 放水率 = `original=APPROVED & recheck=REJECTED` ÷ `original=APPROVED` 的有效复判数；
  - 误伤率 = `original=REJECTED & recheck=APPROVED` ÷ `original=REJECTED` 的有效复判数。
- v1 提供 `ReviewService#recheckStats(since)` 查询 + `GET /admin/quality/recheck-stats?days=` 只读接口 + 单测；**是否上质量看板卡片单独评估**，避免本期同时改前端契约。
- 分母只算「有效复判」：跳过（无 reviewer / 不可判定 / 漂移 / 无快照）不写 `review_recheck_log`，天然不进分母。

**（4）验证**

- 单测（`ReviewRecheckExecutorTest`）：`REJECTED→APPROVED` 落 `discrepancy=1` 且事件 `direction=overturned_rejection`；`REJECTED→REJECTED` 记一致；`INCONCLUSIVE` 原判跳过；无快照驳回记录跳过 `snapshot_missing`；`APPROVED` 路径回归不变。

- IT（候选 SQL）：无快照 `REJECTED` 不入样、有快照 `REJECTED` 入样、已抽检记录排除、`INCONCLUSIVE` 排除。

**边界**：

| # | 决策 | 选项 | 推荐 | 理由 |
|---|---|---|---|---|
| M1 | `[MECHANICAL_CHECK]` 注入位置 | ① 新增第六段 `mechanicalCheck` + 新占位符 `{{MECHANICAL_CHECK}}`；② 并进 `selfReviewSignal`；③ 并进 `attachmentContent` 头部 | **①** | 机械结论需要一条「有机械结论的验收项以机械结论为准」的规则有明确引用位置。② 的语义损失是**具体的**：`prompts/subtask-review.md:51` 自带强规则「显示自审未通过时不得仅凭自报证据判 `pass=true`」，机械结论并入后该规则的作用域变模糊——模型可能把「数字 `MISMATCH`」套进自审口径，或反过来把自审失败读成数字不符。代价 8 处改动（构造点**两处**，见接线清单），另有额外收益：`ReviewEvidenceAssembler.text()`（`:208`）对缺字段返回 `""`、紧凑构造器再兜一次 null ⇒ **历史 `review_record.snapshot` 无 `mechanicalCheck` 键时复判照常渲染，无需回填脚本** |
| M2 | 报告声称的数字由谁提供 | ① reviewer 在 `coverage.evidenceRef` 写出声称值与出处；② 平台 regex 从报告正文抽「数字 + 单位」候选 | **①，但 v1 不输出 `claim` 行** | regex 抽取会误抓（「2026 年」「第 181 行」「共 3 章」），机械预检一旦自己做 NLP 抽取，它本身就成了不可靠源——与「确定性计算」的定位冲突。**且存在时序约束**：机械段在 `buildEvidenceView`（`ReviewExecutionEngine:131`，LLM 调用**之前**）装配，而声称值来自 reviewer 的**输出** ⇒ 首轮注入里 `claim` 行必为空，示例照抄会让实现者去找一个不存在的来源。故 v1 机械侧只输出**实测值**；「声称值 ↔ 实测值」的确定性比对**下放到 `RV-11`**（该闸本就要解析 `coverage`，从 `evidenceRef` 抽 `claim=` 是顺手），既不留时序矛盾，也不让模型自己做减法 |
| M3 | v1 是否做列级聚合比对 | ① 只做行数级；② 同时做「按维度列分组聚合」 | **①，但差值必须双口径输出** | 列级聚合需推断「哪列是维度、哪列是数值、哪列是主键」，无 CSV 库且列语义不可靠（数字列可能是 ID），收益低、误判面大，推迟 v2。**但差值不能只算一种口径**：金标准 `199080 − 198899`（`lines`）= `+181`，而 `199080 − 198897`（`data`）= `+183`——两者都判 `MISMATCH` 但差值不同，只输出 `data` 口径会让金标准断言 `MISMATCH(+181)` 失败。故实测值 `lines`/`rows`/`data` 三值分列（本就是为了解错位），比对端同样要给出 `delta_lines` 与 `delta_data`，或要求声称值带口径（`claim=199080 basis=lines`） |

#### 断言集 v1（全部确定性，可单测）

**A. 文件级（单文件自证）**

| 断言 | 计算方式 | 输出 | 不可算时 |
|---|---|---|---|
| 编码 | 复用 `ReviewEncodingDetector`（`RV-7` 已有判据） | `encoding=utf-8` / `encoding=damaged` | `damaged` ⇒ 整文件 `UNAVAILABLE`，不硬算 |
| 物理行数 | 按 `\n` 计数（末行无换行时 +1） | `lines=198899` | — |
| 记录数 | CSV 记录数（引号内换行算同一条） | `rows=198898` | 解析失败 ⇒ `UNAVAILABLE(parse_error)` |
| 数据行数 | 记录数 − 表头 1 行 | `data=198897` | 无表头 ⇒ `data=rows` 并在输出标 `header=absent` |
| 列数 | 首行分隔符计数 + 1 | `cols=7` | — |
| 列数不齐 | 统计与首行列数不同的记录数 | `ragged=0` / `ragged=k` | `ragged>0` ⇒ `UNAVAILABLE(ragged_rows)` |

**关键口径**：`lines`（物理行）≠ `rows`（CSV 记录）≠ `data`（数据行）。执行方报告常写 `wc -l` 结果（= `lines`），而验收标准说的「多少条记录」应是 `data`。三者必须分别给出，否则比对口径必然错位。

**B. 族级（分片族完整性）**

- **族识别**：`X.csv` 与 `X.part-01.csv` / `X.csv.part-01` / `X-part-01.csv` 同族（取前缀 `X`）；同族成员按编号排序。
- **断言**：
  - `parts=N`（族内分片数）、`present=N`（实际存在的编号连续段长度）
  - 缺片 ⇒ `missing=03,07`（明确列出缺的编号）
  - `sum_data=Σ(各片 data)` —— **每片的表头行必须各自扣除**，直接相加会多算 `N-1` 行
  - `sum_data` 与主件 `data` 比对：`MATCH` / `MISMATCH(±k)`
- **不可算**：各片列数不一致 ⇒ `UNAVAILABLE(part_cols_mismatch)`；族内无主件 ⇒ 只输出 `sum_data`，不做比对。

**C. 报告声明（受 M2 约束：v1 不输出 `claim` 行）**

- 机械侧**只算实际值**，且实测值必须三值分列（`lines` / `rows` / `data`），供 `RV-11` 与 reviewer 选择口径。
- **v1 不输出 `claim` 行**：声称值来自 reviewer **输出**，而机械段在 `buildEvidenceView`（LLM 调用**之前**）装配 ⇒ 首轮无来源（见 M2 决策的时序约束）。声称值比对下放到 `RV-11` 解析 verdict 时做，落点 `coverage.evidenceRef`。
- `RV-11` 落地后若要回填本段，格式为 `claim value=199080 basis=lines delta_lines=+181 delta_data=+183`——**必须带 `basis`**，否则口径错位（金标准 `+181` 是 `lines` 口径，`data` 口径为 `+183`）。
- 无声称值 ⇒ 不输出该行（不猜测）。差值为 0 ⇒ `MATCH`；否则带符号差值。
- **配套 prompt 改动**：`prompts/subtask-review.md:138` 现限定 `evidenceRef` 只能填「附件文件名」或「执行过的命令」，承载 `claim=199080 basis=lines` 必须同步放开（接线清单原先只列 `:134` / `:139`，漏了 `:138`）。

#### 输出格式（紧凑、可引用、可冻结）

```
[MECHANICAL_CHECK] v1
file id=2119683891861348354 name=detail.csv lines=198899 rows=198898 data=198897 cols=7 encoding=utf-8 ragged=0
family name=detail.csv parts=25 present=25 missing=- sum_data=198897 main_data=198898 MATCH
```

- **v1 没有 `claim` 行**（M2 时序约束）：声称值比对由 `RV-11` 在解析 verdict 后完成。
- **每条以 `id=` 开头**：`coverage.evidenceRef` 才能引用到具体附件（`RV-8` 台账的前置）。
- `v1` 版本号：格式变更时 reviewer 与冻结快照都能感知，避免旧快照被按新规则解读。
- 段落上限 **1,200 字符**：超出时按「`MISMATCH` 行 > `UNAVAILABLE` 行 > `file` 行 > `family` 行」优先级截断，并标 `omitted=k`。

#### 判定口径（三态，不是二态）

| 结论 | 含义 | 对 reviewer 的要求 |
|---|---|---|
| `MATCH` | 全部可算断言一致 | 可据此判 `covered`，`method=mechanical` |
| `MISMATCH` | 至少一条不一致，带符号差值 | **照常驳回**，且在 `issues` 引用该行 |
| `UNAVAILABLE` | 无法计算，**必须带原因** | 等价 `not_verifiable`，**不得据此驳回**、不得据此判 `covered` |

`UNAVAILABLE` 的五个合法原因：`parse_error` / `ragged_rows` / `part_cols_mismatch` / `encoding_damaged` / `too_large`。

**`UNAVAILABLE` ≠ 不适用**：非表格文件（`.md` 报告、`.log`、`.json`）由 `isTabular(fileName, mimeType)` 在入口拦掉，**根本不产生 `file` 行**——这与「表格文件算不出来」是两回事。不要把「这本就不是表格」写成 `UNAVAILABLE`，否则 reviewer 会误以为「本该能算但平台不行」，进而按「证据不可得」处理。

#### 硬约束（防机械预检自己变成不可靠源）

1. **体积上限**：单文件 ≤ 50 MB 或 ≤ 500 万行；超限 `UNAVAILABLE(too_large)`，不做流式。
2. **无 CSV 库，手写受限解析器**：只支持逗号 / 制表符分隔 + 双引号转义。遇到「引号内换行」时按 CSV 规则合并为一条记录并计 `multiline=k`；若合并逻辑与物理行冲突致无法判定，降级 `UNAVAILABLE(parse_error)` 而不是猜。
3. **容差 0**：整数比对不容忍误差；浮点先四舍五入到整数再比。
4. **确定性**：同一输入必得同一输出，无时间 / 随机 / 环境依赖（单测用同输入两次调用逐字比对）。
5. **明细数据绝不注入**：只注入聚合结论，逐行内容不进 Prompt。
6. **复用已读全文，不二次下载**：`ReviewEvidenceAssembler.readAttachmentContent`（`:383`）返回的是**完整字节**（`loadContent` 无上限），截断发生在调用之后 ⇒ 机械预检在**截断前**取同一份 `content`，零额外对象存储 IO。

#### 单测清单（表驱动，全部纯函数）

1. `lines` / `rows` / `data` 三值差异：无表头、末尾无换行、含引号内换行（`multiline=k`）

3. 族识别：三种命名形态（`X.part-01.csv` / `X.csv.part-01` / `X-part-01.csv`）与「不同族前缀不误并」
4. 族缺片 ⇒ `missing=` 准确列出编号
5. 族 `sum_data` 扣除各片表头（关键：`N` 片各带表头时总和不多算 `N-1`）
6. 编码损坏 ⇒ `UNAVAILABLE(encoding_damaged)`，不做行数统计
7. 超上限 ⇒ `UNAVAILABLE(too_large)`
8. `MATCH` / `MISMATCH` 带符号差值
9. **v1 无 `claim` 行**：任何输入下输出都不含 `claim`（时序约束的回归守卫，防后续实现者"顺手"加回来）
10. 段长超 1,200 ⇒ 按优先级截断 + `omitted=k`
11. 确定性：同输入两次调用输出逐字相同
12. **同一实测文件对 `lines` 与 `data` 两个口径的差值不同**（金标准场景：`claim=199080`，`lines=198899` ⇒ `delta_lines=+181`，`data=198897` ⇒ `delta_data=+183`）。这一组直接守卫金标准断言 `MISMATCH(+181)` 不被 `data` 口径打偏

- 不做 JSON / Excel / Parquet 解析（v1 只 CSV / TSV）
- 不从报告正文抽数字（M2 决策 ①）
- 不做列级分组聚合（M3 决策 ①，推迟 v2）
- 不做跨文件语义维度映射（「模块」与「项目」是否同一维度由 reviewer 判断）
- 不做流式大文件解析
- 不用机械结论自动定 `verdict`（只提供证据，不代替判定）

#### 验收与不可验证边界

- **可验证**：单测 11 组全过；一次真实任务中 `[MECHANICAL_CHECK]` 在 prompt 中可见且 `review_record.snapshot` 冻结了同一段；`coverage.method=mechanical` 被判为 `covered` 时 `covers()` 成立。
- **本轮不可验证（必须如实标注）**：本地 `attachment` 表仅 19 行、最大 17 KB、全是沙箱探针小文件，**没有** 35 附件（25 片 + 主件 + 报告 + 日志）那批真实数据 ⇒ 断言集是基于已知案例（`199080` vs `198899`）与 CSV 通用结构推导的，**未用真实数据校准过**。实现交付后第一件事是用服务器库导出的真实批回放，校验 `data` 与执行方报告的口径是否真的对得上；若执行方报告用的是 `lines` 而非 `data`，则比对口径需再调整。

### RV-8 结构化证据台账（设计）

> **状态**：已完成（2026-11-14 代码 + 单测）｜ **剩余动作**：—

- **落地记录（2026-11-14）**：新增 `review/support/ReviewEvidenceLedger`（`MAX_ENTRIES=60`，`Entry` / `render` / `parse` / `find` / `anyTruncated` / `anyAbsent` / `gap` 纯函数）；台账与 `RV-9` 配额同源产出（`ReviewEvidenceAssembler.buildEvidenceContent` 一次分配同时返回正文与台账），`ReviewEvidenceView.evidenceLedger` + `{{EVIDENCE_LEDGER}}` 独立第七段；`ReviewEvidenceAssembler.freezeEvidence` / `frozenEvidenceView` 原样冻结与复判读回。状态四值 `injected|truncated|absent|not_textual`、`range=head|tail|head+tail`、`reason` 逐条，超 60 条标 `omitted=k`。单测 `ReviewEvidenceLedgerTest` 9 例 + `ReviewEvidenceAssemblerFrozenTest` 七段冻结/恢复断言。

- **定位**：核验 Prompt 里的附件正文是**被预算裁剪过的**，模型看不到「哪些附件没注入、注入了多少、为什么没注入」。台账把这件事变成确定性的结构化事实，与 `RV-9` 的配额分配**同源产出**——配额分配时记什么，台账就写什么，不允许两处各算一遍。
- **为什么是独立第七段**（`ReviewEvidenceView.evidenceLedger` + 占位符 `{{EVIDENCE_LEDGER}}`）：台账描述的是「注入行为」，不是附件正文；塞进 `attachmentContent` 会被 64k/200k 预算计入自身，且与正文混读。独立字段的另一收益：历史快照无该键时 `text()` 返回 `""`，复判照常渲染，无需回填脚本（与 `RV-10` M1 同一条兼容路径）。
- **格式（v1，紧凑文本，确定性）**：

  ```
  [EVIDENCE_LEDGER] v1 totalChars=200000 entries=35 omitted=0
  entry id=2119683891861348354 name=detail.csv chars=155000 status=truncated range=head+tail shown=8192
  entry id=2119683891861348355 name=report.md chars=9000 status=injected range=full shown=9000
  entry id=2119683891861348356 name=broken.csv chars=0 status=absent reason=unreadable
  entry id=2119683891861348357 name=chart.png chars=0 status=not_textual
  ```

  - `status` 四值：`injected`（全文注入）/ `truncated`（区间注入，`range=head|tail|head+tail`）/ `absent`（正文不可读，`reason=unreadable`）/ `not_textual`（二进制或媒体，本就不进正文）。
  - `chars` 是**原文总字符数**（码点计数，与 `ToolResultPruner` 同口径），`shown` 是实际注入字符数。
  - 台账行按「交付物主件 → 族 → 单文件」与 `RV-9` 的优先级同序；单条上限 60 行，超出标 `omitted=k`（`k` 为未列出的条目数）。
- **冻结**：`ReviewEvidenceAssembler.freezeEvidence` 增 `frozenEvidence.evidenceLedger`；复判侧 `frozenEvidenceView` 原样读回。台账是「判定当时模型看到了什么」的直接证据，**不允许复判时按当前附件重新生成**（否则漂移对账失效）。
- **不做**：不落独立表；不记每段字符的 sha256（`RV-10` 已对执行产出做摘要，附件级摘要由 `RV-12` 工具按需给）；不把台账喂给 reviewer 做「完整性」判定（它只解释注入事实，不构成验收证据）。

### RV-9 证据族预算与区间注入（设计）

#### 11.1 声称值 ↔ 实测值比对（承接 `RV-10` M2）

- **来源**：reviewer 在 `coverage[].evidenceRef` 写 `claim=<整数>`，可选 `basis=lines|rows|data`（示例：`claim=199080 basis=lines`）。平台**不**从报告正文抽数字（`RV-10` M2 决策）。
- **实测值解析**：从 `[MECHANICAL_CHECK]` 文本解析 `file id=<id> … lines=… rows=… data=…` 行。比对对象选择是确定性的：
  1. `evidenceRef` 含 `id=<数字>` 且机械段有该 `id` ⇒ 用该文件；
  2. 否则机械段**恰好一行** `file` ⇒ 用该行；
  3. 否则不可比对 ⇒ 只出 `WARN(claim_without_measured)`，**不猜**。
- **比对**：`claim` 与实测值逐整数比较，容差 0。`basis` 缺省 ⇒ `WARN(claim_basis_missing)`（不阻断，但提示模型补口径）；`basis` 非法值 ⇒ 同一条 WARN。`delta` 必须**双口径输出**（`delta_lines` 与 `delta_data`），否则金标准 `+181`（`lines` 口径）会被 `data` 口径的 `+183` 打偏。
- **处置**：`pass=true` 且 `delta≠0` ⇒ `BLOCK(claim_measured_mismatch)`（数字对不上却判通过，是硬缺陷）；`pass=false` 且 `delta≠0` ⇒ `WARN(claim_measured_mismatch_on_reject)`（驳回理由里的数字写错不影响「不通过」结论，但要让复核看到）。
- **输出落点**：`ReviewExecutionEngine.collectFindings` 与 `ReviewVerdictValidator` / `ReviewCoverageCritic` 同批执行；`recordVerdictFindings` 沿用现有 `sub_task_auto_review_verdict_warn` 时间线，`enforced` 由 BLOCK 数决定。

#### 11.2 驳回侧 `evidence_unavailable` → `INCONCLUSIVE`

- **要解决的错判**：reviewer 把「平台没给它看全」写成 `pass=false` 的驳回（典型：155k CSV 被剪到 5k，reviewer 判 `not_verifiable` 后仍给出驳回结论）。这类驳回会消耗返工预算，而返工方不可能补齐「平台注入不足」。
- **触发条件（四条同时成立才降级，缺一不降）**：
  1. `verdict.pass=false`；
  2. `coverage` 中**没有** `status=failed`（没有任何一条判为不合格）；
  3. `coverage` 中**至少一条** `status=not_verifiable`；
  4. 平台侧存在**可指认的证据缺口**：`evidenceRef` 引用的 `id` 在 `RV-8` 台账中为 `absent`，或该文件 `status=truncated`；若 `evidenceRef` 未写 `id`，则要求「注入正文存在截断」这一事实成立（`ledger` 任一条 `truncated`）。
- **处置**：产出 `BLOCK(evidence_unavailable_rejection)`，由 `ReviewExecutionEngine` 返回 `inconclusive()`（与 `RV-2` 现有三态出口同一路径），`SubTaskReviewServiceImpl.markInconclusive` 的人工介入原因改为 `review_evidence_unavailable`（新增常量），**不写返工、不计返工次数**。
- **不降级的反例（必须有回归测试）**：`pass=false` 且存在 `failed` 条目 ⇒ 正常驳回（质量不达标）；`pass=false` 但平台证据齐全 ⇒ 正常驳回；`pass=true` ⇒ 本闸不参与。
- **粘滞标记清理（同批）**：复核出口（判通过 / 正常驳回）落库前，清理**评审侧**写入的 `manualIntervention`（白名单：`review_verdict_invalid` / `review_evidence_unavailable` / `reviewer_disagreement`），**不清**派单侧原因（如 `dispatch_skip_execution_dense`）；`markInconclusive` 自身保持「先清理旧评审标记再写新标记」，避免同一任务叠两条。前端「返工已达上限（0 次）」的误导文案由标记不再粘滞而自然消失，不新增状态、不改状态机。

## 4. 关键设计决策

| # | 决策 | 取舍与理由 |
|---|---|---|
| D1 | `RV-1` **分级处置**（`Block` 只留逻辑矛盾项，其余 `Warn`），而非一次全 `Block` | 真机 `review_record` 仅 12 条（§2.3 事实 20），其中 `Warn` 四项**零命中**。零命中在 n=12 上证明不了「不会误伤」，只能证明「没观察到」。全 `Block` 上线会把「模型漏写 analysis」变成「全量转人工」。故先 `Warn` 埋点，n≥50 再议。对齐 `TD-11`「只标不拒」先例。 |
| D2 | `RV-3` 覆盖判据用 **`criterionRef` 子串归属**，不用「条数相等」 | 实测 `acceptance` 半角 `;` **0 命中**、全角 `；` 9 条、圈号仅 5 条，且存在条目内嵌套 `；`（§2.3 事实 21）。按「分号拆分」实现必然过拆或全拆成 1 条 ⇒ `条数相等` 判据几乎必然失败 ⇒ 全量 `INCONCLUSIVE`。子串归属对分隔符风格不敏感，且与 `missingEvidence.acceptanceRef` 复用同一匹配器。 |
| D3 | `SR-5` 台账**前置**于 `SR-2`/`SR-3` | 平台无执行记录（§2.3 事实 23），「以平台侧记录为准」缺少事实源。不建台账则自审证据只能读模型自填，等于没改。 |
| D4 | `SR-3` 与 `FinalReportFidelityGate` **判不同对象、只共享结构** | 两者都问「证据是否存在」，但一个判单子任务收尾轮、一个判终报告脚本。若合成一个闸门，则「子任务证据」与「终报告证据」双写一算，必分叉（判据 4）。 |
| D5 | 三态新增 `INCONCLUSIVE` 而**不**复用 `REJECTED` | 「证据不足」与「质量不达标」的处置相反：前者该转人工（不该返工），后者该返工。混装会让返工预算被空转消耗（与 `TD-11`/`TD-12` 同源病根）。 |
| D6 | 沙箱只提供事实，**不做判定** | `exitCode=0` 不等于内容达标（脚本可能只验证了无关的事）。判定权留在 reviewer / LLM，与 ADR-004 §4 一致。 |
| D7 | 缺陷指纹替换**挂起** | `RepeatedFailureGate` 已用真机语料校准（真停滞相似度 0.18~0.25，故加评分停滞第二条件）。替换需对照实验，不与本计划混批。 |

## 6. 风险与边界

| 风险 | 缓解 |
