## 0. 定位与边界（★先读）

**① 问题来源**

- **用户请求（2026-11-02）**：希望做一个「类似 TRAE 的个人工作台面板」（左对话 + 右侧栏：助理身份 / 最近任务 / 工作产物 / 项目历史），并问「能否实现、优先做哪些、不做的话给理由」。
- **本次评估结论**：可行。执行链（`RequirementChat` 对话 + 任务时间线 + 产物侧栏）**80% 可复用**；真实缺口集中在三处——**用户归属**（`listConversations()` 等全库查询无用户维度）、**产物聚合读取侧**（`ExecutionArtifactService` 只有写面 `materialize`、没有查询面）、**助理身份**（无 `assistant_profile` 数据源）。
- **差距表锚点**：`G-021`（内部 LLM 能力面）/ `G-022`（技能↔模型能力引用边）已完结；本次工作台是新的「助理入口层」，尚未登记（需立 `PA-x` 号段 + 差距表 §0/§1.1 + `README.md` §2.3）。

**② 本计划做什么**

把本次评估 §7 的 PR0/PR1/PR2 落为可执行的 `PA-x` 任务序列，产出：

1. **`PA-1`~`PA-3` 地基三件**：用户归属模型（owner 落会话/任务/长期记忆 + 查询过滤）、用户级长期记忆（`long_term_memory` 启用 `USER` 类型 + 画像表职责分层）、助理身份（`assistant_profile` 表 + 对话头部展示）。
2. **`PA-4` 统一工作台**：`RequirementChat.vue` 改造为「左对话 + 右栏三段（任务概况 / 最近任务 / 最近产物）」，接**真实任务状态与产物**（复用 TaskTimeline / Artifact），非静态卡片；旧「对话新建」入口的产物面板逻辑保持不变。
3. **`PA-5` 产物聚合读取侧**：新增「我的产物」查询接口，三源归一（执行产物 + 会话附件 + 技能产物）。
4. **`PA-6` 事件订阅扩展 / `PA-7` 成本可见性**：工作台实时刷新任务状态（复用 SSE）+ 接入已就绪的 `G-026` 额度监控。
5. **`PA-8`~`PA-10` 后置登记不启动**：自动化定时、插件/模板市场、IM 渠道、移动端——见 ③ 边界。

**③ 本计划不做什么**（边界，防越界）

1. **不做多租户/团队协作** —— 与 owner 模型正交。依据：本次评估 §7 明确不推荐 + §8 风险 3（归属改造回归面大）。单用户隔离先行，owner 直滤。
2. **不做自动化编排工作流画布** —— 无需求来源。依据：本次评估 §7「明确不推荐优先做」；越界扩张属治理规则 §3.2 明令防的两类事故之一。
3. **不做助理人格市场 / 多助理人格** —— 只做**单一**助理身份卡。依据：本次评估 §6.6 行 15（`assistant_profile` 字段直接抄）范围即单助理。
4. **不在本计划里做第二个助理解析形态** —— 先把工作台一个形态跑通，通用化由第一个的结果判断。依据：本次评估 §7（PR1 优先统一工作台本体）。
5. **不在本计划内做 IM 渠道适配器 / 移动端响应式** —— 无触发条件。依据：本次评估 §7 PR2（有条件再做）。

**④ 诚实边界**

- **单人环境今天可用，不等于多用户可用**：所有查询先按「无 owner 过滤」起步并标注，`PA-1` 落库前勿宣称「多用户隔离已生效」——`MetaObjectHandler.getCurrentUser()` 现恒返回 `"system"`（无真实用户维度）。
- **产物聚合≠产物鉴权**：`PA-5` 先做「查询面聚合展示」，下载/预览的越权防护（本次评估 §6.6 行 3：uid 级文件隔离 + 全接口强制当前用户）**不在本计划首批**，仅在 `research/` 记为后续方向。
- **工作台接入真实状态 ≠ 事件全量落地**：`PA-6` 复用既有 SSE 把「任务状态刷新」接通是 P1；`G-026` 的刷新间隔 / 浮球穿透等精细化不承诺在本计划内做全。
- **「记住我」的暗示必须等记忆落地**：UI 上出现「记住你」按钮前，`PA-2` 的用户级长期记忆必须先落库（本次评估 §8 风险 2 记忆承诺风险）。
- **身份卡展示 ≠ 身份可编辑配置**：`PA-3` 只做「展示 + 读数据源」，不做人格/技能编排 UI。

### PA-12 上下文窗口与压缩（token 分项占用 + 手动/自动压缩）

> **状态**：已完成 ｜ **剩余动作**：—（v1.1 已接入：澄清 prompt 用「滚动摘要 + `seq > compacted_until_seq`」替代纯 40 条窗口，轮次入口自动压缩；单测 10/10、澄清回归 117/117 通过）

- **做什么**：为助理会话与新建对话提供统一「上下文窗口」：token 分项占用（系统提示词 / 系统工具 / Skill / 消息 / 其他）+ 百分比；手动 `/compact` 或按钮强制压缩；达到 `trigger_ratio` 自动压缩（对齐 QwenPaw 9 段渐进压缩、Yuxi 256K/保留 10 条）。压缩只改「喂给模型的上下文」，`requirement_message` 全量保留可回查。

- **HelloAI 具体调整方案**：
  - **数据模型（迁移 V135）**：新增 `conversation_context_state`（`conversation_id` 主键、`compacted_until_seq`、`summary`、`summary_version`、`trigger_ratio NUMERIC(4,3) DEFAULT 0.800`、`reserve_ratio NUMERIC(4,3) DEFAULT 0.200`、`enabled`、`context_size`、`owner_id`、`last_compact_at` + 审计列）。
  - **后端**：
    - `TokenEstimator`（纯函数：`charsPerToken` 可配 + 每条消息固定开销；单测覆盖中英混排）；
    - `ContextUsageService`：五项拆解，优先用后端上一次模型调用的 `usage.prompt_tokens`，调用前用估算；
    - `ContextCompactor.compact(conversationId, force)`：persist → trigger（非 force 且 `tokens <= trigger_ratio × contextSize` 跳过）→ pre-fold（折叠已完成轮工具结果）→ split（保留尾 = `reserve_ratio × contextSize` + 首条用户锚点）→ summarize（滚动摘要，失败保留上一版）→ update state；
    - Prompt 渲染改造：`ClarifyPromptRenderServiceImpl.windowHistory(40)` 固定滑窗改为「滚动摘要 + 保留尾」；助理 prompt 同走压缩；
    - 接口：`GET /requirement-conversations/contextWindowById/{id}`、`POST /requirement-conversations/compactById/{id}`；
    - 配置：`conversation.context.compact.enabled` / `trigger-ratio=0.80` / `reserve-ratio=0.20` / `output-reserve-tokens`。
  - **前端**：上下文窗口浮层（五项百分比 + 「压缩上下文」按钮 + 接近阈值提示）；压缩后刷新消息视图与占用。
- **验收**：`TokenEstimator` 单测通过；自动压缩在阈值触发、手动压缩强制生效；压缩后原始消息行数不变、`summary_version` 递增；`/contextWindowById/{id}` 五项之和≈总占用；被压缩内容仍可经检索回查。
- **边界**：首版检索用 `pg_trgm`/ILIKE，向量检索二期；摘要失败保留上一版并降级为仅折叠工具结果，不阻断对话。
- **设计 / 调研**：`design/HelloAI 助理对话与上下文窗口设计.md` §3.3~§3.6；调研 `research/HelloAI 个人助理可行性评估与落地建议（2026-11-02）.md` §6.8.5~§6.8.6。

## 11. 追加：助理对话补齐 SSE 流式 / 思考过程 / 停止生成（2026-11-03）

> **状态**：已完成（编译 / 类型检查通过；真实链路待后端重启后复测）｜ **性质**：助理链路传输层对齐（后端接口扩容 + 前端流式渲染）｜ **来源**：用户 2026-11-03 实测反馈「工作台联网搜索没有思考过程、没有 SSE、发送按钮不能暂停」，并裁定「先按建议全量对齐，把 AssistantChatService 改成流式返回」

### 11.1 做了什么

- **后端服务层**：`AssistantChatService` 新增 `streamCreateConversation` / `streamSendMessage`（`Flux<ChatStreamEvent>`），与同步 `createConversation` / `sendMessage` 同语义；同步端点保留作兜底。
  - 流式轮只在「幂等落 user 消息 + 自动压缩」前置段持 `ConversationRoundLocker`，LLM 段不持锁（停止生成不会卡住会话）。
  - 事件序：`progress(正在检索历史与记忆…)` → 可选 `progress(正在联网检索：xxx)` → 可选 `progress(已检索 N 条 · xx.xs)` → `reasoning` / `token` 增量 → `done` / `error`。
  - 终态在 `concatWith(Flux.defer(...))` 内落 assistant 消息（`ClarifyReplyParser.buildWebSearchOnlyPayload` 生成 `webSearch` + `process` payload）并原子自增 `round_count`；客户端中止时 defer 不执行，未完成回复不落库。
- **进度文案去重**：抽出 `RoundProgressText`（`searching` / `searchResult` / `abbreviate`），澄清链路 `ClarifyStreamServiceImpl` 与助理链路共用，删除澄清侧私有实现。
- **Controller**：新增 `POST /assistant/streamCreate`、`POST /assistant/streamSend/{id}`；把澄清 / 助理四条 SSE 通道收敛到同一个 `streamSse(response, scene, streamFactory)` 骨架（SseEmitter 超时、断开 dispose、订阅前断开竞态守卫、`StreamFrameAggregator` 聚合、`Flux.defer` 同步异常转 error 帧）。
- **前端**：`paths.ts` 增两个流式路径；`chatStream.ts` 增 `streamAssistantCreate` / `streamAssistantSend`（复用 `consumeSse` 内核，多传本轮 `skill`）；`Workbench.vue` 接入流式状态（正文 60ms / 思考 80ms 节流）、过程区（检索步骤 + 思考，正文开始自动折叠、可展开）、历史消息 `WebSearchBar` + 过程回看、发送按钮「发送 ↔ 停止生成」双态、收尾拉 detail 对齐落库全文。

### 11.2 关键口径

- **一套协议，两个入口**：助理与需求对话不再分叉传输层；区别只在 service 内部（检索预注入 vs 澄清编排），事件协议、聚合、取消语义完全一致。
- **锁只护前置段**：与澄清流式轮同口径；LLM 段不持锁，避免「停止生成」后锁仍未释放。
- **轮数原子自增**：流式轮不基于锁外快照回写 `roundCount`，改用 `round_count = COALESCE(round_count, 0) + 1`。
- **过程数据必须落库**：`payload.process{thinking,steps}` + `payload.webSearch` 随 assistant 消息持久化，刷新/切换会话后仍可回看，而非只在流里出现一次。
